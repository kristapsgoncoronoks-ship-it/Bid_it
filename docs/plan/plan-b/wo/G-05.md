## G-5 — Audit chain + domain events

**Effort M (4–6d) · P0 · Depends: G-3.** Prepend `shared/00_MASTER_CONTEXT.md`.
Spec: BA_bidit.md §7.1 M11.

### Objective & value
Accountants and auditors buy trust: every change attributable, tamper-evident,
verifiable offline. Built before business features so no mutation ever ships unaudited.

### Steps
1. `audit_entries`: org_id, seq (per-tenant monotonic), actor, action, entity_type,
   entity_id, payload JSONB (diff summary, no secrets), prev_hash, hash
   (sha256(prev_hash||canonical_json)), created_at. UNIQUE(org_id, seq) so concurrent
   appends CONFLICT rather than fork; retry-on-conflict in the recorder.
2. No UPDATE/DELETE grants for the app role on the table (enforced in migration; test).
3. `audit.record(db, ctx, action, entity, payload)` — best-effort (never raises into
   the business op) but commits ATOMICALLY with it (same transaction).
4. Offline verifier CLI: `python -m app.tools.audit_verify --org X export.jsonl`
   re-walks the chain; exported file carries prev_hash/hash so a third party can verify.
5. Domain-event seam: `events.emit(kind, payload)` — in-process now, the webhook/
   notification consumer plugs in later; events are NOT the audit trail (separate concerns).
6. Wire authz denials (G-4 TODO hook) into audit.

### Acceptance criteria
- [ ] Two concurrent appends for one org: one wins, one retries; final chain verifies; no gap/fork.
- [ ] Tampering with any payload byte → verifier reports first broken link.
- [ ] App role literally cannot UPDATE/DELETE an entry (SQL test expects permission error).
- [ ] A failed audit write does not fail the business operation (fault-injection test) BUT the op+audit commit together on success (rollback test: op rolls back → no orphan audit row).

### Self-verify
Paste verifier output over a 100-entry chain incl. a deliberate-tamper run.
