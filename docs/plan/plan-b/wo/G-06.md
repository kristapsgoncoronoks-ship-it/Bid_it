## G-6 — Job queue + scheduler + worker

**Effort M (4–6d) · P0 · Depends: G-3.** Prepend `shared/00_MASTER_CONTEXT.md`.

### Objective & value
OCR, PDF, email, webhooks, dunning, recurring generation — none may run in a request.
This is the async backbone; its idempotency keys are what make "recurring jobs never
duplicate invoices" a constraint instead of a hope.

### Steps
1. `jobs` table: id, org_id, kind, payload JSONB, status(queued|running|done|failed|dead),
   attempts, max_attempts, run_at, lane(cpu|io), idempotency_key,
   UNIQUE(org_id, kind, idempotency_key) WHERE idempotency_key IS NOT NULL,
   last_error, timestamps. Claim via `FOR UPDATE SKIP LOCKED`.
2. Worker entrypoint `python -m app.worker [--lane cpu|io]`; handler registry
   `@job_handler(kind)`; per-job timeout; exponential backoff; dead-letter after
   max_attempts with an ops-visible listing.
3. Transactional enqueue: `jobs.enqueue(db, ...)` participates in the caller's
   transaction — business row and its job commit or roll back TOGETHER (test this).
4. Scheduler: `python -m app.scheduler` — computes due daily kinds per org with
   deterministic keys `f"{kind}:{date}"`; safe to run twice (unique key absorbs).
5. SLO probe: oldest-queued-age + dead count exported as metrics; `/internal/queue-health`
   (permission-gated) for ops.
6. Tenant context inside handlers: job carries org_id; handler runs with the GUC set
   (RLS applies to workers exactly as to requests — test with a cross-org probe).

### Acceptance criteria
- [ ] Two workers, 100 jobs: every job runs exactly once (SKIP LOCKED proven).
- [ ] Same idempotency_key enqueued twice → one row.
- [ ] Rollback test: business tx aborts → its job never becomes visible.
- [ ] Scheduler run twice for a date → no duplicate jobs.
- [ ] A handler querying another org's rows gets zero (RLS in worker context).
