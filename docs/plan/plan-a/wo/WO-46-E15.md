**WORK ORDER 46 — Extraction learning loop (E1.5). Effort L (6–8d, scoped to a conservative first slice). Priority P2. Milestone M1. Depends on: E1.2 (line-item provenance — shipped WO-13).**

### Objective and business value

Verified evidence, read straight off `HEAD=af78f38`:

`app/models/extraction_field.py::ExtractionField.reviewed_value` is written by
`POST /invoices/captures/{run_id}/review` (`app/api/routes/invoices.py:451`) and
audited (`audit.A.CAPTURE_REVIEW = "capture.field_review"`, WO-12) but is read
back **only for display** on that one run — nothing aggregates it, and the next
document from the same vendor is parsed with zero knowledge of what a human
corrected last time. ARCH_plan (E1.5) names this exact gap: *"`reviewed_value`
is stored for audit only; nothing feeds back."* Every capture-review correction
since WO-12 shipped is a discarded training signal. Fleet Fuel's retired
`capture_confidence` module (per `docs/plan/shared/specs/BA_fleet_fuel.md`)
proved the shape worth harvesting — per-(supplier × field) correction
history as an advisory hint, never a gate — without carrying over a line of its
code (§10 prohibition: rules survive as specification, bytes do not).

Who pays more for this gap: every reviewer re-types the same correction (a
mis-parsed vendor legal name, a line `category` no parser ever reads) on every
single invoice from a vendor that sends the same template every time — pure
repeated manual toil with zero payoff, forever. A same-vendor hint that
proposes last time's correction turns a blank field into a one-click accept,
which is the difference between "the tool watches you re-do the same fix
monthly" and "the tool gets less annoying the more you use it" — a retention
lever, not a one-off convenience.

### Scope

**In scope**
- `app/models/capture_field_memory.py` (**new**) — `CaptureFieldMemory`:
  one row per `(org_id, vendor_name, field)`; `vendor_name` is the SAME
  exact-stripped key `vendors.get_or_create_vendor` matches a vendor on (a
  pending, unconfirmed capture has no `vendor_id` yet to key by, only the raw
  captured header `vendor_name` string). Counters `observed_count` /
  `corrected_count` (the accuracy denominator/numerator) + `last_original_value`
  / `last_corrected_value` (the most recent correction, i.e. the suggestion
  text).
- Migration (**new**) — `capture_field_memory` table + RLS policy in the SAME
  migration (`TENANT_TABLES = ("capture_field_memory",)`); register
  `CaptureFieldMemory` in `app/core/tenant.py::TENANT_MODELS`.
- `app/services/capture_memory.py` (**new**) — the learning loop itself:
  - `normalize_vendor(name) -> str | None` — the shared key function.
  - `observe_fields(db, org_id, vendor_name, fields)` — bumps
    `observed_count` once per field name for a freshly-parsed run (the
    denominator).
  - `record_correction(db, org_id, *, vendor_name, field, original_value,
    corrected_value)` — bumps `corrected_count` and stores the suggestion;
    called ONLY when a review submission actually changes a field's effective
    value (not a same-value resubmit).
  - `hints_for(db, org_id, vendor_name, fields) -> dict[str, FieldHint]` —
    READ-ONLY lookup of the current suggestion per field name, for a vendor
    with `corrected_count > 0`. This is the ONLY thing the API layer is
    allowed to surface; nothing in this module writes an `ExtractionField` row.
- `app/services/extraction.py::extract_upload` — after `record_fields`, calls
  `capture_memory.observe_fields` with the run's raw captured header
  `vendor_name` and the run's distinct field names.
- `app/schemas/invoice.py::FieldProvenanceOut` — three new, additive, optional
  fields: `suggested_value`, `suggestion_observed_count`,
  `suggestion_corrected_count` (all `None`/absent-signal when there is no
  history — never a fabricated hint).
- `app/api/routes/invoices.py`:
  - `review_capture_fields` — when a submitted field's effective value
    actually changes, also calls `capture_memory.record_correction` in the
    SAME transaction as the existing field update + `capture.field_review`
    audit event (no new audit action — the existing one already covers this
    mutation; the memory row is a derived index over it, not a second
    user-facing action).
  - `capture_fields` (GET) and the response of `review_capture_fields` (POST)
    both attach the vendor's current hints to each field's
    `FieldProvenanceOut` via a small shared helper.
- `backend/tests/test_capture_memory.py` (**new**) — unit coverage for the
  service.
- A case added to `backend/tests/test_capture_review_api.py` — the end-to-end
  acceptance case (two captures, same vendor, a correction on the first
  proposes as a hint on the second) + the §4.19 non-mutation proof + a
  cross-tenant isolation case.

**Out of scope**
- Any frontend surfacing of the hint (`CaptureReview.tsx`) — ARCH_plan's own
  file list for E1.5 names backend files only (`new
  app/services/capture_memory.py, migration`); a follow-up order wires the
  hint into the review screen once this slice is proven. Tracked below under
  "Left undone".
- Auto-applying a hint to `reviewed_value`, `value`, or any invoice field —
  explicitly forbidden by §4.19 and by E1.5's own acceptance line ("a
  suggestion, never an auto-apply"); this order does not build an "accept
  hint" one-click endpoint either (that would still be a human-initiated
  write through the EXISTING review endpoint, but is additional surface this
  slice does not need to ship the learning loop itself).
- Cross-vendor or fuzzy-vendor-name matching (e.g. "ACME CORP" vs "Acme
  Corp Ltd" resolving to the same memory row) — the key is the exact-stripped
  string, matching `get_or_create_vendor`'s own matching discipline. A
  vendor-name-normalization improvement is a separate, vendor-master-data
  concern, not this order's.
- An "accuracy %" or confidence-boost figure surfaced anywhere outside the
  two raw counters on the wire — no new dashboard tile, no change to
  `extraction_provider.py`'s existing `confidence`/`low_confidence` semantics
  (E1.2's honest-provenance contract is unchanged; a hint is an ADDITIONAL,
  separate signal, never blended into the parser's own confidence number).

### Implementation guidance

1. **Migration first.** `alembic revision --autogenerate -m "capture field memory"`,
   then hand-edit: composite-free (no FK to `extraction_runs`, this table
   outlives any single run — it survives across every capture from a vendor),
   just `org_id` FK to `organizations` + a `UniqueConstraint(org_id, vendor_name,
   field)` + RLS in the same migration (`TENANT_TABLES = ("capture_field_memory",)`,
   copy the `_PREDICATE` block from `98d1896eeb26_extraction_fields.py` verbatim).
2. **The vendor key is the RAW captured header `vendor_name`, not a corrected
   one.** At `observe_fields` time (parse, before any review) the only vendor
   signal available is `draft.draft.vendor_name` as the parser produced it —
   use that string, exact-stripped, as the key for EVERY field observed on
   that run (including for `field == "vendor_name"` itself: the key and the
   field's own captured value are the same string by construction). This is
   what makes the loop self-consistent: the next document from a vendor whose
   invoices are read by the same parser path reproduces the same raw string,
   so the lookup at hint-time (using the SAME `draft.vendor_name` off the new
   run's `draft_json`) hits the same row. Do not key by `reviewed_value` —
   that would fragment history the moment a vendor name gets corrected once.
3. **`observe_fields` runs once per DISTINCT field name per run**, not once
   per line occurrence — `category`/`quantity`/etc. appear on every line item,
   but the memory is per-(vendor × field-name), matching Fleet Fuel's
   supplier×field granularity (not supplier×field×line-position, which would
   never accumulate enough history to mean anything — a 3-line invoice one
   month and a 7-line invoice the next share no line positions).
4. **`record_correction` fires only on a genuine change.** In
   `review_capture_fields`, compare `item.reviewed_value` against the SAME
   `old` value the existing audit-meta computation already derives
   (`f.reviewed_value if f.reviewed_value is not None else f.value`); only
   when `new != old` is it a correction signal. A same-value resubmit (which
   the endpoint still accepts and still audits, unchanged) teaches the memory
   nothing — resubmitting an already-correct value is not evidence the parser
   was wrong.
5. **Hints are attached at READ time, never written into the row.** In
   `capture_fields` and the response of `review_capture_fields`, after
   building `[FieldProvenanceOut.model_validate(f) for f in fields]`, resolve
   the run's vendor_name from `run.draft_json` (factor the existing
   try/except pattern in `capture_review_queue` into a small shared helper —
   don't duplicate it a third time), call `capture_memory.hints_for` once for
   all field names on the run, and set `suggested_value`/
   `suggestion_observed_count`/`suggestion_corrected_count` on the matching
   Pydantic objects post-validation (they are ordinary mutable model
   instances). Never populate `value` or `reviewed_value` from a hint.
6. **Fails open, never blocks.** Any failure resolving a hint (bad
   `draft_json`, no memory row, no vendor name yet) must leave the response
   exactly as it is today — hint fields `None`, nothing else different. Wrap
   the vendor-name-from-draft_json parse in the same broad
   `except Exception` pattern already used in `capture_review_queue` (a
   malformed cached draft must not break the review screen).
7. **No new audit action.** The correction is already audited by the
   existing `capture.field_review` event with old→new meta (§4.16 already
   satisfied by WO-12); the memory row is a derived aggregate over that same
   mutation, not a new user-facing action requiring its own audit line.

### Invariants this order must preserve

- **§4.19 (AI never silently mutates a financial record)** — no model is
  wired here, but the same discipline is the whole point of this order: the
  learning signal is advisory-only, computed from historical human
  corrections, surfaced as a labelled suggestion, and NEVER auto-applied.
  Proven by a test that runs the full observe→correct→hint cycle and then
  asserts a FRESH run's `ExtractionField.value`/`.reviewed_value` are
  untouched by the hint (they still show the parser's own raw capture, not
  the suggestion) until a human posts the existing review endpoint.
- **§4.1 (tenant isolation)** — `CaptureFieldMemory` is added to
  `TENANT_MODELS` (ORM guard) and gets an RLS policy in the same migration
  (`tests/test_rls.py::test_rls_migration_covers_every_tenant_table`);
  proven by a test where two orgs have vendors of the IDENTICAL name and a
  correction recorded in org A produces zero hint in org B.
- **§4.4 (opaque 404, never 403)** — unchanged; this order adds no new
  by-id route.
- **§4.16 (every mutating operation is audited)** — the correction that
  drives `record_correction` is already audited by the existing
  `capture.field_review` event in the same transaction (WO-12); this order
  adds no additional financial mutation that would need its own event —
  `CaptureFieldMemory` itself is a derived learning index, not a financial
  record, and its own row is not separately audited (consistent with e.g.
  `settled_metrics`-style derived aggregates elsewhere not carrying their own
  audit trail — only the operation that fed them does).
- **§4.20 (wire contract)** — `FieldProvenanceOut` gains only additive,
  optional fields; every existing consumer (frontend, tests) is unaffected
  when they are `None`.

### Database / migration impact

New table `capture_field_memory`: `id` (GUID pk), `org_id` (FK
`organizations.id`, `ondelete=CASCADE`), `vendor_name` (String(255)), `field`
(String(40)), `observed_count`/`corrected_count` (Integer, default 0),
`last_original_value`/`last_corrected_value` (String(500), nullable),
`created_at`/`updated_at`. `UniqueConstraint(org_id, vendor_name, field)` +
index `(org_id, vendor_name)`. RLS policy (`tenant_isolation`) added in the
SAME migration, Postgres-only branch, mirroring
`98d1896eeb26_extraction_fields.py`. No backfill (a brand-new table starts
empty; the loop begins learning from the first correction after this ships).
Downgrade drops the RLS policy then the table — safe, loses only the
accumulated hint history (no financial data, nothing else depends on it).

### Testing requirements

`tests/test_capture_memory.py` (new)
- `test_observe_then_no_correction_yields_no_hint` — `observe_fields` alone
  (no correction) produces `hints_for() == {}` for that field.
- `test_correction_produces_a_hint_for_the_same_vendor` — `record_correction`
  then `hints_for` returns the corrected value, `corrected_count == 1`.
- `test_hint_uses_most_recent_correction` — two corrections for the same
  (vendor, field) with different values; `hints_for` reflects the SECOND
  (most recent), and `corrected_count == 2`.
- `test_hint_scoped_to_exact_vendor_name` — a differently-spelled vendor name
  (even a trivial case difference) gets no hint; exact-stripped match only.
- `test_normalize_vendor_strips_and_none_on_blank` — `normalize_vendor`
  boundary cases (`None`, `""`, `"  "`, leading/trailing whitespace).

`tests/test_capture_review_api.py` (additions)
- `test_correction_on_one_capture_hints_the_next_same_vendor_capture` — E1.5's
  own acceptance line, end to end: upload+review capture 1 for vendor V,
  correct field X from A to B; upload capture 2 for the SAME vendor V (same
  raw vendor_name); `GET .../fields` on capture 2 shows
  `suggested_value == "B"` for field X while `value`/`reviewed_value` for
  that field on capture 2 are STILL the parser's own raw capture (not `"B"`)
  — the §4.19 non-mutation proof, in the same test — exercised through the
  real HTTP path (`auth_client`/`parse_upload`, not a hand-written query).
- `test_hint_absent_for_a_different_vendor` — capture 2 from a DIFFERENT
  vendor shows no hint for the same field name.
- `test_hint_not_recorded_on_same_value_resubmit` — resubmitting a field's
  existing value through `.../review` does not bump `corrected_count` (no
  false learning signal from a no-op confirm).
- `test_hint_cross_tenant_isolated` — org A corrects a field for vendor
  "Acme Fuel Co"; org B, with an IDENTICALLY named vendor and an identical
  capture, sees NO hint (opaque — not merely absent by coincidence, proven by
  seeding org B with a same-name vendor and same field).

### Rollback strategy

Migration downgrade drops `capture_field_memory` (RLS policy first) —
written and exercised by `alembic upgrade head && alembic downgrade -1 &&
alembic upgrade head` in the self-verification block. Losing the table loses
only accumulated hint history, nothing financial and nothing another table
references (no FK points at it). A code-only revert is otherwise safe: the
three new `FieldProvenanceOut` fields are additive and default to `None`.
