**WORK ORDER 72 — G3.5: receipt control — cadence × activity expectation,
cross-control statuses, the orphan check, and slot-level overrides that
survive re-runs (board G3.5, `BA_fleet_fuel.md` §3.J — no dedicated
R-number). Effort L (6-12d). Priority P1. Milestone M3. Depends on: WO-50
(G1.2 — `fuel_transactions`, the activity source), WO-52 (G2.4 —
`invoice_match.resolve_invoice_ref`/`registered_invoices`, the ONE
"covered by a registered invoice" implementation), WO-58 (G2.6 slice 3 —
`extraction.invoice_ids_with_documents`, the vaulted-document batch seam;
and `vat_receipt_waivers`, whose boundary with this order is documented
below), WO-53 (G1.3 — `close.run_close`, which gains the control stage),
WO-60 (G2.10 — the checklist whose claim-level receipt-control item this
order deliberately does NOT touch).**

### Objective and business value

Verified at HEAD=`9d461f7` (this order's baseline, **1718 passed / 10
skipped**, full-suite run recorded at WO-71's close-out): nothing in
`app/services/transport/` answers `BA_fleet_fuel.md` §2.3/§3.J's question
*"did we receive every invoice the supplier issued?"*. The pieces that
exist all answer DIFFERENT questions: `checklist.submission_checklist`'s
`receipt_control` item (WO-60) is CLAIM-scoped — "does any supplier with
unresolved synthetic transactions inside THIS claim's grain lack a
registered invoice" — and `waiver.set_waiver` (WO-58, R15) is the claim-
level legal exclusion for a genuinely-uninvoiced supplier. Neither knows a
supplier's invoicing CADENCE, so neither can detect the §3.J headline
failure: a **semi-monthly** supplier (E100, DKV — §5.1) whose second
half-month invoice never arrived, or a **monthly-per-country** supplier
(Q8) that invoiced three of the four countries with activity. There is no
persisted expectation grid, no `MISSING`-slot chase list, no orphan check,
and no cadence configuration anywhere (`grep -rn cadence
backend/app/services/transport/` finds only two "G3.5's concern, not this
order" deferral comments, `parsers/bp.py:79` and `parsers/eurowag.py:29`;
seven G3.2 work orders defer cadence enforcement here by name).

Who pays: §2.3 verbatim — *"A missing invoice is un-recoverable VAT.
Cadence × activity is the only way to know what **should** have arrived."*
Every gate built so far validates what DID arrive; only an expectation
model can see what NEVER arrived. A fleet that fuelled in the back half of
June with a semi-monthly card and never received the H2 invoice silently
forfeits that VAT — the claim submits clean (nothing unresolved: the H2
transactions may not even be ingested if the statement never came, or sit
resolvable against the H1 invoice), the deadline passes, the money is
gone. The chase list ("MISSING — activity but no invoice registered →
chase the supplier", §3.J item 3) is the operational surface that recovers
it while recovery is still possible.

### The harvested specification (cited verbs, and the four questions the
standing order asks)

**What cadence values exist** — §3.J item 1, verbatim: *"Each supplier has
an **invoicing CADENCE** (`suppliers.invoice_cadence`): `semi-monthly`
(one invoice per half-month: E100, DKV) · `monthly` (MOEVE, BP, TFC,
PORTONE) · `monthly-per-country` (one per month **per country with
activity**: Q8)."* Three values, a closed set. §5.1's per-network table
carries the same assignments and tags Eurowag's cadence "—" (parser only —
no cadence, deliberately absent from the defaults below).

**Where cadence is configured** — harvested as a supplier-master column
(`suppliers.invoice_cadence`, §3.J item 1 and §4.4's schema sketch). This
codebase has NO transport supplier master (a fuel transaction's `supplier`
is a free-text network code, `fuel_transaction.py`; the nearest analogue,
WO-61's `supplier_vat_registrations`, is a transport-local tenant table
keyed on that same free-text code). Decision: a new transport-local tenant
table `vat_supplier_cadences (org, supplier) → cadence` (the WO-61
precedent), admin-written via an audited `set_cadence`/`remove_cadence`,
PLUS a module-level `DEFAULT_CADENCES` constant carrying §5.1's harvested
per-network assignments (keys matching the G3.2 parser `network` codes,
upper-cased: E100/DKV semi-monthly; MOEVE/BP/TFC/PORTONE monthly; Q8
monthly-per-country). `cadence_for` resolves admin row → harvested default
→ `None`. A supplier resolving to `None` generates NO expectations and is
skipped — the R61/WO-66 opt-in-by-absence discipline ("an ungoverned
supplier behaves exactly as before"; "the expectation IS the opt-in").
Defaults are safe to ship ON because every output of this order is
advisory (below): the worst a wrong default produces is a chase-list row
an admin can waive or fix with `set_cadence`.

**What "orphan" means precisely** — §3.J item 3, verbatim: *"Plus an
**orphan check** — every transaction must be covered by a registered
invoice."* An orphan is a TRANSACTION (not a slot, not a document): a
`FuelTransaction` in the period whose `invoice_ref` does not resolve to a
registered invoice via the ONE resolution order
(`invoice_match.resolve_invoice_ref` — C3's "so the two can never drift").
It is the transaction-grain complement of the slot-grain `MISSING` status:
`MISSING` says "a whole expected invoice never arrived"; an orphan says
"this specific line is not covered by anything that did arrive". The
inverse direction (a registered document with no transactions) is NOT
harvested as part of §3.J and is not built here.

**What "overrides survive" means** — §3.J item 4, verbatim: *"Results
persist in engine-owned `invoice_receipt_control`; **manual overrides
(waived / note) survive re-runs.**"* Survive RE-RUNS of the control
itself: `run_receipt_control` recomputes and upserts each slot row's
COMPUTED columns (`status`, `txn_count`) on the slot's natural key, and
NEVER writes the two OVERRIDE columns (`waived`, `note`) — an existing
row's overrides pass through every recomputation (including one triggered
by a re-ingest that changed the underlying activity) untouched. The only
writer of `waived`/`note` is the explicit, audited
`set_control_override`.

**What surface reports the misses** — §3.J's verbs are *"answers"*,
*"cross-control"*, *"persist"*, *"chase the supplier"* — monitoring verbs.
There is no "block"/"halt"/"refuse" anywhere in §3.J, in deliberate
contrast to R25's two regimes ("halts the close", "blocks registration")
and the G2.6 gates ("cannot be filed"). The master-context §4.19 advisory
discipline therefore applies to the FINDINGS: a `MISSING` slot or an
orphan transaction NEVER gates a claim, a submission, an ingest or the
close — the blocking side of receipt control remains exactly where WO-58/
WO-60 put it (R15 waivers + the claim-level checklist item feeding
`status.derive_stage`). The surface is (a) the persisted
`vat_receipt_controls` rows (the §3.J "engine-owned
`invoice_receipt_control`" grid, readable via `list_controls`), (b) the
read-only `orphan_transactions` report, and (c) a stage inside
`close.run_close` — harvested from §3.H H4's stage list
`consolidate → build_master → history → run_control → backup`: the close
RUNS the control (persisting the period's grid) after rebuilding claim
lines, and completes regardless of what the control FINDS. (An EXCEPTION
inside the stage still halts the close via the existing job rollback —
that is R31's "halts on the first failure" for infrastructure failures,
not a finding gating anything.)

### Boundary vs WO-58's receipt-control waivers (documented per the
standing order)

Two different "receipt control" artifacts exist in the harvested spec and
they stay two different artifacts here:

| | WO-58 `vat_receipt_waivers` (R15, §3.C9) | THIS ORDER `vat_receipt_controls` (§3.J) |
|---|---|---|
| Grain | (org, **claim**, supplier) | (org, **entity, supplier, period, slot, country**) |
| Question | "may this genuinely-uninvoiced supplier be legally EXCLUDED from this claim?" | "did every invoice the cadence says should exist actually arrive?" |
| Effect | HARD: excluded from claim lines by construction; stamped into `status_note`; feeds the blocking checklist item | ADVISORY: a persisted worklist status; never touches a claim, line, lock, freeze, checklist or ingest |
| `waived` semantics | legal waiver, REFUSED if the supplier has registered invoices (R15) | "stop chasing this slot" — a worklist mute with a note; no refusal rule, no claim effect |

`set_control_override(waived=True)` on a slot has ZERO effect on any gate
— proven by test. The two tables share the word "waive" because the BA
does (§3.C9 vs §3.J item 4); the module docstrings on both sides
cross-reference this boundary.

### Implementation guidance

1. **The half-month boundary is days 1-15 / 16-end** — §3.J says only
   "one invoice per half-month"; the 15/16 split is the natural calendar
   reading (E100's own two invoices per month bill the 1st-15th and
   16th-EOM). A DOCUMENTED INTERPRETATION of an underspecified phrase,
   flagged in the module docstring exactly like WO-50's `line_seq` and
   WO-52's heuristics. Slot keys: `M` (monthly / per-country), `H1`, `H2`.
   `country` column: the ISO code for `monthly-per-country` rows, `""`
   (empty string, NOT NULL — NULL would break the natural key's
   uniqueness, WO-50's own lesson) otherwise.
2. **"Received" reuses the ONE resolution implementation** — a slot is
   received iff ≥1 of its transactions resolves via
   `invoice_match.resolve_invoice_ref(entity_id, supplier,
   refund_country=txn.country, invoice_ref=txn.invoice_ref)`. Never a
   second matching heuristic (C3's anti-drift rule; the same discipline
   `checklist._unresolved_suppliers` follows). Resolve once per DISTINCT
   `(supplier, country, invoice_ref)` key within a run — a legitimate
   batching of the same function, not a fork of it.
3. **"`+ DOC`" reuses WO-58's batch seam** — collect the resolved slots'
   distinct invoice ids, ONE call to
   `extraction.invoice_ids_with_documents` per run (never per slot — the
   N+1 `docs_index()` lesson). `received_doc` iff ≥1 of the slot's
   resolved invoice ids is documented; else `received_no_doc`.
4. **Enumeration = the period's transactions, not the cadence table** —
   (entity, supplier) pairs come from `fuel_transactions WHERE period=?`;
   a configured supplier with zero transactions in the period produces NO
   rows (expectation = cadence × ACTIVITY — with zero activity anywhere,
   nothing is expected; the grid would be all-`no_activity` noise). Within
   an enumerated pair, semi-monthly ALWAYS emits both `H1` and `H2` (one
   may be `no_activity` — the acceptance case), monthly emits its one `M`
   slot, per-country emits only countries with ≥1 transaction (§3.J
   "per country **with activity**", verbatim — an inactive country is
   structurally unenumerable and deliberately absent).
5. **The upsert preserves overrides by never writing them** — SELECT the
   existing row on the natural key; if present, assign `status`/
   `txn_count` only; if absent, INSERT with `waived=False, note=None`.
   `set_control_override` is the only code path that assigns `waived`/
   `note` (grep-provable, like R5's "only withdraw releases locks"
   structural test). Rows are never deleted by a re-run — a slot whose
   activity vanished on re-ingest recomputes to `no_activity`, keeping its
   override history.
6. **Fail OPEN by absence, and advisory throughout** — no cadence ⇒ no
   expectation (skip, counted in the summary as `unmanaged_suppliers` so
   the operator can see what is NOT being controlled); findings never
   raise. `run_receipt_control` itself raises only on real infrastructure/
   validation failures (bad period, module off) — inside the close that
   propagates and halts per R31, which is correct: a close that could not
   PERSIST the control grid did fail a stage; a close whose grid contains
   `missing` rows did not.
7. **Module gate + opaque 404** — every public service function gates on
   the `transport` entitlement first (the invariant pattern);
   `set_control_override` looks up `(id, org_id)` and raises
   `NotFoundError("Receipt control row not found",
   code="receipt_control_not_found")` — cross-tenant indistinguishable
   from unknown (§4.4).
8. **Audit** — `set_cadence` (old→new on change; idempotent no-op audits
   nothing — the `set_active` convention), `remove_cadence`,
   `set_control_override` (old→new for both columns), and one
   `TRANSPORT_RECEIPT_CONTROL_RUN` summary per run (the
   `TRANSPORT_CLOSE_RUN` batch pattern: org_id + meta, no target row).
9. **Money is untouched** — this order reads `FuelTransaction` rows and
   counts them; it sums nothing, converts nothing, and stores no amount.
   No `q2` call sites should appear; a reviewer finding one should ask
   why.

### Database / migration impact

One new migration, two tenant tables:
- `vat_supplier_cadences`: `org_id`, `supplier` String(60), `cadence`
  String(20) CHECK ∈ {semi-monthly, monthly, monthly-per-country};
  `UNIQUE(org_id, supplier)`; `UNIQUE(org_id, id)`.
- `vat_receipt_controls`: `org_id`, `entity_id` (composite FK →
  `issuer_profiles`, RESTRICT), `supplier` String(60), `period`
  String(7), `slot` String(2) CHECK ∈ {M, H1, H2}, `country` String(2)
  NOT NULL default `''`, `status` String(16) CHECK ∈ {no_activity,
  received_doc, received_no_doc, missing}, `txn_count` Integer,
  `waived` Boolean NOT NULL default false, `note` Text NULL;
  `UNIQUE(org_id, entity_id, supplier, period, slot, country)`;
  `UNIQUE(org_id, id)`; index `(org_id, period)`.
RLS (`ENABLE`/`FORCE` + the standard tenant policy) for BOTH tables in the
SAME migration. Downgrade drops both tables + policies — safe: loses only
cadence config and the control grid (both recomputable/re-enterable;
nothing else references either table). Verified up/down/up on scratch
Postgres 16 with the pg-only suite.

### Rollback strategy

Code revert: delete the two new modules + the `close.py` stage call +
audit members; migration downgrade drops both tables and their policies
(tested up/down/up). Lost on downgrade: cadence config + the control grid
+ slot overrides — all re-enterable/recomputable; no other table
references either. No kill switch needed: `transport` stays default-OFF
and absent from every plan's module set.
