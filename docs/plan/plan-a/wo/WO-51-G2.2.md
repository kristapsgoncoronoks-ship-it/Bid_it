# WO-51 — `vat_claimed_invoices`: the one-invoice-one-submission lock table (board G2.2)

<!-- ═══════════════ COPY FROM HERE: WO-51 ═══════════════ -->

**WORK ORDER 51 — the lock table: transactional invoice-claim locking + withdraw-only
release (board G2.2). Effort M (3-5d). Priority P0. Milestone M3. Depends on: WO-49
(G1.1/G2.1 — claim grain), WO-50 (G1.2 — `fuel_transactions`, which built the
composite `(org_id, id)` unique constraint this order's FK targets).**

### Objective and business value

WO-49 shipped the claim aggregate (`VatRefundClaim`) and WO-50 shipped the typed
`fuel_transactions` line item, but nothing yet enforces the rule the whole refund
engine's legal defensibility rests on: **the same invoice can never be claimed
twice.** Without a lock, two overlapping submissions (a duplicate submission, a
race between two operators, or the same invoice mistakenly pulled into both a
quarterly and an annual claim) can both succeed, producing two refund applications
for the same VAT — a claim that is either double-recovered (fraud exposure to the
tax authority) or refused outright once the overlap is discovered, either way
putting the client relationship and the firm's standing with the refunding
authority at risk. This is a correctness property, not a feature: it must hold
under real concurrent writers, not just in a single-threaded test.

**Citation check, verified against the source text (master-context §9 — a citation
mismatch is reported, not silently followed, per WO-50's precedent):**
`ARCH_plan.md` line 874 tags this task `G2.2 ... (R4, R5)`. Reading
`BA_fleet_fuel.md`'s R-table directly (lines 1361-1362): **R4 and R5 are correct
this time** — R4 is verbatim *"One-invoice-one-submission lock,
`UNIQUE(entity, refund_country, supplier, invoice_ref)`, acquired in the same
transaction as the status change via a plain INSERT; a lost race raises and aborts
the whole transition. Two concurrent submissions over an overlapping invoice:
exactly one succeeds; the loser's status is unchanged."* R5 is verbatim *"Only an
explicit withdraw releases locks. `rejected`, rejection (3B), confiscation (3C) and
appeal (3D) keep them. After 3B, the invoice cannot be claimed in another period;
after withdraw, it can."* Both map exactly onto this order's scope — no correction
needed, unlike WO-50's G1.2/R29-R30 mismatch. The narrative prose in
`BA_fleet_fuel.md` §3.C ("C5. ONE-INVOICE-ONE-SUBMISSION locks", lines 458-463, and
"C7. Only `withdraw_claim` releases locks", lines 470-474) is the same rule restated
with implementation detail (`BEGIN IMMEDIATE`, "plain INSERT not INSERT OR IGNORE")
and is the primary source this order builds from, alongside the R4/R5 rows
themselves and the schema fragment at §4.3 lines 1032-1033 (`vat_claimed_invoices
(entity, refund_country, supplier, invoice_ref) UNIQUE = THE LOCK. Released ONLY by
withdraw_claim.`). One deliberate widening: `ARCH_plan.md`'s own G2.2 description
(line 874) states the constraint as `UNIQUE(org, entity, refund_country, supplier,
invoice_ref)` — the harvested BA text omits `org` because Fleet Fuel was
single-tenant; this codebase adds `org_id` to every tenant-scoped uniqueness
constraint (identical widening WO-49 already applied to the claim grain and WO-50
to the transaction natural key), so the ARCH_plan wording — not the literal BA
sentence — is what ships.

Who pays more without this: every future gate (G2.3's `is_synthetic()` wiring,
G2.4's claim-line materialization, G2.5's freeze, G2.6's checklist/period-end/
minimum stack) assumes a caller can safely say "this invoice is now claimed" and
have that statement be durable and race-proof. Building the gate stack on top of an
unlocked or lock-that-doesn't-really-lock foundation would mean discovering the
double-claim bug only after a real client's claim is filed twice — the single most
expensive class of bug this vertical can ship, because it is not a code revert, it
is a call to a tax authority.

### Scope

**In scope**
- `VatClaimedInvoice` (`app/models/transport/lock.py`) — the lock row.
  `UNIQUE(org_id, entity_id, refund_country, supplier, invoice_ref)` is THE lock
  (verified natural key, see citation note above). Denormalized `entity_id`/
  `refund_country` columns (not read through `claim_id`) so the uniqueness
  constraint spans **every** claim, not just the one that happens to hold this
  row — a second, later claim for a different period must still collide with an
  already-locked invoice. A required composite `(org_id, claim_id)` FK into
  `vat_refund_claims` (which claim currently holds this lock, `ondelete=CASCADE`
  — mirrors `vat_claim_lines.claim_id`, WO-49; moot in practice since no code
  path deletes a claim), a required composite `(org_id, entity_id)` FK into
  `issuer_profiles` (`RESTRICT`, matching every other transport table), and a
  required composite `(org_id, fuel_transaction_id)` FK into `fuel_transactions`
  (`RESTRICT` — WO-50 built the `(org_id, id)` unique constraint specifically for
  this; see Implementation guidance §2 for what "one representative transaction
  row" means and what it deliberately does not yet solve).
- `app.services.transport.lock` — two functions:
  - `submit_claim(db, org_id, *, claim_id, invoices)` — a **minimal stub status
    transition** (draft → submitted) that exists to prove the locking primitive,
    not to be the future G2.6 gate stack. Acquires one lock row per invoice via a
    plain `INSERT` (never an upsert) in the SAME flush as the claim's `status`
    flip; a lost race on ANY lock raises `IntegrityError` at `flush()`, still
    inside the caller's open transaction, so a `rollback()` discards the failed
    lock row(s) **and** the status flip together — nothing partially applied.
  - `withdraw_claim(db, org_id, claim_id)` — the **only** function in this
    codebase that deletes a `VatClaimedInvoice` row. Refuses (409,
    `code="claim_not_locked"`) unless the claim is currently `submitted`/
    `approved`/`paid` (R5's "only an explicit withdraw releases; rejection/
    confiscation/appeal keep them" — modeled here by there being no OTHER
    function that could reach a locking state and shed its locks, since no
    reject/approve/pay transition exists yet — see Implementation guidance §4).
- Gated on the `transport` module entitlement first, identical pattern to
  `claim.get_or_create_claim`/`fuel_ingest.ingest_transaction`.
- Migration `<rev>_vat_claimed_invoices.py` — one new tenant table, RLS in the
  same migration.
- Two new audit actions: `A.TRANSPORT_CLAIM_SUBMIT`, `A.TRANSPORT_CLAIM_WITHDRAW`.
- **The concurrency test** — real Postgres, `asyncio.gather`, two separate
  sessions/connections, two different claims racing to lock the SAME invoice key;
  exactly one wins; the loser's claim row is provably unchanged in the database
  (not just "the insert failed") because its whole transaction rolled back.
- **The withdraw-only-release test** — proves nothing else can shed a lock.

**Out of scope** (explicitly, future M3 work orders)
- **The full 1A-5 status state machine** (R17, G2.7) — `submit_claim` here is a
  stub covering exactly draft→submitted; no code/checklist/period-end/deadline/
  minimum gate, no `approved`/`paid`/`rejected` transition, no `status_code`
  derivation ships in this order.
- **The checklist/period-end/minimum-amount/deadline gate stack** (R6-R10, R15,
  G2.6) and **wiring `is_synthetic()` into the lock path as "the lock gate"**
  (R3, G2.3's *consumer* side — the predicate itself already shipped in WO-49;
  this order does not call it). Flagged as the natural next slice — see
  Recommendation for WO-52.
- **Claim-line materialization/freezing** (G2.4/G2.5) — no `VatRefundClaimLine`
  row is written by this order; `submit_claim`'s `invoices` argument is a
  caller-supplied list of `(supplier, invoice_ref, fuel_transaction_id)` tuples,
  not derived from `vat_claim_lines` (which stays unpopulated until G2.4/G2.5).
- **Annual-claim-as-mop-up / quarterly-overlap-blocks-as-duplicate** (R6, G2.6)
  — this order's `submit_claim` does not special-case `-YEAR` vs `-Qn` periods;
  it treats every overlap identically (the natural-key collision refuses it).
  The annual "exclude, don't conflict" carve-out is a **gate rule** layered on
  top of this primitive, not a change to the primitive itself — a future WO
  should be able to build it entirely inside G2.6 by checking `ref_period` before
  calling `submit_claim`, without touching this table or these two functions.
- **Fee freezing** (R13, G2.9), **any `api/routes/transport/*` route**, **any
  UI**, **the monthly close** (G1.3/G1.4 — WO-50's report already noted G1.4
  depends on this order's FK target existing, but the close job itself is not
  built here).

### Implementation guidance

1. **Read `BA_fleet_fuel.md` §3.C5/C7 (lines 458-474) and §4.3 (lines 1020-1039)
   before writing a column.** The `BEGIN IMMEDIATE` / "plain INSERT not INSERT OR
   IGNORE" phrasing is SQLite-specific implementation detail from the retired
   system; the Postgres-native equivalent this order actually ships is: a plain
   ORM `INSERT` (via `db.add()` + `flush()`, never an `on_conflict_do_nothing`
   upsert) inside the SAME session/transaction as the claim's status mutation,
   so a `UniqueViolation` at flush time propagates as `IntegrityError` and the
   caller's `rollback()` — never a partial commit — is what "aborts the whole
   transition" means on this stack.
2. **Why `fuel_transaction_id` is a single required FK, not a list.** The BA
   natural key is invoice-grained (`entity, refund_country, supplier,
   invoice_ref`), but `fuel_transactions` is line-grained — one invoice can
   correspond to several transaction rows (multiple fuel purchases on one
   invoice). WO-50 built exactly one `(org_id, id)` FK target, sized for
   referencing ONE row. This order interprets "a RESTRICT FK into
   `fuel_transactions`" (per the hand-off in WO-50's report and `ARCH_plan.md`
   line 144/865) as: `submit_claim`'s caller supplies ONE representative
   transaction id per invoice being locked (in practice, the first/anchor line
   the future note-matching service resolved for that `invoice_ref`) — enough to
   give the DB a real, RESTRICT-protected anchor per lock row, proving the FK
   shape end to end. Protecting **every** transaction row sharing an
   `invoice_ref` from deletion (not just the anchor) is a service-level
   concern the future close/re-close guard (G1.4) must add on top — e.g. a
   query "does any locked invoice_ref match this transaction's invoice_ref"
   before a period-scoped delete — and is flagged here explicitly as NOT solved
   by the FK alone, so G1.4 does not assume it is. Documented as an
   interpretation of an underspecified boundary, mirroring how WO-50 flagged its
   own `line_seq` natural-key choice.
3. **`submit_claim`'s `invoices` parameter is a plain list of
   `(supplier, invoice_ref, fuel_transaction_id)` — never derived from
   `vat_claim_lines`.** That table stays empty until G2.4/G2.5; this order's
   test fixtures build the list directly from `FuelTransaction` rows created via
   WO-50's `fuel_ingest.ingest_transaction`. `entity_id`/`refund_country` for
   every lock row are read off the **claim**, never re-supplied per invoice — a
   claim's grain already fixes those two fields, so allowing them to vary per
   invoice would let a caller lock an invoice under the wrong entity/country by
   mistake.
4. **Why `withdraw_claim` is "the only function that releases" by construction,
   not by a runtime flag.** The WO's requirement is "a release function that
   only fires on an explicit withdraw action... prove nothing else can trigger
   it as a side effect". Since this order deliberately does NOT build
   `approve`/`reject`/`pay` transitions (out of scope — the full state machine
   is G2.7), there is currently no OTHER code path in the entire `app/services/
   transport/` tree that issues a `DELETE` against `vat_claimed_invoices` — a
   grep-based test asserts this (`test_g2_2_withdraw_claim_is_the_only_function_
   that_deletes_a_lock_row`), and a behavioral test proves that directly
   flipping `claim.status` on the ORM object (simulating a hypothetical future
   transition that forgets to call `withdraw_claim`) does NOT cascade a lock
   release — there is no trigger, no `ondelete` cascade from `vat_refund_claims`
   into `vat_claimed_invoices` keyed on a status value, only on row deletion
   (which no code path performs). When G2.7 later adds real `approve`/`reject`/
   `pay` transitions, each one must positively NOT call `withdraw_claim` (R5) —
   this order's test suite is the regression net that a future PR breaking that
   would trip.
5. **`submit_claim` refuses an empty invoice list** (`code="empty_claim_set"`,
   422) — mirrors R6's future "an annual claim with an empty claim_set is
   refused" spirit at the primitive level, though the annual/quarterly
   distinction itself is out of scope here.
6. **Migration:** `alembic revision --autogenerate`, then hand-edit — RLS for
   the new table in THIS migration (`TENANT_TABLES` module-level tuple,
   identical pattern to `fc45baaf3283_fuel_transactions.py`). Verify `alembic
   upgrade head && alembic check` reports no drift on BOTH SQLite (implicit,
   via the `backend` CI job) and the scratch Postgres 16 instance (port 5433),
   and a downgrade/upgrade round-trip is clean.
7. **`README.md`/`test_docs_truth.py`:** recount `__tablename__` across
   `app/models/**/*.py`; update both together (68 → 69 tables; +1 revision).

### Testing requirements

`backend/tests/transport/test_g2_2_lock.py` (SQLite, service-level):
- `test_g2_2_submit_claim_acquires_one_lock_row_per_invoice_and_flips_status` —
  the happy path; asserts `VatClaimedInvoice` rows exist with the right
  denormalized `entity_id`/`refund_country`, claim status is `submitted`, one
  `AuditEvent` with `action="transport.claim_submit"`.
- `test_g2_2_natural_key_uniqueness_constraint_rejects_a_raw_duplicate_insert` —
  the DB constraint itself, bypassing the service (the lost-race backstop,
  mirroring WO-49/WO-50's own grain-uniqueness tests).
- `test_g2_2_submit_claim_on_an_already_locked_invoice_raises_integrity_error_
  and_leaves_the_claim_status_unchanged` — same-session proof: seed one lock row
  directly, then call `submit_claim` with an overlapping invoice; assert
  `IntegrityError` at flush and, after `rollback()`, the claim's status column
  reads back `draft` from a fresh query (not just "unchanged in memory").
- `test_g2_2_submit_claim_refuses_a_non_draft_claim` — 409
  `code="claim_not_draft"`.
- `test_g2_2_submit_claim_refuses_an_empty_invoice_list` — 422
  `code="empty_claim_set"`, writes nothing.
- `test_g2_2_withdraw_claim_deletes_every_lock_row_for_that_claim_and_sets_
  status_withdrawn` — happy path; the SAME invoice key can then be locked by a
  DIFFERENT claim (R5's "after withdraw, it can" acceptance line, verbatim).
- `test_g2_2_withdraw_claim_refuses_a_claim_that_never_held_locks` — 409
  `code="claim_not_locked"` on a `draft` claim; nothing deleted.
- `test_g2_2_withdraw_claim_is_the_only_function_that_deletes_a_lock_row` — a
  grep-based structural test over `app/services/transport/lock.py` asserting
  exactly one function body contains a `delete(VatClaimedInvoice)` statement,
  and it is `withdraw_claim`.
- `test_g2_2_directly_flipping_claim_status_never_cascades_a_lock_release` — the
  withdraw-only-release proof: seed a `submitted` claim with locks, mutate
  `claim.status` on the ORM object directly to `"rejected"` (simulating a
  hypothetical future transition that does NOT call `withdraw_claim`) and
  commit; assert the lock rows are still present afterward — nothing but
  `withdraw_claim` can make them disappear.
- `test_g2_2_transport_disabled_by_default_is_inert` — both `submit_claim` and
  `withdraw_claim` raise `PermissionError` (403, `code="module_not_enabled"`)
  before any row is queried or written, on a module-disabled org.
- `test_g2_2_unknown_claim_is_a_404_not_found_never_a_500`,
  `test_g2_2_cross_tenant_claim_is_opaque_not_found_never_leaks_across_orgs` —
  the cross-tenant adversarial case, overlapping-looking data across two orgs.

`backend/tests/test_transport_lock_concurrency.py` (real Postgres, `pg_only`,
mirrors `test_numbering_concurrency.py`'s structure):
- `test_two_concurrent_submissions_over_the_same_invoice_exactly_one_wins` — two
  DIFFERENT `VatRefundClaim` rows (same entity/refund_country, distinct
  `ref_period` so the claim grain itself doesn't collide), each racing via
  `asyncio.gather` with its OWN session/engine connection to `submit_claim` an
  overlapping invoice key (same `supplier`+`invoice_ref`, pointing at the SAME
  `FuelTransaction` anchor row — the realistic "two operators tried to claim the
  same underlying purchase" scenario). Asserts: exactly one `VatClaimedInvoice`
  row exists for that natural key; exactly one of the two claims reads back
  `status="submitted"` from a **fresh** query (not the in-memory object); the
  OTHER claim reads back its **original pre-submission status**
  (`"draft"`) from a fresh query — proving the whole transaction rolled back,
  not just the lock insert.
- `test_withdraw_then_reclaim_by_a_different_claim_succeeds` — after
  `withdraw_claim` on the winner, a THIRD claim can `submit_claim` the same
  invoice key — R5's "after withdraw, it can" acceptance line proven on real
  Postgres (not just SQLite), where the previous test already proved the
  opposite ("cannot, while locked") on the same infrastructure.

### Rollback strategy

Migration downgrade (`alembic downgrade -1`) drops `vat_claimed_invoices` (and
its Postgres RLS policy) — safe, nothing outside this order's own tests ever
writes to it. A code-only revert without the migration downgrade is safe (the
table simply goes unused). No kill switch is needed for a production incident:
the `transport` module stays default-OFF and is absent from every plan's module
set, so `submit_claim`/`withdraw_claim` are unreachable by any tenant regardless
of code presence.
