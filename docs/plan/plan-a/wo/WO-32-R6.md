### Objective and business value

`backend/app/services/reimbursement.py::mark_paid` (route `backend/app/api/routes/reimbursements.py::pay_batch`,
lines ~161–195) lets the SAME `EXPENSE_APPROVE`-holding account that called `create_batch` immediately call
`pay_batch` on that same batch, alone. This is inconsistent with the analogous AP payment-run flow
(`app/services/payment_run.py::_enforce_sod`, `mark_paid`/`approve_run`), which the codebase's own
`00_MASTER_CONTEXT.md` invariant §4/8 names as the canonical example of "segregation of duties where
money moves." A reimbursement batch produces a real SEPA credit-transfer file
(`reimbursement.py::batch_sepa`) — an unsupervised single account can originate AND settle an employee
payout end to end with no second set of eyes, exactly the fraud/error surface SoD exists to close.
Evidence: `docs/audit/functional-audit.md` §2.2; `docs/audit/remediation-roadmap.md` R6.

Closing this removes a control gap the product cannot self-serve past: once reimbursements go live for an
unsupervised customer (any org beyond a single-admin org, which already has its own documented override
escape hatch — see below), a compromised or careless single account being able to move real money to a
bank file with zero second-party review is exactly the kind of gap that kills trust with a finance-lead
buyer doing due diligence, and is the same class of control this roadmap has already fixed twice
(payment runs — pre-existing; expense-report approval — WO-30's R4).

### Scope

**In scope:**
- `backend/app/models/expense.py::ReimbursementBatch` — add `created_by_id` (nullable GUID), mirroring
  `PaymentRun.created_by_id`.
- A new Alembic migration adding that column (additive only, no new table, existing RLS/FORCE policy on
  `reimbursement_batches` already covers the new column).
- `backend/app/services/reimbursement.py` — `create_batch` accepts and stores `created_by_id`; a new
  `_sod_conflict`/`_enforce_sod`-equivalent (single "creator" role — batches have no separate approval
  stage, per the existing `assert_exportable` docstring); `mark_paid` takes `actor_id`, `actor_email`,
  `is_platform_admin`, `override_sod` and enforces creator ≠ payer before settling, with the same audited,
  explicit platform-admin override pattern as `payment_run.py` (`override_sod=True` AND
  `is_platform_admin` required; never silent).
- `backend/app/schemas/reimbursement.py::BatchPay` — add `override_sod: bool = False`.
- `backend/app/api/routes/reimbursements.py` — `create_batch` passes `created_by_id=current.id`;
  `pay_batch` passes `actor_id=current.id`, `actor_email=current.email`,
  `is_platform_admin=bool(current.is_platform_admin)`, `override_sod=body.override_sod`.
- `backend/app/services/audit.py::A` — new `REIMBURSE_SOD_OVERRIDE = "reimbursement.sod_override"` action.
- New test file `backend/tests/test_reimbursement_sod.py` mirroring `tests/test_payment_runs_sod.py`'s
  structure (creator-cannot-pay-own-batch, a different user can pay, platform-admin override is audited
  and requires the explicit flag).

**Out of scope:**
- Any "approver" role/stage for reimbursement batches (there isn't one today — each underlying expense
  report is individually approved before it can be batched; this order does not add a second approval
  stage on the batch itself, only a maker≠checker check on the pay action, matching the roadmap's own
  proposed solution).
- R7/R14/R16/R18 — separate roadmap items, separate work orders.
- Any frontend UI for the `override_sod` escape hatch — `PaymentRuns.tsx` (the precedent) exposes no such
  UI either; it is a cross-tenant platform-operator-only path, never surfaced to a tenant user. Existing
  generic error-toast handling (`onErr`/`apiError`) in `Reimbursements.tsx` already surfaces the new 403
  without any frontend code change.
- The single-admin-org escape hatch question (an org with exactly one user cannot ever satisfy maker≠checker)
  is already precedented by `payment_run.py` (same limitation exists there today, accepted risk, not
  reopened by this order).

### Implementation guidance

1. Add `created_by_id` to the `ReimbursementBatch` model (GUID, nullable — matches `PaymentRun.created_by_id`
   exactly, including the "legacy rows have NULL, fall back to email" tolerance).
2. Write the migration: `op.add_column("reimbursement_batches", sa.Column("created_by_id", app.models.base.GUID(), nullable=True))`.
   Downgrade drops it. No RLS change (existing table, existing FORCE RLS policy already covers every column).
3. In `reimbursement.py`, add `_sod_conflict(batch, actor_id, actor_email) -> str | None` (returns `"creator"`
   or `None` — only one role exists here, unlike payment runs' creator/approver pair) and
   `_enforce_sod(db, batch, *, actor_id, actor_email, is_platform_admin, override_sod) -> None`, structured
   identically to `payment_run._enforce_sod`: on conflict with no override, raise `AppError(...,
   code="maker_is_checker", status=403)` directly (NOT `ReimbursementError` — the route must not catch and
   remap this to 409; mirror `payment_run.py`'s import of `app.core.errors.AppError`). On conflict WITH a
   valid platform-admin override, audit `A.REIMBURSE_SOD_OVERRIDE` with `meta={"control": "maker_is_checker",
   "stage": "pay", "conflict_role": "creator", "actor": actor_email}` and proceed.
4. `create_batch` stores `created_by_id` alongside the existing `created_by` email.
5. `mark_paid` calls `_enforce_sod` before any state mutation (before the `BATCH_OPEN` status check is fine
   either order — actually check status FIRST as today, then SoD, to keep the existing "batch is X; only an
   open batch can be paid" `ReimbursementError` → 409 behavior unchanged for that case; SoD is the second
   gate, matching `payment_run.mark_paid`'s ordering — status check first, then `_enforce_sod`).
6. Route: `pay_batch` passes the four new actor/override arguments; `create_batch` passes `created_by_id=current.id`.
7. Fail-closed default: with `actor_id`/`actor_email` unset (should never happen — `current` is always an
   authenticated user) the conflict check simply can't match, so no accidental lockout; this mirrors
   `payment_run.py`'s own fail-closed comment.

### Invariants this order must preserve

- **§4/8 Segregation of duties** — this order is closing that exact gap for a second "money moves" surface
  (reimbursement payout, in addition to the pre-existing payment-run control).
- **§4/16 Audit on mutation** — the override path is audited (`REIMBURSE_SOD_OVERRIDE`); the ordinary
  denial path needs no audit row (nothing changed) — matches `payment_run.py`'s treatment.
- **§4/20 Wire contract frozen** — the 403 denial is `{"detail", "code": "maker_is_checker"}` via the
  existing `AppError` → JSON exception handler, identical shape to the payment-run precedent; `BatchPay`
  gains one new **optional** field (`override_sod`, default `False`) — additive, not breaking.
- **Tenancy** — no new tenant-scoped table; `reimbursement_batches` keeps its existing RLS/FORCE policy
  covering the new column automatically (no migration change needed there).

### Database / migration impact

One additive nullable column on an EXISTING tenant table (`reimbursement_batches.created_by_id`, GUID).
No new table → no new RLS policy required (`test_rls.py::test_rls_migration_covers_every_tenant_table`
only tracks the *table* set, unaffected by a new column). Backfill: NULL for every pre-existing batch —
the SoD check's email fallback (`actor_email == batch.created_by`) still covers those rows exactly as
`payment_run.py`'s equivalent NULL-`created_by_id` legacy rows are covered. Downgrade drops the column —
safe, loses only the id-based (vs. email-based) attribution precision for future SoD checks on batches
created before the column existed, never lossy for money/ledger data.

### Rollback strategy

Code revert is a plain git revert (no data migration to unwind beyond the column). Migration downgrade
drops `created_by_id` — safe, no data loss beyond that single attribution column (email-based `created_by`
is untouched and remains the fallback identity source). No one-way effect (no session revocation, no data
correction). Narrow mitigation short of a full revert: disabling the check is NOT an option (it is the
fix); if the override path itself needs pausing, unset `is_platform_admin` on the relevant account(s) —
same operational lever the payment-run precedent already relies on.
