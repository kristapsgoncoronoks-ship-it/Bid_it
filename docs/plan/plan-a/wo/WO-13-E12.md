# WORK ORDER 13 — Line-item provenance (board E1.2)

**WORK ORDER 13 — Line-item provenance & confidence (board E1.2). Effort L 6–12d. Priority P1. Milestone M1. Depends on: WO-12 (E1.1 capture-review UI, complete at `148cbfb`).**

Baseline (recorded, per process rules — no pre-change re-run): **1000 passed, 4 skipped** at `148cbfb` (the 4 skips are pg-only markers, verified separately on Postgres).

### Objective and business value

Provenance covers only five header fields. Verified evidence: `backend/app/services/extraction_provider.py:42` — `_HEADER_FIELDS = ("invoice_number", "vendor_name", "issue_date", "due_date", "currency")` is the complete set any provider captures; `backend/app/models/extraction_field.py` has no line scope (one row per *top-level* field, per its own docstring); the E1.1 review screen honestly captions the gap at `frontend/src/pages/CaptureReview.tsx:545` — "Line items don't carry per-field confidence yet — check the amounts against the document." So the part of an invoice that actually carries the money — quantities, unit prices, line amounts, tax rates — has **no per-field status, no confidence, no original-vs-reviewed trail**, on exactly the OCR paths (`pdf_ocr._parse_row` heuristics, confidence 0.55) where a misread digit is most likely.

Who stops losing money: the finance lead reviewing a 40-line fuel statement read by OCR currently gets "verify every figure" as a document-level warning and no per-cell signal about *which* figures were confidently read vs guessed — so they either re-check everything (re-keying by another name, the exact cost the product exists to remove) or check nothing (a wrong amount enters the AP record and survives until reconciliation). Line-item confidence turns that into a targeted five-second glance at the amber cells. It is also the prerequisite for E1.5's learning loop (per-vendor field-mapping memory needs line-scoped corrections to learn from).

### Scope

Per ARCH_plan E1.2 (M1, §"EPIC E"): *"Extend `extraction_fields` to line-item scope. Acceptance: a line-item field carries the same honest confidence semantics — `None` means exact (a typed field), not "unknown"; PDF text `0.85`; OCR `0.55`. Testing: per-provider provenance assertions."* (ARCH names `app/models/extraction.py` / `app/services/extraction.py`; the real modules are `app/models/extraction_field.py` + `extraction_run.py` and `app/services/extraction.py` + `extraction_provider.py` + `parser.py` — recorded here as the E1.1-style naming correction, per master context §9 "report what you found".)

**In scope:**
- `ExtractionField.line_index` (nullable int; NULL = header field, `n` = 0-based position in the draft's `line_items`) + the Alembic migration.
- Line-scoped `FieldCapture`s from every provider, six fields per line (`description`, `category`, `quantity`, `unit_price`, `amount`, `tax_rate`):
  - CSV/JSON (`parser.py`): presence-based status per raw cell (`extracted` when the source row has the key non-empty, `defaulted` when `_line_from`'s default filled it — incl. `amount` computed as qty×unit), confidence `None` (deterministic → exact).
  - e-invoice XML (UBL/CII, incl. embedded in PDF): confidence `None` (structured source).
  - PDF text-layer: `0.85`; PDF OCR / image OCR: `0.55` — same `LOW_CONFIDENCE_THRESHOLD = 0.75` flag rule.
- **Deliberate flag-rule difference for line fields** (documented in code): a line field flags `low_confidence` when its *confidence* is below threshold or its status is `missing` — a `defaulted` line field does NOT flag (unlike the header five). Rationale: `category` is structurally defaulted on nearly every line of every provider (no parser reads a category) and `tax_rate` is legitimately 0/filled on most; flagging them would put dozens of meaningless flags on every capture and drown the queue's "needs a look" count, destroying the signal the E1.1 pill exists to give. The `defaulted` status badge still shows honestly in the UI; it just doesn't demand review.
- Persistence (`extraction.record_fields`) and stable read order (`fields_for_run`: header rows first, then by line, then by field name).
- Wire shapes (additive only, §4.20): `line_index: int | null` on `FieldProvenance`, `FieldProvenanceOut`, and `FieldReviewIn` (so a correction can target `line_items[2].amount`).
- Correction endpoint `POST /invoices/captures/{run_id}/review`: match on `(field, line_index)`; audit meta keys `line_items[{i}].{field}` for line corrections (header keys unchanged).
- Frontend: `CaptureReview.tsx` line-item table becomes provenance-aware **and editable** — per-cell low-confidence emphasis, per-line status/confidence detail, reviewed-value seeding on reload, line corrections included in "Save corrections"; the E1.1 limitation caption is REMOVED. `types.ts` gains `line_index`.
- Tests: per-provider provenance assertions (deterministic None / text-layer 0.85 / OCR 0.55), CSV/JSON extracted-vs-defaulted per cell, correction round-trip + audit for a line field, migration up/down/up; updates to the two tests that encoded the header-only limitation (see Testing).

**Out of scope (anti-scope-creep):**
- Extraction learning loop over the new line corrections — **E1.5**.
- Hash re-upload detection — **E1.3**; scored duplicate candidates — **E1.4**; email provider adapter — **E1.6**; AI capture policy — **E1.7**.
- Any change to the validation engine's line-math rules (`recon_*`) — WO-7 owns those; confirm-time totals are already recomputed server-side (§4.10) and this order integrates by *not duplicating* them.
- Wiring the dead AP workflow states — **C1.9**.
- Reworking `pdf_ocr`'s row heuristics to report per-cell char-level confidence — the per-method confidence model (ARCH's own acceptance) stands.

### Implementation guidance

1. **Model + migration first.** Add `line_index` (Integer, nullable) to `ExtractionField`; migration uses `batch_alter_table` (SQLite-safe), no backfill needed — every existing row is a header row and NULL already means that. Single head before/after; `alembic upgrade head && alembic check`; exercise up→down→up.
2. **Schema seam.** `line_index: int | None = None` on the three Pydantic models (`ge=0` on `FieldReviewIn`). Additive on responses and an optional request field — the frozen wire contract (§4.20) is preserved; every existing client payload still validates.
3. **Providers.** In `extraction_provider.py` add `_LINE_FIELDS = ("description", "category", "quantity", "unit_price", "amount", "tax_rate")` and `_line_captures(draft, *, method, provider)` mirroring `_header_captures`: per line `i`, per field, value from the `LineItemIn`; status `extracted` for description/quantity/unit_price/amount (present by construction), `defaulted` for `category` (no parser reads one) and for `tax_rate == 0` (the parsers' fill value; a non-zero rate was read/inferred from the document → `extracted`); confidence = the method's score for `extracted` fields (None deterministic / 0.85 text / 0.55 OCR), None for defaulted. Line flag rule: `low_confidence = (status == "missing") or (confidence is not None and confidence < LOW_CONFIDENCE_THRESHOLD)` — document WHY it differs from the header rule (see Scope). Append to `fields` in `PdfProvider` (all three pdf methods), `EInvoiceProvider`, `ImageProvider`.
4. **CSV/JSON keep the honest presence data** they alone have: in `parser.py`, `_parse_csv`/`_parse_json` build line provenance from the RAW row dicts (which keys were actually present) → status per cell; original_value = the raw cell text, normalized_value = the parsed value. `_captures_from_provenance` carries `line_index` through; deterministic confidence stays None. The computed-amount case (`amount` absent, qty×unit used) is `defaulted` — the server would recompute it identically on confirm, so it is a fill, not a read.
5. **Persist + read.** `record_fields` writes `line_index`. `fields_for_run` orders `line_index NULLS FIRST, line_index ASC, field ASC` so the header five stay first and line rows group per line deterministically on both SQLite and Postgres.
6. **Correction endpoint.** Key the lookup by `(field, line_index)`; a body item without `line_index` targets the header row exactly as today. Audit meta key for a line correction: `line_items[{i}].{field}` (header keys unchanged — no existing audit consumer breaks). Same §4.16 pattern: `audit.record` before the commit, atomic with the mutation. Out-of-range / unknown `(field, line_index)` pairs are ignored exactly like unknown header fields today (no mutation → no audit event).
7. **Queue counts** (`GET /invoices/captures/review`): no code change — `low_confidence_fields`/`total_fields` now naturally include line fields. With the line flag rule, deterministic captures contribute 0 new flags; OCR captures flag their genuinely-uncertain cells. Document in the route docstring.
8. **Frontend.** `CaptureReview.tsx`: line table cells become inputs (description/category/qty/unit/amount/tax %) seeded from the draft with any `reviewed_value` line rows applied on load (same seeding effect as headers); per-cell amber emphasis + a per-cell provenance note (`aria-describedby`, same badge/confidence vocabulary as headers — `null` renders "exact"); `corrections()` extends to line fields emitting `{field, line_index, reviewed_value}`; REMOVE the "don't carry per-field confidence yet" caption. Client-side subtotal stays display-only — the server recomputes on confirm (§4.10) and WO-7's `recon_*` validation still gates. No new UI library, existing primitives only.
9. **Money basis:** provenance stores *strings* (captured text); no arithmetic is added anywhere in this order — the only line math (display subtotal, server recompute) already exists. No new float path.

### Invariants this order must preserve

- **§4.19 (advisory extraction):** line captures are suggestions with confidence; a human confirms; corrections are `reviewed_value` provenance via the audited endpoint; the machine's capture is never rewritten; nothing touches an invoice before Confirm.
- **§4.16 (audited mutation):** line corrections ride the existing `capture.field_review` event, old→new per key, atomically with the field update.
- **§4.10 (server recomputes totals):** untouched — `persist_invoice` still recomputes line amount/tax/total from the confirmed draft; edited provenance never feeds arithmetic.
- **§4.20 (frozen wire contract):** all shape changes are additive optional fields; no existing response field changes meaning or type; error shape untouched.
- **§4.1/§4.2 (tenancy):** no new table — the RLS set-equality test is untouched; `extraction_fields` already carries org_id + RLS + ORM-guard registration; all reads/writes stay behind `fields_for_run`/`get_capture` org filters.
- **§4.4 (opaque 404):** unchanged behaviour on the existing endpoints, still proven by `test_capture_endpoints_cross_tenant_404`.
- **§4.9 (no float money):** no new arithmetic; confidence stays `Decimal`/`Numeric(4,3)`.

### Rollback strategy

Code revert + `alembic downgrade -1` (written and exercised; loses only line-scoped provenance rows' scoping — reverts to header-only capture, the E1.1 state, and the UI caption returns with the revert). No one-way effects: audit rows written with line keys remain valid history (the chain never requires an action/key shape to persist). Narrow mitigation without revert: none needed — the feature is additive and read-path-safe (a NULL `line_index` renders exactly as before).
