# WO-50 — `fuel_transactions`: the typed transaction model + idempotent ingestion + product-group derivation (board G1.2)

<!-- ═══════════════ COPY FROM HERE: WO-50 ═══════════════ -->

**WORK ORDER 50 — `fuel_transactions` foundation: typed model, natural-key idempotent
ingestion, `product_group` derivation (board G1.2). Effort L (6-12d). Priority P0.
Milestone M3. Depends on: WO-49 (G1.1 — transport context skeleton + module
entitlement).**

### Objective and business value

WO-49 shipped the claim grain (`VatRefundClaim`/`VatRefundClaimLine`) and the one
centralized `is_synthetic()` predicate, but nothing yet produces a claim line's
`invoice_ref`/`vat_id`/`net_eur`/`vat_eur` from real fuel-card data — there is no
typed transaction model in the tree (`app/models/transport/fuel_transaction.py`
does not exist; verified at `453872d`, WO-49's own report, and
`ARCH_plan.md`'s own dependency chain `G1.1 → G1.2 → G2.1 → G2.2 → ...`). Fleet
Fuel's own transaction table has **no primary key and no unique constraint** —
idempotency was "DELETE-by-period, whole month, every reload" (`BA_fleet_fuel.md`
§8.1 item 6) — and its single `note` column simultaneously carried an invoice
number, a rebate explanation and a cash-at-pump flag (§8.1 item 5), which is
*why* `_resolve_inv`'s matching heuristic and the entire `note_invoice_overrides`
admin table exist in the source system at all. Both are named explicitly as dead
weight that must not be reproduced (§8.1 items 4-6) and as the reason G1.2 is a
prerequisite for the lock table (G2.2): `vat_claimed_invoices`'
`UNIQUE(entity, refund_country, supplier, invoice_ref)` and the future frozen
`vat_claim_lines` population both need a transaction row that can be referenced
by a stable, structural key — not "whatever DELETE-by-period left behind".

**Citation correction, verified against the source text (master-context §9 — a
citation mismatch is reported, not silently followed):** `ARCH_plan.md` line 853
tags G1.2 as `(R29, R30, and Fleet Fuel §8.1 items 4-6)`. Reading
`BA_fleet_fuel.md`'s R-table directly, **R29 and R30 are NOT about
`fuel_transactions`** — R29 is "the engine owns and writes the product data; the
app reads it read-only at the connection level" and R30 is "the legal claim
record lives in a separate store from the analytics/transactions store the
monthly close rebuilds" (lines 1396-1397). Those are real rules, already
satisfied by this codebase's existing `dataproduct`-vs-`vat_refund_claims`
separation pattern (WO-49's `vat_refund_claims`/`vat_claim_lines` already live
apart from any future engine-owned analytics store) and not specific to this
order's scope. The content this order actually needs — the canonical
transaction schema (field list, `product_group` precedence, the two-tier
`net_eur`/`net_eur_eff` discount model) — lives in `BA_fleet_fuel.md` **§4.2
"The core business entity — a validated fuel TRANSACTION"** (lines 976-1018),
and the "what not to carry forward" guidance (typed schema, split `note`,
natural key) lives in **§8.1 items 4-6** (lines 1479-1487), which *is* correctly
cited. This order builds from §4.2 + §8.1 items 4-6, the parts of the citation
that are real; the R29/R30 tag itself is a mislabel in `ARCH_plan.md` this
order does not attempt to fix (out of scope — a planning-doc typo, not a code
defect) but does not follow into the implementation.

Who pays more without this: every future G1.x/G2.x work order (the monthly
close, the goods-code mapping, the lock table, claim-line materialization,
excise, benchmark, anomaly detection) reads fuel line-item data — without a
typed, deduplicated, structurally-keyed transaction table underneath, each of
them either re-derives its own ad-hoc dedup (drift risk, the exact bug §8.1
item 6 exists to prevent) or blocks on this order. Getting the natural key and
`product_group` precedence right now, with the parametrized test matrix this
order requires, is cheaper than discovering a duplicate-ingestion or
mis-grouped-HVO bug after the lock table and close job are already built on
top of it.

### Scope

**In scope**
- The `FuelTransaction` model (`app/models/transport/fuel_transaction.py`) —
  columns per `BA_fleet_fuel.md` §4.2's canonical schema, adapted to this
  codebase's typed-column/Decimal/tenant conventions: `entity_id` (composite FK
  into `issuer_profiles`, same reuse as `VatRefundClaim`), `supplier`, `country`
  (supply country = VAT jurisdiction), `vehicle_ref`, `txn_date`, `txn_time`,
  `station`, `product`, `product_group` (derived, see below), `qty`
  (**deliberately not money-quantized**), `currency`, `net_local`/`vat_local`/
  `gross_local`, `net_eur`, `vat_eur`, `net_eur_eff`, the FX provenance
  quadruple (`fx_rate`/`fx_ecb_rate`/`fx_ecb_date`/`fx_source` — reusing the
  platform's existing 4-value `fx_source` enum from `app/models/fx.py`, not
  Fleet Fuel's own 3-value one — see Implementation guidance §5), `period`
  (`YYYY-MM`, retained for the future G1.3/G1.4 period-scoped close).
  **Split `note`** (§8.1 item 5) into `invoice_ref` (nullable — the raw
  matching reference captured at ingestion, resolved to `invoice_id` by a
  future note-matching service) and `provenance_note` (nullable free text —
  rebate explanation / cash-at-pump flag / capture lineage), never a single
  overloaded column.
- **The natural key** (§8.1 item 6: *"Add a natural key (supplier, invoice line
  identity) so duplicate suppression is structural"*) — `UNIQUE(org_id,
  entity_id, supplier, period, line_seq)`, where `line_seq` is the caller-
  supplied, deterministic 1-based position of this line within its source file
  for that `(entity, supplier, period)` group. See Implementation guidance §2
  for why `line_seq` was chosen over an `invoice_ref`-keyed alternative.
- **`app.services.transport.product_group.derive_product_group(product: str) ->
  str`** — the ONE centralized derivation (mirrors `claim_gates.is_synthetic()`
  being centralized for the same drift-prevention reason: `product_group`
  "drives the Art. 9 goods code", §4.2 row 8, so a second ad-hoc
  implementation is exactly the kind of drift R3's centralization pattern
  exists to prevent). Precedence **PROMO → HVO → {AdBlue, Parking, Toll/Fees}
  → Diesel (multilingual tokens) → Service/Other (default)**, verbatim per
  §4.2 row 8.
- **`app.services.transport.fuel_ingest.ingest_transaction()`** — insert-or-
  no-op on the natural key, gated on the `transport` module entitlement FIRST
  (same `modules.is_enabled` / `PermissionError(code="module_not_enabled")`
  pattern as WO-49's `get_or_create_claim`), entity resolved through
  `issuer.get_by_id` (opaque 404, never a raw join), audits exactly once per
  actual insert (never on a no-op replay).
- **The FK linking `fuel_transactions` to the AP invoice table** — a nullable
  composite `(org_id, invoice_id) -> invoices(org_id, id)` FK, `ondelete=SET
  NULL`, per ADR-P3 rule 1 verbatim (*"Fuel detail lives in `fuel_transactions`
  with a nullable FK to the AP invoice it was captured from"*,
  `VAT_HARVEST.md` E.2). This is how `fuel_transactions` and `vat_claim_lines`
  "eventually relate" (both carry a nullable FK into the SAME `invoices` table)
  without `fuel_transactions` referencing `vat_claim_lines` directly or vice
  versa — matching ADR-P3's explicit ban on a second cross-domain reference
  path. The future note-matching/materialization service (G2.4/G2.5) is what
  populates `invoice_id` on both sides from the resolved `invoice_ref`; **no
  code in this order populates it.**
- A composite `(org_id, id)` unique constraint on `fuel_transactions` — the
  future FK target for the G2.2 lock table (`vat_claimed_invoices`) per
  `VAT_HARVEST.md` E.2 ("a RESTRICT FK from `vat_claimed_invoices` makes
  accidental deletion an error").
- Migration `<rev>_fuel_transactions.py` — one new tenant table, RLS in the
  same migration, defense-in-depth CHECK constraints (`product_group` restricted
  to the exact 7-value set, `fx_source` restricted to the platform's existing
  4-value set).
- Tests: natural-key dedup idempotency, the raw-duplicate-insert DB-level
  backstop, `product_group` precedence (parametrized, every category + the
  documented tie-break), tenancy isolation (cross-org probe, opaque 404 on a
  cross-tenant entity), module-off inertness.
- `docs/transport/rules.md`, `docs/architecture/adr/0023-...md`,
  `README.md` (table-count truth-up), `TODO.md` updated in the same order.

**Out of scope** (explicitly, future M3 work orders)
- **Claim-line materialization/population from transactions** (R2/R16,
  G2.4/G2.5) — no code in this order writes a `VatRefundClaimLine` row from a

### Implementation guidance

1. **Read `BA_fleet_fuel.md` §4.2 (lines 976-1018) before writing a column.**
   The field list, the `product_group` precedence sentence (row 8), and the
   `net_eur_eff` two-tier discount-model note are the load-bearing source
   text — do not paraphrase the precedence order, copy its exact wording into
   the docstring the way WO-49 copied `is_synthetic()` verbatim.
2. **Why `line_seq`, not an `invoice_ref`-keyed natural key.** §8.1 item 6 says
   only "(supplier, invoice line identity)" — underspecified. `invoice_ref` is
   NOT always known at ingestion time (many fuel-card feeds are per-card-
   statement, not per-invoice, and `invoice_ref` is nullable here exactly
   because of that); keying uniqueness on a nullable column is unsound
   (`NULL <> NULL` under a UNIQUE constraint lets duplicate NULLs silently
   through on every dialect this project targets). `period` was Fleet Fuel's
   own partition/idempotency unit (§4.2 row "period... DELETE-by-period is the
   idempotency unit") and is always known at ingestion. `line_seq` is the
   position of this row within the source file for its
   `(entity, supplier, period)` group, assigned by the CALLER (the future
   parser/ingestion pipeline) deterministically — re-parsing the identical
   file yields the identical sequence, so `ingest_transaction()` called twice
   with the same file is idempotent by construction; a corrected/appended file
   adds new `line_seq` values without colliding with previously-ingested ones.
   This is documented as a deliberate interpretation of an underspecified BA
   phrase, not an invented requirement — flagged in the model docstring.
3. **`product_group` precedence, and what is NOT fully specified.** The
   PROMO → HVO → {AdBlue, Parking, Toll/Fees} → Diesel-last → Service/Other-
   default order and the multilingual diesel token list (`DIESEL`, `ON ACT`,
   `GASOLEO`, `GASOIL`, `GAZOLE`, `"ON "`) are exact, verbatim from §4.2 row 8.
   The specific token sets for HVO/AdBlue/Parking/Toll-Fees/PROMO themselves
   are NOT given in the source text beyond the category names — choose a
   small, obviously-representative token per category (`"HVO"`, `"PROMO"`,
   `"ADBLUE"`/`"AD BLUE"`, `"PARKING"`, `"TOLL"`/`"ROAD TOLL"`), document this
   explicitly as an extensible best-effort set (mirroring how WO-49 flagged
   goods-code *mapping* itself as future work while shipping only the R11
   schema-level defense), and leave a documented seam for extending the token
   list without a migration (module-level tuples, not a DB table — the mapping
   TABLE is future work per G2.8).
4. **`ingest_transaction` checks the module entitlement with `modules.
   is_enabled`, never `modules.require_enabled`** — identical reasoning to
   WO-49's `get_or_create_claim` (a service raises `AppError`, never
   `fastapi.HTTPException`). Check BEFORE any query.
5. **`fx_source` reuses the platform's existing 4-value enum** (`eur`,
   `stated`, `ecb`, `unknown` — `app/models/fx.py::FxSource`/
   `FX_SOURCE_CHECK`), not Fleet Fuel's own 3-value `eur`/`ecb`/`none`. This is
   a deliberate alignment with master-context invariant §4.15 ("One FX
   convention... `fx_source ∈ {eur, stated, ecb, unknown}`") over a literal
   harvest — the platform's own convention wins where the two differ, per
   ADR-P3 rule 4 ("Transport reuses the platform floor unchanged").
6. **`qty` is never passed through `app.core.money.q2`** — it is the €/L
   denominator, explicitly NOT money-quantized (§4.2 row 9, master-context
   §4.9's own qty carve-out). Every monetary column (`net_local`, `vat_local`,
   `gross_local`, `net_eur`, `vat_eur`, `net_eur_eff`) IS quantized via `q2`
   inside `ingest_transaction` before the row is built — the caller may pass
   an un-quantized Decimal; the service is the single point that rounds.
7. **Migration:** `alembic revision --autogenerate`, then hand-edit — add the
   `product_group` CHECK (7-value set), the `fx_source` CHECK (reuse
   `FX_SOURCE_CHECK` from `app/models/fx.py`), RLS for the new table in THIS
   migration (`TENANT_TABLES` module-level tuple, identical pattern to
   `02d418169f97_transport_vat_claim_grain.py`). Verify `alembic upgrade head
   && alembic check` reports no drift, and a downgrade/upgrade round-trip is
   clean.
8. **`README.md`/`test_docs_truth.py`:** recount `__tablename__` across
   `app/models/**/*.py`; update both the README prose and the test's
   hardcoded literal together (67 → 68 tables; Alembic revision count +1).

### Database / migration impact

One new tenant table, `fuel_transactions`, RLS-policy'd in
`<rev>_fuel_transactions.py` (SQLite in tests = no-op; Postgres =
`ENABLE`/`FORCE ROW LEVEL SECURITY` + the standard `tenant_isolation` policy,
identical predicate to every other tenant table). No column added to any
existing table. Backfill: none (the table starts empty; nothing in this order
populates it outside test fixtures). Downgrade drops the table (and its
Postgres RLS policy) cleanly — verified via `alembic downgrade -1 && alembic
upgrade head`; nothing is lost on downgrade because nothing outside this
order's own tests ever writes to it yet.

### Rollback strategy

Migration downgrade (`alembic downgrade -1`) drops `fuel_transactions` (and its
Postgres RLS policy) — safe, loses nothing because nothing outside this
order's own tests ever writes to it. A code-only revert without the migration
downgrade is safe (the table simply goes unused); the reverse (reverting the
migration while the code is still deployed) would error the moment
`ingest_transaction` is called, so always downgrade the migration in the same
step as reverting the code. No kill switch is needed for a production
incident: the `transport` module stays default-OFF and is absent from every
plan's module set, so the table is unreachable by any tenant regardless of
code presence.
