# WO-47 — Quota keyed off the org's plan, not the user's role (H1.3)

<!-- ═══════════════ COPY FROM HERE: WO-47 ═══════════════ -->

**WORK ORDER 47 — Quota keyed off the org's plan, not the user's role (H1.3). Effort M (3–5d). Priority P0. Milestone M2. Depends on: nothing (H1.2, the plan-ladder reconciliation, is owner-blocked — see Scope/Out of scope below; this order does NOT wait on it).**

### Objective and business value

Verified evidence, read straight off `HEAD=a7cf6c6` (repo tip when this order
was opened; confirmed unchanged through `HEAD=7164416`):

`backend/app/services/access.py::LIMIT_DEFAULTS` was a `dict[UserRole, tuple[int,
int]]` — the monthly invoice/upload cap was looked up by the **acting caller's
stored role** (`enforce_invoice_quota(db, org_id, role)` /
`enforce_upload_quota(db, org_id, role)`, called with `current.role` at every
call site — `app/api/routes/invoices.py:218`/`792`,
`app/api/routes/email.py:322`). Meanwhile the USAGE those limits are checked
against was always counted **org-wide**:
`access.invoices_this_month(db, org_id)` and `access.usage_count(db, org_id,
"upload")` never filtered by user. That mismatch is a real, demonstrable bug,
not a hypothetical one: two members of the identical paying organization saw
**different** caps purely because of an internal permission role that has
nothing to do with what the ORG pays for — a `user_free` teammate could be
blocked at 10 invoices/month while an `admin` teammate in the SAME org
(`LIMIT_DEFAULTS[UserRole.admin] == (0, 0)`, unconditionally unlimited) sailed
straight past the org-wide count with no cap at all, and vice-versa a
low-privilege member's usage silently ate into what should have been a
high-privilege member's separate "unlimited" allowance. `ARCH_plan.md` M2
names this exact defect: *"the quota model is probably wrong (it keys off the
user's role, not the org's plan) and must be fixed before the first invoice,
not after."* Confirmed exactly as described — not a hypothesis, the actual
mechanism read off the file.

Who pays more for this gap: once Stripe go-live happens (M2, still
owner-blocked on live credentials — `docs/DECISIONS-NEEDED.md` §2), the first
customer who buys, say, the `starter` plan and staffs it with a mix of
`user`/`admin`/`finance_manager` seats will get a cap that is **incoherent
with what they were billed for** — either an admin on their team gets
unlimited usage the plan never priced in (revenue leakage on every such org),
or a low-role teammate on a generously-capped plan gets refused while the
org's real plan-level allowance sits unused (a support ticket and a churn
risk on day one of paid usage). Fixing this NOW, while billing is still dark,
means the metering substrate is correct BEFORE the first real invoice goes
out — fixing it after go-live means reconciling disputed usage against money
already charged.

### Implementation guidance

1. **Confirm the bug first.** Read `access.py::LIMIT_DEFAULTS`,
   `enforce_invoice_quota`/`enforce_upload_quota`'s call sites, and
   `invoices_this_month`/`usage_count` — confirm usage is counted org-wide
   while the limit was role-keyed, exactly as described above, before
   touching anything (behaviour-preserving-refactor discipline: know the
   current behaviour cold before changing it).
2. **Pick indicative per-plan defaults WITHOUT inventing new business
   numbers.** Carry the existing role-keyed defaults forward 1:1 onto the
   plan dimension: the former free-tier default (10 invoices/20 uploads)
   becomes `trial`; the former paying-individual default (1000/2000) becomes
   `starter` (the cheapest paid plan); the former
   admin/owner/business-role-unlimited default (0/0) becomes `pro` and
   `enterprise` (the business-oriented paid plans). This reassigns numbers
   that already existed in the codebase to the corrected dimension — it does
   NOT propose a new pricing/limit policy, so it does not trip the H1.2
   decision gate. Mark them `# indicative` in `plans.py`'s docstring and
   note they are sysadmin-overridable per plan (same override mechanism as
   before, `access.set_limits`).
3. **Migration: `alembic revision --autogenerate`, then hand-edit.**
   Autogenerate detects a straightforward drop+create (rename detection needs
   manual config it doesn't have here) — that is fine and simpler to reason
   about than a batch-mode column rename: `role_policies` is a GLOBAL,
   sysadmin-editable ADMIN-OVERRIDE table, never tenant data, never
   referenced by a foreign key. Any existing role-keyed override rows are
   semantically meaningless under the new model (a role string like
   `"user_free"` is not a plan key) — dropping the table discards them
   safely; `access._get_or_seed` lazily reseeds fresh plan-keyed defaults
   (from `plans.Plan.monthly_invoice_limit`/`monthly_upload_limit`) the next
   time each plan's row is read. Document this reasoning in the migration's
   own docstring (§ Documentation rule: state why, not just what).
4. **`CurrentOrg` is a zero-extra-query dependency.** `app/api/deps.py::
   get_current_org` reuses the SAME cached `(User, Organization)` tuple
   `get_current_identity` already fetched — adding `current_org: CurrentOrg`
   to a route signature costs nothing extra on the request path. Prefer this
   over having `access.py` re-fetch the `Organization` row itself.
5. **Usage counting stays untouched.** `invoices_this_month`/`usage_count`
   already scope by `org_id` only — this order changes ONLY which number the
   count is compared against (`plan`-keyed limit instead of `role`-keyed),
   never the counting logic itself.
6. **The "never lose a document" guardrail is ALREADY satisfied by the
   existing mechanism — verify, don't redesign.** Every quota check
   (`enforce_invoice_quota`/`enforce_upload_quota`) already runs BEFORE
   anything is persisted: `create_invoice` calls it before
   `persist_invoice`; `upload_invoice` calls it before `file.read()`/
   `documents.store()`; `confirm_inbound` calls it before the row is
   converted to a real `Invoice`. A block therefore never discards data that
   was ever accepted — it simply refuses to admit a new one, and the 402
   response is explicit (not a silent drop). Preserve this ordering exactly
   (do not move a quota check to after a write) and add the module docstring
   in `access.py` stating the overage-policy rationale explicitly (block, not
   auto-charge — auto-charge needs H1.1's live billing provider) so a future
   change doesn't accidentally invert the ordering.
7. **`paid` metadata**: the OLD `ROLE_META` had `paid=False` only for
   `user_free`. The NEW `_PLAN_META` must compute `paid = not plan.trial`
   (NOT `bool(plan.price_eur)`, which would wrongly mark `enterprise` —
   `price_eur=None`, "contact us" — as unpaid).

### Invariants this order must preserve

- **§4.1/§4.3 (tenant isolation)** — `plan_policies` is GLOBAL (system-wide,
  not tenant-scoped), exactly like the `role_policies` table it replaces —
  no RLS policy needed or added (same as before); usage counting stays
  strictly `org_id`-scoped, proven unchanged by the existing
  `invoices_this_month`/`usage_count` tests.
- **§4.6 (deny-by-default authorization)** — untouched: quota enforcement is
  orthogonal to `Permission`/`authz.require` and this order does not change
  who may create an invoice, only how the org-wide cap is computed.
  `PUT /access/matrix/{plan}` keeps the exact same two-layer gate
  (`SETTINGS_MANAGE` + in-handler `is_platform_admin` check) as the route it
  replaces — proven by `test_only_platform_operator_edits_the_global_matrix`.
- **§4.20 (wire contract)** — the `role`→`plan` field rename on
  `PlanPolicyOut`/`UsageOut` IS a breaking wire change (deliberate, not
  additive) — the SPA (`frontend/src/lib/types.ts`,
  `frontend/src/pages/Access.tsx`) is updated in the SAME order so nothing
  is left consuming a field that no longer exists. Every other response
  shape (`InvoiceDetailOut`, `UploadAccepted`, etc.) is untouched.
- **Roadmap guardrail (never lose a document because of a limit)** — proven
  by `test_a_blocked_upload_never_stores_the_file_never_loses_it`: a blocked
  upload leaves ZERO trace (no `ExtractionRun`, no stored file) beyond what
  was already accepted before the cap was hit.

### Database / migration impact

Drop `role_policies` (String(20) `role` unique key + 2 int limit columns);
create `plan_policies` (String(20) `plan` unique key + the same 2 int limit
columns; `UniqueConstraint("plan", name="uq_plan_policy_plan")`). Global
table, no tenant scoping, no RLS, no FK references from any other table.
Backfill: none — `access._get_or_seed` lazily reseeds each plan's row (from
`plans.Plan`'s new default fields) the first time it is read after upgrade.
Downgrade recreates `role_policies` and drops `plan_policies` — written and
exercised (`alembic upgrade head && alembic downgrade -1 && alembic upgrade
head`, verified clean in the self-verification block). What is lost on
downgrade: any sysadmin overrides set via the NEW `plan_policies` table
(same category of loss as the upgrade — an admin-override table, not
financial/tenant data); nothing else depends on either table.

### Rollback strategy

Migration downgrade recreates `role_policies` and drops `plan_policies` —
written and exercised in the self-verification block. Losing
`plan_policies` on downgrade loses only sysadmin-set quota overrides (never
financial or tenant data, nothing else references it). A code-only revert
(without the migration downgrade) is NOT safe on its own — the model/table
names would mismatch the DB — so a rollback must always downgrade the
migration in the same step as reverting the code, in that order (code
revert first would 500 on the now-missing `plan_policies` table; run
`alembic downgrade -1` immediately after or before the code revert, never
leaving them split across a deploy).
