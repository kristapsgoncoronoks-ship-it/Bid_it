**WORK ORDER 63 — `app.services.transport.parsers.e100` (`E100Parser`), the
second network registered into WO-62's `fuel_card_parser` registry.
Effort M-L (5-8d). Priority P1. Milestone M3. Depends on: WO-62 (G3.2
slice 1, the registry + `statement_ingest.ingest_statement` — satisfied,
unmodified by this order).**

### Objective and business value

Verified at HEAD=`415c515` (this order's baseline, confirmed live below):
`app/services/transport/parsers/` contains exactly one module, `eurowag.py`;
`fuel_card_parser._default_parsers()` registers exactly one network,
`Eurowag`. WO-62's own report and `TODO.md`'s WO-62 entry both name E100 as
the recommended next slice, in this exact priority order ("1. **E100**" of
six named future networks) — `ARCH_plan.md` line 934-935 confirms G3.2 as a
single P1/XL task (7 networks) depending only on G3.1 (satisfied), with
G3.3 (the validation-regime epic) explicitly depending on G3.2 completing,
not on any other M3 work. No other M3/G-task is ready-and-unblocked ahead
of continuing G3.2: G2.9 (fee freezing) and G2.10 slice 2 stay
decision-gated/deferred per the last several WO reports; G3.3 itself is
blocked on G3.2. E100 is therefore both the order WO-62 itself recommended
and the order `ARCH_plan.md`'s dependency graph actually prefers.

E100 is R20's OWN SECOND worked example (`BA_fleet_fuel.md` §3.B1, line
390-392): *"`extract._e100_seller_name()` / `_e100_seller_vat()` **anchor**
seller name and VAT to the `"E100 International Trade"` marker itself,
because a generic seller/buyer heuristic was grabbing the **buyer's**
(client's) LV VAT id from the annexe pages where it repeats."* WO-62 closed
R20 for Eurowag only; this order is the natural, harvested-spec-backed
second proof that the registry pattern generalizes — and, more importantly,
it is the first parser in this codebase to encounter a genuinely different
MONEY MODEL: Eurowag's statement supplies `net_local`/`vat_local`/
`gross_local` as three independently-given figures; E100's invoices are
**VAT-inclusive gross** (`BA_fleet_fuel.md` §5.1's own table: *"VAT-inclusive
gross; two invoices/month; station-colour discount tiers"*) — only the
gross figure (and a VAT rate) are given, and `net_local`/`vat_local` must be
**derived** by the reverse calculation. Every subsequent VAT-inclusive
network this codebase will ever onboard (Moeve is the next one named in
WO-62's "Out of scope" list) needs this exact code path to exist first.

Who pays more without this: `fuel_transactions` stays reachable from only
ONE of seven real networks; every Baltic entity's E100 statements (a live,
paying, semi-monthly-cadence network per `BA_fleet_fuel.md` §5.1) have no
path into the claim engine at all, and R20 — "the whole product thesis" per
§3.B — stays proven for exactly one network out of seven, which is not
enough to trust the pattern generalizes to the harder VAT-inclusive
networks (E100, Moeve) that make up half the remaining board item.

### Implementation guidance

1. **The reverse VAT-inclusive-gross calculation is the load-bearing
   correctness property this order exists to prove.** E100's statement
   supplies `gross_local` (VAT-inclusive) and a per-line `vat_rate`
   (percentage, e.g. `"21.00"`) — NOT independently-given `net_local`/
   `vat_local` the way Eurowag's CSV does. Derive, per line, entirely in
   `Decimal`:
   ```
   net_local = gross_local / (Decimal(1) + vat_rate / Decimal(100))
   vat_local = gross_local - net_local
   ```
   Both results stay UNROUNDED Decimals in the returned `ParsedFuelLine` —
   `fuel_ingest.ingest_transaction` remains the ONE place `q2` rounds
   (WO-50's convention, unchanged, proven by re-running WO-62's own
   `ingest_transaction` call site unmodified). Bound `vat_rate` to
   `0 <= vat_rate <= 100` at parse time and raise `ValueError` outside that
   range — a defensive, conservative gate (no real EU VAT rate is outside
   it) matching this order's "refuse rather than guess on an inconsistent
   row" instruction; `gross_local` itself is not sign- or range-restricted
   (mirrors Eurowag's own lack of a sign check — a credit/correction line
   is not ruled out by either parser). Set `ParsedFuelLine.provenance_note`
   to record the reverse-calc basis (`gross_local`/`vat_rate` as read) —
   `provenance_note`'s own docstring calls it "free-text lineage"; this is
   exactly that, and the ONLY place this derivation is visible for a human
   reviewing a captured line, since G3.3's numeric tie-out does not exist
   yet.
2. **Entity anchoring: anchor to the marker STRING itself, never a
   seller/buyer position heuristic — R20's own second worked example.**
   `BA_fleet_fuel.md` §3.B1 states the hazard explicitly: a generic
   heuristic grabs the BUYER's VAT id from annexe pages where it repeats.
   This parser's `_detect_entities` therefore inspects ONLY lines
   containing the literal substring `"E100 International Trade"` — exactly
   the discipline `EurowagParser._detect_entities` uses for its own label
   (never inspecting unlabelled legal-form-shaped text elsewhere) — and
   extracts the VAT number and entity name from THAT SAME line only. A
   buyer VAT number printed on an unrelated annexe line (no marker
   present) must never enter `parsed.entities`. Write this as the
   load-bearing test case, mirroring WO-62's own Czech-factoring-entity
   test: a statement whose footer carries BOTH a genuine
   `"E100 International Trade sp. z o.o., VAT reg. No.: PL..."` line AND
   an unrelated `"Client VAT reference (repeats on every annexe page):
   LV..."` line — assert only the PL entity is detected.
3. **What is verbatim vs a documented interpretation — flag both, loudly,
   in the module docstring, exactly as `eurowag.py` does.** VERBATIM: the
   anchor discipline itself ("anchor to the marker", never a seller/buyer
   position heuristic) and the marker string `"E100 International Trade"`
   (`BA_fleet_fuel.md` §3.B1 line 390-392, quoted directly). A DOCUMENTED
   INTERPRETATION (say so, the same way WO-62 flagged Eurowag's CSV column
   layout and WO-50 flagged `line_seq`): the exact per-line transaction CSV
   column layout, AND the exact footer wording around the marker (the
   source gives the marker string but no worked invoice-footer sentence
   for E100 the way it quotes Eurowag's `"Pārdevējs / Verkoper:"` line
   verbatim) — choose a small, obviously-representative shape and say so.
   Do NOT present either as harvested fact.
4. **A malformed row aborts the WHOLE statement at parse time** — unchanged
   discipline from `eurowag.py`, now also covering an out-of-range
   `vat_rate` (which this parser must treat as exactly as fatal as an
   unparseable decimal, never silently clamped).
5. **`ingest_statement` needs NO changes.** It already reads
   `parsed.network` off the returned `ParsedStatement` rather than a
   caller-supplied string, and already treats `net_local`/`vat_local`/
   `gross_local` as opaque figures it forwards to `ingest_transaction`
   without inspecting how they were produced. This order's DB-touching
   tests exist specifically to PROVE that claim for a second, structurally
   different network — not to add new orchestration.
6. **Every monetary figure stays `Decimal`, never `float`**, including
   inside the reverse-calc division — Python's `Decimal.__truediv__`
   between two `Decimal`s stays exact-context `Decimal` arithmetic; never
   route through `float()` at any point in the derivation.

### Invariants this order must preserve

- **R21 (marker-only matching, no fuzzy auto-pairing)** — `E100Parser`

### Testing requirements

`backend/tests/transport/test_g3_2_e100_fuel_card_parser.py` (pure, no DB):
- registry: `E100Parser` is present in `fuel_card_parser.parsers()`
  alongside `Eurowag`; `select()` correctly dispatches an E100 file to
  `E100Parser` and a Eurowag file to `EurowagParser` in the same test
  (proves the two networks coexist without collision); an E100 file is
  never accidentally `handles()`-matched by `EurowagParser` and vice versa.
- `E100Parser.handles()`: recognizes a well-formed E100 statement; refuses
  a file missing the marker; refuses undecodable bytes; does not match on
  a partial/incidental mention of "E100" outside the exact marker line.
- `E100Parser.parse()` — the money model: a line with `gross_local="121.00"`
  and `vat_rate="21.00"` yields `net_local` and `vat_local` that sum back
  to `gross_local` (`net_local + vat_local == gross_local`, within the
  Decimal arithmetic's own exactness — no rounding has happened yet) and
  match the hand-computed reverse figures; `line_seq` is 1-based and stable
  across an identical re-parse; a missing required column, an unparseable
  `gross_local`/`vat_rate` decimal, a `vat_rate` outside `[0, 100]`, an
  invalid country code, and a statement with zero data rows each raise
  `ValueError` naming the problem; a malformed row aborts the WHOLE
  statement (asserted directly on `parse()`, mirroring
  `test_g3_2_parse_raises_on_an_unparseable_decimal_and_writes_nothing_
  partial`'s pattern).
- Entity anchoring — R20's second worked example: a genuine
  `"E100 International Trade sp. z o.o."` marker line with its own VAT is
  detected; an unrelated buyer-VAT annexe line elsewhere in the SAME
  document is NOT (`test_g3_2_e100_parse_reads_the_marker_entity_not_the_
  buyer_annexe_vat`); a statement with no marker at all still ingests its
  transaction lines (entity absence doesn't block money capture); a marker
  line with no resolvable VAT prefix warns and detects nothing.

`backend/tests/transport/test_g3_2_e100_statement_ingest.py` (DB) — mirrors
`test_g3_2_statement_ingest.py`'s structure exactly, against E100 fixtures,
through the UNMODIFIED `ingest_statement`:
- Happy path: creates the `FuelTransaction` row(s) (`supplier == "E100"`)
  AND a `SupplierVatRegistration` (`source="capture"`) in one call; the
  stored `net_eur`/`vat_eur` reflect the reverse-calculated (then `q2`-
  rounded) figures, never the raw gross.
- Idempotency: re-ingesting the IDENTICAL file twice produces exactly one
  transaction row and one registration row.
- R22 end-to-end for a SECOND network: an admin-curated registration set
  BEFORE ingestion is never overwritten by the E100 statement's own
  captured entity.
- Module-off: `PermissionError` raised BEFORE parsing; zero rows written.
- Cross-tenant: an entity id real in org B, referenced from org A, is a
  `NotFoundError` (opaque).
- Unrecognized statement / invalid period: unchanged error codes,
  `unrecognized_fuel_card_statement` / `invalid_period`, zero rows written.
- The two-phase FX guarantee against an E100 statement: a non-EUR E100
  line converts correctly via a seeded ECB rate; a statement with one
  clean EUR E100 line and one line in an uncached currency writes
  **neither** line.
- Cross-tenant isolation with IDENTICAL E100 statement text ingested into
  two different orgs: zero shared rows, distinct ids.

existing consumer are unaffected (the two parsers do not share state or
call into each other). No kill switch needed: the `transport` module stays
default-OFF and absent from every plan's module set, so none of this is
reachable by any tenant regardless of code presence.
