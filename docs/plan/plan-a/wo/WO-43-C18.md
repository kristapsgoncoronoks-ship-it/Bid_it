# WO-43 — Wire `reclaimable_tax`; fix the "Reclaimable VAT" figure (board C1.8)

<!-- ═══════════════ COPY FROM HERE: WO-43 ═══════════════ -->

**WORK ORDER 43 — Fix `reclaimable_tax` and the reclaimable-VAT figure (board C1.8). Effort S (1–2d). Priority P2. Milestone M1. Depends on: none.**

### Objective and business value

Verified evidence, read straight off `HEAD=91ec9ac` (`origin/claude/bidit-invoice-data-analytics`):

- `app/models/expense.py::ExpenseItem.reclaimable_tax` is a per-line boolean
  (default `True`, documented "whether the tax on this item is reclaimable
  — some categories/countries aren't"). It is captured on every write
  (`app/services/expenses.py::build_items`) and **read by nothing** — exactly
  what `docs/plan/plan-a/ARCH_plan.md` C1.8 names.
- `GET /expenses/summary` (`app/api/routes/expenses.py`, the KPI behind
  `Expenses.tsx`'s "Reclaimable VAT" card) computed
  `SUM(ExpenseReport.vat_total)` over **every** report owned by the caller —
  including `draft` (not yet reviewed, can still change) and `rejected`
  (never approved for reimbursement; that VAT was never going to be
  reclaimed via this report). No status filter at all.
- The expense-report PDF export (`app/services/expenses.py::build_pdf`)
  printed a row literally labelled `"Reclaimable VAT"` whose value was
  `report.vat_total` — the total tax paid on the report, not the reclaimable
  subset.

Both surfaces show the same wrong (too-high) number to a finance lead or a
claimant's bookkeeper on any tenant with a non-reclaimable line (client
entertainment, an exempt category, a country that disallows the deduction)
or a draft/rejected report sitting in their history. Per §1 of the master
context, "every one of [the product's] promises dies if a number is wrong"
— this is exactly that failure mode on a real dashboard KPI and a real
printed export, not an edge case.

### Scope

**In scope**
- `app/services/expenses.py`: two new functions —
  `reclaimable_vat_of(items)` (pure, in-memory, for the PDF) and
  `reclaimable_vat_total(db, org_id, employee_id)` (the query form, for the
  summary route) — both apply the same rule: only `reclaimable_tax=True`
  items, and (for the query form) only reports with
  `status NOT IN ('draft', 'rejected')`.
- `app/api/routes/expenses.py::summary` calls
  `expenses.reclaimable_vat_total` instead of its inline
  `SUM(ExpenseReport.vat_total)` query.
- `app/services/expenses.py::build_pdf` gains a `"VAT"` row (the
  pre-existing `report.vat_total`, unchanged meaning) above the corrected
  `"Reclaimable VAT"` row (now `reclaimable_vat_of(report.items)`); the
  bold/line-above "total row" table style moves to the (now third) `Total`
  row.
- `docs/architecture/adr/0029-reclaimable-vat-figure.md` — the decision
  record required by C1.8's acceptance criterion ("a decision is recorded
  in an ADR"): wire the field, don't delete it.
- `docs/architecture/domain-modules.md` — one-line note on the Expenses row.
- `backend/tests/test_expenses.py` — new coverage (below); existing
  `test_foreign_currency_eur_and_summary` must pass **unmodified** (its
  fixture is a single `submitted` report with both items defaulting
  `reclaimable_tax=True`, so the corrected computation yields the same
  `"7.50"` it always did).

**Out of scope**
- Any change to `ExpenseReport.vat_total`'s meaning or storage — it remains
  "total tax paid on the report," used elsewhere (line-item PDF rows,
  `compute_totals`) exactly as today.
- A per-line partial-reclaim percentage (today's field is boolean
  all-or-nothing) — noted as a future "revisit when" in the ADR, not built
  here.
- A migration — `reclaimable_tax` already exists as a NOT NULL, defaulted
  column on every row; this order only reads it.
- Any wire-shape change — `ExpenseSummary.reclaimable_vat` stays a
  `Decimal`; the SPA (`Expenses.tsx`) needs no change.

### Implementation guidance

1. **Characterise first.** Run `test_expenses.py` green at `HEAD` before
   touching anything; note `test_foreign_currency_eur_and_summary` asserts
   `s["reclaimable_vat"] == "7.50"` today (accidentally correct — see
   scope note above) so it is the regression guard that the fix is
   behaviour-preserving on an all-reclaimable, non-draft fixture.
2. **`reclaimable_vat_of(items)`** — mirrors `compute_totals`'s shape
   exactly (a pure Python sum over an in-memory list), just filtered to
   `i.reclaimable_tax`. No DB access — `build_pdf` already has
   `report.items` loaded (the route's `selectinload(ExpenseReport.items)`).
3. **`reclaimable_vat_total(db, org_id, employee_id)`** — join
   `ExpenseItem` to `ExpenseReport` (not a subquery over `vat_total`,
   which is report-grain and would need its own re-derivation); filter
   `org_id` explicitly even though the ORM guard/RLS also apply — matches
   the codebase's per-query-filter tenancy discipline (§4.1), and this
   table didn't have one before. Exclude `("draft", "rejected")` via
   `status.notin_(...)`, not two negated equality clauses (matches the
   existing `.in_(...)` idiom two lines above it in the same route).
4. **`build_pdf`'s table row-index styling** — adding a `"VAT"` row shifts
   every existing row index in the `TableStyle` down by one; update
   `LINEABOVE`/`FONTNAME`/`TEXTCOLOR` from row `1` to row `2` (the new
   `Total` row) rather than leaving the bold/line-above emphasis on the
   now-`"Reclaimable VAT"` row.
5. **Money basis.** `reclaimable_vat_of`/`reclaimable_vat_total` both
   return through `money.q2` (`q` in this module) — no new float path.

### Invariants this order must preserve

- **§4.9** (Decimal, `q2`, never float) — both new functions round through

- **§4.1/§4.3** (tenancy: per-query `org_id` filter) — `reclaimable_vat_total`

  is a pure computation fix behind an existing field.

  decision record; `domain-modules.md` gets the one-line pointer.
