### Task selection rationale

R11 is the last remaining bounded, ready-now item in Milestone C after WO-40
closed R12. WO-40 had already investigated R11 in passing (its own task-
selection section) and confirmed it was real and unchanged; this WO re-verifies
against the current tree (`61855bc`) before touching anything, per the
coordinator brief's standing instruction to confirm before fixing:

- `backend/app/models/sso.py:35-37` — the `client_secret` column still carries
  `# TODO: secret store (ADR-0016)` as a trailing inline comment, directly
  under the class docstring (lines 17-20) which already states, correctly,
  that the field "is **sealed at rest** (AES-256-GCM via `keyvault.py`,
  ADR-0016) — written encrypted by `sso_config`, read back with
  `keyvault.read_secret`."
- Confirmed the docstring's claim against the actual implementation, not just
  re-trusting the prose: `app/services/sso_config.py:51`
  (`upsert_connection`) calls `keyvault.seal(data["client_secret"],
  aad=CLIENT_SECRET_AAD)` before ever writing the column, and
  `app/services/oidc.py:276` (`finish_login`) calls
  `keyvault.read_secret(connection.client_secret,
  aad=sso_config.CLIENT_SECRET_AAD)` before ever using it. Both call sites
  read exactly as described.
- Confirmed `docs/architecture/adr/0016-config-secrets.md` is itself accurate
  and not aspirational — its "Implementation status" section states
  verbatim: "First consumer: the **SSO OAuth client secret is sealed at rest**
  (`sso_config` seals on write, `oidc` unseals on use, the API never returns
  it)."

So the TODO is exactly what the roadmap says: a stale comment describing
work that is already done, sitting one line below a docstring that already
says so. This is a documentation-only fix — no code logic changes.

### Objective and business value

Delete the dangling `# TODO: secret store (ADR-0016)` comment. Left in place,
it actively misleads a future reader (human or AI work-order agent) into
re-investigating or re-implementing secret sealing that has existed and been
tested since ADR-0016 shipped, and it contradicts the accurate docstring two
lines above it — exactly the kind of small, checkable inconsistency that
erodes trust in the codebase's self-documentation (the same class of concern
R12/WO-40 addressed for the root README/ARCHITECTURE numbers). No production
code, schema, or behavior changes; the value is purely removing a false signal.
