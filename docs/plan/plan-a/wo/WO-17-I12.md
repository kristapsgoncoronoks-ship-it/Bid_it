**WORK ORDER 17 — Grouped navigation IA: wire the shell to the live app (board I1.2). Effort M 3–5d. Priority P1. Milestone M1. Depends on: F1.1 (WO-14, complete at `4deb1af`).**

## Task selection rationale (per the M1 board)

M1's exit criteria (`ARCH_plan.md` §"M1") lists seven checkboxes. Six are satisfied by WO-12..16 (capture-review, line-item provenance, AR/master-data screens, composed home dashboard). The seventh is explicit and still unchecked: *"The grouped navigation IA (Overview / Payables / Receivables / Insights / Workspace) replaces the flat ~25-item nav."* This is the only remaining named M1 UI-shape deliverable, which makes it the clearest "next" pick over the other unblocked M1-board rows:

- **I1.2** — P1, `Deps: F1.1` (done at WO-14), not owner-blocked, and it is the literal text of the one open M1 exit-criterion checkbox. **Selected.**
- I1.3 (P0·S, cash-position relabel) is smaller and unblocked, but it is *not* a named M1 exit-criterion checkbox (WO-16 §"Left undone" scoped it narrowly to the dashboard tile's own label, and the page-level relabel is explicitly deferred prose, not a checklist item) — it loses the tie-break to the item ARCH_plan's own exit gate names outright. It remains the natural next pick after this order.
- I1.5 (report writers) and E1.3/E1.6/E1.7 are real M1-board rows but unblock nothing else on the M1 board and are not named in the M1 exit criteria the way the nav IA is.
- H1.4 (next on the stated critical path `E1.1 → I1.1 → H1.4 → first charge`) is M2 and owner-blocked (Stripe credentials, §H1.1) — excluded by the task-selection rules.

## Verified premise (evidence at `48ca7a0`)

1. **The flat nav is real and current.** `frontend/src/components/Layout.tsx:8-40` — a single `NAV` array of 28 entries (`Dashboard` … `Settings`), rendered as one unbroken row of `NavLink`s in the header (`Layout.tsx:68-85`), filtered in place by `module` / `admin` (`isAdminOrAbove`) / `owner` (`isOwner`) flags. `Sessions` and `Sign out` are separate hardcoded controls next to it (`Layout.tsx:94-105`), not part of `NAV`.
2. **A complete, accessible, responsive grouped shell already exists — and is used by exactly one route.** `frontend/src/components/shell/AppShell.tsx` (fixed 16rem sidebar on `lg+`, hamburger→`Drawer` below `lg`, sticky top bar, skip link, org+entity `ScopeSwitcher`s, `SearchInput`, `UserMenu`) is mounted only by `frontend/src/design/DesignLayout.tsx`, which is reachable solely under the fixtures-only `/design/*` routes (`frontend/src/App.tsx:92-109`). `docs/DESIGN_SYSTEM.md:8` states this in writing: *"the live app's pages and routes are untouched."*
3. **`AppShell` is not actually reusable as shipped — it is hard-wired to the design fixture's nav.** `AppShell.tsx`'s internal `NavList` imports `NAV_GROUPS` directly from `./nav` (module-level import, not a prop) and hardcodes the "is this the root item" check as `item.to === "/design"` (`AppShell.tsx:3,39`). `UserMenu`'s "Account settings" link is hardcoded to `href="/design/settings"` (`UserMenu.tsx:35`). Wiring the live app therefore requires making the shell's nav, its root-match rule, and its account link **caller-supplied** — not swapping one hardcoded list for another.
4. **No legal-entity model exists in the backend.** `grep -rn "legal_entit\|class Entity" backend/app/models/*.py` finds only an optional `legal_entity_id` column on `Invoice`/`ApprovalPolicy` — no entity table, no list endpoint. `AppShell`'s second `ScopeSwitcher` ("legal entity") is fixture-only (`design/fixtures.ts::FIXTURE_ENTITIES`). Wiring it live with invented data would violate master-context §10 ("No invented functionality"); it stays unmounted for the live app (documented follow-up below).
5. **No global-search backend exists.** `grep -rn "search" backend/app/api/routes/*.py` hits only `invoices.py` (a list filter param) and `scim.py` (SCIM filter syntax) — no omnisearch endpoint. Mounting `AppShell`'s `SearchInput` live with no handler would be exactly the "placeholder code" master-context §10 forbids; it stays unmounted for the live app (documented follow-up below).
6. **`OrgSwitcher.tsx` duplicates `ScopeSwitcher`'s single-option/multi-option behaviour** (`frontend/src/components/OrgSwitcher.tsx` — plain text when `orgs.length <= 1`, else a picker) and is imported nowhere except `Layout.tsx` (`grep -rln OrgSwitcher frontend/src` → 2 hits, itself + `Layout.tsx`). It is fully replaceable by `ScopeSwitcher` (`kind="organization"`) wired to the same `/auth/organizations` query and `/auth/switch-org/{id}` mutation, and becomes dead code once the shell is wired — deleted here.
7. **`/reimbursements` and `/issuer` are routed (`App.tsx:145,149`) but never in `NAV`** — both are reached today only via in-page links (`Expenses.tsx:60`, `Issue.tsx:45,59,641`, `Settings.tsx:86`). This is pre-existing behaviour, not a regression this order introduces; they stay off the top-level nav (out of scope — see below).
8. **No live e2e spec exists for the nav**, and — separately, verified while confirming this — **`frontend/e2e/dashboard.spec.ts` and `frontend/e2e/masters.spec.ts` are not run by CI.** `frontend/package.json`'s `"test:e2e"` script is `playwright test e2e/smoke.spec.ts` (one file, literally), and `.github/workflows/ci.yml`'s `frontend-e2e` job runs only `npm run test:e2e`. Both specs were added correctly (WO-14/WO-16) and pass locally, but neither is part of the automated gate — a pre-existing gap in the same class the master-context DoD warns about ("CI green, reproduced locally"). Fixed in the same change so the new nav spec does not become the third stranded file (see Scope).

### Objective and business value

Build the grouped Overview / Payables / Receivables / Insights / Workspace navigation into the *live* app by generalising the already-built, already-accessible, already-tested `AppShell` to accept a caller-supplied nav (instead of importing the fixture's), and mount it from `Layout.tsx` with the real 28 destinations grouped, permission-filtered and module-filtered exactly as today — replacing the flat unbroken row of 28 links plus a full functional rewrite is explicitly *not* needed: the shell, the switchers, the drawer, the user menu and every accessibility behaviour documented in `docs/DESIGN_SYSTEM.md` §3 already exist and are already covered by `smoke.spec.ts`'s role/name-based assertions over `/design`. This order's job is wiring, not invention.

Who pays: today a trial user on a laptop sees 28 links in one header row (`Layout.tsx`'s `<nav className="flex items-center gap-1">` wraps or truncates at anything under ~1400px) and nothing at all on a phone — the mobile expense-submission flow `docs/DESIGN_SYSTEM.md` already built for one-handed use is unreachable through the live nav that ships today. ARCH risk **C-6** ("trial users hit the unfinished half and conclude the product is unfinished") applies directly to the *chrome*, not just missing screens — a flat 28-item bar reads as an MVP prototype next to any grouped SaaS competitor a prospect has open in another tab. This is also the last checkbox standing between the current state and a clean M1 exit-criteria pass.

### Scope

**In scope:**

*Shell generalisation (additive to the public shell API, `docs/DESIGN_SYSTEM.md` §2 table updated to match):*
- `frontend/src/components/shell/nav.ts`: add optional `end?: boolean` to `NavItem` (root/dashboard items only); set `end: true` on the design fixture's own `/design` Dashboard entry (replaces the hardcoded check in `AppShell`, behaviour-identical for `/design`).
- `frontend/src/components/shell/AppShell.tsx`:
