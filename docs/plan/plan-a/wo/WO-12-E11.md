# WORK ORDER 12 — Capture-review UI (board E1.1)

**WORK ORDER 12 — Capture-review UI: the extraction/provenance front door (board E1.1). Effort L 6–12d. Priority P0. Milestone M1. Depends on: WO-1..11 (M0 complete — all 12 exit-gate criteria MET at `033b610`); ARCH dependency C1.1 (one validation engine) is already merged.**

Baseline (recorded, per process rules — no pre-change re-run): **993 passed, 4 skipped** at `033b610` (the 4 skips are pg-only markers, verified separately on Postgres).

### Objective and business value

The intake backend is complete end to end — `POST /invoices/upload` (202 + run id, `backend/app/api/routes/invoices.py:592`), the worker parse (`app/services/extraction.py::extract_upload`), per-field provenance rows (`app/models/extraction_field.py`: `status extracted|defaulted|missing`, `confidence` where `None` means *exact*, `original_value`/`normalized_value`/`reviewed_value`, `provider`, `low_confidence`), the human-review queue (`GET /invoices/captures/review`, `invoices.py:327`), the correction write path (`POST /invoices/captures/{run_id}/review`, `invoices.py:390`), duplicate candidates (`GET /invoices/duplicate-candidates`, `invoices.py:289`) and saved-invoice lineage (`GET /invoices/{id}/extraction`, `invoices.py:429`) — **with zero frontend consumption of the extraction detail** (verified by grep during planning: no page reads `captures/review`, `FieldProvenance`, or `duplicate-candidates`). The only capture surface, `frontend/src/pages/Upload.tsx`, shows a plain editable draft: no per-field status, no confidence, no original-vs-normalized, no duplicate warning, no document pane, and corrections typed there are never recorded through the review endpoint — so `reviewed_value` provenance is never captured for UI uploads.

This is ARCH_plan's "single highest revenue-per-day item": the #1 job-to-be-done (stop re-keying invoices, trust what was captured) has a complete backend and no front door. A finance lead cannot see *what the machine read, from where, with what confidence* before it becomes an invoice — which is the trust moment the product sells. Until this screen exists, per-field provenance, the `0.75` low-confidence flag and the review queue are dead inventory.

**Naming note (deliberate deviation from ARCH_plan's file names).** ARCH E1.1 names `ReviewQueue.tsx` / `InvoiceReview.tsx`. The repo already has `Review.tsx` (the *validation* queue) and `ReviewInvoice.tsx` (the *AP approval* detail). Creating `InvoiceReview.tsx` next to `ReviewInvoice.tsx` is a collision trap, so the new screens are **`CaptureQueue.tsx`** and **`CaptureReview.tsx`** (routes `/captures` and `/captures/:runId`). The existing Review/ReviewInvoice screens are NOT duplicated or modified — they serve a different lifecycle stage (post-save validation/approval), and this order's screens end exactly where those begin (at invoice creation).

### Scope

**In scope:**
- `frontend/src/pages/CaptureQueue.tsx` (**new**) — the parsed-but-unconfirmed capture queue over `GET /invoices/captures/review`: file, invoice number, vendor, method, warnings, low-confidence field count, duplicate flag, age; pagination; loading/empty/error states; row → `/captures/:runId`.
- `frontend/src/pages/CaptureReview.tsx` (**new**) — the extraction-review detail: source-document pane (PDF/image preview, download fallback) side by side with per-field provenance (status badge, confidence with low-confidence emphasis, original vs normalized vs reviewed value, provider), editable header fields + line-item draft, duplicate warnings (`exact` vs `cross_supplier`), parse warnings, queued/running poll state, failed state with retry, "Save corrections" (records `reviewed_value` through the review endpoint) and "Confirm & create invoice" (`POST /invoices` with `extraction_run_id`). Nothing persists to the invoice record before the human confirms (§4.19).
- Routing (`frontend/src/App.tsx`) + nav (`frontend/src/components/Layout.tsx`, label "Captures").
- `frontend/src/lib/types.ts` — capture/provenance/duplicate types; extend `ParsedDraft` (fields, extraction_run_id) and `InvoiceCreate` (extraction_run_id) to match the backend wire shapes that already exist.
- `frontend/src/pages/Upload.tsx` — after the 202, navigate to `/captures/{run_id}` instead of duplicating a second inline draft editor (the capture screen owns polling/review/confirm; the ARCH acceptance chain "upload → 202 + run id → poll → review → confirm" becomes ONE canonical flow). The upload dropzone itself is unchanged.
- Two **small additive read-only backend endpoints** (real gaps found in recon, both under the invoices router's structural `INVOICE_READ`):
  1. `GET /invoices/captures/{run_id}/fields` → `list[FieldProvenanceOut]` — the *live* field rows (including `reviewed_value`). Gap: today the live rows are readable only as the *response of the correction POST* or after save via `/invoices/{id}/extraction`; on reload of the review screen, recorded corrections would be invisible (the poll endpoint replays parse-time `draft_json`).
  2. `GET /invoices/captures/{run_id}/source` → the stored original bytes, served inert (`X-Content-Type-Options: nosniff`, `Content-Disposition` via `core.security_headers.content_disposition`, mime from the document registry). Gap: **no route serves `documents.UPLOADS`** (verified: `documents.load` callers are logos/receipts/attachments/email only), and E1.1's acceptance requires the side-by-side document.
- One **audit fix on the existing correction endpoint** (`POST /invoices/captures/{run_id}/review`): it mutates and commits with no `audit.record` — a §4.16 violation in the exact path this UI now exercises. Add action `A.CAPTURE_REVIEW = "capture.field_review"` with per-field old→new meta.
- Backend tests for all three (cross-tenant 404, auth, bytes round-trip, audit row, reviewed-value persistence).

**Out of scope (anti-scope-creep):**
- Line-item per-field confidence — **E1.2** (line items render from the draft; only the five header fields carry provenance today, honestly labelled as such in the UI).
- Hash-based re-upload detection — **E1.3**; scored duplicate candidates beyond exact-number — **E1.4**; extraction learning loop — **E1.5**; email-intake provider adapter — **E1.6**; AI capture policy wiring — **E1.7**.
- The composed home dashboard tile linking here — **I1.1**.
- Any change to the AP validation/approval screens (`Review.tsx`, `ReviewInvoice.tsx`) or their endpoints — **C1.9** owns dead-state cleanup.
- New Playwright *visual* baselines (local gate, per process rules); the e2e harness covers only the fixtures-driven `/design` showcase, so no live-app e2e is added (recorded as a follow-up).

### Implementation guidance

1. **Backend first (small):** add `A.CAPTURE_REVIEW`; in `review_capture_fields` collect `{field: {"old": f.reviewed_value or f.value, "new": item.reviewed_value}}` for the fields actually matched, call `audit.record(db, audit.A.CAPTURE_REVIEW, target_type="extraction_run", target_id=run_id, meta={"fields": changes})` **before** the commit so it persists atomically (§4.16 pattern).
2. Add `capture_fields` GET: `extraction.get_capture` (opaque 404 when None) then `extraction.fields_for_run` → `list[FieldProvenanceOut]`. Read-only; inherits router-level `INVOICE_READ`.
3. Add `capture_source` GET: `extraction.get_capture` (opaque 404), 404 when `source_sha256` is empty; load bytes via `documents.load(documents.UPLOADS, ...)` (404 if missing); mime from the document registry row `(org_id, sha256, kind="uploads")`, falling back to `application/octet-stream`; respond with `content_disposition(run.source_filename or "document", fallback="attachment")` + `nosniff` — mirror `invoice_review.download_attachment`. Never guess a renderable type server-side; the SPA decides how to preview from the mime.
4. **Frontend types:** mirror the backend schemas exactly (`FieldProvenance`, `CaptureReviewItem`, `CaptureReviewQueue`, `DuplicateReport`); `ParsedDraft` gains `fields?: FieldProvenance[]` and `extraction_run_id?: string | null`; `InvoiceCreate` gains `extraction_run_id?: string | null`. Never move anything across the wire (§4.20) — these are the shapes the API already emits.
5. **CaptureQueue.tsx:** TanStack Query over `/invoices/captures/review?page=&page_size=`; `QueryState` wrapper; `EmptyState` ("Nothing waiting for review — upload an invoice") linking to `/upload`; `Pagination`; low-confidence count rendered as an amber pill when > 0, duplicate flag as a rose "possible duplicate" pill; method via existing `methodLabel`/`METHOD_STYLES`.
6. **CaptureReview.tsx:** three data sources — poll `GET /invoices/upload/{runId}` (`refetchInterval` while `queued|running`), `GET /invoices/captures/{runId}/fields`, and (once a draft number exists) `GET /invoices/duplicate-candidates?invoice_number=…&exclude vendor logic none — pass vendor_id only if the draft resolved one`. States: queued/running → progress panel; failed → `ErrorState` + Retry button (`POST /invoices/upload/{runId}/retry`); already saved (`status === "saved"` or `invoice_id` set) → notice linking to the invoice; parsed → the review layout.
7. Review layout: left pane = source document (fetch `/captures/{runId}/source` as a blob; `application/pdf` → `<object>` with an object URL, `image/*` → `<img>`, anything else → a download card; revoke object URLs on unmount). Right pane = the five header provenance fields, each a labelled input seeded from `reviewed_value ?? draft value`, with: status badge (`extracted` slate / `defaulted` amber / `missing` rose), confidence (render `None` as "exact — structured source", a value `< 0.75` with the amber low-confidence treatment the backend flags), original vs normalized when they differ, provider caption. Line items in the same editable table shape `Upload.tsx` had, with a caption that per-line provenance arrives in E1.2. Totals recomputed client-side for display only — the server recomputes on save (§4.10).
8. Actions: "Save corrections" posts ONLY fields whose value differs from the captured value to `/invoices/captures/{runId}/review`, then invalidates the fields query (the reviewed value + cleared flag round-trip from the server). "Confirm & create invoice" posts the edited draft (with `extraction_run_id`) to `/invoices`; on success navigate to `/invoices/{id}`. A duplicate warning NEVER blocks confirm (duplicates are advisory by design, E1.4's note) — it demands a `ConfirmDialog` acknowledgement when `exact` candidates exist. Quota errors (`apiError`) surface inline.
9. **Accessibility (definition of done):** every input labelled; the document pane has an accessible name; badges carry text not colour alone; the confirm dialog is the existing focus-trapped `ConfirmDialog`; the queue table is a real `<table>` with headers; all actions reachable by keyboard.
10. `Upload.tsx`: on 202 navigate straight to `/captures/{runId}`; delete the now-dead inline editor code paths.

### Invariants this order must preserve

- **§4.19 (AI/extraction advisory):** extraction output remains a *draft a human confirms*. Nothing writes to the invoice record until "Confirm & create invoice"; corrections are stored as `reviewed_value` provenance, never silently applied to a financial record; low-confidence fields are visually distinct, and the UI presents `original`/`normalized`/`reviewed` honestly (a `None` confidence is shown as *exact*, not unknown).
- **§4.16 (every mutation audited):** the correction POST gains its missing audit event, hash-chained via the existing `audit.record`, committed atomically with the field update.
- **§4.4 (opaque 404):** both new GETs return an indistinguishable 404 for another tenant's run id; proven by test.
- **§4.1 (three-layer tenancy):** both new reads filter by `org_id` via `extraction.get_capture`/`fields_for_run`; no new table, so the RLS set-equality test is untouched.
- **§4.10 (server recomputes totals):** the confirm POST sends line items; totals shown client-side are display-only.
- **§4.20 (frozen wire contract):** no existing response shape changes; the two endpoints are additive with `response_model` declared (`capture_source` is a binary `Response`, like the existing download routes).
- **§4.6/7 (structural authz):** both new routes sit under the invoices router's `INVOICE_READ` dependency; no raw-role checks.

### Rollback strategy

Pure code revert (one commit range); no migration. The audit action string is additive — old rows are unaffected, and reverting stops new events without breaking the hash chain (the chain never requires an action to keep existing). The two GET endpoints are read-only; removing them cannot orphan data. Frontend revert restores the old Upload inline editor.
