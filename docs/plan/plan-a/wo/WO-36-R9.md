### Task-selection rationale (read this first)

Per the coordinator's instructions, candidates considered from `docs/audit/remediation-roadmap.md`
Milestone C were: R8 (OIDC SSRF guard), R9 (duplicate CSV-sanitization helper), R13 (`test_fx.py`
owner-only test gap), R15 (load testing — explicitly out per "no external creds/infra" guidance and
too large for one WO), R17 (Payment Run Cancel confirmation), R19 (onboarding checklist — too large/
product-shaped for a bounded WO), and R14 (backup/restore — investigated separately, see below). R10/
R11/R12 are P4 doc-hygiene and were deprioritized per the coordinator's explicit preference for P3 over
P4 and correctness/security value over doc hygiene.

**R14 was investigated and NOT selected.** Its roadmap entry calls it "decision-gated, not code," and
that characterization holds up on inspection, but with a caveat worth recording: `docs/DEPLOY-HOSTINGER.md`
already documents a manual `pg_dump`/`tar` backup runbook, and `docs/architecture/deployment.md` §5
already documents a restore runbook (provision from PITR → point `DATABASE_URL` → `alembic upgrade head`
→ `integrity.verify_documents` → resume traffic) with an explicit "drill this quarterly" instruction —
so the roadmap's own acceptance bar ("a documented... DR runbook exists and is linked from
`docs/DECISIONS-NEEDED.md`") is *already substantially met by prose*, just not cross-linked from
`DECISIONS-NEEDED.md`. What is missing — an automated restore-drill *test* that actually runs
`pg_dump`/`pg_restore` against a scratch Postgres and asserts `integrity.verify_documents` finds zero
corruption after — is a strictly larger, more infra-coupled undertaking than this order's budget (it
needs a second scratch database/cluster lifecycle inside the Postgres CI job, a decision about where
object-storage bytes come from in that drill, and touches the same "what does our production backup
story actually look like" question the roadmap defers to infra) — not a same-day bounded fix like R9.
It is left open, with this note added to the roadmap under R14 for the next session.

**R9 was selected.** It looked par­tially closed already: WO-29 extracted a shared
`app/core/csv_safety.py::sanitize_cell` and had `erp_export._safe`/`audit_export._safe`/
`report_writers._safe_cell` delegate to it — but WO-29's own "Out of scope" section explicitly named a
**fourth** duplicate it deliberately left untouched: `backend/app/api/routes/issued.py::_csv_safe`
(line 1130), used by the `_csv()` helper backing `/issued/reports/{summary,receivables,partners,vat}`
`?format=csv`. Recon for this WO confirmed: (1) the duplicate still exists byte-for-byte as of `bd9d9f6`
(`grep -rn '\[:1\] in ("="' backend/app` finds exactly one hit, this file); (2) it protects a *live,
attacker-reachable* field — `report_partners`'s CSV includes `p.partner`, sourced from
`IssuedInvoiceCreate.buyer_name` (`schemas/issued.py:34`, an unconstrained `str | None`, max_length=200,
no character restriction) — the exact CSV-injection class R1 fixed elsewhere; and (3) **no test in the
repo exercises formula-injection safety for this route** (`grep -n "formula_injection\|_csv_safe" tests/
test_issued*.py` returns nothing), unlike every sibling exporter R1 touched. This is precisely the
mechanism the roadmap warns caused R1 in the first place ("a helper copied per-file is a helper a fourth
writer can forget to copy" — `csv_safety.py`'s own docstring) — leaving it open is a live, if currently
theoretical (the helper today happens to be correct), consistency/regression risk with zero
regression-test coverage. It is real, bounded (one file, one route module, no schema/migration, no
API-shape change), and matches the coordinator's stated preference for correctness/security value with a
clear bounded fix.

### Objective and business value

`backend/app/api/routes/issued.py:1130` (`_csv_safe`) re-implements, in a fourth location, the exact
CSV/Excel formula-injection mitigation that `app/core/csv_safety.py::sanitize_cell` (introduced in WO-29)
already centralizes for `erp_export.py`, `audit_export.py`, `report_writers.py`, `payment_run.py`,
`reimbursement.py`, and `explore.py`. Today the duplicate happens to implement the identical trigger set
(`= + - @ \t \r`) and is therefore not itself a live vulnerability — but it is exactly the kind of
per-file copy that let three of *six* CSV writers ship unprotected before R1/WO-29 (`docs/audit/
remediation-roadmap.md` R1), and it backs a route (`/issued/reports/partners?format=csv`) whose
`partner` column is sourced directly from an unconstrained, buyer-supplied free-text field
(`buyer_name`) — the same CSV-injection shape R1 fixed on the payment-run/reimbursement/explore
exporters. It also currently has **zero dedicated test coverage**, unlike every sibling exporter, so a
future edit to this route's CSV logic could silently regress the protection with no CI signal.

Removing the fourth copy means every CSV/Excel writer in the codebase shares one, single,
independently-tested implementation of a security-relevant string transform — a real reduction in the
chance that the *next* new exporter (or an edit to this one) drifts from the others, which is the
concrete failure mode the roadmap's own R9 rationale names. It costs the business nothing (no behavior
change for any well-formed export) and removes a specific, named residual risk the prior work order
(WO-29) explicitly flagged and deferred rather than silently missed.
