# WO-54 — Frozen claim lines + frozen VAT base at submission (board G2.5)

**WORK ORDER 54 — G2.5: frozen claim lines + frozen VAT base at submission
(board G2.5). Effort M (3-5d). Priority P0. Milestone M3. Depends on: WO-51
(G2.2 — the lock table), WO-52 (G2.4 — `build_claim_lines`).**

### Objective and business value

WO-49-53 shipped the claim grain, the lock table, the claim-line builder and
the monthly close, but nothing yet makes a SUBMITTED claim's figures
immutable — verified at HEAD=`9bff986` (this order's baseline, 1303 passed/10
skipped): `VatRefundClaimLine.frozen_at` has been in the schema since WO-49
(the M3 opener) and stays permanently NULL; `VatRefundClaim.vat_eur`/
`vat_local`/`currency` are declared but never written by any code path.
`ARCH_plan.md`'s own critical path names this order explicitly: **"G2.5
(frozen claim lines) is the linchpin: it is what makes ADR-P3's translation
of the Fleet Fuel isolation rule sound, and every downstream gate assumes
it."** `BA_fleet_fuel.md` C10 ("FEE FREEZING — the rate freezes at
submission...") is the harvested source for the freeze-at-submission pattern,
narrowed here to exactly the VAT-base half (fee freezing itself is G2.9,
explicitly out of scope).

Who pays more without this: G2.6's future gate stack, G2.9's fee freezing,
and G2.7's status derivation all need to read a claim's frozen figures as
ground truth. Building any of them against an unfrozen claim would mean "the
filed amount" keeps changing after filing — the exact defect ADR-P3 exists to
prevent (a re-close silently altering a claim already sent to a tax
authority). Landing the freeze now, atomically with lock acquisition
(WO-51), is strictly cheaper than discovering the gap once G2.6/G2.9 are
already built assuming it.

### Scope

**In scope**
- `app.services.transport.freeze.freeze_claim_lines(db, org_id, claim)` —
  stamps `frozen_at` on every currently-unfrozen `VatRefundClaimLine` for the
  claim and sets `claim.vat_eur`/`vat_local`/`currency` from EXACTLY those
  lines' totals (C10 — never a raw period `SUM`). Refuses (409,
  `code="claim_currency_mismatch"`) if the claim's lines carry more than one
  distinct local currency — see Implementation guidance §1 for why (master-
  context invariant §4.14).
- `app/services/transport/lock.py::submit_claim` calls `freeze_claim_lines`
  in the SAME flush as its existing lock-acquisition + status-flip writes —
  a lost lock race now rolls back the freeze too, nothing partially applied.
- **Additive schema extension** on `vat_claim_lines` (migration
  `bc783e1ec7c2`): `net_local`, `vat_local`, `currency` (all nullable) — WO-49
  shipped only EUR columns on the line; freezing the claim's VAT base in
  local currency (C10) needs the local figure captured PER LINE, which
  `build_claim_lines` (G2.4, WO-52) did not populate. This order extends that
  already-shipped function additively (no signature change, no behavior
  change to its EUR output) rather than re-deriving local amounts at freeze
  time from `fuel_transactions`.
- `build_claim_lines` now refuses (422, `code="claim_line_mixed_currency"`)
  if a single (invoice, product_group) bucket's underlying transactions
  disagree on `currency` — the same invariant-§4.14 discipline, applied one
  level down.
- `claim_lines.py::_period_months` → already renamed public `period_months`
  in WO-53; unaffected here except by association (same file).

**Out of scope** (explicitly, future M3 work orders)
- **Fee freezing** (R13, G2.9) — `claim.fee_pct`/`fee_min`/`fee_eur` stay
  NULL; C10's fee-freezing half is a separate future order.
- **The checklist/period-end/minimum/deadline gate stack** (G2.6), wiring
  `is_synthetic()` into the lock path as a gate (G2.3's consumer side),
  status derivation (G2.7), Art. 9 goods-code mapping (G2.8).
- **Deriving `submit_claim`'s `invoices` argument from the claim's own
  frozen lines** — it stays a caller-supplied list (WO-51's existing
  contract, unchanged); reconciling the two is flagged as G2.6's job, not
  invented here.
- **Any `api/routes/transport/*` route**, **any UI**.

### Implementation guidance

1. **Why a mixed-currency claim refuses to freeze, at BOTH levels.** Each EU
   member state charges VAT in one national currency, so a `refund_country`'s
   invoices are almost always all one currency — but nothing at ingestion
   enforces that. Summing raw `vat_local` figures across currencies would
   violate master-context §4.14 ("no aggregate sums across currencies
   without a recorded conversion... never labels a foreign amount EUR").
   `build_claim_lines` refuses at the BUCKET level (a single line's own
   transactions disagree); `freeze_claim_lines` refuses at the CLAIM level
   (two different lines disagree) — two independent checks, not redundant,
   since a claim can have zero cross-bucket disagreement while still (in
   theory) holding lines seeded some other way with different currencies.
2. **Why the schema extension is additive, not a rewrite of WO-52.**
   `VatRefundClaimLine` shipped with only `net_eur`/`vat_eur` (WO-49); WO-52
   (G2.4) never needed local-currency figures because nothing consumed them
   yet. This order needs them for C10's freeze and adds them the same way
   this codebase's own convention allows ("R6 — reimbursement batch maker
   id: additive column only") — `alembic revision --autogenerate` detects
   exactly the 3 new columns, no data migration/backfill needed (existing
   rows, if any, simply have `NULL` local figures; they get real ones the
   next time `build_claim_lines` rebuilds them, which happens before every
   freeze since the claim must still be `draft`).
3. **Freezing computes over exactly the claim's OWN lines — not a
   `fuel_transactions` re-query.** `build_claim_lines` (G2.4) already scopes
   a claim's lines to exactly its own `(entity, refund_country, period)`; a
   claim's lines ARE its claim_set by construction (unlike Fleet Fuel's live
   `invoice_lines()`, which needed an explicit "exclude what's not in this
   claim" step because it queried live). Summing the claim's lines directly
   is therefore the faithful translation of C10's "computed over exactly the
   locked claim_set... not a raw SUM over the period" — see `freeze.py`'s
   module docstring for the full argument.
4. **The freeze runs INSIDE `submit_claim`'s existing transaction, never as
   a separate call.** `freeze_claim_lines` does not flush or commit; it only
   mutates ORM state. `submit_claim` calls it before adding lock rows, then
   flushes once — a lost lock race's `IntegrityError` at that single flush
   rolls back the freeze mutations too (proven by `test_g2_5_lost_lock_
   race_leaves_the_claim_unfrozen`, mirroring WO-51's own same-session
   backstop test).
5. **An empty claim (no lines yet) freezes to zero, not an error.** Whether
   an empty claim_set should be REFUSED at submission is G2.6's future gate
   (C6's "an annual claim with an empty claim_set is BLOCKED" narrows to a
   period/annual distinction this order does not implement) — `freeze_
   claim_lines` itself just does the arithmetic over whatever lines exist
   (zero is a valid, if degenerate, input) and flags this explicitly rather
   than silently assuming a future gate already exists.
6. **Migration:** `alembic revision --autogenerate`, then hand-edit for the
   docstring only (no RLS change needed — `vat_claim_lines` is an existing
   RLS-policy'd table; adding a column to it does not require a new policy).
   Verify `alembic upgrade head && alembic check` reports no drift, and a
   downgrade/upgrade round-trip is clean.
7. **`README.md`/`test_docs_truth.py`:** the Alembic revision count moves
   76 → 77; table count (70), model/service/route module counts are
   unaffected (no new table, `freeze.py` lives inside the `services/
   transport/` SUBPACKAGE so the top-level `service_modules` count — which
   globs non-recursively — does not change).

### Invariants this order must preserve

- **§4.9/§4.10 (money quantized, server recomputes)** — `freeze_claim_lines`
  re-quantizes the summed `vat_eur`/`vat_local` via `q2` before writing the
  claim; never trusts a pre-computed total.
- **§4.14 (no aggregate sums across currencies without a recorded
  conversion)** — the two mixed-currency refusals (bucket-level in
  `build_claim_lines`, claim-level in `freeze_claim_lines`); proven by
  `test_g2_5_build_claim_lines_refuses_a_bucket_with_mixed_currency_
  transactions` and `test_g2_5_freeze_refuses_when_lines_span_multiple_
  currencies`.
- **§4.16 (every mutating operation is audited)** — `submit_claim`'s
  existing `TRANSPORT_CLAIM_SUBMIT` audit event now also records
  `frozen_line_count` in its `meta`; the freeze itself is not separately
  audited (it is part of the SAME submission event, not a distinct
  mutation) — `test_g2_5_audit_meta_records_the_frozen_line_count`.
- **§10 "no new tenant-scoped table without an RLS policy in the same
  migration"** — moot; this order adds columns to an EXISTING RLS-policy'd
  table, not a new table.
- **ADR-P3 (a re-close cannot alter a filed claim)** — this order is the
  mechanism that makes that true: `frozen_at` stamped + `vat_eur`/`vat_local`
  computed once, at submission, over exactly the claim's own lines.
- **ADR-P3 rule 2 (reads the core through services, never joins)** —
  `freeze.py` reads only `app.models.transport.vat_claim` (its own domain);
  `test_transport_services_do_not_import_other_domain_models` stays green.

### Database / migration impact

Three new nullable columns on the EXISTING `vat_claim_lines` table
(`net_local`, `vat_local`, `currency`) — no new table, no RLS change (the
table already carries its policy from WO-49's migration). No backfill:
existing rows (if any) get `NULL` local figures until the next
`build_claim_lines` rebuild, which always runs before a freeze (the claim
must still be `draft`). Downgrade drops the 3 columns cleanly — verified via
`alembic downgrade -1 && alembic upgrade head`; nothing is lost that a
future rebuild wouldn't recompute anyway.

### Rollback strategy

Migration downgrade (`alembic downgrade -1`) drops the 3 new columns —
safe; nothing is lost that a future `build_claim_lines` rebuild wouldn't
recompute. A code-only revert (removing the `freeze_claim_lines` call from
`submit_claim`) is safe in isolation but would leave the 3 columns
populated-but-unused until the migration is also reverted; the two should
revert together for cleanliness, though neither ordering breaks anything
(the columns are nullable and additive). No kill switch is needed for a
production incident: the `transport` module stays default-OFF and is
absent from every plan's module set, so `submit_claim`/`freeze_claim_lines`
are unreachable by any tenant regardless of code presence.
