# WO-59 — G2.7: status lifecycle 1A→5, the AUTO-code gate + the soft 2B reminder (board G2.7, R12/R17)

<!-- ═══════════════ COPY FROM HERE: WO-59 ═══════════════ -->

**WORK ORDER 59 — G2.7: status lifecycle 1A->5 — the AUTO-code derivation,
the "system-controlled" refusal, and the soft `2B` document-request
reminder. Effort M (3-5d). Priority P0. Milestone M3. Depends on: WO-58
(G2.6 complete — R6/R7/R8/R9/R10/R15 all now real gates `derive_stage`
reads from).**

### Objective and business value

WO-49 shipped `vat_refund_claims.status_code` as a nullable column but
nothing anywhere reads or writes it. Verified at HEAD=`d6f6cb2` (this
order's baseline, 1369 passed/10 skipped): `grep -rn "status_code"
app/services/transport/` returns zero writers and zero readers outside the
model + one test seeding it directly. `BA_fleet_fuel.md` D1/D3/D4/R17 is
explicit: pre-submission codes `1A/1B/1C/1E` must be SYSTEM-DERIVED and
never user-settable ("is system-controlled — it follows the checklist
automatically"), and the only legal first manual step from an unlocked
claim is `2` (Submit) — every other manual code attempted before
submission must be refused. R12 additionally requires `2B` (a document
request from the tax authority) to carry a deadline that is a SOFT
reminder only — CJEU C-133/18 *Sea Chefs* is explicit that a missing
document response can never auto-forfeit the claim.

Who pays more without this: with no `derive_stage()`, a customer-facing
readiness view (a future G2.7-consumer, e.g. G4.4's client claim-status
portal) has nothing to compute "is this claim ready, and if not, why" from
— it would have to re-derive the same checks ad hoc, risking drift from the
gates WO-56/57/58 already built. And without `set_status_code`'s refusal
of AUTO codes, an operator could hand-type `status_code="1E"` on a claim
that has NOT actually cleared the underlying checks, corrupting the one
figure a future ops dashboard trusts as "safe to submit".

### Scope

**In scope**
- `app.services.transport.status.derive_stage` — a pure, read-only preview
  (no writes) computing one of `AUTO_CODES = ("1A", "1B", "1C", "1E")` for
  a `draft` claim, per D3's literal order: any non-period item failing
  (an un-waived `UNMATCHED`/synthetic unfrozen line, OR a resolved invoice
  missing a document — reusing WO-58's `document_gate`/`claim_gates.
  is_synthetic`, never re-deriving either check) -> `"1A"`; else period not
  ended (`deadline.period_ended`) -> `"1B"`; else a "caveat" is present
  (DOCUMENTED INTERPRETATION, see Implementation guidance §1) -> `"1C"`;
  else `"1E"`.
- `app.services.transport.status.set_status_code` — R17's two literally
  tested behaviours: refuses `AUTO_CODES` (`code="status_code_system_
  controlled"`, message containing "system-controlled"); refuses any
  MANUAL code while the claim is still `draft` (`code="claim_not_
  submitted"`). On an already-locked claim (`submitted`/`approved`/`paid`),
  stamps the workflow `status_code` label (+ optional `action_deadline` —
  R12) WITHOUT touching the coarse engine `status` column (see
  Implementation guidance §2 for why the engine-state transitions
  themselves are explicitly deferred).
- `lock.submit_claim` additively stamps `claim.status_code = "2"` in the
  same flush as the existing lock/freeze/status-flip writes (a two-line,
  backward-compatible extension of an already-shipped function, the same
  pattern WO-54/55/56/57 each used).
- A small non-raising twin of WO-58's document gate,
  `document_gate.missing_document_invoice_ids` (returns the list instead
  of raising) — `enforce_document_presence` is refactored to call it and
  raise only if non-empty, so there is exactly ONE query implementation,
  never two.

**Out of scope** (explicitly, future work)
- **The ENGINE_OF-driven engine-state transitions for manual codes 3, 3A,
  3B, 3C, 3D, 4, 4A, 5** (moving `claim.status` itself to `approved`/
  `paid`/`rejected`). These are entangled with G2.9's fee-freezing/
  settlement-route logic (C10/C11/C12: `record_payment`, `compute_fee`,
  `payout_to`) — G2.9 stays explicitly decision-gated (no established
  customer/fee-rate concept to build against, `docs/DECISIONS-NEEDED.md`
  §10). Building a "3A moves the claim to paid" transition without that
  fee logic would either invent a fee-free payment concept or silently
  collide with G2.9's future scope. `set_status_code` therefore manages
  ONLY the workflow-code LABEL (+ `action_deadline`) in this order, never
  the engine `status` column, for any manual code — a narrower, explicitly
  documented limitation, not a silent gap.
- **Inter-code sequencing** (e.g. refusing `3A` before `3` has been set).
  Without real engine-state knowledge (deferred above), enforcing a manual-
  code ORDER beyond "the claim must already be locked" would be guessing;
  R17's own acceptance test only requires refusing a manual code on an
  UNLOCKED claim, which this order proves.
- **G2.10 (the adjustable checklist as data)** — `derive_stage`'s "non-
  period checklist items" are, for now, the two concrete checks this
  codebase actually has (unresolved lines, missing documents) rather than
  a data-driven rule set; flagged explicitly as the natural next slice
  that will REPLACE this order's checklist proxy, not sit alongside it.
- Any `api/routes/transport/*` route, any UI.

### Implementation guidance

1. **The "caveat" (1C) signal is a DOCUMENTED INTERPRETATION, not given
   verbatim.** `BA_fleet_fuel.md` D3 says only "verdict has a caveat (not
   `READY*`)" without defining what produces a caveat — the harvested
   checklist engine (`submission_checklist()`) that would normally emit
   that verdict is G2.10, not yet built. This order's reading: a caveat
   exists when the claim WOULD need an explicit override to submit
   cleanly — reusing `minimum.below_minimum` (previewed via `freeze.
   preview_vat_base`, exactly like `lock.submit_claim`'s own R8 gate) OR
   `waiver.waived_suppliers` returning a non-empty set (a waiver is, by
   definition, an accepted compromise — "we know this money is
   unclaimable" — not a full-strength pass). Both are PURE reads of
   already-shipped functions; no new check is invented.
2. **Why `set_status_code` never touches `claim.status`.** See "Out of
   scope" above — the alternative (building a partial engine-state
   machine for SOME manual codes but not others) risks a worse defect
   than a documented gap: a claim silently reaching `approved`/`paid`
   through a path that never validated fee/settlement invariants G2.9 is
   supposed to own. Refusing to guess here is the same discipline
   `is_synthetic()`'s own docstring states explicitly (fail toward
   blocking, never invent).
3. **`derive_stage`'s non-period check order matches D3 literally**: check
   "all non-period items pass" FIRST (before period-end) — a claim
   missing a document is `"1A"` even if the period also hasn't ended yet;
   only once non-period items all pass does period-end get checked. This
   is the harvested order verbatim, preserved even though checking
   period-end first might seem more natural.
4. **`missing_document_invoice_ids` de-duplicates the query, doesn't add
   one.** `enforce_document_presence` (WO-58) already does exactly this
   computation, just wrapped directly in a raise; extracting the list-
   returning half and having the raising function call it keeps ONE
   query implementation for both the blocking gate (R10) and the new
   non-blocking preview (`derive_stage`, R12/R17's own G2.7).
5. **`submit_claim` stamping `status_code = "2"`** happens in the SAME
   flush as the existing lock/freeze/status writes — a lost lock race
   rolls back the status_code stamp too (nothing partially applied,
   mirrors every prior additive extension to this function).

### Invariants this order must preserve

- **§4.16 (every mutating operation is audited)** — `set_status_code`
  emits an `AuditEvent` with old->new `status_code`; `derive_stage` writes
  nothing, needs none.
- **§4.4 (opaque 404, never 403)** — `status.py`'s claim lookup mirrors
  every other transport service's org-scoped `_get_claim`.
- **R3's `is_synthetic()` centralization** — `derive_stage`'s "unresolved
  line" check calls `claim_gates.is_synthetic`, never re-derives the
  `UNMATCHED`/`INPUT`/`ALL:` predicate.
- **ADR-P3 rule 2** — no new import of a foreign domain's model; `status.py`
  only touches `app.models.transport.*`.
- **G2.9's decision-gate is not silently crossed** — `set_status_code`
  makes zero change to `fee_pct`/`fee_min`/`fee_eur`/`paid_amount`/
  `claim.status`, proven by a dedicated test.

### Testing requirements

`backend/tests/transport/test_g2_7_status.py`:
- `derive_stage` returns `"1A"` when an unresolved `UNMATCHED` line exists;
  returns `"1A"` when a resolved invoice has no vaulted document (even
  with the period already ended);
- `derive_stage` returns `"1B"` when all non-period items pass but the
  period has not ended;
- `derive_stage` returns `"1C"` when everything else passes but the claim
  is below the Art. 17 minimum (a below-minimum "verdict caveat");
  returns `"1C"` when a receipt-control waiver is active on an otherwise-
  clean claim;
- `derive_stage` returns `"1E"` when every check passes cleanly;
- `derive_stage` refuses (409, `code="claim_not_draft"`) on a non-draft
  claim;
- `set_status_code` refuses each of `"1A"`/`"1B"`/`"1C"`/`"1E"` with 409
  `status_code_system_controlled`, message containing "system-controlled";
- `set_status_code` refuses `"3A"` on a `draft` claim with 409
  `claim_not_submitted`;
- `set_status_code("2B", action_deadline=...)` on a `submitted` claim
  stamps the label + deadline, leaves `claim.status` == `"submitted"`
  UNCHANGED, and does not prevent a subsequent `withdraw_claim` call
  (proves "blocks nothing" literally);
- `set_status_code` refuses an unknown code string (`code="unknown_
  status_code"`);
- `submit_claim` end-to-end: after a successful submission,
  `claim.status_code == "2"`.

### Acceptance criteria (verifiable checklist)

- [ ] `derive_stage` returns the correct one of `1A`/`1B`/`1C`/`1E` for
      each of the five scenarios above, verified by a dedicated test per
      scenario.
- [ ] `set_status_code("1C", ...)` is refused (409) with a message
      containing "system-controlled" — matches R17's own acceptance
      wording verbatim.
- [ ] `set_status_code("3A", ...)` on a `draft` claim is refused (409
      `claim_not_submitted`).
- [ ] `set_status_code("2B", action_deadline=date(...))` on a submitted
      claim changes `status_code`/`action_deadline` only —
      `claim.status` is provably unchanged, and `withdraw_claim` still
      succeeds afterward (R12's "blocks nothing", literally proven).
- [ ] `submit_claim` stamps `status_code == "2"` on every successful
      submission (extends WO-58's own document-gate test).
- [ ] `enforce_document_presence` and `derive_stage`'s document check
      share ONE query implementation (`missing_document_invoice_ids`) —
      no duplicated `ExtractionRun`/`invoice_ids_with_documents` query.
- [ ] Full backend suite green on SQLite; `mypy app` clean; `ruff` clean;
      no migration to check (`alembic check` still clean, no drift).

### Rollback strategy

Code-only revert: remove `status.py`, its call sites (the one line in
`submit_claim`, the `document_gate.missing_document_invoice_ids`
refactor), and the new audit action. No migration to downgrade (none
created). No kill switch needed: the `transport` module stays default-OFF
and absent from every plan's module set, so none of this is reachable by
any tenant regardless of code presence.
