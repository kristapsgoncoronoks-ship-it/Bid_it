**WORK ORDER 25 — Remove dead AP workflow states (board C1.9). Effort S 1–2d. Priority P2. Milestone M1. Depends on: E1.1, E1.2, E1.3 (done).**

### Objective and business value

`app/models/invoice.py::WorkflowState` declares three members — `uploaded`, `processing`,
`review_required` — and `app/services/invoice_workflow.py` wires them into `TRANSITIONS`
(`uploaded → {processing, review_required, draft}`, `processing → {review_required, draft}`,
`review_required → {draft}`), `LABELS` and `EDITABLE`. Recon for this order (exhaustive grep
across `backend/app`, `backend/tests`, `frontend/src`) confirms **none of the three is ever
assigned**: the only two `Invoice(...)` construction sites in application code —
`app/api/routes/invoices.py::create_invoice` (line 165) and `app/seed.py` (lines 174, 221) —
never pass `workflow_state`, so every invoice lands on the column default,
`WorkflowState.draft` (`app/models/invoice.py:139-145`, and the same default is repeated as
the Postgres `server_default` in migration `e7b9c1d3f5a2`). No route, service, worker, or
extraction/capture path (`email_intake.py`, `waiting_room`-equivalent ingestion) ever writes
`uploaded`, `processing`, or `review_required` to `workflow_state`; a repo-wide grep for the
bare string literals `"uploaded"`, `"processing"`, `"review_required"` inside `backend/app`
finds them **only** at their own enum-member declaration (`app/models/invoice.py:43-45`).
The one place that treats them as reachable is `backend/tests/test_invoice_workflow_unit.py`,
which asserts the three legality checks as part of a "happy path" chain
(`test_happy_path_transitions_are_legal`, lines 33-36) and references
`S.review_required` in `test_editable_and_locked_sets` (line 81) — both assert the *shape of
the transition graph*, not any assignment observed in production code, so per
`00_MASTER_CONTEXT.md` §9 ("if a test breaks, first determine whether it asserted correct
behaviour") these are graph-shape tests that must be updated to match the graph after
deletion, not evidence the states are alive. The frontend has one dead-code UI branch:
`frontend/src/pages/ReviewInvoice.tsx::STATE_TONE` carries badge-tone entries for
`review_required`, `uploaded` and `processing` (lines 87, 98-99) that can never be reached
because `workflow_state` on the wire is always one of the eleven live values.

Dead reachable-but-never-entered states are a maintenance and correctness hazard in a state
machine that a reviewer's SoD/optimistic-concurrency/record-lock logic depends on being
exhaustive (`docs/architecture/engineering-rules.md`, ADR on idempotency/concurrency): every
future contributor reading `TRANSITIONS`/`EDITABLE`/`LABELS` has to independently verify
these three are inert before trusting them, and the Postgres native enum
(`invoice_workflow_state`, created `native_enum=True` in migration `e7b9c1d3f5a2`) accepts
values the application will never write, which is a silent widening of the money-adjacent
workflow_state contract. Removing them shrinks the graph to exactly what is real, removes
three permanently-`False` branches from `is_editable`, and removes a DB-level enum value that
a bug or a manual `UPDATE` could otherwise write into a column the whole review/approval/
payment pipeline treats as canonical.

### Database / migration impact

One new migration, `backend/alembic/versions/<new>_remove_dead_ap_workflow_states.py`,
`down_revision = 'b45eaac2f3f7'` (current head). Recreates the Postgres native enum type
`invoice_workflow_state` to drop three unused labels (`uploaded`, `processing`,
`review_required`) from the `invoices.workflow_state` column; no column, index, or table is
added or removed, and no `TENANT_TABLES`/RLS policy is touched (this migration does not
concern a tenant-scoped table addition). Backfill: none needed — the pre-flight guard proves
zero rows carry a dropped value before any DDL runs. Downgrade re-adds the three enum labels
(`ALTER TYPE ... ADD VALUE`, natively reversible) and is safe to run; nothing is lost on
downgrade because no row can be holding a value that was just dropped moments before by this
same migration's upgrade. SQLite path is a no-op (dialect-guarded), matching the precedent in
`e7b9c1d3f5a2_invoice_review_approval.py`.

### Rollback strategy

Code revert: standard `git revert` of the commit(s) — the enum/graph/test/frontend edits are
plain source changes with no one-way effect. Migration: `alembic downgrade -1` re-adds the
three enum labels via `ALTER TYPE ... ADD VALUE`, which is written and tested (up/down/up in
the self-verification block) — nothing is lost on downgrade since no row can hold a dropped
value in the window between drop and re-add. No data migration, no session revocation, no
irreversible effect. Narrow mitigation short of a full revert: none needed — the change is
inert until read, and no code path this order touches is on a hot/critical path that a partial
rollback would need to isolate.
