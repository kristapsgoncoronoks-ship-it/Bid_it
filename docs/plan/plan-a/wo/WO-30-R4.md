### Objective and business value

`POST /api/v1/expenses/{id}/decision` (`backend/app/api/routes/expenses.py::decide`, line 760)
loads the target `ExpenseReport` with a plain `select()` — `_load()` (line 135) takes no lock
parameter at all, unlike every other money-adjacent decision route in the codebase
(`payment_runs.py::_load(..., lock=True)`, `reimbursements.py::_load(..., lock=True)`,
`issued.py::_load(..., lock=True)`, `invoice_review.py`'s version-gated mutations). Worse,
`ExpenseDecision` (`backend/app/schemas/expense.py:64`) carries no `version` field at all, so
there is no optimistic-concurrency guard of any kind — not even the weaker, lock-free pattern
`invoice_review.py` uses. Two concurrent decisions on the same pending step (two approvers
racing, or a doubled click/retried request from one approver) can both read the step as
`pending`, both call `expense_approval.decide_step(...)`, and both commit — producing two
`STEP_APPROVED` writes to the same row (a lost-update on the step, not just the report), two
audit rows for what should be one decision, and up to two `webhooks.emit()` calls for the same
logical event (`expense.approved`), each of which can fan out to a subscribed integration. The
same unlocked `_load()` call also serves the `mark_reimbursed` action (handled inside the same
`decide()` handler, not a separate route) — so the one action that changes payment-adjacent
state (`reimbursed_at`, `decided_by`) on the report is exactly as unguarded as approve/reject.
Evidence: `docs/audit/test-baseline.md` finding #2, strengthened in `docs/audit/agent-debate.md`
§6.

Finance/ops teams rely on the approval chain and the audit trail it produces to prove who
approved what and when — this is precisely the "audit-ready financial record" promise in
`docs/plan/shared/00_MASTER_CONTEXT.md` §1. A silently duplicated approval (two audit rows,
a corrupted webhook fan-out to a payroll/ERP integration) erodes exactly that trust the moment
the expense module goes self-serve with more than one designated approver — which is the
common case, not an edge case, once a customer has more than one manager. Closing this before
General Release (Milestone B) removes the last unlocked money-adjacent decision route in the
codebase.

### Implementation guidance

1. Add the column to `ExpenseReport`: `version: Mapped[int] = mapped_column(Integer, default=1,
   server_default="1", nullable=False)`, placed near the other lifecycle fields (after
   `decision_note`, matching where `Invoice.version` sits relative to its own status fields).
2. `alembic revision --autogenerate -m "expense report version"`, then hand-edit: confirm it
   is a single `op.add_column("expense_reports", sa.Column("version", sa.Integer(),
   nullable=False, server_default="1"))` plus a matching `op.drop_column(...)` downgrade — no
   other diff should appear (verify the autogenerate against the model diff only added this
   one column; if it proposes anything else, hand-trim the migration to just this column, same
   as WO-8/WO-9's precedent of hand-editing autogenerated files).
3. Schema: add `version: int` to `ExpenseDecision` (no default — required, matching
   `BatchPay.version`/`ExpenseApprovalPolicyUpdate.version`'s existing precedent in this same
   file) and to `ExpenseReportOut` (`from_attributes=True` already set on the base model via
   `ExpenseReportOut`'s `model_config`, so the ORM's `version` attribute is picked up
   automatically once present on the model).
4. `expenses.py::_load`: add `*, lock: bool = False`; when set, `.with_for_update()` before
   the `db.scalar(...)` call — mirror `reimbursements.py::_load` verbatim (including its
   comment on SQLite ignoring `FOR UPDATE`/writes serializing there, Postgres taking the real
   lock).
5. `expenses.py::decide()`: change `r = await _load(db, current.org_id, report_id)` to
   `r = await _load(db, current.org_id, report_id, lock=True)`. Immediately after (before the
   segregation-of-duties check, mirroring `invoice_review.py`'s "version check right after
   load, before other domain checks" ordering), add:
   ```python
   if body.version != r.version:
       raise HTTPException(
           status.HTTP_409_CONFLICT,
           f"This report was changed by someone else (your version {body.version}, "
           f"current {r.version}). Reload and re-apply your decision.",
       )
   ```
   At the end of the function — after both branches (the multi-step chain-decision branch and
   the owner/finance progression branch) have set `r.status`/`r.decided_at`/etc., but before
   the `if r.status in (...): await webhooks.emit(...)` block — add `r.version += 1`. This
   single bump point covers approve/reject/return_for_correction/mark_for_reimbursement/
   mark_reimbursed uniformly (one handler, one lock acquisition, one version check, one bump —
   closing the `mark_reimbursed` bypass the roadmap calls out, by construction: there is no
   separate `mark_reimbursed` route to independently forget to lock).
6. Frontend: add `version: number` to the `ExpenseReport` interface in `types.ts` (it already
   flows through `ExpenseReportDetail extends ExpenseReport`, so no separate edit needed
   there). In `ExpenseDetail.tsx`, change `decide` to
   `(action: string) => act.mutate({ path: "decision", body: { action, version: r.version } })`
   — identical shape to `PaymentRuns.tsx`'s `{ version: r.version }` pattern (do not invent a
   new confirmation/refetch pattern; a 409 surfaces via the existing generic `onError: (e) =>
   toast.error(apiError(e))`, same as every other versioned mutation in this codebase).
7. Update every existing test call site (listed in "Files to touch") to supply `version`.
   Two shapes of fix apply:
   - **Single decision on a freshly-submitted report** (the common case): hardcode
     `"version": 1` — the report has never been decided on, so its version is still the
     column default.
   - **Sequential decisions on the same report within one test** (e.g.
     `test_expense_approval_chain.py::test_sequential_two_approver_chain`,
     `test_expense_management.py::test_full_lifecycle_submit_approve_reimburse`,
     `test_expenses.py::test_approval_workflow`): do not hardcode incrementing numbers: fetch
     the report's current `version` via `GET /expenses/{id}` immediately before each decision
     call (or read it off the previous decision's JSON response, which already returns the
     bumped value), and send that. This is more robust than counting bumps by hand and matches
     how a real client would behave (read-then-write).
8. Write `tests/test_expense_decision_version.py` (plain SQLite, no skip needed): submit a
   report, decide once successfully (version 1→2), then retry the SAME decision call with the
   original `version: 1` body and assert `409` with the report's status **unchanged** from the
   first decision (the loser's state is not partially applied) — the single-process SQLite
   equivalent proof of the guard, cheap to run on every CI job (not just the Postgres one).
9. Write `tests/test_expense_decision_concurrency.py`, structured like
   `tests/test_credit_note_lock_concurrency.py` (real HTTP through `ASGITransport`, since the
   fix lives in the route's `_load(..., lock=True)` call, not a standalone service function —
   same reasoning WO-26/27 used, not `test_payment_run_pay_concurrency.py`'s direct-service-call
   shape, because `decide()`'s logic is not factored into a callable service function the way
   `payment_run.mark_paid` is). Register an org (owner = expense approver by default), invite
   and appoint a second approver, invite a third member as the report's employee/owner (not an
   approver — required for segregation of duties), submit a complete report (comment + receipt
   on every item) with no approval policy configured (→ one generic open step, `approver_id
   IS NULL`, so BOTH approvers may legally act on it — this is the reachable-by-default race,
   not a contrived one), register a webhook endpoint subscribed to `expense.approved`, then
   fire two concurrent `POST /decision {"action": "approve", "version": 1}` calls (one per
   approver token) via `asyncio.gather` + `asyncio.Barrier(2)`. Assert exactly one returns
   `200` and the other returns `409` (never both `200`, never both `409`); assert the report's
   final `status == "approved"` and exactly one `WebhookDelivery` row with
   `event_type="expense.approved"` exists (no double fan-out); assert exactly one
   `ExpenseApprovalStep` row is `STEP_APPROVED` (the step itself is not double-written).
10. Prove the fix both ways on the scratch Postgres cluster: revert the `lock=True` +
    version-bump locally, run the new concurrency test, confirm it FAILS (both decisions can
    succeed, or the step ends up double-decided); reapply, confirm it PASSES. Paste both
    outputs in the final report.

### Invariants this order must preserve

- **§4/13 — no over-payment/over-crediting/over-decision, enforced under a row lock.** R4 is
  the concurrency-guard gap this invariant names; this order closes it for the decision path,
  proven on real Postgres (SQLite cannot exercise a genuine row lock — hence the two-tier test
  strategy: a cheap SQLite version-conflict unit test plus a Postgres-only true-concurrency
  test).
- **§4/16 — every mutating operation is audited.** `decide()` already calls `audit.record(...)`
  inside the same transaction as the status/version write for every action branch; the lock
  and version bump do not move that call or change what it records — the concurrency test
  additionally proves no *duplicate* audit-adjacent side effect (the webhook fan-out) occurs.
- **§4/20 — wire contract frozen / additive-only wire changes.** This is the one deliberate,
  reported exception the roadmap itself calls out ("a new required `version` field on the
  decision request (a breaking API change for any existing integration...)"): a **required**
  new request field is *not* additive. It is scoped to a single internal-only route
  (`/expenses/{id}/decision`) with no documented external API consumer today (this codebase's
  `/api/v1/ingest` and MCP surfaces are read-only/AP-intake — no external caller decides an
  expense report), matching the precedent already set for `ReimbursementBatch`/
  `ExpenseApprovalPolicy`'s own required `version` fields in the same module family. Documented
  explicitly here rather than silently — see "Documentation to update" below.

### Rollback strategy

Code revert for the route/schema/frontend changes — no one-way effect (a 409 the client
retries with a fresh version is the only new user-visible behavior, and it is strictly safer
than the prior silent-double-decision behavior it replaces). The migration's downgrade drops
`expense_reports.version`; safe or lossy only for the counter itself, not for any decision
data. If only a narrow mitigation is needed short of a full revert, disabling the frontend
build's send-version change would revert to `version: undefined`, which the required-field
schema would then 422 on every decision — i.e. there is no safe *partial* rollback that keeps
decisions working with the field made optional again without a second small edit
(`ExpenseDecision.version` back to `int | None` with the guard skipped when `None`,
mirroring `invoice_workflow.assert_version`'s explicit "`expected is None` means the caller
opted out" escape hatch) — call this out explicitly if a narrow mitigation is ever needed
rather than a full revert.
