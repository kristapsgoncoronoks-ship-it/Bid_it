### Task-selection rationale (read this first)

Per the coordinator's instructions, candidates considered from `docs/audit/remediation-roadmap.md`
Milestone C were: R13 (`test_fx.py` owner-only test doesn't test owner-only), R15 (load/concurrency
testing — explicitly flagged as larger/product-shaped, only pick if nothing smaller/higher-value
remains), R17 (Payment Run "Cancel" confirmation), R19 (onboarding checklist — same "larger/
product-shaped" caveat as R15), R10/R11/R12 (P4 doc/code hygiene, lower priority than any open P3).
R9 and R8 are closed (WO-36, WO-37) and skipped per the coordinator's explicit instruction. R5(a)/R14
are owner/decision-blocked and skipped.

**R13 was selected.** Verified first (per master-context §9, never assume): `backend/app/api/routes/
fx.py`'s `POST /fx/refresh` route (lines 119-126) declares `dependencies=[Depends(require_perm(authz.
Permission.SETTINGS_MANAGE))]` — a genuine, already-correct structural authorization gate. But
`backend/tests/test_fx.py::test_refresh_owner_only_and_graceful` (lines 209-215), the ONLY test that
exercises this route, uses only the `auth_client` fixture (always the workspace OWNER) and never sends
a single request as a role that lacks `SETTINGS_MANAGE`. Its own name and docstring ("owner_only" /
"refresh is allowed") assert a claim the test body cannot possibly falsify — a non-owner call is never
made, so if the `Depends(require_perm(...))` line were deleted entirely, or downgraded to a permission
every role holds, this test would keep passing with zero code change. This is a real, if narrow,
regression gap: SETTINGS_MANAGE-gated routes are exactly the class of route WO-1 hardened deliberately
(`test_authz_routes.py` proves the sibling routes `/webhooks`, `/jobs`, `/access/matrix`, `/modules`,
`/settings/validation` each deny a non-privileged role and allow `admin`) — `/fx/refresh` is the one
member of that family whose "owner only" claim was never actually machine-checked. Compared to R17 (a
UX-consistency nicety on a route the roadmap itself calls "cosmetic, not a control gap") this is a
correctness defect in the regression net itself for an already-shipped authorization control — smaller
and more bounded than R17 (one file, one test function, no frontend build/Playwright required) while
carrying more direct §4.6-adjacent value (closing a silent gap in the proof that a `settings.manage`
gate actually rejects). R15/R19 remain correctly out of scope as larger/product-shaped work.

### Objective and business value

`test_refresh_owner_only_and_graceful` is the sole test coverage for `POST /api/v1/fx/refresh`'s
authorization. Its name promises "owner only" but its body issues exactly one request, always as the
org owner, and asserts only `200` + a graceful `ok` field — it never issues a denied-role request and
never asserts a `403`. Per master-context §7.6 ("authorization tests... proven by a test for at least
one granted role and one denied role") and the established sibling pattern in
`tests/test_authz_routes.py`, this is a gap in the regression net: today's route code is correct
(verified: `SETTINGS_MANAGE` is held only by `Role.OWNER` and `Role.ADMINISTRATOR` in
`app/core/authz.py::ROLE_PERMISSIONS`), but nothing in the test suite would catch a future regression
that widened or removed that gate. ECB-rate-cache refresh is a low-blast-radius admin action, but the
same test file/pattern is copy-pasted for higher-stakes gates elsewhere in the codebase — a test that
silently doesn't test what its name claims is a hazard to anyone reading it as a model to extend, and
undermines the "tests are the regression net" discipline the whole plan runs on (master-context §5,
"Baseline discipline").
