# WO-55 — Art. 9 goods-code mapping (board G2.8)

**WORK ORDER 55 — G2.8: the Art. 9 goods-code mapping (board G2.8). Effort S
(1-2d). Priority P0. Milestone M3. Depends on: G1.2 (`fuel_transactions`/
`product_group`, WO-50) only — independent of the G2.2/G2.4/G2.5 chain.**

### Objective and business value

WO-49 shipped the DB-level defense (`ck_vat_claim_lines_goods_code_never_9`)
but explicitly deferred the actual mapping function; WO-52's `build_claim_
lines` left every line's `goods_code` `NULL` (its own docstring: "derive a
goods_code (Art. 9 mapping is G2.8, independent of this order)"). Verified at
HEAD=`2dd72f1` (this order's baseline, 1309 passed/10 skipped): no
`app/services/transport/goods_code.py` exists anywhere in the tree.
`BA_fleet_fuel.md` A6 (lines 316-330) gives the EXACT harvested table — this
is the rare case where the source text is fully specified, not
underspecified like the note-matching heuristics (WO-52) or the natural key
(WO-50): *"Diesel -> 1 Fuel, HVO -> 1 Fuel, Promo adj -> 1 Fuel (price
correction), AdBlue -> 10 Other, Toll/Fees -> 4 Road tolls, Parking -> 10
Other, Service/Other -> 10 Other... an unknown product group defaults to
code '10' (Other) — NEVER '9'."* `ARCH_plan.md` scopes this as depending on
G1.2 ONLY, independent of the G2.2-G2.7 critical-path chain, making it a
small, self-contained slice to land opportunistically alongside the larger
G2.6 gate stack that is queued next.

Who pays more without this: every claim line built so far (WO-52 onward)
carries a `NULL` `goods_code` — the evidence pack/workbook (future G2.12,
depends on G2.8) has nothing to report per Art. 9, and a filed claim with no
goods code is incomplete on its face to a refunding tax authority. Landing
this now, while it is still small and isolated, is strictly cheaper than
discovering the gap once the evidence-pack builder is already assuming a
populated `goods_code`.

### Scope

**In scope**
- `app.services.transport.goods_code.GOODS_CODE` — the harvested table,
  verbatim, `dict[str, tuple[str, str]]` (code, description) keyed by
  `product_group`.
- `app.services.transport.goods_code.derive_goods_code(product_group) ->
  str` and `goods_code_and_description(product_group) -> tuple[str, str]` —
  pure functions, no DB access, no claim/transaction dependency.
- `app/services/transport/claim_lines.py::build_claim_lines` now sets
  `goods_code=derive_goods_code(product_group)` on every constructed line
  (an additive behavior change to an already-shipped function — no
  signature change, no migration, since the column already existed
  nullable since WO-49).

**Out of scope** (explicitly, future M3 work orders)
- **The checklist/period-end/minimum/deadline gate stack** (G2.6), **fee
  freezing** (G2.9), **status derivation** (G2.7) — all independent of this
  order and untouched.
- **Art. 9(2) sub-codes** (G4.10, P3/S, e.g. truck diesel `"1.1.2"`) — this
  codebase, like Fleet Fuel, emits only the top-level code (`"1"`, `"4"`,
  `"10"`); `BA_fleet_fuel.md` itself flags refund-state sub-code opt-ins as a
  "known gap to consider," not this order's job.
- **Any evidence-pack/workbook consumer of `goods_code`** (G2.12) — this
  order populates the field; nothing yet reads it into a report.
- **Any `api/routes/transport/*` route**, **any UI**.

### Implementation guidance

1. **Copy the harvested table VERBATIM (`BA_fleet_fuel.md` A6, lines
   316-330) — do not re-derive or re-order it.** This is one of the rare
   fully-specified harvest points (unlike WO-50's `line_seq` or WO-52's
   note-matching heuristics); there is no "documented interpretation" needed
   here, only faithful transcription.
2. **List every one of the 7 `PRODUCT_GROUPS` values explicitly in
   `GOODS_CODE`, even though `derive_product_group()` never returns an 8th
   value today.** The `.get(pg, ("10", "Other"))` default exists for a
   FUTURE 8th `product_group` (defense-in-depth), not as a shortcut for
   today's known 7 — `test_g2_8_every_product_group_is_explicitly_mapped_
   not_left_to_the_default` asserts this structurally (assert the absence
   of an implicit fallback, per WORK_ORDER_TEMPLATE §8 rule 8).
3. **This mapping has NO dependency on a claim, a transaction, or the
   database.** It is a pure function of `product_group: str`. Do not add a
   DB round-trip, an org/tenant parameter, or a module-entitlement gate —
   there is nothing to gate (it makes no query, mutates nothing, and is
   already only reachable through `build_claim_lines`, which itself gates
   `transport` on entry).
4. **`build_claim_lines`'s change is additive, not a new contract.** No
   caller passes a `goods_code`; the function computes it internally from
   `product_group`, which it was already deriving per-transaction (`WO-50`'s
   `derive_product_group`) and grouping by. No existing test asserted
   `goods_code is None` (verified: the full `tests/transport/` suite passes
   unmodified before AND after this change).
5. **Two independent layers, not one.** WO-49's DB CHECK constraint
   (`ck_vat_claim_lines_goods_code_never_9`) already blocks `"9"` at the
   storage level; this order adds the APPLICATION-level guarantee (the
   mapping function itself never emits `"9"`) — `test_g2_8_no_mapped_code_
   is_ever_9` proves the app-level half, `test_r11_goods_code_shape.py`
   (WO-49) already proves the DB-level half. Neither replaces the other.

### Database / migration impact

None. `vat_claim_lines.goods_code` has been a nullable `String(2)` column
with its `<> '9'` CHECK constraint since WO-49's `02d418169f97` migration;
this order only starts WRITING a non-NULL value to it, which requires no
schema change.

### Testing requirements

`backend/tests/transport/test_g2_8_goods_code.py` (13 tests):
`derive_goods_code` matches the harvested mapping for all 7 `PRODUCT_GROUPS`
values (parametrized); every `PRODUCT_GROUPS` value has its own explicit
`GOODS_CODE` entry (not falling through to the default); no mapped code is
ever `"9"`; an unrecognised product group (including the literal string
`"9"` itself, to prove it isn't accidentally echoed back) defaults to
`"10"`; `goods_code_and_description` returns the full `(code, description)`
pair for both a known and an unknown group;
`build_claim_lines` populates the correct `goods_code` per constructed line
across three different product groups in one claim; no claim line ever
persists `goods_code == "9"` across all 7 groups plus an unrecognised one
(app-level proof alongside WO-49's DB-level CHECK constraint).
