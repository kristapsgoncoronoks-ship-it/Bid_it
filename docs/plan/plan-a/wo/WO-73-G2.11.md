# WO-73 — G2.11: customer lifecycle + per-country activation gates (R44)

<!-- ═══════════════ COPY FROM HERE: WO-73 ═══════════════ -->

**WORK ORDER 73 — G2.11: the customer lifecycle `prospect → pending → active
→ inactive` + per-(customer × refund country) activation, gating claim
submission (board G2.11, R44; `BA_fleet_fuel.md` §3.F F1/F3, §3.E "Activation
gates layered on top", §3.D D5). Effort M (3-5d). Priority P0. Milestone M3.
Depends on: WO-49 (G1.1/G2.1 — the claim grain + the `issuer_profiles` R1
entity decision this order's tables key to), WO-56 (G2.6 slice 1 — the D5
gate order inside `lock.submit_claim` this gate composes with), WO-60 (G2.10
— the adjustable checklist, whose boundary with the coarse activation flags
§3.E defines and this order preserves).**

### Objective and business value

Verified at HEAD=`f6339a1` (this order's baseline, **1744 passed / 10
skipped**, coordinator-verified full-suite run at WO-72's close-out): nothing
in `app/services/transport/` knows whether a claimant entity is a live,
contracted client. `lock.py::submit_claim` (lines 165-330) gates on
draft-status, period-end (R7), Art. 17 minimum (R8), the annual mop-up /
duplicate block (R6), and document presence (R10) — but an entity created
five minutes ago with zero onboarding (`tests/transport/conftest.py::
make_entity` inserts a bare `IssuerProfile`) submits a legally-binding VAT
refund claim to a foreign tax authority exactly like a fully-contracted
client. There is no lifecycle state anywhere (`grep -rn "prospect\|activation"
backend/app/services/transport/` returns nothing), so R44's own acceptance
line — *"Submitting a claim for a prospect is refused with the activation
message"* — is currently false, and per-country activation (F3: PoA and
country documents received before filing in that country) has no
representation at all.

Who pays: the claim is filed **in the client's name under a power of
attorney**. Filing for a customer who has not signed the contract, provided
the payout bank account, or granted the country PoA is not a data-quality bug
— it is an unauthorised legal act by the platform operator (the accountancy
practice), and a refund paid against a wrong or absent mandate is money
misdirected under Art. 8(1) 2008/9/EC. The harvested system treated this as a
hard gate for exactly that reason (F1: *"Every legal/claim gate keys off
`status == 'active'`"*). The same gate is also the commercial switch: an
`inactive` (churned) client stops consuming filing capacity the moment the
flag flips, without touching their historical claims.

### The harvested specification — the standing order's five questions, answered with citations

**1. The exact state set and transitions; who moves a state; is it audited.**
§3.F F1, verbatim: *"`CUSTOMER_STATES = ("prospect", "pending", "active",
"inactive")`"*; *"`add_prospect` is idempotent on company_name and never
downgrades a real client of any status"*; *"`promote_prospect` (prospect →
pending) is the onboarding handoff; `set_activation` toggles pending ↔
active"*. §4's state table adds the `active → inactive` edge (*"Customer:
prospect → pending → active → inactive"*). This order builds EXACTLY those
harvested edges — `(none) → prospect` (`add_prospect`), `prospect → pending`
(`promote_prospect`), `pending ↔ active` (`set_activation`), `active →
inactive` (`set_inactive`) — and nothing else: `inactive` is terminal in this
slice (no re-onboarding edge is harvested; adding one is a one-line future
decision, not invented here — master-context §10 "no invented
functionality"). Every transition is an explicit call by an operator (F3:
*"activation stays an explicit admin click"* — enforced today as the
documented intent for the future route's admin permission, since no
`api/routes/transport/*` surface exists yet; the same posture as WO-56's
`override_minimum` boolean) and every real state change is audited old→new
(§4.16); idempotent no-ops audit nothing (the WO-60 `set_active` convention).
For the refund country, §4's state table: *"Refund country (per customer):
(none) → requested → active"* — `request_country` ((none) → requested,
idempotent, never downgrades) and `set_country_activation` (requested ↔
active; refuses a country never requested — the harvested order is linear).

**2. What each gate keys off — `active` only?** Yes. F1: *"Every legal/claim
gate keys off `status == 'active'` — a prospect is ignored exactly like a
pending customer."* There is no partial-privilege state: `prospect`,
`pending` and `inactive` are all equally not-`active`, and the gate tests
equality with `"active"`, never rank. Same for the country: §3.E's second
bullet requires the refund country *"separately activated"* — only a
country-activation row at `status == "active"` passes; `requested` (documents
being gathered) does not.

**3. What per-country activation gates precisely — claim creation?
submission? both?** SUBMISSION ONLY, both gates. §3.E places the activation
gates on the STATUS TRANSITION (*"Activation gates layered on top
(`set_status`, when `gate_activation=True`)"*), not on claim construction —
and the harvested system necessarily PREPARED claims for not-yet-active
customers: the whole 1A stage (§3.D D3 — checklist items failing on a draft
claim) exists to describe a claim whose customer's onboarding is incomplete,
and the activation refusal message itself (*"complete the trade registry,
bank account and signed contract on the Customers page first"*) assumes a
claim already exists to be refused. So `claim.get_or_create_claim`,
`claim_lines.build_claim_lines` and the checklist stay ungated; the ONE new
gate call sits in `lock.submit_claim`.

**4. Where in the D5 gate order does the R44 gate sit?** D5, verbatim:
*"Submission gate order in `set_status_code`: checklist (1A) → period-end
(1B) → national-currency minimum (Art. 17) → then `set_status(engine)` which
applies synthetic/duplicate/document gates."* §3.E puts the activation gates
*"layered on top"* of `set_status` — i.e. at the ENTRY of the engine-gate
group, before its synthetic/duplicate/document gates. Mapped onto
`submit_claim`'s existing order (whose docstring already tracks D5): **after
the R8 minimum, before the R6 mop-up/duplicate block** — draft-status →
non-empty set → period-end (R7) → minimum (R8) → **activation (R44)** →
mop-up/duplicate (R6) → waiver stamp (R15) → document presence (R10) →
freeze → lock → status flip. A claim failing the R44 gate never freezes or
locks — the existing "nothing mutated before the last gate passes" property
is preserved. One harvested nuance documented rather than reproduced: §3.E
says Fleet Fuel's `set_status_code` passed `gate_activation=False` because
*"the adjustable checklist supersedes the coarse activation flags"* — but
R44's own acceptance line (*"submitting a claim for a prospect is refused
with the activation message"*) is the binding M-level requirement, its
message is the ACTIVATION message (not a checklist item), and the checklist
here (WO-60, a partial harvest) checks data completeness, never the status
flag — a prospect with perfect data would sail through it. Bid_it has exactly
ONE submission path (`set_status_code` refuses `"2"`; only `submit_claim`
submits), so the gate is UNCONDITIONAL there — fail-toward-blocking, the
`is_synthetic()` discipline.

**5. Are prospect/pending entities excluded from `run_close`/claim
building?** NO — and the harvested text agrees: F1 scopes the rule to
*"every legal/claim GATE"*, and nothing in §3.F/§3.H excludes a non-active
customer from PREPARATION (the opposite: preparation-under-onboarding is what
the 1A stage and the checklist chase board describe). `run_close` only ever
touches `draft` claims (WO-53), which hold no legal effect; rebuilding a
pending customer's draft lines at the close is exactly the onboarding-era
prep work the harvested product sold. `close.py` is therefore UNCHANGED by
this order. ("Ignored exactly like a pending customer" = ignored BY THE
GATES, not dropped from the pipeline.)

### Design decision — where lifecycle state lives (the standing order's explicit question)

A **transport-local tenant table keyed to the entity**, following WO-61
(`supplier_vat_registrations`) and WO-72 (`vat_supplier_cadences`) — NOT new
columns on `IssuerProfile`. Reasons, with citations: (a) WO-49's R1 decision
reuses `issuer_profiles` as the claimant registry, and that model is a
shared AP/AR-domain table (`app/models/issuer.py` — the invoice-issuing
SELLER profile every `issued_invoices` row snapshots); a transport lifecycle
column there would leak vertical-only semantics into the core domain ADR-0023
walls off (`test_boundaries.py::test_transport_services_do_not_import_other_
domain_models` exists to prevent exactly this coupling, and transport reads
the entity ONLY via `app.services.issuer.get_by_id`, ADR-P3 rule 2); (b) the
harvested `customers.db` was itself a SEPARATE store from the supplier/
product masters (§4.1's DB table: *"`customers.db` — our clients (CRM)"*),
so a dedicated table is the faithful shape, not a workaround; (c) WO-72's
`vat_receipt_controls` already established the exact pattern this order
copies — composite `(org_id, entity_id)` FK into `issuer_profiles`,
`ondelete=RESTRICT`, RLS in the same migration. One translation documented
(the WO-50 `line_seq` / WO-72 15-16-split precedent): `add_prospect`'s
harvested idempotency key is `company_name` because company name WAS the
customer identity in Fleet Fuel's `customers` table (§4.4's schema sketch);
in this codebase the customer identity IS the issuer-profile row, so
`add_prospect(org, entity_id)` is idempotent on `(org_id, entity_id)` — the
same rule (one lifecycle per customer; re-adding never downgrades), the key
translated to this codebase's customer identity. Name-based lookup belongs
to the future G4.8 estimate funnel (M5), which resolves a typed company name
to an entity before calling `add_prospect`.

### Implementation guidance

1. **The transition map is data, the verbs are thin.** One private
   `_transition(db, org, entity_id, *, expected_from, to, action_verb)`
   enforces the edge set and audits; the public verbs (`promote_prospect`,
   `set_activation`, `set_inactive`) each name their harvested edge. A
   disallowed edge refuses with 409 (`lifecycle_transition_invalid` /
   `not_a_prospect`), naming both states in the message.
2. **`add_prospect` never downgrades** — if a lifecycle row exists at ANY
   status it is returned UNCHANGED and nothing is audited (F1 verbatim;
   the idempotent-no-op-audits-nothing convention).
3. **The gate fails CLOSED and mutates nothing.** `enforce_activation` runs
   before the R6 block, so a refused claim never freezes, locks, or flips —
   assert `status == "draft"`, zero lock rows, zero `frozen_at` after the
   refusal. Customer gate first, then country gate (§3.E's own bullet
   order) — a prospect in an unactivated country reports
   `customer_not_active`, the more actionable message.
4. **Money is untouched** — no amounts, no `q2` call sites.
5. **Opaque 404** — every entity_id resolves via `issuer.get_by_id`;
   cross-tenant indistinguishable from unknown (§4.4).
6. **Fixture raises, never assertion weakening** — a pre-existing test
   changes ONLY by adding `activate_entity(...)` (and its import). Tests
   asserting gates that run BEFORE R44 (module-off, not-draft, empty set,
   `period_not_ended`, `below_minimum`) need no change and get none — their
   passing unmodified is itself the gate-order proof.

### Database / migration impact

One new migration, two tenant tables:
- `vat_customer_lifecycles`: `org_id`, `entity_id`, `status` String(10)
  CHECK ∈ {prospect, pending, active, inactive};
  `UNIQUE(org_id, entity_id)`; composite FK → `issuer_profiles` RESTRICT.
- `vat_country_activations`: `org_id`, `entity_id`, `country` String(2),
  `status` String(10) CHECK ∈ {requested, active};
  `UNIQUE(org_id, entity_id, country)`; composite FK → `issuer_profiles`
  RESTRICT.
RLS (`ENABLE`/`FORCE` + the standard tenant policy) for BOTH tables in the
SAME migration. Downgrade drops both tables + policies — safe: loses only
lifecycle/activation state (re-enterable by the admin; no other table
references either), and after downgrade the gate code would fail at query
time rather than silently pass — but downgrade is paired with the code
revert anyway. Verified up/down/up on scratch Postgres 16 with the pg-only
suite re-run.

### Rollback strategy

Code revert: delete the two new modules, the one-line gate call in
`lock.py`, the audit members, the fixture helper; migration downgrade drops
both tables + policies (tested up/down/up). Lost on downgrade:
lifecycle/activation state — admin-re-enterable; nothing else references
either table. No kill switch needed: `transport` stays default-OFF and
absent from every plan's module set.
