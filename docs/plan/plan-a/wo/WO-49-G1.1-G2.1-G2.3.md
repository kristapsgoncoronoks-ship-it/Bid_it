**WORK ORDER 49 — M3 opener: the transport-vertical foundation (claim grain, `is_synthetic()`, module entitlement) (board G1.1, G2.1 partial, G2.3). Effort M (3-5d). Priority P0. Milestone M3. Depends on: nothing (M2's owner-blocked items are untouched).**

### Objective and business value

M3 (`docs/plan/plan-a/ARCH_plan.md` — "M3 — Transport vertical, phase 1: the VAT
refund claim engine") is a 70-100 engineer-day milestone: the EU cross-border VAT
refund claim engine harvested as *specification* (never code, never data — see
`docs/plan/shared/VAT_HARVEST.md` E.0 PII quarantine) from the retired Fleet Fuel
system. Its exit criteria cite R1-R17, R29-R32, R44, R45 of
`docs/plan/shared/specs/BA_fleet_fuel.md` plus explicit architectural requirements
(claim grain, one centralized `is_synthetic()` predicate, transactional lock
acquisition, withdraw-only release, annual-as-mop-up, the deadline/minimum/
period-end gate stack, Art. 9 goods codes, fee freezing, frozen claim lines,
the `2B` soft-reminder rule, checklist-as-data). Verified evidence at HEAD=`021540a`
(repo tip when this order opened; baseline suite **1169 passed, 8 skipped**): no
`app/models/transport/`, `app/services/transport/`, or `api/routes/transport/`
directory exists; `app/services/modules.py::MODULES` has no `transport` entry;
`app/core/authz.py::Permission` has no VAT-domain member. ADR-0023 (accepted
BEFORE any of this existed, deliberately) states the six binding seam rules and
its own "Revisit when" clause names this exact moment: *"The transport vertical's
first implementation PR opens (the six rules become CI assertions)."*

Who pays more without this: the five Baltic transport entities the Fleet Fuel BA
describes are live contingency-fee revenue against money that is otherwise
**permanently forfeited** — 30-Sep-year+1 is a fatal time-bar (CJEU C-294/11
*Elsacom*). M3 is also, per the plan's own risk register (T-2), the highest-risk
milestone to get wrong: 2,422 Fleet Fuel tests are being discarded in the harvest,
and losing one gate either forfeits a client's money or files an invalid claim.
This order does not attempt the revenue-facing surface (no submission, no gates,
no UI) — it builds the ONE thing every future gate in M3 depends on: a correct
claim grain, a single non-duplicated `is_synthetic()` predicate, and the
entitlement fence around the whole vertical. Getting these three interfaces right
BEFORE the checklist/lock/deadline/fee gates exist is cheaper than fixing a
drifted `is_synthetic()` copy-pasted into four places after the fact — which is
literally the bug R3 exists to prevent (`BA_fleet_fuel.md` C2: *"so they all block
the same set of synthetic refs"*).

### Scope

**In scope**
- The claim aggregate root `VatRefundClaim` — `(org, entity, refund_country,
  ref_period)` grain, period ∈ `{YYYY-Qn, YYYY-YEAR}` (R1). `entity_id` reuses the
  EXISTING `issuer_profiles` registry (the org's own legal entities) rather than a
  new legal-entity table — see the model docstring for the harvested-spec citation
  justifying this reuse.
- The (future-materialized) claim-lines model `VatRefundClaimLine` — one row per
  `(invoice, product code)` shape, `invoice_ref`/`vat_id` as their OWN typed
  columns (never the Fleet Fuel overloaded `note` column), a nullable composite FK
  to the AP `invoices` table, `frozen_at` (NULL until a future submission service
  stamps it). No code in this order populates a line.
- `app.services.transport.claim_gates.is_synthetic(ref, vat_id)` — the ONE
  centralized R3 predicate, harvested verbatim, ready for the (future) lock gate/
  checklist gate/readiness check/workbook builder to import.
- `app.services.transport.claim.get_or_create_claim` — the one reachable entry
  point into the transport tables today: idempotent on the grain key, validates
  the period shape, resolves the entity through `issuer.get_by_id` (a service call,
  never a raw join), gated on the `transport` module entitlement FIRST.
- Module entitlement: `transport` key in `app.services.modules.MODULES`, default
  OFF, `core=False` — deliberately absent from every `PLANS[...].modules` set
  (pricing is a commercial decision this order does not make; recorded in
  `docs/DECISIONS-NEEDED.md` §10).
- Four new `Permission` members (`VAT_READ`, `VAT_WRITE`, `VAT_SUBMIT`,
  `TRANSPORT_READ`) with rows in all 8 `ROLE_PERMISSIONS` entries (ADR-P3 rule 5) —
  landed now, ahead of any route, so every future transport route only has to
  declare an already-reviewed permission.
- Migration `02d418169f97_transport_vat_claim_grain.py` — both new tenant tables,
  RLS policy in the SAME migration, defense-in-depth CHECK constraints (`ref_period`
  shape, `goods_code <> '9'` per R11 even though the goods-code mapping module
  itself is future work).
- `tests/test_boundaries.py` extended with the ADR-P3 rule 2 CI assertion (no
  `services/transport/*` module may import another domain's models) + a self-test
  seeding a violation to prove the detector actually detects.
- `docs/transport/rules.md`, `docs/architecture/adr/0023-...md`,
  `docs/security/authorization-policy-matrix.md`, `docs/DECISIONS-NEEDED.md`,
  `TODO.md`, `README.md` (scale-line truth-up) updated in the same order.

**Out of scope** (explicitly, future M3 work orders per `ARCH_plan.md`'s G2.x
sequence)
- **The lock table + lock acquisition (R4/R5, G2.2)** — `vat_claimed_invoices`,
  the transactional INSERT-not-upsert race behavior, withdraw-only release. Needs
  `fuel_transactions` (G1.2) to exist first for the FK target to mean anything.
- **The gate stack (R6-R10, R15, G2.6)** — annual-as-mop-up, hard period-end,
  Art. 17 minimums in the correct currency, the 30-Sep deadline scanner, receipt-
  control waivers. None of these can run yet — there is nothing to gate.
- **Fee freezing + settlement (R13, G2.9)**, **status derivation (R12/R17, G2.7)**,
  **Art. 9 goods-code mapping (R11, G2.8)** — the CHECK constraint against `"9"`
  ships now as schema-level defense-in-depth; the mapping table itself does not.
- **Claim-line materialization/note-resolution (R2/R16, G2.4/G2.5)** — the schema
  exists; the service that populates and freezes it does not.
- **`fuel_transactions` (G1.2)**, **the monthly close job (G1.3/G1.4)**, **capture/
  entity-resolution (G3.x)**, **any `api/routes/transport/*` route**, **any UI**.
- **Which subscription plan(s) price `transport`** — a commercial decision,
  recorded as owner-blocked in `docs/DECISIONS-NEEDED.md` §10, not decided here.

### Implementation guidance

1. **Read the seam rules before writing a model.** ADR-P3 (`ARCH_plan.md` line
   106) and `docs/plan/shared/VAT_HARVEST.md` E.2 are the binding architecture;
   `BA_fleet_fuel.md` rows 985/1020-1042/1358-1373 are the exact rule text. Do not
   paraphrase the R3 predicate — copy it verbatim into the docstring.
2. **`entity_id` reuses `issuer_profiles`, not a new table.** The harvested spec
   defines "entity" as *"our own legal entity that bought the fuel"* — exactly
   what `IssuerProfile` already models (an org's own legal identities, already
   multi-entity per org). Composite FK `(org_id, entity_id) → issuer_profiles
   (org_id, id)`, `ondelete=RESTRICT`.
3. **`get_or_create_claim` checks the module entitlement with `modules.is_enabled`
   (a bool), never `modules.require_enabled`** (which raises `fastapi.
   HTTPException` directly — correct for a route `_guard`, wrong for a service
   that must signal via `app.core.errors.AppError`). Raise `PermissionError(...,
   code="module_not_enabled")` instead, checked BEFORE any query.
4. **Entity lookup goes through `issuer.get_by_id(db, org_id, entity_id)`** — already
   org-scoped, so an unknown OR cross-tenant entity id both resolve to the same
   `NotFoundError` (404), never a 403 and never a cross-tenant leak (tenancy
   invariant §4.4).
5. **Migration:** `alembic revision --autogenerate`, then hand-edit — add the
   `ref_period` shape CHECK, the `goods_code <> '9'` CHECK, RLS for both new
   tables in THIS migration (`TENANT_TABLES` module-level tuple, same pattern as
   `a3f556aac756_capture_field_memory.py`). Verify `alembic upgrade head &&
   alembic check` reports no drift, and a downgrade/upgrade round-trip is clean.
6. **`test_boundaries.py`:** the new assertion scans `app/services/transport/*.py`
   imports for any `app.models.<other>` prefix; allow only `app.models.transport`
   and `app.models.base`. Ship the self-test (seed a file importing
   `app.models.vendor`, assert the SAME detection logic flags it) per
   `WORK_ORDER_TEMPLATE.md`'s "a check that cannot fail proves nothing" rule.
7. **Widening `ROLE_PERMISSIONS` breaks `test_authz.py`'s exact-set assertions
   BY DESIGN** (READ_ONLY's frozenset literal) — this is a deliberate grant
   widening, not a weakened test; update the literal, do not delete the assertion.
8. **`README.md`/`test_docs_truth.py`:** recount `__tablename__` across
   `app/models/**/*.py` (rglob, not the flat `_py_module_count` the module-count
   assertions use) and the `alembic/versions/*.py` glob; update both the README
   prose and the test's hardcoded literal together.

### Invariants this order must preserve

- **§4.2 (RLS/model set-equality)** — `tests/test_rls.py::
  test_rls_migration_covers_every_tenant_table` proves `TENANT_MODELS` and the
  migration's `TENANT_TABLES` are exactly `{vat_refund_claims, vat_claim_lines}` ∪
  the pre-existing set; no drift either direction.
- **§4.3 (composite `(org_id, id)` FKs)** — `vat_refund_claims.entity_id` →
  `issuer_profiles(org_id, id)`; `vat_claim_lines.claim_id` →
  `vat_refund_claims(org_id, id)`; `vat_claim_lines.invoice_id` →
  `invoices(org_id, id)`. All three composite, never a bare single-column FK.
- **§4.4 (opaque 404, never 403, on a cross-tenant fetch)** —
  `test_r1_cross_tenant_entity_is_opaque_not_found_never_leaks_across_orgs`.
- **§4.6/§4.7 (deny-by-default authorization, structural coverage)** — the 4 new
  permissions get explicit rows in all 8 `ROLE_PERMISSIONS`; `test_authz_coverage.py`
  stays green (no route declares them yet, so nothing to classify).
- **§4.16 (every mutating operation is audited)** — `get_or_create_claim`'s
  creation path calls `audit.record(..., org_id=org_id)` (explicit org, not the
  ambient contextvar, since this service is callable outside an HTTP request);
  the idempotent second call does NOT re-audit (`test_r1_get_or_create_claim_
  upserts_never_duplicates` asserts exactly one `AuditEvent`).
- **§10 "no new tenant-scoped table without an RLS policy in the same migration"**
  — both tables ship their policy in `02d418169f97_transport_vat_claim_grain.py`.
- **ADR-P3 rule 1 (transport owns only transport tables)** — zero columns added
  to `invoices`, `line_items`, or `vendors`; the FK direction runs from transport
  INTO the AP invoice table, never the reverse.
- **ADR-P3 rule 2 (reads the core through services, never joins)** —
  `test_transport_services_do_not_import_other_domain_models` + the entity lookup
  going through `issuer.get_by_id`.

### Database / migration impact

Two new tenant tables, `vat_refund_claims` and `vat_claim_lines`, both RLS-policy'd
in `02d418169f97_transport_vat_claim_grain.py` (SQLite in tests = no-op; Postgres
= `ENABLE`/`FORCE ROW LEVEL SECURITY` + the standard `tenant_isolation` policy,
identical predicate to every other tenant table). No column added to any existing
table. Backfill: none (both tables start empty; nothing in this order populates
`vat_claim_lines`). Downgrade drops both tables (and their RLS policies on
Postgres) cleanly — verified via `alembic downgrade -1 && alembic upgrade head`;
nothing is lost on downgrade because nothing is written by this order's code paths
in the first place (only test fixtures ever insert a row today).

### Rollback strategy

Migration downgrade (`alembic downgrade -1`) drops both new tables (and their
Postgres RLS policies) — safe, loses nothing because nothing outside this order's
own tests ever writes to them. A code-only revert without the migration downgrade
is safe in the direction of dropping the code first (the tables simply go unused);
the reverse (reverting the migration while the code is still deployed) would error
on the missing tables the moment `get_or_create_claim` is called, so always
downgrade the migration in the same step as reverting the code. The narrowest
mitigation that doesn't require any revert: the module stays default-OFF and is
absent from every plan's module set, so the entire vertical is unreachable by any
tenant regardless of code presence — no kill switch is even needed for a
production incident, since nothing can reach it today.
