# WORK ORDER 16 — Composed home dashboard (board I1.1)

**WORK ORDER 16 — Composed home dashboard: "what needs me today" (board I1.1). Effort M 3–5d. Priority P0. Milestone M1. Depends on: E1.1 (WO-12), C1.6 (WO-15) — both complete at `1efcbbb`.**

Baseline (recorded, per process rules — no pre-change re-run): **1024 passed, 4 skipped** at `1efcbbb` (the 4 skips are pg-only markers, verified separately on Postgres).

## Task selection rationale (per the M1 board)

ARCH_plan's critical path (§"5.2") runs `(M0 exit gate) → E1.1 → I1.1 → H1.4 → first charge`. E1.1/E1.2/F1.1/C1.6 are done (WO-12..15); I1.1 is the **P0** row that both deps unblocked, and it gates nothing less than the first sellable home surface. Selected.

## Verified premise (evidence at `1efcbbb`)

1. **The home page is a spend-analytics page, not a worklist.** `frontend/src/pages/Dashboard.tsx` renders KPI cards + charts off `GET /analytics/*` only — every query requires `REPORT_READ`, so an EMPLOYEE's home is a wall of silent failures, and *nothing* on it answers "what needs me today" (no approvals, no captures, no overdue, no deadline).
2. **No composed read exists.** `grep -rni dashboard backend/app --include=*.py` finds prose only (`cash_position.py:1` docstring etc.); no dashboard service/schema/route. The SPA would need ~7 fan-out calls with per-call 403 handling.
3. **The canonical figures all exist** (ADR-0023 projection rule — compose, never fork):
   - AP due-soon/overdue: `app/services/ap_aging.py::summary/worklist/summarize` (`DueSummary`, single-currency amounts + `other_currencies`, `DUE_SOON_DAYS=7`).
   - AR outstanding/overdue: `app/services/issued_reports.py::receivables` (`ReceivablesReport.total_outstanding/overdue_outstanding`, single-currency).
   - Cash position: `app/services/cash_position.py::summary` (receivables − payables; **a working-capital gap, not a bank balance** — the honest label is I1.1's stated requirement; the full relabel of `/cash-position` itself stays I1.3).
   - Captures pending review: the queue filter in `app/api/routes/invoices.py:343-348` (`ExtractionRun.status=="parsed" AND invoice_id IS NULL`) + `ExtractionField.low_confidence` (`app/models/extraction_field.py:69`).
   - Expense approvals: the `pending_approvals` count inline in `app/api/routes/expenses.py:410-418`.
4. **Four "waiting on me" aggregates do NOT exist as service functions** (grep-verified): a cross-invoice pending `ApprovalStep` query (`ApprovalStep` appears only in `invoice_review.py`/`approval_policy.py`/models; per-invoice `steps_for` only); an expense pending count as a *service* (it is inline route code); a payment-runs-awaiting-check count (`PaymentRun.status == "open"`, maker≠checker per `payment_run._sod_conflict`); a pending `VendorChangeRequest` count (only `list_change_requests`). Per the projection rule these must be **added to the canonical services** and consumed — never computed in the route or SPA.
5. **Permissions are heterogeneous** (`app/core/authz.py`): `REPORT_READ` is held by every business role **except EMPLOYEE**; `INVOICE_READ` by **all 8**; approvals need `INVOICE_APPROVE`/`EXPENSE_APPROVE`/`PAYMENT_WRITE`/`SETTINGS_MANAGE`. The SPA has **no** permission awareness (`src/lib/roles.ts` is rank-based) and its 403s are silent (no toast) but leave dead cards.
6. **Deep links can't filter today**: no page under `src/pages/*` reads `useSearchParams`; `GET /invoices` filters by `status`/`validation_status` but **not** by `workflow_state`, so "invoices awaiting approval" has no linkable worklist.

### Objective and business value

Build the P0 composed home dashboard: one `GET /api/v1/dashboard` projection over the canonical read services, returning per-section data **only where the caller holds that section's canonical permission** (section = `null` otherwise), and rebuild `Dashboard.tsx` as a scannable "what needs me today" surface — approvals waiting on me, captures needing review, overdue in and out, deadline risk (due within 7 days), and the cash position under its honest working-capital label — every tile linking to a filtered worklist.

Who pays: the finance lead's daily loop starts at "what needs me", not at charts — this is the screen that makes the product a *workspace* rather than a report viewer (activation metric FRV = confirm invoices + a value action, `docs/product/metrics.md`). Every persona gets a working home: today an EMPLOYEE's home is broken by design (silent 403 wall), an approver can't see their queue anywhere, and deadline risk (the 7-day window before late-payment interest and supplier escalation) is buried two pages deep. H1.4 (first charge) is next on the critical path; nobody pays for a product whose front door is someone else's wall.

### Scope

**In scope:**

*Backend — canonical aggregates (added to the owning services, per ADR-0023):*
- `app/services/approval_policy.py`: `ApInboxItem` dataclass + `waiting_for(db, org_id, *, user_id, can_approve_any, limit=10)` — invoices in `WorkflowState.submitted|partially_approved` whose **current** pending step (lowest `seq` with `status=="pending"`) is assigned to the user or open (`approver_id IS NULL` and the caller holds `INVOICE_APPROVE`), excluding invoices the user submitted (SoD parity with `invoice_review._guard_decider`).
- `app/services/expense_approval.py`: `pending_report_count(db, org_id)` — org-wide `ExpenseReport.status=="submitted"` count; `app/api/routes/expenses.py` summary refactored to consume it (one definition).
- `app/services/payment_run.py`: `runs_awaiting_check(db, org_id, *, checker_id)` — `RUN_OPEN` runs excluding those the checker made (`created_by_id == checker_id`).
- `app/services/vendors.py`: `pending_change_count(db, org_id, *, exclude_requester_id)` — `CR_PENDING` requests not requested by the caller.
- `app/services/extraction.py`: `pending_review_filters(org_id)` (the one queue definition) + `ReviewQueueSummary` + `review_queue_summary(db, org_id)` (pending runs + low-confidence field count); `app/api/routes/invoices.py::capture_review_queue` refactored to build its base select from `pending_review_filters` (one definition).

*Backend — the projection:*
- `app/services/dashboard.py` (**new**): `home(db, user, org_id, today=None)` composing `approval_policy` / `expense_approval` / `payment_run` / `vendors` / `extraction` / `ap_aging.summary` / `issued_reports.receivables` / `cash_position.summary`, gating each section by `authz.has(user, <the canonical surface's permission>)` and the `expenses`/`issuing` sections additionally by `modules.enabled_keys` (module off ⇒ section/count `null`, matching nav behaviour). No math beyond integer counts of composed items.
- `app/schemas/dashboard.py` (**new**): `DashboardOut{as_of, approvals|null, captures|null, payables|null, receivables|null, cash|null}` (fields below in Testing).
- `app/api/routes/dashboard.py` (**new**): `GET /dashboard`, `response_model=DashboardOut`, router-level `require_perm(INVOICE_READ)` — the one permission every business role holds (verified matrix) — with the real narrowing done per-section server-side; registered in `app/api/router.py`.
- `GET /invoices` gains a `workflow_state` filter (any `WorkflowState` value + virtual alias `in_approval` = `submitted|partially_approved`; unknown → 422) and `InvoiceOut` gains `workflow_state` (additive, from_attributes) — the linkable approvals worklist.

*Frontend:*
- `src/pages/Dashboard.tsx` rebuilt: one `GET /dashboard` query; attention tiles (approvals / captures / overdue payables / due soon ≤7d / overdue receivables) as links; approvals card with the inline AP mini-worklist (items → `/invoices/:id`) + sub-counts (expenses → `/expenses`, runs → `/payment-runs`, supplier changes → `/vendors`); cash card labelled **"Working-capital gap (receivables − payables) — not a bank balance"** → `/cash-position`; the existing spend snapshot (charts) kept **below** and rendered only when the payload shows `REPORT_READ` (`cash != null`) — no 403 fan-out; loading skeletons, an all-clear empty state, `QueryState` error handling. A section the payload nulls renders **nothing** (no dead card, no toast).
- `src/pages/Invoices.tsx`: initialise filters from URL params (`status`, `workflow_state`, `validation_status`) so tiles deep-link a *filtered* worklist; render the workflow state when filtering by it.
- `e2e/dashboard.spec.ts` (**new**, mocked-API pattern from `masters.spec.ts`): full-payload render + links, and a reduced-permission payload rendering no gated cards.

**Out of scope (anti-scope-creep):**
- Grouped navigation IA — **I1.2** (nav untouched).
- Relabelling the `/cash-position` **page** and its copy — **I1.3** (this order labels only the dashboard's own tile honestly; `net_position` maths untouched).
- Forward cash forecast — **I1.4**; report writers — **I1.5**.
- Fixing `analytics.summary()`'s hard-coded `"EUR"` or the cash-position AP-side multi-currency sum — **C1.7** (documented, projected as-is; the dashboard's own new sections use only the currency-honest sources).
- Any new approval capability (reassign-from-dashboard, bulk approve) — the decision surfaces stay `/invoices/:id`, `/expenses/:id`, `/payment-runs`, `/vendors`.
- Queue/DLQ health on the tenant dashboard — `queue_health.snapshot` is deliberately unscoped (platform SLO probe), not tenant data.

### Implementation guidance

1. Characterisation first: `pytest tests/test_capture_review_api.py tests/test_expenses*.py tests/test_payment_runs.py tests/test_vendor_changes.py tests/test_cash_position.py tests/test_ap_aging.py tests/test_authz_routes.py -q` green before touching anything (every refactor here is behaviour-preserving for the existing surfaces).
2. Canonical aggregates go in **before** the projection; each is a pure read (no commit, no audit — nothing mutates). `waiting_for` picks the *current* step per invoice (lowest pending `seq`) in Python after one ordered join — a later pending step is not actionable and must not count.
3. The projection service returns section `None` (never `{}` zeros) when the permission/module is absent — the SPA hides, not zeroes, the card. Docstring states the fail direction: a section that *errors* is a bug and propagates (all sources are same-DB reads inside one request; no partial-failure masking).
4. Money basis: counts are ints; every amount is passed through from its canonical source unchanged (`DueSummary` single-currency + `other_currencies`; `ReceivablesReport` single-currency; `cash_position` as-is). The dashboard adds **zero** arithmetic on amounts — state this in the service docstring.
5. Route gate: `require_perm(INVOICE_READ)` with a comment recording *why* (weakest permission held by all 8 business roles; sections narrow server-side to each canonical surface's own permission — the composed endpoint never widens what any role could already read).
6. `workflow_state` filter: validate against `WorkflowState` + `in_approval` alias before querying; 422 with a stable message otherwise. Additive only — no existing param changes.
7. Frontend: single `useQuery<Dashboard>(["dashboard"])`; tiles are `<Link>` cards (whole tile clickable, visible focus ring); attention encoded with the existing tone system (rose overdue / amber due-soon & low-confidence); all-clear renders a positive empty state, not a blank page. Spend snapshot below reuses the existing chart components with queries `enabled: !!dash.data?.cash`.
8. Targeted suites while implementing; ONE full backend suite at the END in the background, polled to the final line; `npm run build` + `npx playwright test` for the SPA.

### Invariants this order must preserve

- **§4.1/§4.2 (tenancy):** every new query filters `org_id`; no new table (nothing for RLS). Proven by the cross-tenant test (identical-looking seeds, zero leakage).
- **§4.4 (opaque 404):** untouched — the dashboard has no by-id fetch; the new list filter changes no 404 behaviour.
- **§4.6/§4.7 (structural authz):** the new route declares `require_perm(INVOICE_READ)` router-level (coverage gate passes with no allowlist edit); per-section narrowing uses `authz.has` against the *same* permission each canonical route declares — asserted by the section-visibility tests.
- **§4.8 (SoD):** the approvals inbox *excludes* what SoD forbids acting on (own submissions; runs the checker made) — the count never invites a forbidden action.
- **§4.9/§4.10 (money):** no float, no new arithmetic on amounts, no client-side money math beyond display formatting.
- **§4.14 (no cross-currency sums):** the new sections project only currency-honest sources; the known `cash_position`/`summary()` C1.7 caveats are projected unchanged and stay C1.7's scope.
- **§4.16 (audit):** the dashboard mutates nothing; no audit events required (and none of the refactored reads lose one — none had one).
- **§4.20 (wire contract):** all changes additive — new route, new optional `workflow_state` param, new `InvoiceOut.workflow_state` field; no field moves or changes shape.

### Rollback strategy

Pure code revert (one commit range): no migration, no data effect. The new wire surface (`/dashboard`, `workflow_state`, `InvoiceOut.workflow_state`) disappears with the revert; the SPA commit reverts with it (same range), so no orphaned consumer. Narrow mitigation: reverting only the SPA commit restores the old analytics home against an unchanged backend.
