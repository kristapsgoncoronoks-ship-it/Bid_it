**WORK ORDER 44 — Duplicate detection beyond exact invoice number (E1.4). Effort M (2–3d). Priority P2. Milestone M1. Depends on: C1.1 (shipped WO-7).**

### Objective and business value

Verified evidence, read straight off `HEAD=86bfdb0`:

`app/services/duplicates.py::candidates` (the E1.1 capture-review duplicate
warning, `GET /invoices/duplicate-candidates`) matches **only on exact
`invoice_number`**, split into `exact` (same supplier) and `cross_supplier`
(different supplier). A vendor that re-sends the same invoice under a
slightly different number (a common re-issue pattern — "INV-1042" vs
"INV-1042-R", or a scanned copy typed in with one digit different) is
invisible to it: same vendor, same amount, same date, different number —
zero signal today. ARCH_plan (E1.4) names this exact gap and its intended
shape: *"Add scored candidates (amount ± tolerance, date proximity, vendor)
as advisory — duplicate detection never blocks, by design."* This is a
second AP double-payment vector (the first, exact-number, is already
covered) with no code path watching for it at all.

### Scope

**In scope**
- `app/services/duplicates.py`: a new `ScoredCandidate` dataclass and
  `scored_candidates(db, org_id, *, vendor_id, total, currency, issue_date,
  exclude_invoice_id=None, exclude_invoice_number=None)` — same vendor,
  amount within a tolerance band, issue date within a proximity window;
  returns a `score` (0–100, advisory only, never a gate) and a human-
  readable `reason`.
- `app/schemas/invoice.py`: `ScoredCandidateOut` (mirrors
  `DuplicateCandidateOut` + `score`/`reason`); `DuplicateReportOut` gains an
  additive `scored: list[ScoredCandidateOut]` field.
- `app/api/routes/invoices.py::duplicate_candidates`: optional
  `vendor_id`/`total`/`currency`/`issue_date` query params; when all four
  are supplied, also runs `scored_candidates` (excluding the invoice number
  already being checked, so a row never appears in both `exact`/
  `cross_supplier` and `scored`).
- Frontend: `frontend/src/lib/types.ts` (`DuplicateReport.scored`,
  `ScoredCandidate`); `frontend/src/pages/CaptureReview.tsx` passes the
  draft's computed subtotal/currency/issue_date/vendor_id and renders a
  distinct, lower-urgency advisory banner (never blocking) for `scored`
  hits, separate from the existing exact/cross_supplier "possible
  duplicate" banner.
- `backend/tests/test_duplicates.py` (new) + a route-level test in
  `backend/tests/test_invoices.py`.

**Out of scope**
- Any change to the existing exact-number `candidates()` function or its
  wire shape — purely additive.
- Blocking a save on a scored match — duplicate detection is advisory by
  design (ARCH_plan's own words), unchanged here.
- Cross-supplier scored matching — E1.4's example and the existing
  exact-number precedent both frame this as a same-vendor signal; a
  cross-vendor near-amount coincidence is materially noisier and out of
  scope.
- A configurable tolerance/window (admin setting) — fixed constants for
  this order, named clearly so a future order can promote them.

### Implementation guidance

1. **Tolerance/window constants**, named at module scope in
   `duplicates.py`: `_AMOUNT_TOLERANCE_PCT = Decimal("0.01")` (1%),
   `_DATE_PROXIMITY_DAYS = 14`. A same-vendor invoice outside both windows
   scores 0 and is dropped, never returned at score 0 (keeps the list
   meaningfully short).
2. **Query, don't post-filter the whole table.** Filter
   `Invoice.org_id`, `Invoice.vendor_id`, `Invoice.currency` (mixed-
   currency amount comparison is meaningless — reuse the tenancy/§4.14
   discipline already established elsewhere) and a `BETWEEN` on
   `Invoice.total` computed from the tolerance band at the query level;
   score and reason are then computed in Python over the (small) result set.
3. **Score formula** — amount component up to 60 (60 at an exact match,
   linearly decaying to 0 at the tolerance boundary), date component up to
   40 (40 at same-day, linearly decaying to 0 at the proximity boundary);
   sum, cap at 100. Exact formula is implementation detail — the acceptance
   criterion is the ORDERING and PRESENCE guarantee (below), not a specific
   number.
4. **Reason string** — plain English, e.g. `"Same vendor, same amount,
   issued 2 days apart"` / `"Same vendor, amount within 1%, same day"`.
5. **Exclude what's already surfaced.** `scored_candidates` takes
   `exclude_invoice_number` so a same-number row (already in `exact`/
   `cross_supplier`) never double-appears in `scored`.
6. **Route**: only run `scored_candidates` when `vendor_id`, `total`,
   `currency` and `issue_date` are ALL present — a caller checking only by
   number (today's only caller-supplied shape) gets `scored: []`, byte-
   compatible with today's behaviour. `total` arrives as a `Decimal`-
   parseable string query param (mirrors `money`-typed query params
   elsewhere); reject a malformed value with the existing 422 path (schema-
   level `Decimal` coercion), not a 500.
7. **Frontend.** `CaptureReview.tsx` already computes `subtotal` from
   `draft.line_items` for display — reuse it (rounded via the existing
   `money`-adjacent helpers, not a new float path) as the `total` param,
   alongside `draft.currency`, `draft.issue_date`, and the already-resolved
   `vendorId`. Render `scored` in a visually distinct (amber, not rose)
   advisory block — lower urgency than an exact-number hit, still visible,
   still never blocking confirm.

### Invariants this order must preserve

- **§4.20** (wire contract) — `DuplicateReportOut.scored` is a new,
  additive field; existing callers/tests of `exact`/`cross_supplier` are
  unaffected. `duplicate_candidates`'s new query params are all optional
  with back-compatible defaults.
- **§4.1** (tenancy) — `scored_candidates` filters `org_id` explicitly,
  same discipline as `candidates()`.
- **§4.9** (Decimal, never float) — amount comparisons and the tolerance
  band use `Decimal` throughout; scoring arithmetic on `int`/`Decimal`
  only, never a bare float.
- **Advisory, never blocking** (E1.4's own acceptance criterion, and the
  existing precedent `candidates()` already sets) — no save/confirm path
  is gated by `scored_candidates`; it is surfaced, not enforced.

### Database / migration impact

None. Reuses `Invoice`'s existing columns (`vendor_id`, `total`, `currency`,
`issue_date`) — no new table, no new column.

### Testing requirements

`tests/test_duplicates.py` (new)
- `test_scored_candidates_same_amount_same_date_different_number` — two
  invoices, same vendor, same total, same issue_date, different numbers;
  the first appears in the second's `scored_candidates` with `score > 0`
  and a non-empty `reason`.
- `test_scored_candidates_excludes_other_vendor` — a same-amount/date
  invoice from a DIFFERENT vendor never appears (E1.4 is same-vendor only).
- `test_scored_candidates_excludes_other_currency` — a same-vendor,
  same-amount-in-a-different-currency invoice never appears (no cross-
  currency amount comparison).
- `test_scored_candidates_outside_tolerance_scores_zero_and_is_dropped` —
  an invoice far outside both the amount tolerance and the date window is
  absent from the result, not present at score 0.
- `test_scored_candidates_excludes_same_number` — a same-vendor,
  same-amount, same-number invoice (already an `exact` match) does not
  also appear in `scored` when `exclude_invoice_number` is passed.
- `test_scored_candidates_ranks_closer_match_higher` — two same-vendor
  candidates, one closer in amount+date than the other; the closer one's
  score is strictly higher and it sorts first.

`tests/test_invoices.py`
- `test_duplicate_candidates_scored_requires_all_four_params` — omitting
  any of `vendor_id`/`total`/`currency`/`issue_date` returns
  `scored: []` (today's callers unaffected).
- `test_duplicate_candidates_scored_end_to_end` — all four params
  supplied; the route surfaces a `scored` hit through the real HTTP path
  (authz + tenancy unchanged from the existing endpoint's coverage).

### Acceptance criteria (verifiable checklist)

- [ ] A same-vendor, same-amount, same-date, different-number invoice
      surfaces in `scored_candidates` with a `score > 0` and a non-empty
      `reason` — E1.4's stated acceptance case, verbatim.
- [ ] A different-vendor or different-currency near-match never appears.
- [ ] An out-of-tolerance, out-of-window match is dropped, not scored 0.
- [ ] `scored` never duplicates a row already in `exact`/`cross_supplier`.
- [ ] `GET /invoices/duplicate-candidates` is fully backward compatible —
      no new required params, `scored: []` when the optional params are
      absent.
- [ ] Nothing about save/confirm is blocked by a scored match.
- [ ] Full backend suite green; `mypy app` clean; `ruff` clean;
      `alembic heads` unchanged (no migration); frontend `npm run build`
      clean.

### Rollback strategy

Pure application-code + additive-schema change, no migration, no removed
field. A `git revert` of this order's commit(s) is safe and complete.
