# WO-58 — G2.6 slice 3: document-presence gate + receipt-control waivers (board G2.6, R10/R15)

<!-- ═══════════════ COPY FROM HERE: WO-58 ═══════════════ -->

**WORK ORDER 58 — G2.6 slice 3: the document-presence gate (R10) + receipt-
control waivers (R15). Effort M (3-5d). Priority P0. Milestone M3. Depends
on: WO-57 (G2.6 slice 2 — the annual mop-up/duplicate-block gate, whose
order this order extends), WO-52 (G2.4 — `invoice_match.registered_invoices`,
which the waiver refusal reuses).**

### Objective and business value

WO-56/57 landed four of the six G2.6 gates (period-end, minimum, annual
mop-up, quarterly duplicate-block). Verified at HEAD=`e0f6a70` (this order's
baseline, 1357 passed/10 skipped): `app/services/transport/lock.py::
submit_claim` still has no check that every invoice about to be frozen into
a claim actually has a captured document behind it, and no way to exclude a
genuinely-uninvoiced supplier's synthetic `INPUT` transactions from a claim
without either leaving them stuck as an unresolvable `UNMATCHED` line
forever or inventing a fake registered invoice to paper over the gap.
`BA_fleet_fuel.md` C8/R10 is explicit: *"Every invoice in the claim set must
have >=1 vaulted document, else BLOCKED - physical document missing."* C9/R15
is equally explicit about the ONLY waivable case: *"the ref is synthetic AND
starts with INPUT AND the supplier has NO registered invoice at all for that
refund country... waiving a supplier that HAS invoices is REFUSED."*

Who pays more without this: filing a VAT reclaim with the tax authority
while missing the underlying invoice for even one line is a real rejection
risk — Directive 2008/9/EC requires the invoice to exist and be producible
on request; a claim built on an unproven line risks the WHOLE application,
not just that line. And without a governed waiver mechanism, a genuinely
uninvoiced supplier (the invoice legitimately never arrives — a lost
receipt, a supplier that never issues one for cash purchases) permanently
stalls the claim on an `UNMATCHED` line that can never resolve, with no
principled way to say "we know this money is unclaimable, exclude it and
move on" — the client either can't submit at all, or the operator invents
an override that isn't what R16's override table is for (R16 changes an
ASSOCIATION between a note and a real invoice; it was never meant to paper
over a genuinely missing invoice).

### Scope

**In scope**
- **R10** — `app.services.transport.document_gate.enforce_document_presence`:
  for a claim's currently-unfrozen `VatRefundClaimLine` rows with a non-NULL
  `invoice_id` (the real, resolved lines — an `UNMATCHED` line has no
  `invoice_id` and is out of this gate's scope by construction), checks
  every DISTINCT `invoice_id` has >=1 linked capture with real stored bytes
  (`ExtractionRun.source_sha256 IS NOT NULL`) via a new batch helper on the
  AP-domain service seam, `app.services.extraction.invoice_ids_with_
  documents` (one query, no N+1 — mirrors Fleet Fuel's own `docs_index()`).
  Wired into `lock.submit_claim`'s gate order, after the R6 mop-up/duplicate
  block and before the freeze.
- **R15** — a new tenant table `vat_receipt_waivers` (org, claim, supplier)
  + `app.services.transport.waiver` (`set_waiver`, `remove_waiver`,
  `waived_suppliers`): `set_waiver` refuses (422,
  `code="waiver_supplier_has_invoices"`) a supplier with >=1 registered
  invoice for the claim's refund country (reusing `invoice_match.
  registered_invoices`, never re-deriving the check); otherwise records the
  waiver on a `draft` claim, idempotently. `claim_lines.build_claim_lines`
  excludes a waived supplier's transactions from grouping ENTIRELY (before
  the resolution/grouping step — "excluded from the claim by construction",
  C9 verbatim) so a waived supplier's `INPUT` transactions never produce an
  `UNMATCHED` line at all. `lock.submit_claim` stamps every waiver active on
  the claim into `status_note` at submission (C9's "the waiver use is
  stamped into the claim's `status_note` on submission").
- Migration for `vat_receipt_waivers` (1 new tenant table, RLS in the SAME
  migration); `app/core/tenant.py::TENANT_MODELS`, `app/models/transport/
  __init__.py`, `docs/transport/rules.md` (R10/R15 rows),
  `tests/test_tenancy_parity.py::EXEMPT` (no route yet), 2 new
  `audit.A` actions.

**Out of scope** (explicitly, future M3 work orders)
- **G2.7 (status lifecycle 1A->5)** and **G2.10 (the adjustable checklist as
  data)** — the checklist items this order's gates will eventually FEED
  ("receipt control: required invoices received" / "all invoice refs
  resolved") are still hard-coded submission gates here, not data-driven
  rules a customer's admin can toggle. Flagged as the natural next slice.
- **Blocking submission on a remaining, un-waived synthetic/`UNMATCHED`
  line.** R3's `is_synthetic()` predicate is still not wired as an actual
  submission-blocking gate anywhere (WO-49's own docstring already flags
  this as a gap for a future consumer) — this order does not close it; it
  only makes sure a WAIVED supplier's synthetic lines never appear in the
  first place. An unwaived `UNMATCHED` line today still freezes and locks
  along with everything else, unchanged from before this order (a real,
  pre-existing gap, not introduced by this order, and not this order's
  scope to fix — it belongs to whichever future order finally wires
  `is_synthetic()` into the lock/checklist gate the way R3's own docstring
  says it must).
- **G2.9 (fee freezing)** — still decision-gated (`docs/DECISIONS-NEEDED.md`
  §10), untouched.
- Any `api/routes/transport/*` route, any UI. `set_waiver`/`remove_waiver`
  are service functions only, same as every prior transport slice.

### Implementation guidance

1. **The document-presence gate reads the claim's own MATERIALIZED lines,
   never the caller-supplied `invoices` tuple list `submit_claim` still
   takes.** `submit_claim`'s `invoices` parameter and `vat_claim_lines` are
   still two independent things (WO-57's own docstring: "still never derived
   from `vat_claim_lines`... a future slice will derive it automatically").
   The thing that actually gets FROZEN as the claim's content is the lines
   table (`freeze.freeze_claim_lines` sums `VatRefundClaimLine` rows, never
   the `invoices` tuple), so R10 must check DOCUMENT PRESENCE against that
   same authoritative source — the claim's currently-unfrozen lines with a
   resolved `invoice_id` — not against the caller-supplied tuple list. This
   also means R10 needs no new coupling to `submit_claim`'s existing
   parameter shape.
2. **`app.services.extraction.invoice_ids_with_documents` is the ONE new
   read seam transport is allowed to add** — `tests/test_boundaries.py::
   test_transport_services_do_not_import_other_domain_models` forbids
   `services/transport/*` from importing `app.models.extraction_run`
   directly (or any AP-domain model); it must read through a service
   function, exactly like `invoice_match.py`'s existing `app.services.
   invoices`/`app.services.vendors` imports. Batch it as ONE query
   (`WHERE invoice_id IN (...) AND source_sha256 IS NOT NULL`) — never a
   loop calling `list_for_invoice` once per invoice (the N+1 `docs_index()`
   was explicitly built to avoid in Fleet Fuel).
3. **Waiver grain is `(org, claim, supplier)` — narrower than the harvested
   `(entity, refund_country, ref_period, supplier)`.** Since a claim's own
   grain already IS `(entity, refund_country, ref_period)` (G2.1's own
   uniqueness), pointing the waiver at `claim_id` via a composite FK gets
   the identical key with one column instead of three, and ties the waiver's
   lifecycle to the claim it belongs to (mirrors why `vat_claim_lines`
   points at `claim_id` rather than re-deriving the grain per row).
4. **`set_waiver`'s refusal reuses `invoice_match.registered_invoices` —
   never re-derives "does this supplier have a registered invoice" as a
   second implementation.** This is the same drift-prevention discipline
   `is_synthetic()`/`derive_product_group()`/`derive_goods_code()` all
   follow: one function computes "registered invoices for (supplier,
   refund_country)", every consumer (resolution, override validation, now
   waiver validation) calls that one function.
5. **Exclusion in `build_claim_lines` happens BEFORE the resolution/grouping
   loop, not as a post-filter on the built groups.** A waived supplier's
   transaction must never even be handed to `invoice_match.
   resolve_invoice_ref` — C9's "excluded from the claim by construction"
   means it never touches the resolution machinery, the `claim_set`, the
   locks, the doc-gate or the frozen VAT base at all. Fetch `waiver.
   waived_suppliers(db, org_id, claim.id)` once, then `continue` past any
   transaction whose `.supplier` is in that set, before the existing
   grouping logic runs.
6. **The waiver status_note stamp happens once per submission, listing
   EVERY waiver currently on the claim** (not just ones that "mattered" this
   time) — simplest faithful reading of C9 that doesn't require tracking
   per-waiver "was this actually used" state. Format:
   `"Receipt-control waiver applied: <supplier1>, <supplier2> (no registered
   invoice for <refund_country>)"`, appended to `status_note` the same way
   the R8 override note already is (newline-joined if a note already
   exists).
7. **Gate order inside `submit_claim`** (extends D5, matching what WO-56/57
   already established): status=draft -> non-empty `invoices` -> R7
   period-end -> R8 minimum (+ override note) -> R6 mop-up/duplicate-block
   (narrows `invoices`) -> **R15 waiver note stamp** -> **R10 document-
   presence gate** -> G2.5 freeze -> lock acquisition -> status flip ->
   flush -> audit. Nothing mutates before R10 passes (module docstring
   convention every prior G2.6 slice states explicitly).
8. **`remove_waiver` is new, minor CRUD symmetry, not a harvested
   requirement on its own** — R15 only specifies `add_waiver`'s refusal
   behaviour; an un-waive path is basic administrative correctness (an
   admin who waived the wrong supplier before submission must be able to
   undo it) and is scoped narrowly: only reachable on a `draft` claim,
   mirroring every other pre-submission mutator in this module family.

### Invariants this order must preserve

- **§4.16 (every mutating operation is audited)** — `set_waiver`/
  `remove_waiver` each emit an `AuditEvent`; the document gate performs no
  write (a pure check), so it needs none.
- **§4.4 (opaque 404, never 403)** — `waiver.py`'s `_get_claim` mirrors
  `lock.py`/`claim_lines.py`'s own org-scoped lookup exactly.
- **ADR-P3 rule 2 (transport reads the core through services, never a raw
  model join)** — proven by the pre-existing
  `test_transport_services_do_not_import_other_domain_models`, extended by
  this order's new `extraction.invoice_ids_with_documents` seam.
- **R3's `is_synthetic()` centralization is untouched** — this order adds
  no second synthetic-detection implementation; waiver eligibility is
  checked via "does the supplier have a registered invoice", a different
  question answered by the pre-existing `registered_invoices`.
- **Master-context §4.2 (no new tenant table without RLS in the same
  migration)** — `vat_receipt_waivers` ships RLS in its own migration,
  proven by `test_rls.py::test_rls_migration_covers_every_tenant_table`.

### Database / migration impact

One new tenant table, `vat_receipt_waivers`: `org_id`, `claim_id` (composite
FK `(org_id, claim_id) -> vat_refund_claims(org_id, id)`, `ondelete=CASCADE`
— a waiver has no meaning once its claim is gone), `supplier` (String(60)),
`id`, `created_at`/`updated_at`. `UniqueConstraint(org_id, claim_id,
supplier)` — a second `set_waiver` call on the same key is a no-op, not a
duplicate row. RLS (`ENABLE`/`FORCE ROW LEVEL SECURITY` + the standard
tenant-isolation policy) lands in the SAME migration. No column changes to
any existing table. Downgrade drops the table and its RLS policy — safe
(a rolled-back deploy simply has no waiver history; nothing else reads this
table).

### Testing requirements

`backend/tests/transport/test_g2_6_document_gate.py`:
- a claim line resolved to a real invoice WITH a linked, hashed capture
  passes the gate (no raise);
- a claim line resolved to a real invoice with NO linked capture at all
  raises `ConflictError` (409, `code="invoice_document_missing"`), naming
  the invoice number;
- a claim line resolved to a real invoice whose ONLY linked capture has a
  NULL `source_sha256` (a manually-typed invoice, never actually captured
  from a file) is treated as missing a document too;
- an `UNMATCHED` line (`invoice_id IS NULL`) is invisible to this gate —
  a claim with only unmatched lines and no real invoices passes trivially;
- `submit_claim` end-to-end: a claim whose only real invoice line has no
  document is refused before the freeze (lines stay unfrozen, claim stays
  `draft`); attaching the document then lets the exact same submission
  succeed.

`backend/tests/transport/test_g2_6_waiver.py`:
- `set_waiver` succeeds for a supplier with zero registered invoices for
  the claim's refund country;
- `set_waiver` REFUSES (422, `code="waiver_supplier_has_invoices"`) a
  supplier that HAS >=1 registered invoice for that country, message
  containing "note-matching fix";
- `set_waiver` is idempotent — a second call with the same
  (claim, supplier) key returns the existing row, no duplicate;
- `set_waiver`/`remove_waiver` both refuse (409, `code="claim_not_draft"`)
  on a non-draft claim;
- `remove_waiver` un-waives, returning `True`; a second call returns
  `False` (nothing left to remove);
- `submit_claim` end-to-end: a claim with one waived supplier's synthetic
  transaction and one normal registered-invoice transaction submits
  successfully with `status_note` containing "Receipt-control waiver
  applied" and the supplier's name; the frozen `vat_eur` reflects ONLY the
  non-waived transaction's VAT (the waived supplier's amount never counted).

`backend/tests/transport/test_g2_4_claim_lines.py` (extended): a waived
supplier's transaction produces ZERO claim lines (not even an `UNMATCHED`
one) alongside a normal supplier's transaction producing its usual line.

### Acceptance criteria (verifiable checklist)

- [ ] A claim line's invoice with zero linked, hashed captures blocks
      `submit_claim` with 409 `invoice_document_missing`, naming the
      invoice number, before anything freezes or locks.
- [ ] The same claim submits successfully once >=1 capture with a real
      `source_sha256` is linked to that invoice.
- [ ] An `UNMATCHED` line never triggers the document gate (it has no
      `invoice_id`).
- [ ] `set_waiver` on a supplier with a registered invoice for the claim's
      refund country is refused (422 `waiver_supplier_has_invoices`); on a
      supplier with none, it succeeds.
- [ ] A waived supplier's transactions produce ZERO claim lines (not an
      `UNMATCHED` line) when `build_claim_lines` runs.
- [ ] `submit_claim` on a claim with an active waiver stamps
      `status_note` with "Receipt-control waiver applied" + the supplier
      name, and the frozen `vat_eur` excludes the waived supplier's amount.
- [ ] `remove_waiver` un-waives on a draft claim; both `set_waiver` and
      `remove_waiver` refuse on a non-draft claim (409 `claim_not_draft`).
- [ ] `vat_receipt_waivers` carries RLS in its own migration; `test_rls.py`
      set-equality check stays green.
- [ ] Full backend suite green on SQLite; the 7 pg-only RLS/concurrency
      test files pass together on a scratch Postgres 16 cluster; `mypy app`
      clean; `ruff` clean; `alembic upgrade head && alembic check` clean.

### Rollback strategy

Code revert: remove `document_gate.py`, `waiver.py`, the `receipt_waiver.py`
model, and their call sites in `claim_lines.py`/`lock.py`. Migration
downgrade drops `vat_receipt_waivers` and its RLS policy — safe, no other
table references it, and dropping it loses only waiver history (a claim
with a dropped waiver simply reverts to treating that supplier's synthetic
lines as ordinary `UNMATCHED` ones on the next `build_claim_lines` call).
No kill switch needed for a production incident: the `transport` module
stays default-OFF and absent from every plan's module set, so none of this
is reachable by any tenant regardless of code presence.
