# WO-57 — G2.6 slice 2: annual mop-up + quarterly duplicate-block (board G2.6, R6)

<!-- ═══════════════ COPY FROM HERE: WO-57 ═══════════════ -->

**WORK ORDER 57 — G2.6 slice 2: the annual claim mop-up + quarterly overlap
duplicate-block (R6). Effort M (3-5d). Priority P0. Milestone M3. Depends
on: WO-56 (G2.6 slice 1 — period-end + minimum gates, whose gate order this
order extends).**

### Objective and business value

WO-56 landed the period-end and minimum gates but `submit_claim` still
accepted an `invoices` list without checking whether ANY of those invoices
were already locked by a DIFFERENT claim — the only backstop was the raw DB
UNIQUE constraint, surfacing as an opaque `IntegrityError` regardless of
WHY the overlap happened. Verified at HEAD=`7f15a20` (this order's baseline,
1352 passed/10 skipped): `app/services/transport/lock.py` has no logic
distinguishing "this invoice belongs to a quarter the annual claim should
mop up" from "this is a genuine duplicate submission." `BA_fleet_fuel.md` C6
is explicit: *"An annual claim is the MOP-UP, not the whole calendar year. A
`-YEAR` claim EXCLUDES invoices already locked to a quarter (not a conflict
— `continue`); a QUARTERLY claim treats any overlap as a duplicate and
BLOCKS. If a yearly claim has an empty `claim_set` → BLOCKED - nothing to
claim annually."*

Who pays more without this: without the mop-up exclusion, an annual claim
that legitimately tries to sweep up whatever a quarter DIDN'T already claim
would instead crash with a raw `IntegrityError` the moment it touched ANY
quarter-locked invoice — making the annual "mop-up" pattern (Fleet Fuel's
own design for catching invoices no quarterly claim got to) unusable in
practice. And without the quarterly duplicate-block being a CONTROLLED
check (rather than relying on the raw DB exception), a legitimate quarterly
resubmission attempt gets an opaque low-level error instead of a clear,
typed one naming which invoice(s) collided.

### Scope

**In scope**
- `app.services.transport.lock._apply_annual_mop_up_or_duplicate_block` —
  for an ANNUAL (`-YEAR`) claim: silently excludes (from the set to lock)
  any invoice already locked by a QUARTERLY claim; treats an invoice already
  locked by ANOTHER ANNUAL claim as a blocking duplicate (fail-closed
  interpretation, see Implementation guidance §1); refuses
  (`code="empty_claim_set"`) if nothing is left after exclusion. For a
  QUARTERLY claim: ANY existing lock overlap on the caller-supplied
  `invoices` list blocks the WHOLE submission
  (`code="duplicate_invoice_lock"`, 409) before any freeze/lock write.
- Wired into `lock.submit_claim`'s gate order, after R7/R8, before the
  freeze — matching D5's overall ordering (checklist → period-end →
  minimum → the duplicate/lock machinery).
- One pre-existing WO-51 test updated to match the NEW, cleaner error path
  (see Implementation guidance §2) — not a weakened assertion, a real
  improvement in what gets proven.

**Out of scope** (explicitly, future M3 work orders)
- **R10 (document-presence gate)**, **R15 (receipt-control waivers)** — the
  remainder of the G2.6 stack; each needs its own new query/table and is a
  separate slice (flagged as WO-58+).
- **G2.9 (fee freezing)** — still decision-gated, untouched.
- **Deriving `submit_claim`'s `invoices` argument from the claim's own
  frozen lines automatically** — still a caller-supplied list; the
  reconciliation between "what the caller says to lock" and "what the
  claim's own materialized lines say" remains a documented future
  concern, not solved by this order.
- **Any `api/routes/transport/*` route**, **any UI**.

### Implementation guidance

1. **The annual-vs-annual overlap case is a documented INTERPRETATION, not
   given verbatim.** `BA_fleet_fuel.md` C6 only describes excluding a
   QUARTER's lock from an annual mop-up; it never addresses what happens
   when the EXISTING lock belongs to another ANNUAL claim (a genuine
   annual-annual duplicate, e.g. two different years' claims somehow
   targeting the identical invoice key, or a data error). This order
   treats that case as a blocking duplicate — fail-closed, matching the
   same discipline `is_synthetic()`'s docstring states explicitly (never
   invent a match; refuse rather than guess).
2. **Updating the one WO-51 test is a real improvement, not a weakened
   assertion (master-context §9).** `test_g2_2_submit_claim_on_an_already_
   locked_invoice_...` seeded an existing lock directly then called
   `submit_claim`, expecting a raw `IntegrityError` at flush. With R6's new
   pre-check, this EXACT scenario (a same-session, already-committed
   duplicate) is now caught BEFORE any mutation with a clean, typed
   `ConflictError` — strictly better UX, and the test's core property
   (claim status unchanged) still holds, now because nothing was ever
   touched rather than because a rollback discarded a partial write. The
   test was renamed and its exception type updated; the raw DB-constraint
   proof lives on unchanged in `test_g2_2_natural_key_uniqueness_
   constraint_rejects_a_raw_duplicate_insert`, and the genuine-race proof
   in `tests/test_transport_lock_concurrency.py`.
3. **The pre-check does NOT replace the DB-level race backstop.**
   `_existing_locks_by_key` is a plain SELECT with no locking read — two
   truly concurrent submissions can both see "no existing lock" before
   either commits, so the plain-INSERT + UNIQUE-constraint mechanism (R4,
   WO-51) remains the actual concurrency guarantee. This order's pre-check
   only improves the ALREADY-COMMITTED-duplicate case (the common,
   non-racing scenario); re-verified on real Postgres (scratch cluster,
   torn down after use) that `test_transport_lock_concurrency.py` still
   passes unchanged.
4. **Scoped to (entity, refund_country), matching every other lock query.**
   `_existing_locks_by_key` filters on `org_id`+`entity_id`+`refund_country`
   — an identical `invoice_ref` locked under a DIFFERENT entity is not an
   overlap at all (proven by `test_g2_6_annual_mop_up_never_touches_a_
   different_entitys_locks`).

### Invariants this order must preserve

- **§4.6 (concurrency: exactly one wins, the loser's state is unchanged)**

### Testing requirements

`backend/tests/transport/test_g2_6_annual_mop_up.py` (5 tests): an annual
claim excludes a quarter-locked invoice without conflict and still locks a
genuinely new one; an annual claim with nothing left after exclusion is
refused (422 `empty_claim_set`, claim stays draft); a quarterly claim
blocks the WHOLE submission on any overlap (409 `duplicate_invoice_lock`,
NOTHING locked, not even the genuinely-new invoice); two annual claims
overlapping the same invoice is a blocking duplicate (the fail-closed
interpretation); the lookup never crosses entity boundaries.

`backend/tests/transport/test_g2_2_lock.py`: the updated test proves the
claim status stays `draft` after the new, cleaner refusal.

### Acceptance criteria (verifiable checklist)

- [x] An annual claim's invoice list, containing both a quarter-locked
      invoice and a new one, submits successfully with only the new one
      locked.
- [x] An annual claim whose ENTIRE invoice list is already quarter-locked
      is refused (422 `empty_claim_set`) rather than submitting with zero
      locks.
- [x] A quarterly claim overlapping ANY existing lock is refused (409
      `duplicate_invoice_lock`) with NOTHING locked — not a partial lock of
      the non-overlapping invoices.
- [x] Two annual claims targeting the same invoice key: the second is
      refused as a duplicate, never silently excluded.
- [x] The lookup is scoped per (entity, refund_country) — an identical
      invoice_ref under a different entity never collides.
- [x] The one updated WO-51 test still proves "claim status unchanged after
      a refused submission," now via the new, cleaner exception path.
- [x] Full backend suite green on SQLite; the 7 pg-only RLS/concurrency
      test files pass together on a scratch Postgres 16 cluster (re-run
      after this order's lock.py changes); `mypy app` clean; `ruff` clean;
      no migration to check.

### Rollback strategy

Code-only revert: remove `_apply_annual_mop_up_or_duplicate_block` and its
call site from `submit_claim`; revert the one WO-51 test back to its
`IntegrityError` expectation. No migration to downgrade (none created). No
kill switch needed for a production incident: the `transport` module stays
default-OFF and absent from every plan's module set, so `submit_claim` is
unreachable by any tenant regardless of code presence.
