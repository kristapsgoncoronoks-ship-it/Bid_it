## Implementation guidance

1. **`mailgun.py` first, as pure functions** (no I/O, trivially unit-testable):
   - `verify_signature(token: str, timestamp: str, signature: str, signing_key: str) -> bool`: HMAC-SHA256 over `timestamp + token`, keyed by `signing_key`, compared to the hex-decoded `signature` via `hmac.compare_digest` (never `==` — timing-safety, mirroring the existing shared-secret comparison in `email.py::inbound`).
   - `is_fresh(timestamp: str, *, max_age_seconds: int = 300) -> bool`: parse `timestamp` as a Unix epoch int; reject (return `False`) if missing/unparsable/in the future beyond a small clock-skew allowance/older than `max_age_seconds`. This is replay protection Mailgun's own docs recommend — a captured valid signature must not be replayable indefinitely.
2. **The route.** Accept the request as `Request` (Mailgun's field count varies — `attachment-count` tells you how many `attachment-N` file parts to expect; iterating a fixed schema is more transparent than a generic form scan, so read `attachment-count` and loop `1..count`). Build the SAME rejection story as the existing endpoint:
   - No `mailgun_signing_key` configured → `_inbound_auth_failed()` (reuse the existing helper — byte-identical response, so the two auth mechanisms are indistinguishable to a prober).
   - Missing `timestamp`/`token`/`signature` fields, bad signature, or stale timestamp → `_inbound_auth_failed()`.
   - Token-to-org resolution via `email_intake.token_from_address(recipient)` then `email_intake.resolve_org` — unknown token → `_inbound_auth_failed()` (same generic 401; never a distinguishable 404, preserving the existing enumeration-safety property for the recipient-token space).
   - Module gate (`email_intake` enabled for the resolved org) → mirror the generic endpoint's explicit 403 (this one CAN be distinguishable, because at this point the caller already proved knowledge of a valid recipient token + a valid Mailgun signature — same behaviour as the generic endpoint today).
   - Per attachment: read bytes via `await file.read()`, call `email_intake.process_attachment(db, org_id, from_addr=sender, subject=subject, filename=file.filename, content_type=file.content_type, content=content)`. Commit once at the end (mirrors the generic endpoint's one-commit-per-message shape).
3. **Money/rounding:** none — no currency touched by this order.
4. **Gate fail-open/closed statement:** the whole route fails **CLOSED** — an unset signing key, a bad/missing signature, a stale timestamp, or an unknown recipient token all produce the identical 401 and persist nothing. This mirrors B1.6's "an unset secret must never silently open a document-injection door" invariant, extended to the second provider path.
5. **`PUBLIC_ROUTES`:** add `("POST", "/api/v1/email/inbound/mailgun")` with a justification string in the same voice as the existing `/api/v1/email/inbound` entry (its own HMAC signature is the authentication).

## Invariants this order must preserve

- **§4.19 (AI)** — not touched; this is deterministic parsing plumbing, no AI in the path.
- **Tenant isolation (§4.1)** — the new route resolves `org_id` exactly the way the existing generic inbound endpoint does (`token_from_address` → `resolve_org`, unscoped-by-design because the webhook itself is unauthenticated-by-tenant); every downstream call (`process_attachment`, `documents.store`, `jobs.enqueue`) is scoped to that resolved `org_id`, identical to the shipped path. No new query bypasses tenant scoping.
- **Opaque failure (§4.4, extended)** — a bad signature and an unknown recipient token return the SAME response as a missing secret; the route must not let a caller distinguish "real tenant, wrong signature" from "no such tenant" (mirrors the existing `_inbound_auth_failed()` contract, reused rather than reimplemented).
- **§4.16 (audit)** — no NEW mutation type is introduced (attachment intake already isn't separately audited beyond the existing `InboundInvoice` row + the confirm-time `audit.record` call in `confirm_inbound`, unchanged by this order).
- **Upload security** — every attachment still passes through `filesec.check` inside `process_attachment` before any byte is stored; this order adds no path that bypasses it.

## Testing requirements

`backend/tests/test_email_provider_mailgun.py`:
- `test_mailgun_valid_signature_queues_attachment` — a correctly HMAC-signed, fresh request with a valid recipient token and one attachment returns 200 and the attachment appears in `GET /email/inbox` for the resolved org.
- `test_mailgun_bad_signature_rejected` — same request, signature recomputed with the wrong key → 401, `_inbound_auth_failed`-shaped body, **no** `InboundInvoice` row created.
- `test_mailgun_stale_timestamp_rejected` — valid signature over an old timestamp (beyond the freshness window) → 401, nothing persisted (replay protection).
- `test_mailgun_signing_key_unset_fails_closed` — `settings.mailgun_signing_key = None` → 401 even with an otherwise-perfect request (mirrors B1.6's "unset secret never silently opens the door", extended to this path).
- `test_mailgun_unknown_recipient_token_rejected` — valid signature, but the recipient's local-part matches no org's `EmailIntake.token` → 401, **same response shape** as the bad-signature case (enumeration-safety negative assertion — assert response bodies are byte-identical across the two failure modes).
- `test_mailgun_sender_is_never_the_tenant_signal` — two orgs A and B; a request whose `recipient` carries **org A's** token but whose `sender`/`from` field is spoofed to look like it belongs to org B lands the attachment in **org A's** inbox, never B's (the adversarial case the docstring already promises for the generic endpoint, now proven for this adapter too).
- `test_mailgun_module_disabled_returns_403` — resolved org has `email_intake` module off → 403 (parity with the generic endpoint's existing behaviour).
- Plus pure unit tests in the same file (or inline) for `mailgun.verify_signature` / `mailgun.is_fresh` covering the boundary: signature exactly right/one-byte-wrong; timestamp exactly at the freshness boundary/one second past it.

## Rollback strategy

Pure code addition — no migration, no data written by the mere existence of the route. Revert is a plain code revert (delete the new route, the new module, the new `PUBLIC_ROUTES` entry, the new config field). Nothing is one-way: no session is revoked, no data is transformed, no existing endpoint's behaviour changes. The narrow mitigation short of a full revert is simply leaving `mailgun_signing_key` unset in any environment — the route then 401s unconditionally and is inert.
