# WO-61 — G3.1 slice 1: the per-country supplier legal-entity registry (board G3.1, R21/R22)

**WORK ORDER 61 — G3.1 slice 1: `supplier_vat_registrations` — marker-only
per-(supplier, country) legal-entity registration + the per-country
learning rule. Effort M (3-5d). Priority P0. Milestone M3. Depends on:
G1.2 (WO-50, `fuel_transactions` — satisfied), A2.3 (WO-2, vendor bank-
detail second-approver control — satisfied, confirms the codebase's
existing "curated data is never silently clobbered" discipline this order
extends to a new table).**

### Objective and business value

Verified at HEAD=`86c5024` (this order's baseline, 1393 passed/10
skipped): there is no `supplier_vat_registrations` table and no per-
(supplier, country) legal-entity concept anywhere in `app/models/
transport/` or `app/services/transport/`. `BA_fleet_fuel.md` R20-R22 is
explicit that a multi-entity fuel-card network (Eurowag, E100) issues a
DIFFERENT local legal entity per country it operates in, and the claim
must be filed under the entity that actually printed the invoice — never
a buyer, never a factoring/receivables entity a network cedes its
invoices to.

Who pays more without this: filing a VAT reclaim naming the WRONG seller
entity (e.g. a Czech factoring company instead of the Belgian entity that
actually issued the invoice) is a defect a refund authority can reject on
sight — the claim fails on a technicality unrelated to the underlying
spend being genuinely recoverable. And without marker-only matching (no
fuzzy auto-pairing), a similarity heuristic could silently misattribute an
entity, the kind of quiet, hard-to-audit error the codebase's other
matching engines (`invoice_match.resolve_invoice_ref`) deliberately avoid
by falling to `UNMATCHED` rather than guessing.

### Scope

**In scope**
- `supplier_vat_registrations` (new tenant table): `(org, supplier,
  country)` -> `vat_number`, `entity_name`, `source` (`"admin"` |
  `"capture"`). `app.services.transport.supplier_entity`:
  `get_registration` (read), `set_registration` (the ONLY admin-curated
  writer — `source="admin"`, upserts on the key, ALWAYS wins), `learn_
  registration` (the per-country LEARNING function, R22 — seeds a row
  with `source="capture"` ONLY when no row exists yet for that exact
  (supplier, country); a row that already exists — admin OR
  previously-learned — is NEVER overwritten by learning; the group's
  PRIMARY entity, i.e. `Vendor.name`/`Vendor.country`, is never touched by
  either function).
- Marker-only matching (R21): `get_registration` is a PLAIN key lookup —
  no fuzzy/similarity matching of any kind. There is no other function
  anywhere that assigns a supplier/entity pairing without an explicit
  curated marker or a `learn_registration` call.
- Migration (1 new tenant table, RLS in the same migration).

**Out of scope** (explicitly, future work — G3.1's OWN acceptance test
needs it, but it is a separate, XL-effort, P1 feature, `G3.2` in
`ARCH_plan.md`)
- **Actually reading the seller off a real invoice document** (R20 —
  the Eurowag per-country footer parse, the E100 anchor-to-marker logic).
  That is text/PDF extraction — `G3.2` (the fuel-card parser registry,
  P1, XL, 7 supplier networks with real learned quirks) — a materially
  larger, separate effort this order does not start. This order's R20/R22
  acceptance tests therefore exercise `learn_registration` at the FUNCTION
  level with a synthetic "this is what a parser just extracted" input,
  proving the STORAGE/LEARNING rule's correctness independent of who
  calls it — mirroring exactly how WO-49 shipped `is_synthetic()` as a
  standalone predicate with zero real consumers wired in yet.
- **Wiring `learn_registration` into `fuel_ingest.ingest_transaction` or
  any capture/confirm flow** — no such flow captures a seller name/VAT at
  all yet in this codebase; this order ships the callee, not a caller.
- **The vendor pending-change-request UI/admin surface** for a curated
  marker — `set_registration` is a service function only, same scope as
  every prior transport slice (`waiver.set_waiver`, `checklist.
  set_active`).
- Any `api/routes/transport/*` route.

### Implementation guidance

1. **`entity_name` here means the CAPTURED SELLER's legal name (e.g. "Acme
   Belgium BVBA"), a plain string — NOT a foreign-key to `IssuerProfile`.**
   `IssuerProfile` in this codebase is OUR OWN claimant entity (WO-49's own
   reuse, "our legal entity that bought the fuel"); the fuel-card
   network's per-country SELLER is a different party entirely, one this
   codebase has no existing master-data table for. A plain string is the
   honest shape until/unless a future order decides a full vendor-side
   legal-entity registry is warranted — inventing one now would be scope
   creep beyond what R21/R22 ask for.
2. **`learn_registration`'s "never clobbers a curated value" is proven
   both ways**: seeding when NOTHING exists yet (the common case) AND
   refusing to overwrite an EXISTING row regardless of its own `source`
   (an admin marker is permanent; a previously-learned row is also never
   silently replaced by a later, possibly-conflicting capture — a second
   learn call for the SAME key is a no-op, not an update, so two
   different captures for the same country can never fight over which
   wins).
3. **No pending-change-request is EVER queued by `learn_registration`** —
   unlike `VendorChangeRequest` (A2.3, IBAN/critical vendor fields), a
   per-country SELLER entity is diagnostic/filing metadata, not a payment-
   redirection vector; R22's acceptance line is explicit that a successful
   per-country seed must NOT trigger any pending-approval flow. This is a
   deliberate, stated contrast with A2.3's dual-control model, not an
   oversight.
4. **`get_registration` is a single exact-key SELECT — no normalization,
   no fuzzy matching, no ranking.** If a future order ever wants a
   fallback (e.g. "no country-specific registration — fall back to the
   group's home country"), that is a NEW, explicit function, never a
   silent broadening of this one (R21's own "marker-only... no fuzzy
   auto-pairing").

### Invariants this order must preserve

- **§4.16 (every mutating operation is audited)** — `set_registration` is
  always audited (admin action); `learn_registration` is audited ONLY
  when it actually inserts a new row (a refused/no-op learn call is not a
  mutation).
- **§4.4 (opaque 404, never 403)** — N/A directly (no claim/id lookup by
  a caller-supplied id in this order's functions — both are keyed by
  `(supplier, country)` strings, not an opaque id a cross-tenant guess
  could probe); tenant scoping is still enforced via `org_id` on every
  query, proven by the RLS test.
- **Master-context §4.2 (RLS in the same migration)** — `supplier_vat_
  registrations` ships RLS in its own migration.
- **ADR-P3 rule 2** — no new import of a foreign domain's model.

### Database / migration impact

One new tenant table, `supplier_vat_registrations`: `org_id`, `supplier`
(String(60)), `country` (String(2)), `vat_number` (String(32)),
`entity_name` (String(200)), `source` (String(12): `admin`|`capture`),
`id`, `created_at`/`updated_at`. `UniqueConstraint(org_id, supplier,
country)`. RLS in the SAME migration. Downgrade drops the table — safe,
no other table references it.

### Testing requirements

`backend/tests/transport/test_g3_1_supplier_entity.py`:
- `get_registration` returns `None` for an unregistered (supplier,
  country);
- `set_registration` creates a `source="admin"` row; a second call with
  different `vat_number`/`entity_name` UPDATES it (an admin can correct
  their own curated marker);
- `learn_registration` creates a `source="capture"` row when none exists;
- `learn_registration` is a NO-OP (does not overwrite, returns the
  EXISTING row unchanged) when a `source="admin"` row already exists for
  that exact key — R22's "never clobbering a curated value";
- `learn_registration` is ALSO a no-op against a pre-existing
  `source="capture"` row (a second, possibly-conflicting capture never
  silently wins);
- `set_registration` (admin) DOES overwrite an existing `source="capture"`
  row (curated always wins over learned, in either order);
- learning a DIFFERENT country for the same supplier does not touch the
  first country's row, and never touches `Vendor.name`/`Vendor.country`
  at all (no vendor exists in scope of this order's functions — proven by
  asserting no `Vendor` row is created or altered as a side effect);
- cross-tenant isolation: org A's registration for `(supplier, country)`
  is invisible to org B even with an identical key (same supplier name,
  same country) — the tenancy-parity overlap discipline.

### Acceptance criteria (verifiable checklist)

- [ ] `get_registration` is a marker-only exact lookup — no fuzzy/
      similarity code path exists anywhere in `supplier_entity.py`.
- [ ] `set_registration` always wins (admin-curated), whether creating a
