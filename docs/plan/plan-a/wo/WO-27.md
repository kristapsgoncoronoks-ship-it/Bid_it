**WORK ORDER 27 — Fix the RLS "unscoped" GUC losing its NULL identity after the first
scoped transaction on a pooled connection (board — new, discovered while proving WO-26-R2).
Effort M 3–5d. Priority P0. Depends on: nothing. Blocks: any future test that combines
real Postgres + the full HTTP auth chain + more than one authenticated request on a
shared engine/pool.**

### Objective and business value

Every RLS policy in this codebase (`docs/plan/shared/00_MASTER_CONTEXT.md` invariant
"three isolation layers … database-enforced row-level security keyed to a per-transaction
session variable") is written as:

```sql
USING (current_setting('app.current_org', true) IS NULL OR org_id = current_setting(...))
```

`current_setting(name, true) IS NULL` is meant to mean "the app is running unscoped
(bootstrap / platform-operator / worker-claim path) — bypass". **This is only true on a
virgin Postgres backend connection that has never had the custom GUC touched.** Once
ANY code path issues `SELECT set_config('app.current_org', :org, true)` (the app's
`_sync_rls_org` / `apply_db_tenant`, `app/core/tenant.py`) on a given physical
connection — even once, even for a legitimately-scoped request — `current_setting(name,
true)` **never returns SQL NULL again for the rest of that connection's life**. It
returns the empty string `''` instead. Confirmed empirically on Postgres 16 via psql
(reproduction steps below): neither the transaction ending (COMMIT), nor `RESET
app.current_org`, nor an explicit `set_config('app.current_org', NULL, true)` restores
the NULL state — `''` is sticky for the connection's lifetime.

**Consequence:** on a connection that has EVER served a scoped (authenticated) request,
every subsequent UNSCOPED query against an RLS-protected table returns ZERO rows — not
a cross-tenant leak (it fails toward hiding, not exposing), but a silent, hard-to-debug
correctness/availability defect. Concretely, `get_current_identity`
(`backend/app/api/deps.py`) does its FIRST query — `db.get(User, payload["sub"])` inside
`_authenticate()` — deliberately UNSCOPED (the org isn't known yet), then calls
`set_current_org(user.org_id)` afterwards. On a REUSED, already-scoped connection, that
first query now returns `None` → the request gets a bare 401 "Could not validate
credentials", indistinguishable from a bad token. **This means: on a connection pool
that has been warmed up (i.e., any real deployment under any load — pgbouncer or
SQLAlchemy's own pool), a fraction of otherwise-valid authenticated requests will
intermittently 401 depending only on which physical connection the pool happens to
hand back**, plus any genuinely-unscoped path (bootstrap, platform-operator dashboards,
worker-claim queries) sharing that pool risks seeing empty results the same way.

This was never caught because no existing test combines (a) real Postgres, (b) the
full HTTP dependency-injection auth chain (`get_current_identity`'s two-phase
unscoped-then-scoped pattern), and (c) more than one authenticated request sharing an
engine/pool — `tests/test_rls.py` / `test_numbering_concurrency.py` /
`test_payment_run_pay_concurrency.py` all call services directly with explicit Python
`set_current_org()`, never exercising the unscoped-first-query window through HTTP;
`tests/test_tenancy_parity.py`'s HTTP-level probes run on the default SQLite harness
(no RLS). `tests/test_credit_note_lock_concurrency.py` (WO-26-R2) is the first to
combine all three, and used `NullPool` specifically to avoid tripping this defect while
proving the credit-note lock fix — it does NOT fix or even exercise a fix for this bug.

### Reproduction (verified on scratch Postgres 16, NOSUPERUSER role, 2026-07-27)

```sql
BEGIN;
SELECT set_config('app.current_org', 'orgA', true);
SELECT current_setting('app.current_org', true);  -- 'orgA'
COMMIT;

BEGIN;
SELECT current_setting('app.current_org', true);  -- '' (NOT NULL!)
COMMIT;

BEGIN;
SELECT set_config('app.current_org', NULL, true);  -- explicit NULL doesn't help either
SELECT current_setting('app.current_org', true);   -- still ''
COMMIT;

BEGIN;
RESET app.current_org;                              -- RESET doesn't help either
SELECT current_setting('app.current_org', true);    -- still ''
COMMIT;
```

Also reproduced end-to-end: temporarily patching `app/api/deps.py` /
`app/core/tenant.py` with instrumentation showed `get_current_identity`'s entry GUC
read `None` on the connection's first-ever use, and `''` on the second authenticated
HTTP request that happened to reuse the same connection — `db.get(User, ...)` returned
`None` on that second call solely because of this, not any credential problem.

### Scope

**In scope:**
- A fix in `app/core/tenant.py` (`_sync_rls_org`, `apply_db_tenant`, and/or the RLS
  policy SQL itself) that makes "unscoped" reliably distinguishable from "scoped" on a
  REUSED connection. Two candidate directions (pick one, or a third if research turns
  up something better — this WO does not mandate the mechanism, only the outcome):
  1. **App-side sentinel:** always call `set_config('app.current_org', :value, true)`
     on `after_begin` (never skip when org is None), using a reserved sentinel string
     (e.g. `'__unscoped__'`, guaranteed to never collide with a UUID org id) for the
     unscoped case, and update every RLS policy's `USING`/`WITH CHECK` clause from
     `IS NULL` to `= '__unscoped__'` (or `IS NULL OR = ''` for belt-and-braces —
     confirm which values are actually reachable post-fix and cover exactly those).
  2. **Policy-side fix:** change every policy's NULL check to also treat `''` as
     unscoped: `(current_setting(...) IS NULL OR current_setting(...) = '' OR org_id =
     current_setting(...))`. Simpler (one SQL pattern, no sentinel plumbing) but
     doesn't explain WHY `''` occurs — leaves the underlying Postgres GUC quirk
     implicit rather than engineered around; document the reproduction in the
     migration's docstring either way so a future reader doesn't have to rediscover it.
- A migration touching EVERY existing RLS policy (grep `docs/plan/shared/specs` /
  `alembic/versions/*.py` for `TENANT_TABLES` / `CREATE POLICY` — this WO must enumerate
  the full list, likely 20+ tables given `BA_bidit.md`'s "63 tables" and the tenancy
  parity test's 58-table registry).
- A new pg-only regression test that specifically proves the fix: authenticate via
  HTTP on a SMALL pool (`pool_size=1` or `2`, forcing reuse) with TWO OR MORE
  sequential authenticated requests, asserting the second succeeds — this is the direct
  regression test for the bug this WO fixes (distinct from WO-26-R2's test, which
  sidesteps the bug rather than testing its fix).
- Retrofit `tests/test_credit_note_lock_concurrency.py` (and any other new pg-only
  HTTP-level test written after this WO lands) to use a normal pooled engine instead of
  `NullPool`, once the underlying defect is fixed — `NullPool` was a deliberate,
  documented workaround for THIS bug, not the intended long-term pattern (it defeats
  connection pooling's whole purpose and shouldn't be the template for future tests).

**Out of scope:**
- Any change to the credit-note lock (`WO-26-R2`, already shipped independently).
- Production connection-pool configuration (pgbouncer transaction-vs-session pooling
  mode) — this WO is a code-level fix; a follow-up may want to double-check
  `docs/DEPLOYMENT.md`'s pgbouncer guidance still holds once the mechanism changes.

### Security/correctness invariants this order must preserve

- Every RLS-protected table's isolation guarantee (§4.1) must hold identically before
  and after — `test_rls.py`'s existing cross-tenant probes must stay green unmodified.
- The tenancy set-equality parity test (RLS-policy-tables == TENANT_MODELS, both
  directions) must stay green — if the fix changes the migration file(s) that
  `_rls_migration_tables()` scans, the `TENANT_TABLES` module-level list in each
  migration must still be present and accurate.
- No behaviour change to the SCOPED path (the overwhelming majority of requests) —
  this is purely about correctly recognizing "unscoped".
- Fail CLOSED, not open: if the fix is ambiguous about a genuinely-new state, prefer
  "hide the rows" (today's failure mode) over "expose them" — a regression toward
  leaking would be far worse than the current hiding bug.

### Testing requirements

- The new pg-only regression test described above (2+ sequential authenticated HTTP
  requests on a small/reused pool, asserting the SECOND succeeds) — this is the
  primary proof.
- Full `test_rls.py` + `test_numbering_concurrency.py` +
  `test_payment_run_pay_concurrency.py` + `test_credit_note_lock_concurrency.py` green
  on real Postgres.
- A worker-claim / platform-operator-path test (genuinely unscoped, `org=None`
  throughout) run AFTER a scoped request on the same shared pool, asserting it still
  sees all rows it should — this is the other half of the bug (unscoped paths losing
  visibility, not just re-authentication).
- Full backend suite green on SQLite (no behaviour change there — SQLite doesn't have
  RLS, `_sync_rls_org`/`apply_db_tenant` are no-ops per their own dialect check).

### Rollback strategy

The migration is additive-only in effect (policy SQL replacement, no data/column
change) — a straight `alembic downgrade` restores the prior (buggy) policies. Revert is
low-risk; the bug is a hiding failure, not a leak, so a rollback under time pressure is
safe from a security standpoint even if it's not correctness-complete.
