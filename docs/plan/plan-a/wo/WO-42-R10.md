**WORK ORDER 42 — LocalStorage._path true path-boundary containment (board R10). Effort S 1d. Priority P4. Milestone M0 (functional-audit remediation track). Depends on: nothing.**

### Objective and business value
`backend/app/core/storage.py::LocalStorage._path` gated key containment with a bare
`str(p).startswith(str(self.root.resolve()))` check. This is a classic path-boundary
bug: a key resolving to a *sibling* directory whose name textually extends the root's
(e.g. root=`/data/store` vs a resolved path under `/data/store-evil`) would be wrongly
admitted, since `"/data/store-evil/secret".startswith("/data/store")` is `True` in
Python despite `store-evil` not being inside `store` at all. Confirmed live with a
one-line repro before fixing (see Verification).

The roadmap (`docs/audit/remediation-roadmap.md` R10) correctly notes this is **not
currently reachable** — `LocalStorage` keys are always derived from sha256 + org id
by `storage.content_key`, never from unconstrained input — so this is defense-in-depth
hardening, not an active exploit. It is being closed now because the fix is a one-line,
zero-risk correction to an established security-relevant contract (the same shape of
bug this session already found and fixed for real, live paths — R2's credit-note lock
and R8's SSRF guard), and leaving a known-wrong containment check in a security-adjacent
primitive is exactly the kind of residual a future refactor could turn reachable.

### Scope
**In scope:** `LocalStorage._path`'s containment check; one regression test proving the
old check would have wrongly admitted a sibling directory and the new check rejects it.

**Out of scope:** any other storage backend (`MemoryStorage`, S3/object-storage
adapters — not affected, they do not do filesystem path arithmetic); `storage.content_key`
itself (already correct — sha256 + org id, no traversal risk); R15/R19 (unrelated,
explicitly larger/product-shaped, not started here).

### Acceptance criteria
1. `_path` uses `Path.is_relative_to` (or equivalent true containment check), not a bare string `startswith`.
2. A new test constructs a sibling directory (`<root>-evil`) next to the storage root and proves a key resolving into it is rejected with `StorageError`; the test also demonstrates (via a plain assertion, not by reverting code) that the OLD check would have wrongly allowed it.
3. Existing `test_storage.py` suite (incl. `test_local_storage_rejects_path_escape`) passes unmodified.
4. `ruff check`, `ruff format --check`, `mypy app` all clean.
5. Full backend suite green with no regressions.
