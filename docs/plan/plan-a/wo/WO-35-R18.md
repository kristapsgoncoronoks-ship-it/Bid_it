### Objective and business value

`frontend/src/pages/Billing.tsx`'s `choosePlan` (line 44) calls `change.mutate(planKey)` (or
`checkout.mutate(planKey)` when a paid provider is wired) the instant a plan card's button is clicked —
no confirmation step of any kind. Server-side, `PUT /billing/plan`
(`backend/app/api/routes/billing.py:99-104`) silently disables any currently-enabled, non-core add-on
module the target plan doesn't include (`_reconcile_modules`'s twin in the webhook path,
`backend/app/services/billing.py:125-137`, does the same on a Stripe/EveryPay-driven downgrade). A
Trial→Starter switch, for example, drops `issuing`/`email_intake` (Trial includes
`{issuing, expenses, email_intake, budget}`; Starter includes only `{expenses, budget}` —
`backend/app/services/plans.py:29-39`) with a single click and zero warning. This is the same class of gap
R16 just closed on `Issue.tsx`: `PaymentRuns.tsx` already proves the pattern (`ConfirmDialog` before an
irreversible/consequential action), and `Billing.tsx` had drifted from it.

Who benefits: any org owner (the only role with `BILLING_MANAGE`, `backend/app/core/authz.py:84`) managing
their own subscription. A customer mid-trial who has already issued real invoices via the `issuing` module
could downgrade to save cost and only discover afterward that invoice issuing silently stopped working —
exactly the "commercial-clarity" trust gap `docs/audit/commercial-readiness.md` §7 names as blocking
"Controlled paid pilot" status. Warning them BEFORE the click costs nothing and prevents a support
escalation ("why did issuing disappear?") that erodes trust in a self-serve billing flow the product is
counting on for its core monetisation loop (`00_MASTER_CONTEXT.md` §1).

### Scope

**In scope:**
- `Billing.tsx`: before committing a plan change (either the direct in-app `change.mutate` path or the
  hosted-`checkout.mutate` path — both reconcile modules identically server-side, see above), compute
  which currently-enabled, non-core modules the target plan would drop, using data the app **already
  fetches** (no invented/guessed list): the existing `useModules()` hook (`frontend/src/lib/useModules.ts`,
  backed by `GET /modules` → `ModuleOut[]` with `core`/`enabled`/`name`) compared against the target plan's
  `modules: string[]` already present on each `PlanInfo` in `GET /billing`'s `available_plans`. If the
  computed set is non-empty, show a `ConfirmDialog` (`tone="danger"`) naming every affected module by name
  before calling `change.mutate`/`checkout.mutate`; if empty (upgrade, lateral move, or a downgrade that
  happens not to touch any currently-enabled add-on), proceed exactly as today with no added friction.
- A Playwright e2e spec (`frontend/e2e/billing-downgrade-confirm.spec.ts`) mirroring
  `issue-destructive-actions.spec.ts`'s live-app + `page.route` mocking pattern: confirm/cancel/confirm for
  a downgrade that drops an enabled module, plus a same-page assertion that an upgrade with no module loss
  fires no confirm dialog at all.

**Out of scope:**
- Any backend change. `GET /modules` and `GET /billing` already expose everything the dialog needs (see
  above) — confirmed by reading `backend/app/api/routes/modules.py` and
  `backend/app/schemas/{module,tenancy}.py` before starting. `PUT /billing/plan`'s existing seat/module
  reconciliation logic (`billing.py:92-104`) is correct and unchanged; this WO only adds a client-side
  warning in front of it.
- R5(a) (self-serve billing collects no real payment) and the Enterprise `price_eur=None` self-upgrade
  bypass — both already closed/addressed by WO-31 (R5b) and out of R18's acceptance bar.
- R14 (backup/restore tooling) — explicitly decision-gated per the roadmap; not attempted.
- R17 (Payment Run "Cancel" confirmation, P3 backlog) — a separate, unrelated, non-blocking item.
- Regrouping or otherwise redesigning the plan-card layout — no such requirement in R18's acceptance bar.

### Implementation guidance
1. Import `ConfirmDialog` from `../components/ui` and `useModules` from `../lib/useModules` in
   `Billing.tsx`.
2. Add local state: `const [confirmPlan, setConfirmPlan] = useState<PlanInfo | null>(null)`.
3. Add a pure helper (module-scope or inline) `affectedModules(target: PlanInfo, modules: ModuleInfo[]): ModuleInfo[]` returning `modules.filter(m => !m.core && m.enabled && !target.modules.includes(m.key))`.
4. Change `choosePlan` to take the full `PlanInfo` (not just `key`/`price_eur`, so the module-diff has the
   target's `modules` list to hand) and rename the current body to a `commitPlanChange(p: PlanInfo)`
   helper. `choosePlan(p)`: if `affectedModules(p, modulesInfo.data ?? []).length > 0`, `setConfirmPlan(p)`
   and return; otherwise call `commitPlanChange(p)` directly (preserves today's zero-friction path for a
   plan change that drops nothing).
5. Update the card's `onClick` to call `choosePlan(p)` (the whole plan object is already in scope in the
   `.map`).
6. Render one `ConfirmDialog` (outside the card grid, alongside the existing `{b && (...)}` block): title
   `` `Switch to ${confirmPlan?.name}?` ``, body lists the affected module names (`<ul>`/`<li>` — reuse the
   simple list style already used elsewhere, e.g. `PaymentRuns.tsx`'s dialog bodies), explains they will be
   turned off immediately (or "when the new billing period starts" is NOT accurate here — `PUT
   /billing/plan` applies the plan and reconciles modules synchronously, and the webhook path reconciles on
   the subscription-update event — so say "will be disabled" plainly, no false immediacy claim needed since
   it IS immediate on the in-app path and effectively immediate once payment clears on the checkout path).
   `confirmLabel={`Switch to ${confirmPlan?.name}`}`, `tone="danger"`, `loading={busy}`. `onConfirm`: capture
   `confirmPlan`, `setConfirmPlan(null)`, `commitPlanChange(captured)`.
7. Disable plan-switch buttons while `useModules()` is still loading (`modulesInfo.isLoading`), in addition
   to the existing `current || !isOwner || busy` guard — prevents computing the diff against an empty/stale
   module list and skipping a warning that should have fired.
8. New e2e spec: mock `/auth/me`, `/auth/organizations`, `/billing` (current plan = trial, `available_plans`
   including starter which drops `issuing`+`email_intake`), `/modules` (issuing enabled + one other enabled
   add-on), `PUT /billing/plan`. Assert: (a) clicking "Switch to Starter" does NOT call `PUT /billing/plan`
   immediately — the confirm dialog appears first, naming the dropped module(s); (b) cancelling issues no
   request; (c) confirming calls the endpoint exactly once and the dialog closes; (d) a second scenario
   (or second test) where the target plan drops nothing currently enabled fires no dialog and calls the
   endpoint directly on click.
