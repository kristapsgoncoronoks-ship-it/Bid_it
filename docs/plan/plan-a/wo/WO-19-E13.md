(`E1.4`/`E1.5`, despite living under the same Epic-E heading earlier in the doc, are confirmed **not** M1 — they are listed only in the "Backlog — M4" table at line 1634-1635, so they are correctly excluded from selection.)

Verified evidence for the gap itself (read before writing this order, not assumed):
- `backend/app/api/routes/invoices.py:705` (`upload_invoice`) already computes `sha = extraction.sha256_hex(content)` and stores it on `ExtractionRun.source_sha256` (`backend/app/models/extraction_run.py:53`) — but the value is used **only** for content-addressed storage dedup in `app/services/documents.py::store` (one `Document` row per distinct `(org_id, sha256, kind)`), never queried to warn the uploader.
- `backend/tests/test_intake_slice.py::test_repeated_upload_dedups_and_is_idempotent` (lines 102-140) is the executable proof of the current gap: it uploads byte-identical bytes twice and asserts **both** return `202` with **two** separate `ExtractionRun` rows — i.e. it currently encodes "no re-upload detection" as correct behaviour.
- The sibling capability the plan cites ("bank statements have this") is real and stricter: `app/services/reconciliation.py::import_statement` raises `ReconError("this statement was already imported")` on a SHA-256 match with **no override at all** (route maps it to a bare `409` via `HTTPException`, no stable `code`) — proven by `tests/test_reconciliation.py::test_duplicate_upload_refused`. E1.3 is deliberately weaker (advisory + overridable), matching the different word choice in the plan's E1.3 bullet vs. the "advisory-never-block" wording used for the *different* task E1.4.

## Objective and business value

Today a user who drags the same invoice PDF into the upload widget twice — a common slip (a file sitting in Downloads gets attached to two forwarded emails, a double-click fires two file-picker events, a page refresh resubmits) — gets two independent, unlinked `ExtractionRun` rows and **no signal that anything is amiss**. If both captures are reviewed and confirmed independently (each capture-review screen has no visibility into the other), the org ends up with two `Invoice` rows for the same real-world document. That is not a cosmetic annoyance: it feeds directly into `ap_aging`, payment-run selection, and eventually a real double payment to the vendor — the exact class of loss the product's core AP promise ("stops re-keying invoices … produces an audit-ready financial record") exists to prevent.

Who pays: any AP clerk during the messiest part of their day (a backlog of dragged-in PDFs). A same-day, low-risk fix (no schema change, no new table — `ExtractionRun.source_sha256` already exists and is already populated) closes the gap while deliberately **not** blocking the legitimate case (re-submitting the same PDF on purpose, e.g. after a bad first attempt or for a demo) — the override exists precisely so this is a nudge, not a wall, unlike the harder bank-statement gate.

### Scope

**In scope:**
- `backend/app/services/extraction.py`: new `async def check_duplicate_upload(db, org_id, sha256, *, override: bool) -> None` — the ONE place the rule lives (business logic belongs in the service, not the route). Queries the most recent `ExtractionRun` in the same org with the same `source_sha256` and `status != "failed"` (a failed run captured nothing — retrying with the same bytes is not "the same document already on file"); raises `app.core.errors.ConflictError` with `code="duplicate_upload"` and a human message naming the date and whether the prior capture is still pending review or was already saved to an invoice, **unless** `override` is true or no such run exists.
- `backend/app/api/routes/invoices.py::upload_invoice`: add an `override: bool = False` query parameter (same pattern as `invoice_review.py:794`'s `note: str | None = None` alongside `UploadFile` — FastAPI resolves a bare scalar default alongside a file upload as a query param); call `await extraction.check_duplicate_upload(db, current.org_id, sha, override=override)` immediately after `sha = extraction.sha256_hex(content)` and **before** `documents.store(...)` / `extraction.start_capture(...)` / `access.record_usage(...)` — a blocked duplicate stores nothing, enqueues nothing, and burns no metered upload event.
- `frontend/src/pages/Upload.tsx`: on `onError`, branch on `apiErrorCode(e) === "duplicate_upload"` (the helper already exists, precedent: `PaymentRuns.tsx`'s `already_exported`/`skipped_payees` flows) and show the existing `ConfirmDialog` primitive ("You already uploaded this file" / body = the server message / confirm label "Upload anyway") that retries the **same** `File` object with `override: true`.
- **new** `frontend/e2e/upload-duplicate.spec.ts` (mocked-API pattern, no backend — matches `dashboard.spec.ts`/`cash-position.spec.ts`) asserting: first upload succeeds and navigates to `/captures/:id`; re-uploading the same file surfaces the confirm dialog with the server's message; confirming re-sends with `override=true` in the URL and completes the navigation.
- `frontend/package.json`: add the new spec to the explicit `test:e2e` file list (every functional e2e spec must be enumerated — WO-17's finding).
- `backend/tests/test_intake_slice.py`: extend `test_repeated_upload_dedups_and_is_idempotent` (see "Changed assertions" below) and add new tests for the blocked path, the override path, the tenant-scoping of the check, and the "a failed prior run doesn't count" case.

**Out of scope:**
- Email-intake re-upload detection (`app/services/email_intake.py`, which independently computes its own SHA-256 and creates its own capture flow) — that pipeline has no synchronous user to click "override"; an advisory annotation there (never a block) is plausible future work but is a **second choke point**, not "the upload choke point" the plan names in the singular. Left untouched.
- Fuzzy/scored duplicate detection (amount/date/vendor similarity, cross-supplier) — that is **E1.4**, explicitly M4 backlog (`ARCH_plan.md` line 1634), and already has its own advisory-never-block mechanism in `app/services/duplicates.py` (shipped, unrelated to this order).
- Any change to the bank-statement duplicate block (`app/services/reconciliation.py::import_statement`) — already correct for its own (stricter, no-override) use case; not touched.
- Cross-tenant hash matching — the check is deliberately per-`org_id` (RLS already scopes `ExtractionRun`; a cross-tenant match would leak nothing useful and is explicitly asserted absent, see Testing).
- Any new DB column, migration, or index — `ExtractionRun.source_sha256` + the existing `ix_extraction_runs_org_created` index already support the query at this table's expected scale (a per-tenant SELECT with two equality predicates and an inequality, ordered by an indexed column, `LIMIT 1`).

### Implementation guidance

1. In `app/services/extraction.py`, add the import `from app.core.errors import ConflictError` and `from sqlalchemy import select` is already imported. Add `check_duplicate_upload` near `start_capture` (same "async direct-upload capture" section) with a docstring stating the fail-open/fail-closed choice explicitly: **it fails CLOSED by default** (blocks) because a byte-identical SHA-256 match is a near-certain true duplicate — unlike the fuzzy E1.4 signals, which fail open by design — but the block is **user-escapable** via `override`, which is the entire point of E1.3 existing as a *separate, weaker* gate than the bank-statement one.
2. Query shape (mirrors `reconciliation.import_statement`'s dup query, adds the status exclusion and org-scoping already implicit via `ExtractionRun.org_id`):
   ```python
   dup = await db.scalar(
       select(ExtractionRun)
       .where(
           ExtractionRun.org_id == org_id,
           ExtractionRun.source_sha256 == sha256,
           ExtractionRun.status != "failed",
       )
       .order_by(ExtractionRun.created_at.desc())
       .limit(1)
   )
   ```
3. Message: `f"You already uploaded this file on {dup.created_at.date().isoformat()}"` + `" and it was saved to an invoice."` if `dup.status == "saved"` else `" and it's still pending review."` + `" Upload it again if this is intentional."`. Keep it a single string — the wire contract (§4.20) is `{"detail","code"}` only; do not add extra JSON fields to the error body.
4. In `invoices.py::upload_invoice`, insert the check **after** `sha = extraction.sha256_hex(content)` and **before** `await documents.store(...)`. Confirm by reading the surrounding function that nothing between those two lines needs to move.
5. Frontend: change `Upload.tsx`'s mutation input from a bare `File` to `{ file: File; override?: boolean }`; build the query string only when `override` is true (`?override=true`) — do not send `override=false`, keep the default request identical to today's for the non-duplicate path (no behavioural change for the 99% case). Add local state for the pending duplicate (`{ file: File; message: string } | null`) and one `ConfirmDialog` (`tone="danger"`, `confirmLabel="Upload anyway"`) — the existing `<label>`/file-input structure and the plain-error banner both stay for every other error.
6. Playwright spec: use `page.setInputFiles()` on the hidden file input (Playwright supports this without a real filesystem read of arbitrary content via `{ name, mimeType, buffer }`), intercept `**/api/v1/invoices/upload*` with `page.route`, and branch the mocked response on whether the intercepted request URL contains `override=true` — first call → `409 {"detail": "...", "code": "duplicate_upload"}`, second (post-confirm) call → `202 {"extraction_run_id": "...", "status": "queued"}`.

### Invariants this order must preserve

- **§4.20 (frozen wire contract)** — the new failure path is `{"detail": "<message>", "code": "duplicate_upload"}` via the existing global `AppError` handler (`app/main.py::_app_error_handler`) — no new response shape, no bespoke JSON envelope carrying structured duplicate metadata.
- **§4.1-4.4 (tenancy)** — the duplicate query is scoped by `ExtractionRun.org_id == org_id` (the caller's own org from `CurrentUser`); a cross-tenant identical upload must NOT be blocked or referenced (proven by a new test, not asserted by inspection alone).
- **Layering (§3)** — the rule lives in `app/services/extraction.py` (a service), not inline in the route; the route stays a thin controller (parse the query param → call the service → let `AppError` propagate to the existing global handler).
- **No new mutation needs `audit.record`** — creating an `ExtractionRun` capture-lineage row was never audited before this order (capture is provenance, not a financial mutation; audit starts at invoice save/confirm elsewhere in the pipeline) and this order does not change that posture. Explicitly noted here per the master-context "why" rule so a reviewer doesn't read the omission as an oversight.
- **§4.19 (AI)** — not applicable; no AI is involved in this check (pure content-hash equality).

### Database / migration impact

None. `ExtractionRun.source_sha256` and `ix_extraction_runs_org_created` already exist and already carry the values this order queries; no new column, table, or index.

### Testing requirements

All in `backend/tests/test_intake_slice.py` unless noted, using the existing `_file`/`_org_id`/`_drain` helpers already defined in that module:

- `test_repeated_upload_dedups_and_is_idempotent` — **extend, do not weaken** (see "Changed assertions" below): the second call must now pass `params={"override": "true"}` to keep asserting the pre-existing storage-dedup + idempotent-enqueue behaviour; add one new assertion that the response `status_code == 202` for the *overridden* second call.
- **new** `test_duplicate_upload_blocked_without_override` — upload identical bytes twice with no `override`; assert the second response is `409` with `code == "duplicate_upload"` and `"already uploaded"` in `detail`; assert exactly **one** `ExtractionRun` row exists for the org (the blocked attempt created nothing) and exactly one `Document` row (storage was never touched).
- **new** `test_duplicate_upload_override_allowed` — same as above but the second call passes `override=true`; assert `202` and **two** `ExtractionRun` rows (mirrors the extended idempotency test but as a standalone, minimal case a reviewer can read without the storage/job-queue assertions).
- **new** `test_failed_upload_is_not_a_duplicate` — upload bytes that fail to parse (reuse the `bad.json`/`[]` fixture from `test_corrupt_file_fails_with_reason_and_can_be_retried`), `_drain(db_session)` so the run reaches `status == "failed"`, then upload the **same bytes again with no override** — assert `202` (a failed capture must not require an override to retry) and that a **second** `ExtractionRun` row now exists.
- **new** `test_duplicate_upload_is_tenant_scoped` — org A uploads a file; org B (registered fresh, mirroring `test_cross_tenant_capture_access_denied`'s pattern) uploads byte-identical content with no `override` — assert `202`, not `409` (the adversarial cross-tenant case per master-context §8: identical-looking data across tenants must never leak a signal).
- `frontend/e2e/upload-duplicate.spec.ts` — the confirm-dialog → override → success round trip described above.

### Acceptance criteria (verifiable checklist)
