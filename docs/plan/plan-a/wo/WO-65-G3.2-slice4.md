### Objective and business value

Verified at HEAD=`2d33da6`: `fuel_card_parser._default_parsers()`
registers exactly `[EurowagParser(), E100Parser(), Q8Parser()]`; no DKV
parser exists; `statement_ingest._resolve_line` supports exactly two
conversion paths — EUR-identity (`fx_source="eur"`) and cached-ECB
(`fx_source="ecb"`), refusing everything else. `BA_fleet_fuel.md` §5.1's
DKV row (line 1103) gives the network's harvested quirks verbatim:
*"«Client-EE» AS; SEK/EUR; **semi-monthly**; Swedish fiscal rep; flat
1.30 SEK/L diesel discount; **5.63% service fee** on parking/services;
**trusts the supplier's per-line EUR and pro-rates**."* That last clause
is a MONEY MODEL neither of the three shipped parsers has: DKV's own
statement carries a per-line EUR figure computed by the supplier, and
Fleet Fuel TRUSTED that figure instead of running its own ECB conversion,
pro-rating the remaining amount (the VAT) at the same implied rate. This
codebase already has the exact platform convention for that situation —
`app/models/fx.py::FxSource.stated` ("the document / claimant stated the
conversion"), master-context §4.15's four-value enum verbatim, with a
shipped precedent in `app/services/expenses.py::apply_item_fx` ("the
claimant stated the converted amount... record the implied rate so the
conversion is fully documented") — but no transport code path reaches it:
`fuel_transactions.fx_source` is CHECK-constrained to allow `'stated'`
(WO-50 reused `FX_SOURCE_CHECK` as-is, its docstring says the platform's
4-value enum wins over Fleet Fuel's 3-value one for exactly this kind of
case) yet nothing can ever write it.

Who pays more without this: every DKV statement for the «Client-EE»
entity has no path into the claim engine — and worse, forcing DKV through
the existing ECB branch would REPLACE the supplier's own invoiced EUR
figures with recomputed ones that disagree with the legal document (the
invoice is what a refund state audits against), a silent figure mutation
of exactly the kind master-context §4.10/§4.19 exists to prevent. DKV is
also the last remaining network whose model requires touching the shared
`ParsedFuelLine`/`statement_ingest` contract (TFC/Moeve/BP's quirks are
parser-local arithmetic per `BA_fleet_fuel.md` §5.1), so landing it now
stabilizes the contract G3.3's validation regimes will be built against.

### Implementation guidance

1. **The stated-EUR money model (the reason this slice exists).**
   "Trusts the supplier's per-line EUR and pro-rates" decomposes into
   exactly two rules, both DOCUMENTED INTERPRETATIONS of the harvested
   clause (no worked DKV column layout exists in the spec, same flagging
   discipline as every prior parser's shape choice):
   (a) `net_eur = stated_net_eur` — the supplier's figure is used AS
   GIVEN, never recomputed via ECB (the invoice is the legal document a
   refund state audits against);
   (b) `vat_eur = vat_local * stated_net_eur / net_local` — the VAT
   converts at the SAME implied rate the supplier used for the net
   ("pro-rates"), pure `Decimal`, unrounded until `ingest_transaction`'s
   existing `q2` calls.
   `fx_rate = net_local / stated_net_eur`, quantized to 6 dp for storage
   (matches `expenses.apply_item_fx`'s `_RATE_EXP` precedent and the
   `Numeric(18,6)` column); the pro-ration itself uses the exact ratio,
   NOT the quantized rate, so `vat_eur` stays consistent with the stated
   basis. Guard: the implied rate must be finite and strictly positive —
   `net_local == 0`, `stated_net_eur == 0`, or opposite signs each raise
   `ValidationError(code="fx_stated_inconsistent")` in phase 1 (so the
   whole statement writes zero rows, the existing two-phase guarantee).
2. **Best-effort OFFICIAL-rate freeze.** For a stated line, call
   `fx.resolve_rate(db, currency, txn_date)`: present ⇒ freeze
   `fx_ecb_rate`/`fx_ecb_date` alongside the applied rate (R56: both
   frozen, so a later audit can see how far the supplier's rate drifted
   from the reference); absent ⇒ both stay `NULL` and the line still
   ingests (`BA_fleet_fuel.md` §4.2's own `fx_source` row: "no coverage ⇒
   NULL is stored, never a fabricated pass"). This is the observable
   difference from the ECB branch, and a test must prove a DKV SEK line
   ingests with ZERO cached rates in the whole suite fixture.
3. **The DKV CSV shape.** Marker `"DKV STATEMENT"`; columns `txn_date,
   txn_time,vehicle_ref,station,country,product,qty,currency,net_local,
   vat_local,gross_local,net_eur,invoice_ref` (Eurowag's shape + the one
   `net_eur` column). EUR-currency row: `net_eur` must equal `net_local`
   exactly (a mismatch is a malformed row — abort the whole statement,
   code path shared with every other malformed-row case); the parser then
   sets `stated_net_eur=None` so EUR rows ride the untouched identity
   branch. Non-EUR row: `stated_net_eur = net_eur` as read. Same
   malformed-row-aborts-statement discipline as all three prior parsers.
4. **No entity detection, ever, for DKV.** Mirror `q8.py` exactly: no
   scan exists in the module; `entities == []` unconditionally; ONE
   warning per parse using the "not implemented for this network"
   wording; an adversarial test plants a `"DKV Euro Service ... VAT:
   SE..."`-shaped decoy line and asserts `entities` stays empty.
5. **Registration.** `_default_parsers()` appends `DKVParser()` fourth.
   Four distinct literal first-line markers ⇒ registration order remains
   provably irrelevant; the new suite's dispatch test covers all four
   networks in one test, and WO-62/63/64's suites must pass byte-for-byte
   unmodified (they assert their own networks' dispatch, not the list's
   length — verified before writing this order).

### Invariants this order must preserve

- **§4.9 (Decimal, never float)** — the pro-ration and implied rate are
  pure `Decimal`; the ONE rounding point stays `ingest_transaction.q2`
  (plus the 6-dp rate quantization for the storage column, mirroring
  `expenses`).
- **§4.10 (the server recomputes every total — EXCEPT where the document
  is the source of truth)** — the deliberate, loudly-documented exception:
  a stated conversion trusts the LEGAL DOCUMENT's figure and records the
  implied rate + the official reference for audit, exactly the
  already-shipped `FxSource.stated` convention (`expenses.apply_item_fx`,
  ADR-0010). Nothing client-supplied is trusted — the figure comes off
  the parsed statement document itself.
- **§4.14/§4.15 (one FX convention; refuse, never guess)** — the implied
  rate is foreign-units-per-1-EUR and converting divides; an inconsistent
  stated pair REFUSES (`fx_stated_inconsistent`) rather than guessing;
  missing ECB coverage on a stated line stores `NULL` reference fields,
  never a fabricated rate — and never silently downgrades to a guess.
- **Tenancy (§4.1-4.5)** — same two adversarial shapes every transport
  slice proves (cross-tenant opaque 404, overlapping-data isolation),
  proven again for DKV's statement shape.
- **§10 (no invented functionality)** — discount/fee verification,
  cadence enforcement and entity detection are refused in "Out of scope"
  with their owning board ids, not silently attempted.
