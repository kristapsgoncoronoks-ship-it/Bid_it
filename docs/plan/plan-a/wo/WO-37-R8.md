**WORK ORDER 37 — Add an SSRF guard to `oidc.discover()`/`oidc.fetch_jwks()`, reusing the existing webhook-delivery guard (board R8). Effort S 1d. Priority P3. Milestone C. Depends on: nothing (independent of WO-1..36).**

### Task-selection rationale (read this first)

Per the coordinator's instructions, candidates considered from `docs/audit/remediation-roadmap.md`
Milestone C were: R8 (OIDC SSRF guard), R13 (`test_fx.py` owner-only test doesn't test owner-only),
R15 (load/concurrency testing — explicitly flagged by the coordinator as larger/product-shaped, only
pick if nothing smaller/higher-value remains), R17 (Payment Run "Cancel" confirmation), R19 (onboarding
checklist — same "larger/product-shaped" caveat as R15). R9 is closed (WO-36) and skipped. R5(a)/R14 are
owner/decision-blocked per the roadmap and skipped per the coordinator's explicit instruction. R10/R11/R12
are P4 doc-hygiene, deprioritized below any P3 per the coordinator's stated ordering.

**R8 was selected.** It is the highest real security value remaining on the board: unlike R13 (a test
correctness gap on an already-correctly-behaving control) or R17 (a UX-consistency nicety on a
non-money-moving action — cancelling doesn't move money, so the roadmap itself calls it "cosmetic/
consistency, not a control gap"), R8 is a genuine, unmitigated SSRF gap on a *server-side, admin-
configurable, unauthenticated-callback-reachable* network path — the OIDC `issuer` field an org admin
sets via `PUT /sso/connection` has zero URL validation of any kind today (verified below), and the
resulting `discover()`/`fetch_jwks()` calls are plain `httpx` GETs against that admin-supplied host (and,
for `fetch_jwks`, against a `jwks_uri` that comes out of that host's own discovery *response* — a second,
attacker-controlled hop). The codebase already has exactly the right guard for this shape of problem
(`webhooks.assert_public_url`, closing the identical class of bug on the webhook-delivery path), so this
is a "reuse, don't duplicate" fix, not a new control — bounded, single-file, no schema change, no API
shape change, matching the coordinator's "quick, bounded, real security value" framing for R8. R15/R19
were confirmed larger/product-shaped (a load-test harness and a guided-onboarding UX flow respectively)
and were correctly left for a dedicated future WO rather than force-fit into this slot.

### Objective and business value

`backend/app/services/oidc.py`'s `discover(issuer)` (was lines 151-158) and `fetch_jwks(jwks_uri)` (was
lines 161-167) each open a plain `httpx.AsyncClient` GET with **no SSRF guard**, unlike the structurally
identical webhook-delivery path (`app/services/webhooks.py::assert_public_url`, which blocks loopback/
private/link-local/reserved/multicast/unspecified addresses and the `localhost`/`*.localhost` hostnames,
with DNS-resolution-based checking so a hostname that *resolves* to a private address is caught too).
Confirmed before this WO: `backend/app/services/sso_config.py::_EDITABLE`/`upsert_connection` accept
`issuer` from the admin-facing `PUT /sso/connection` route (`backend/app/api/routes/sso.py`) with **zero**
URL validation — no scheme check, no private-address check, nothing. That `issuer` then drives:
1. `discover()` — an unauthenticated, server-side GET to `<issuer>/.well-known/openid-configuration`,
   reachable end-to-end from the **public, unauthenticated** `GET /auth/sso/{slug}/authorize` route the
   instant any org admin (possibly compromised, possibly malicious in a multi-tenant SaaS where tenant
   admins are not implicitly trusted with the platform's internal network) points `issuer` at an internal
   host or the cloud-metadata address `169.254.169.254`.
2. `fetch_jwks()` — a second server-side GET, this time to `jwks_uri`, a value that comes not from the
   admin's config at all but from **the discovery response itself** — so even an issuer host that *looks*
   external is a live SSRF vector the moment that host (or a MITM/DNS-rebind of it) is compromised and
   returns a `jwks_uri` pointing at an internal address.

Both are server-side requests with no user-visible response body returned to the caller (the JSON is
consumed internally, never echoed back raw) — so this is the classic "blind SSRF" shape: an attacker
cannot read the internal response directly through this endpoint, but can use it to probe internal
network topology (timing/error-shape oracle) or, worse, reach an internal metadata/admin service that
acts on an unauthenticated GET alone (the exact `169.254.169.254` cloud-metadata scenario the webhook
guard's own tests already name). Closing it costs nothing for a legitimate deployment (every real IdP —
Okta, Auth0, Azure AD, Google Workspace, a self-hosted Keycloak on a real public/routable hostname — is a
public host and passes the guard unchanged) and removes a residual attack surface that becomes more
consequential, not less, the more this SaaS product grows its number of tenant admins (§1 of the master
context: this is explicitly a multi-tenant product where a tenant admin is not the platform operator).

### Scope

**In scope:**
- `backend/app/services/oidc.py` — a new `_assert_safe_idp_url()` helper that calls
  `webhooks.assert_public_url()` (no new SSRF-detection logic — pure reuse) and wraps
  `webhooks.UnsafeWebhookUrl` into the module's own `SsoError`; called from both `discover()` (on the
  constructed `.well-known/openid-configuration` URL) and `fetch_jwks()` (on `jwks_uri`), **before** any
  `httpx` call is made.
- New tests in `backend/tests/test_sso_oidc.py` proving: (a) `discover()`/`fetch_jwks()` reject every
  private/reserved/loopback/`localhost` URL shape the webhook guard's own test suite already covers, with
  **zero** network attempt made (proven via a fake `httpx.AsyncClient` that records whether `.get()` was
  ever called); (b) a normal public-looking issuer/`jwks_uri` still works unchanged; (c) an end-to-end
  route-level proof — `GET /auth/sso/{slug}/authorize` against a connection whose `issuer` is the cloud
  metadata address returns `502` (the route's existing "IdP unreachable" branch), never a raw 500 and
  never an actual outbound request.
- `docs/audit/remediation-roadmap.md` — mark R8 `CLOSED (WO-37)`.

**Out of scope:**
- Any other Milestone C item (R13, R15, R17, R19, R10, R11, R12) — not touched.
- Applying the guard to `exchange_code()`'s `token_endpoint`. The roadmap's own evidence
  (`security-findings.md` §2.5) and fix statement name only `discover()`/`fetch_jwks()`; `token_endpoint`
  comes from the same discovery response as `jwks_uri` and is arguably the same risk class, but widening
  scope beyond the named finding is exactly the scope-creep this template's anti-scope-creep clause
  exists to prevent. Flagged here as a candidate follow-up, not started.
- Validating `issuer` eagerly at `PUT /sso/connection` config-write time (the webhook pattern validates at
  both write-time, for admin UX, and delivery-time, for DNS-rebind defense-in-depth). The fetch-time guard
  added here is non-bypassable regardless of entry point and is what the roadmap's acceptance bar asks
  for; a write-time check would only add earlier admin feedback, not additional safety, and is left as a
  smaller, independent, later UX improvement rather than folded into a P3 security fix.
- Any change to `webhooks.assert_public_url()`/`UnsafeWebhookUrl` itself — reused exactly as-is.

### Implementation guidance

1. Confirm the gap first (no test currently exercises `discover()`/`fetch_jwks()` unmonkeypatched —
   verified: `grep -n "await oidc.discover\|await oidc.fetch_jwks" tests/test_sso_oidc.py` returns
   nothing before this WO; every existing SSO test monkeypatches both functions away, so adding the guard
   cannot regress any existing assertion).
2. Add `_assert_safe_idp_url(url: str) -> None` to `oidc.py`: call `webhooks.assert_public_url(url)`,
   catch `webhooks.UnsafeWebhookUrl`, re-raise as `SsoError` (the module's own, already-handled error
   type — both call sites already sit inside routes with a broad `except Exception`/`except oidc.SsoError`
   for "IdP unreachable/misconfigured", so no route change is needed for this to surface correctly as a
   502/error-redirect rather than a 500).
3. Call it at the top of `discover()` (on the fully-constructed `.well-known/openid-configuration` URL,
   not the bare `issuer`) and at the top of `fetch_jwks()` (on `jwks_uri` directly), in both cases before
   the `async with httpx.AsyncClient(...)` block — the guard must run before any socket is opened.
4. State the fail-open/fail-closed reasoning in a docstring on `_assert_safe_idp_url` (per master-context
   §6): fails CLOSED (raises) on a private/loopback/link-local/reserved/`localhost` target; fails OPEN on
   a DNS resolution error, identical trade-off to `webhooks.assert_public_url` itself (an offline/
   unresolvable host just won't connect — no new behavior invented here).
5. Add the new tests with a fake `httpx.AsyncClient` (records the last URL `.get()` was called with, so a
   "guard didn't fire" regression is provable, not just "an exception happened somewhere") — no real
   network access in CI. Use RFC 2606 `.test`-TLD hosts (guaranteed never to resolve) for the "allows a
   public issuer" cases, mirroring the existing webhook test's own DNS-fails-open pattern
   (`test_webhook_accepts_public_url_and_rechecks_on_update` uses `example.test`).

### Invariants this order must preserve

- No §4 tenancy/authz/money invariant is touched by this change — it is a pure network-egress guard on an
  SSO service function.
- **Wire contract (§4/20) unaffected** — no route signature, response shape, or status-code contract
  changes for the *happy path*; the only externally-observable delta is that an admin-configured SSRF
  target now produces the *same* 502 the route already produces for "IdP unreachable" (no new status code
  introduced, no behavior contract broken).
- **§6 docstring convention** — the fail-open-vs-fail-closed reasoning is stated explicitly on the new
  helper, matching the existing convention on `webhooks.assert_public_url` itself.

### Rollback strategy

Pure code + test revert — no migration, no schema, no one-way effect, no data transformation. Reverting
restores the pre-WO `discover()`/`fetch_jwks()` byte-for-byte; the only behavioral change this WO
introduces is rejecting a URL shape that was already both a bad idea and (per the roadmap's own severity
call) reachable only by an already-privileged admin actor, so a revert carries no operational risk beyond
re-opening the gap this WO closes.
