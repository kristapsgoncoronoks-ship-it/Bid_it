### Objective and business value

Verified at HEAD=`ff12fa0`: after a statement passes the WO-66 capture
review gate, nothing checks the *identifiers* the capture read off the
document. A seller VAT number captured from a Eurowag footer
(`parsers/eurowag.py::_EW_VAT_RE` is deliberately permissive —
"alphanumeric, 4-17 chars" — so a mangled token IS captured) flows
into `supplier_entity.learn_registration` unexamined; and nothing
anywhere detects that the invoice being registered for entity B was
already registered under entity A — the double-refund-claim shape that
R26's cross-entity duplicate check exists to catch. The harvested spec
names the missing module verbatim: `BA_fleet_fuel.md` §3.I7
"Deterministic post-capture checks (`capture_checks.py`), advisory
only" — IBAN ISO 13616 + MOD-97 (severity **error**); VAT-ID
**structural check only**, the live VIES lookup "deliberately NOT done
inline … offline-graceful, returns 'not checked', never raises/blocks"
(severity **warn**); duplicate = "same normalized invoice number +
amount, **across ALL five entities**, not just this supplier+statement"
(prior-duplicate = **error**; in-batch repeat = **warn**); and
"Unknown/uncheckable inputs yield **no finding** — fail toward not
crying wolf." R26 (§7.2) and `ARCH_plan.md` G3.4 carry the same text.

Who stops losing money: the same invoice claimed by two sister
entities is a duplicate VAT-refund submission — the exact "creates a
duplicate submission" failure `BA_fleet_fuel.md` §Purpose says forfeits
client money or files an invalid claim; catching it AT CAPTURE, before
a claim is ever built, is orders cheaper than a member-state rejection
letter months later. A structurally impossible seller VAT-ID on the
learned registration means the wrong legal entity lands on the claim
form (G3.1's whole point inverted). And because every one of these
signals is heuristic-adjacent (a re-issued invoice, a VAT format
quirk), the harvested system made them ADVISORY — a reviewer triages,
the pipeline never halts. That is the §4.19 shape: advisory, never
mutates, never gates.

### Design decisions (from the harvested spec — cite, then decide)

1. **The exact check list (harvested §3.I7 / R26 — nothing more).**
   (i) IBAN: ISO 13616 structure + ISO 7064 MOD-97, severity `error`.
   (ii) VAT-ID: structural check only, severity `warn`.
   (iii) `vies_check`: offline-graceful, returns "not checked", never
   raises, never blocks — see decision 6.
   (iv) Duplicate: prior cross-entity = `error`; in-batch repeat =
   `warn`. R26 names NOTHING else — no other check is added (no
   invented policy).

2. **Findings flow ALONGSIDE `capture_review`, never through it.**
   The task's open question, decided: `capture_review.BatchReview`
   counts `error` findings into `can_commit` — an R26 `error` fed into
   that lattice would BLOCK registration, which R26/§4.19 forbid
   ("advisory and never gate"; the G3.4 board row: "advisory always").
   So `capture_checks` defines its OWN frozen `CheckFinding` dataclass
   (same `{severity, code, message}` convention, deliberately a
   DIFFERENT type so mypy structurally prevents feeding an advisory
   finding into the blocking lattice), and `ingest_statement` renders
   the findings into `StatementIngestResult.warnings` — the slice's
   established advisory surface (WO-62's "that list IS the review
   surface until a persisted one exists"). The R26 severity is kept
   IN the rendered string (`post-capture check (error): …` /
   `(warn): …`) as reviewer triage rank — an `error`-severity advisory
   finding still never blocks. Warnings ordering extends WO-70's
   stable contract: parser → review → **post-capture** → drift.

3. **"Cross-entity duplicate", precisely.** Harvested: "same
   normalized invoice number + amount, across ALL five entities, not
   just this supplier+statement". Mapped to this schema:
   - *Candidate grain:* one candidate per distinct RAW `invoice_ref`
     in the parsed batch (statements legitimately carry many lines per
     invoice — the check runs at INVOICE grain, never line grain).
     Lines with `invoice_ref=None` are uncheckable → no finding.
   - *Normalization* (documented reconstruction — the source's exact
     rule was not harvested): uppercase + strip ASCII spaces, applied
     identically in Python and in the SQL filter
     (`func.upper(func.replace(invoice_ref, " ", ""))` — portable
     across SQLite and Postgres). Deliberately NARROW (separators like
     `/` and `-` are kept — "2024/001" ≠ "2024001") per "fail toward
     not crying wolf".
   - *Amount:* `q2(Σ net_local + vat_local)` over the candidate's
     lines, compared for EXACT equality, scoped to the SAME currency
     (a PLN 1210.00 invoice is never "the same" as a EUR 1210.00 one;
     amounts may not be compared across currencies — §4.14's ethos at
     the comparison level). Same ref + different amount → NO finding
     (a partial or re-issued invoice is not a duplicate; harvested
     "number + amount" means BOTH must match).
   - *Prior duplicate (`error`):* an already-registered
     `fuel_transactions` group — grouped by `(entity_id, supplier,
     period, normalized ref, currency)` — in the SAME org, ANY entity
     ("across ALL entities"), whose q2 total equals the candidate's,
     EXCLUDING the current `(entity_id, supplier, period)` ingestion
     group: `ingest_transaction` is insert-or-no-op, so an idempotent
     replay of the same file re-sees its own rows and must not
     self-flag (the replay test asserts this).
   - *In-batch repeat (`warn`):* two or more DISTINCT raw refs in the
     current batch normalizing to the same `(normalized ref,
     currency)` with equal q2 amounts — the "same invoice captured
     twice in one batch under a spelling variant" defect. (Within one
     statement, one raw ref aggregates to one candidate — a repeat can
     only arise via normalization collision; that is the honest
     mapping of the harvested batch-of-documents semantics onto a
     one-file batch.)

4. **IBAN check composes `app/core/bank_id.py` — never reimplements.**
   `normalize_iban` + `IBAN_LENGTHS` + `is_valid_iban` are imported
   from core (ADR-P3-clean: `test_boundaries.py` restricts transport
   services' MODEL imports; core imports are the sanctioned direction,
   exactly as `statement_ingest` already imports `app.core.money` /
   `app.core.errors`). ONE documented divergence from `bank_id`'s
   posture: `bank_id` fails CLOSED on an unknown country prefix
   because its callers move money (SEPA); here an unknown-country
   IBAN is UNCHECKABLE and yields NO finding (R26's "unknown or
   uncheckable inputs yield no finding") — the SEPA path keeps its
   fail-closed gate untouched. Empty/absent IBAN → no finding.
   *Producer honesty:* no fuel-card parser emits an IBAN today
   (verified — `grep -n iban app/services/transport/parsers/*.py` is
   empty), and the `ParsedStatement` contract is NOT widened
   speculatively. `run_checks` accepts `iban: str | None = None`;
   `ingest_statement` passes nothing, so the check is proven at
   function level until a producer exists — the exact WO-61 precedent
   (`supplier_entity`: "a standalone predicate with zero consumers
   wired in, proven correct at the function level until a real caller
   exists"). The one IBAN the transport vertical DOES hold today
   (`issuer_profiles.iban`, the refund payout account) is already
   hard-validated at every write path by A2.2 — no advisory duplicate
   of that gate.

5. **VAT-ID structural table: character classes + length from the
   public VIES format table (EU-27), allocation ranges deliberately
   NOT encoded.** The pii-scan heritage (`scripts/pii_scan.py::VAT_RE`,
   WO-6) is prefix + digit-count; this check refines it per country
   (AT `U\d{8}`, NL `\d{9}B\d{2}`, ES/FR/IE alphanumeric shapes, LT
   `\d{9}|\d{12}`, …) but STOPS at structure: registry allocation
   rules (e.g. "BE bodies start 0/1") are not modelled — they change
   by statute, and a false "malformed" on a real seller VAT is
   exactly the crying-wolf R26 forbids. Prefix `EL` maps to Greece
   (the one documented exception, same table as
   `parsers/eurowag.py::_VAT_PREFIX_TO_COUNTRY`). Unknown prefix (XI,
   CH, a non-country token) → no finding. Checked inputs at ingest:
   every `DetectedEntity.vat_number` the parser read off the document
   (the value `learn_registration` is about to store). Severity
   `warn` — harvested verbatim.

6. **The VIES rule: never inline means NO CLIENT AT ALL.** Harvested:
   "the live EU VIES lookup is deliberately NOT done inline
   (rate-limited / frequently unavailable); `vies_check` is
   offline-graceful, returns 'not checked', never raises/blocks."
   Decision (the task's question answered): this order ships
   `vies_check()` as a deliberate no-I/O function that ALWAYS returns
   status `not_checked` — no HTTP client, no SOAP dependency, no
   deferred/offline job, no queue kind. That satisfies both harvested
   acceptance lines ("an unreachable VIES returns 'not checked'" — it
   is structurally unreachable) and §4.19's "with all AI/external
   settings at defaults, zero external calls". A future ONLINE VIES
   job would be new scope (a worker, a cache table, a rate-limiter)
   that no R-rule requires — out of scope entirely, documented here so
   nobody "finishes" the stub inline later. A `not_checked` result
   yields NO warning string at ingest (not a defect, just un-verified
   — no finding for uncheckable, again).

7. **No new table — justified.** Advisory findings are ephemeral
   review output (this slice's surface is
   `StatementIngestResult.warnings`, per WO-62/WO-66/WO-70 precedent);
   the duplicate check READS `fuel_transactions` (org-filtered +
   ORM tenant guard + RLS — all three layers already on that table).
   Nothing is persisted, so no migration, no RLS work, no
   tenancy-parity classification change. A persisted statement
   review-queue remains future scope (named in WO-62's out-of-scope
   list, unchanged).

8. **Failure posture.** The checks never BLOCK (no refusal path exists
   in this module — §4.19's heart), but "advisory" does not mean
   "swallowed": an infrastructure failure in the duplicate SELECT
   (the only I/O) propagates — the session is doomed anyway, and
   master-context §7.1 forbids a bare except. The pure checks
   (IBAN/VAT/VIES) cannot raise on any input by construction
   (`None`/empty/garbage → no finding), which the tests prove with
   adversarial inputs.

### Implementation guidance

1. Build `capture_checks.py` pure functions first (`check_iban`,
   `check_vat_id`, `vies_check`) with the no-finding-on-uncheckable
   contract; unit-test with factory-generated synthetic values
   (`tests/factories/transport.py::synthetic_iban/synthetic_vat_id` —
   runtime-generated, so NO new pii-scan literals; corrupt them at
   runtime for the negative cases).
2. Build `find_duplicates`: candidates from parsed lines (invoice
   grain, decision 3), one org-filtered SELECT with the normalized-ref
   filter, Python-side Decimal aggregation (`q2`), current-group
   exclusion, in-batch collision detection.
3. `run_checks(db, org_id, *, entity_id, supplier, period, lines,
   vat_ids=(), iban=None)` — module-entitlement gate first (identical
   discipline to `ingest_statement`/`learn_registration`), then pure
   checks + duplicates; returns `list[CheckFinding]`.
4. Wire into `ingest_statement` between the review-gate block and
   phase 1 (findings computed pre-write; the group exclusion makes
   ordering irrelevant for correctness, pre-write placement keeps the
   self-rows question moot). Render as
   `post-capture check ({severity}): {message}`.
5. Money: all comparisons on `Decimal`, `q2` (ROUND_HALF_UP); amounts
   are LOCAL-currency, currency-scoped — never cross-currency
   equality. No new gate fails closed: every path in this module fails
   toward NO finding (open), by R26's explicit instruction; the module
   docstring states this and why.
