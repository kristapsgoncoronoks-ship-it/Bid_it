# WO-60 — G2.10 slice 1: the adjustable submission checklist engine + claim-level items (board G2.10, R45)

<!-- ═══════════════ COPY FROM HERE: WO-60 ═══════════════ -->

**WORK ORDER 60 — G2.10 slice 1: the submission checklist as DATA, not
code — the adjustable rule table + the two DATA-type verifiers this
codebase can actually evaluate today, plus the four claim-level items,
replacing `status.derive_stage`'s WO-59 two-check proxy. Effort M-L
(5-8d). Priority P0. Milestone M3. Depends on: WO-59 (G2.7 — `derive_stage`
is the consumer this order rewires), WO-58 (R10/R15 checks this order
reuses, never re-derives).**

### Objective and business value

WO-59 shipped `derive_stage()` with an explicit, documented placeholder:
"this module's 'non-period items' are the two concrete, already-shipped
checks this codebase actually has... A future G2.10 REPLACES this
checklist proxy; it does not sit alongside it." Verified at
HEAD=`49c29c3` (this order's baseline, 1384 passed/10 skipped): there is no
`vat_checklist_rules` table, no adjustable rule anywhere, and no per-
claimant-entity data verifier (customer registration data, bank account)
gating a claim at all. `BA_fleet_fuel.md` §3.E/R45 is explicit: submission
rules must be DATA (key/label/scope/check_type/reference/active/sort), not
hard-coded — "deactivate a rule ⇒ it disappears from the gate."

Who pays more without this: a claim with a blank IBAN or missing VAT/
registration-number data on the claimant entity currently sails straight
to `"1E"` (ready to submit) — nothing checks the entity data that a real
refund authority WILL check before paying out. And with the checklist
hard-coded (WO-59's proxy), every future country/entity-specific
compliance requirement needs a code change and a deploy instead of an
admin toggling a row — exactly the rigidity R45 exists to prevent.

### Scope

**In scope**
- `vat_checklist_rules` (new tenant table): `key`, `label`, `scope`
  (`"customer"` | `"country"`), `check_type` (`"document"` | `"data"`),
  `reference`, `active`, `sort`. `app.services.transport.checklist`:
  `seed_default_rules` (idempotent per org), `list_rules`, `set_active`
  (the ONLY writer of `active` — audited).
- TWO `DATA_VERIFIERS` this codebase can evaluate TODAY, reusing
  `IssuerProfile` fields already on the claimant entity (`entity_id` ->
  `issuer_profiles`, WO-49's own reuse) — no new customer concept, no new
  core-table column: `customer_data` (registration_number + vat_number +
  address_line1 all non-empty) and `bank_account` (a non-empty `iban`).
  Seeded ACTIVE by default; both `scope="customer"`.
- The FOUR claim-level items (`BA_fleet_fuel.md` §3.E, verbatim): receipt
  control (a waivable-but-not-yet-waived supplier, named), unresolved
  refs (a synthetic line that is NOT waivable — has a registered invoice,
  a note-matching fix, not a missing one), documents attached (WO-58's
  `document_gate.missing_document_invoice_ids`), claim period ended
  (WO-56's `deadline.period_ended`) — each reusing an EXISTING pure check,
  never re-derived.
- `submission_checklist(db, org_id, claim_id, *, today=None) ->
  list[ChecklistItem]` — the evaluator. `status.derive_stage` REWIRED to
  consult it (replacing WO-59's two-check proxy exactly as that order's
  own docstring anticipated): any non-period item failing -> `"1A"`;
  else period-ended item failing -> `"1B"`; else the existing caveat
  check (unchanged from WO-59) -> `"1C"`; else `"1E"`.
- Migration (1 new tenant table, RLS in the same migration).

**Out of scope** (explicitly, future G2.10 slice 2+)
- **The `"document"` check_type** (`contract`, `trade_register`,
  `power_of_attorney`) — needs a document-requirements-with-EXPIRY concept
  this codebase does not yet have (the generic `documents` registry has no
  entity link or `valid_until`), and PoA expiry re-blocking a claim to
  `"1A"`. Building it now would mean designing a whole new document-
  linkage table under time pressure; flagged explicitly, not silently
  skipped. `contract`/`trade_register`/`power_of_attorney` rows are
  **NOT seeded** in this slice (only `customer_data`/`bank_account` are) —
  the DEFAULT_CHECKLIST is a documented PARTIAL harvest.
- **The `nace` DATA verifier** — `IssuerProfile` has no `nace_code` column.
  Adding one is a small, safe additive migration, but deliberately deferred
  to the SAME follow-up as the document check_type (both need a design
  decision about whether NACE/document-requirements belong on the core
  `issuer_profiles` table or a transport-owned side table — ADR-P3 rule 1
  spirit, not explicitly this table, but worth a considered answer, not a
  rushed one under this order).
- **`"country"`-scope rules** (the `power_of_attorney` default is
  country-scoped) — no country-scoped rule is buildable yet without the
  document check_type; deferred with it.
- **Any `api/routes/transport/*` route** — `set_active` is a service
  function only, same as every prior transport slice.

### Implementation guidance

1. **`_field_ok`'s "INPUT" placeholder convention does not exist in this
   codebase** — Bid_it's setup/onboarding UX leaves a field genuinely
   `NULL`/empty rather than writing a sentinel string. `DATA_VERIFIERS`'
   translation: a field is "ok" iff it is not `None` and not (after
   `.strip()`) an empty string — the same semantic Fleet Fuel's `_field_ok`
   captured, translated to this codebase's actual data-entry convention
   (a documented interpretation, mirroring every prior "no INPUT
   convention here" translation in this harvest).
2. **The receipt-control / unresolved-refs split reuses R15's own
   `waivable` definition, never re-derives it.** For each remaining
   unfrozen synthetic line (`claim_gates.is_synthetic`): call
   `invoice_match.registered_invoices(supplier, refund_country)` — EMPTY
   means "waivable but not yet waived" (receipt-control item, named by
   supplier); NON-EMPTY means "not waivable, a note-matching fix" (blocks
   the unresolved-refs item). BA's own invariant ("every synthetic ref is
   covered by exactly one of items 1 & 2") holds structurally from this
   split, since a line only reaches either bucket if it is still present
   at all (an actually-waived supplier's transactions never became a line,
   WO-58).
3. **`set_active` is the ONLY writer of `active`** — no route exists yet,
   so this is a service-only CRUD surface (mirrors `waiver.set_waiver`/
   `remove_waiver`'s own scope). Audited with old->new.
4. **`derive_stage`'s caveat (1C) check is UNCHANGED from WO-59** — this
   order only replaces the "non-period items"/"period-end" halves with
   `submission_checklist`'s verdict; the minimum/waiver-based caveat
   signal stays exactly as WO-59 built it.
5. **A future `"document"`/`"country"`-scope rule reaching
   `submission_checklist` today would hit an explicit, fail-closed
   `unsupported_check_type`/`unsupported_scope` refusal** (`AppError`, not
   a placeholder pass) — defensive, since no route can create such a rule
   yet (only `seed_default_rules` writes rows, and it only ever seeds the
   two supported ones), but the evaluator itself must never silently treat
   an unsupported rule as passing.

### Invariants this order must preserve

- **§4.16 (every mutating operation is audited)** — `set_active` emits an
  `AuditEvent` with old->new; `seed_default_rules`'s idempotent inserts
  are NOT separately audited (mirrors `waiver.set_waiver`'s own "no audit
  on a true no-op" convention) — first-seed inserts ARE audited (a new
  row appearing).
- **§4.4 (opaque 404, never 403)** — the claim/rule lookups mirror every
  other transport service's org-scoped pattern.
- **R3/R10/R15 centralization** — `submission_checklist` calls
  `claim_gates.is_synthetic`, `document_gate.missing_document_invoice_ids`,
  `invoice_match.registered_invoices`, `deadline.period_ended` — never a
  second implementation of any of the four.
- **Master-context §4.2 (RLS in the same migration)** — `vat_checklist_
  rules` ships RLS in its own migration.
- **ADR-P3 rule 2** — `checklist.py` reads `issuer_profiles` fields via a
  service call (`app.services.issuers` or the existing entity-lookup
  pattern already used elsewhere in `services/transport/*`), never a raw
  cross-domain model import.

### Database / migration impact

One new tenant table, `vat_checklist_rules`: `org_id`, `key` (String(40)),
`label` (String(120)), `scope` (String(12): `customer`|`country`),
`check_type` (String(12): `document`|`data`), `reference` (String(60),
nullable), `active` (Boolean, default `True`), `sort` (Integer, default
`0`), `id`, `created_at`/`updated_at`. `UniqueConstraint(org_id, key)`. RLS
in the SAME migration. Downgrade drops the table — safe, a rolled-back
deploy simply has no adjustable-rule history; `derive_stage` reverts to
WO-59's two-check proxy only if the CODE is also reverted (a migration
downgrade alone does not revert `status.py`).

### Testing requirements

`backend/tests/transport/test_g2_10_checklist.py`:
- `seed_default_rules` is idempotent (a second call inserts nothing new);
  seeds exactly `customer_data`+`bank_account`, both `active=True`;
- `customer_data` verifier passes when registration_number/vat_number/
  address_line1 are all present; fails (naming the missing field(s)) when
  any is `None` or blank;
- `bank_account` verifier passes with a non-empty `iban`; fails when
  `None`/blank;
- `set_active(key, False)` then `submission_checklist` no longer includes
  that item at all — the acceptance test, verbatim: "deactivate a rule ⇒
  it disappears from the gate";
- receipt-control item names a genuinely-uninvoiced (waivable, unwaived)
  supplier; waiving it removes the item's failure (the supplier no longer
  appears — reuses WO-58's exclusion, so the line doesn't even exist to
  check);
- unresolved-refs item fails when a synthetic line HAS a registered
  invoice (a note-matching case, not waivable) — waiving that supplier is
  separately proven REFUSED (WO-58's own `waiver_supplier_has_invoices`,
  unchanged);
- documents-attached / period-ended items reuse WO-58/56's own pure
  checks — one pass/fail case each, proving no re-derivation (patched via
  a spy/monkeypatch showing the SAME function object is called, or simply
  asserting behavior parity with `document_gate`/`deadline` directly).

`backend/tests/transport/test_g2_7_status.py` (extended): `derive_stage`
returns `"1A"` when the claimant entity has no IBAN (bank_account fails);
deactivating the `bank_account` rule then makes the SAME otherwise-clean
claim return `"1E"`.

### Acceptance criteria (verifiable checklist)

- [ ] `seed_default_rules` creates exactly 2 active rules
      (`customer_data`, `bank_account`); a second call creates zero more.
- [ ] `set_active("bank_account", False)` on an otherwise-blocking claim
      (missing IBAN) makes `submission_checklist`/`derive_stage` stop
      citing it — the rule "disappears from the gate."
- [ ] A claim with a genuinely-uninvoiced, un-waived supplier shows a
      failing "receipt control" item naming that supplier; waiving it
      removes the item.
- [ ] A claim with an UNMATCHED line whose supplier HAS a registered
      invoice shows a failing "unresolved refs" item; attempting to waive
      that supplier is still refused (`waiver_supplier_has_invoices`,
      unchanged from WO-58).
- [ ] `derive_stage` still returns the correct `1A`/`1B`/`1C`/`1E` for
      every WO-59 scenario, now via `submission_checklist` instead of the
      old two-check proxy — WO-59's own test file passes with only the
      documented extensions, no weakened assertions.
- [ ] `vat_checklist_rules` carries RLS in its own migration;
      `test_rls.py` set-equality check stays green.
- [ ] Full backend suite green on SQLite; `mypy app` clean; `ruff` clean;
      `alembic upgrade head && alembic check` clean.

### Rollback strategy

Code revert: remove `checklist.py`, the `checklist_rule.py` model, and
revert `status.derive_stage` to WO-59's two-check proxy. Migration
downgrade drops `vat_checklist_rules` — safe, no other table references
it. No kill switch needed: the `transport` module stays default-OFF and
absent from every plan's module set.
