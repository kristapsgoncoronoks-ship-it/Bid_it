### Objective and business value

Verified at HEAD=`f62dd56`: nothing in this codebase validates a parsed
fuel-card batch before registration, and nothing ties the captured
period back to the figures printed on the supplier's invoice PDF.
`statement_ingest.ingest_statement` (WO-62..65) writes every parseable,
FX-resolvable line — a statement whose VAT exceeds its net on a line,
or whose batch total disagrees with the invoice coversheet by euros,
registers silently. `close.run_close` (WO-53) rebuilds draft-claim
lines for the period with no check that the period's captured
transactions EQUAL what the supplier actually invoiced. `BA_fleet_
fuel.md` R25 (MUST) requires **two independent validation regimes** —
they answer different questions and the harvested source deliberately
kept them separate (§2.1a: *"`validate.py` is not in that chain… Two
separate regimes"*): the **engine tie-out** (*"does what we parsed
equal what the invoice PDF says?"* — fail ⇒ the close halts, the
hand-off artifact is not written) and the **capture review gate**
(*"is this captured batch internally coherent enough to register?"* —
`can_commit = no errors AND tie-out within 2 cents`, warnings never
block).

Who stops losing money: the tie-out is the **onboarding and operating
contract for every supplier** — §5.1's "fill `expected` from the
invoice → run the tie-out: PASS = trained" is how a parser is proven
against reality, and `ARCH_plan.md` T-6 rates parser accuracy the
moat-level risk ("never port a parser without its tie-out fixture").
A line-count off by one is a silently dropped or duplicated
transaction — unrecoverable VAT or a false claim; a batch that
disagrees with the coversheet by €0.03 is mis-keyed money feeding a
legal filing. Both regimes refuse BEFORE bad figures reach a claim,
which is the product's core promise ("every one of those promises
dies if a number is wrong").

### Scope

**In scope:**
- `app/services/transport/capture_review.py` (**new**) — the pure
  capture-review engine: `check_line` (the 9-rule verdict lattice
  `ok < warn < error`), `validate_batch` (per-line findings + the
  batch tie-out vs an optional coversheet total + `can_commit`),
  `review_statement` (the `ParsedStatement` adapter), and the
  23-country `VAT_RATES` coherence table with the four harvested dual
  entries (PL 23/8, ES 21/10, EE 22/20, FI 24/25.5).

  optional `coversheet_total: Decimal | None` keyword; the gate runs
  after parse and BEFORE FX resolution; `can_commit=False` refuses the
  whole statement (`code="capture_review_blocked"`, zero rows
  written); warn findings append to `StatementIngestResult.warnings`.
- `app/models/transport/tie_out.py` (**new**) —
  `FuelTieOutExpectation` (`fuel_tieout_expectations`): the
  per-(entity, supplier, period, currency) expected figures a human

  actual `fuel_transactions` aggregates vs the typed figures; `lines`

  expectation row for (org, period) first, then raise ONE

### Implementation guidance

1. **Capture review gate first (pure, no DB).** `CapturedLine` carries
   the RAW captured strings (`invoice_no`, `date`, `country`, `net`,
   `vat`) — the spec's own shape, so rule 4 ("net/vat parse as
   numbers", error + early return) is real, not vacuously satisfied by
   the typed parser output. Rules verbatim from §2.1a: (1) invoice
   number present → **error**; (2) date matches `YYYY-MM-DD`, empty
   passes → warn; (3) country in the 23-country set → warn; (4) net/vat
   parse as Decimals → **error** + early return; (5) `net > 0` →
   **error**; (6) `vat >= 0` → **error**; (7) `vat <= net` → **error**;
   (8) `net <= 5_000_000` → warn; (9) VAT-rate coherence — `vat/net`
   within ±0.5pp of a known rate for the line's country, `vat == 0`
   deliberately SKIPPED, a country absent from `VAT_RATES` deliberately
   SKIPPED (coherence needs a known rate to cohere WITH; fail toward
   not crying wolf) → warn.
2. **The `VAT_RATES` table.** Only the COUNT (23) and the four dual
   entries are harvested (`BA_fleet_fuel.md` §2.1a); the source
   system's literal table may not be copied (master-context §10). The
   remaining membership + standard rates are a DOCUMENTED
   reconstruction from public VAT law (standard rates are public
   statute, not Fleet Fuel data), flagged in the module docstring the
   same way `product_group.py` flags its token sets.
3. **Batch tie-out on Decimals.** `abs(q2(Σ(net+vat)) −
   q2(coversheet_total)) <= Decimal("0.02")` — quantize BOTH sides
   first so a diff sitting exactly on the boundary never flips on
   binary-float noise; `coversheet_total=None` ⇒ `tie is None` ⇒ no
   tie constraint (the spec's own `can_commit` formula). **Commit
   gate:** `can_commit = (errors == 0) and (tie is None or tie.ok)`;
   warnings NEVER block.
4. **Gate placement: after parse, before FX (fail-CLOSED).** The gate
   is the review verdict on the PARSED batch — it must speak before
   any FX machinery so the operator sees "net must be > 0", not a
   confusing downstream `fx_stated_inconsistent`. A blocked statement
   writes ZERO rows (the two-phase guarantee is upstream-extended, not
   changed).
5. **Existing-fixture consequences (list them in the report).** Three
   ingest suites carry `invoice_ref: ""` rows that previously
   registered fine — those fixtures encoded the ABSENT capability
   (nothing required a batch to identify its invoice before this
   gate). Give those rows synthetic refs; the tests' actual subjects
   (ECB conversion, two-phase FX refusal) are untouched. One DKV test
   (`zero_net_local_stated_line_is_refused`) asserted
   `fx_stated_inconsistent` for a `net_local="0.00"` line — rule 5
   (net > 0, error) now refuses it EARLIER with
   `capture_review_blocked`; align that assertion and keep the FX
   branch's own zero-guard covered via a `stated="0.00", net>0` case
   (which passes the gate and still hits `fx_stated_inconsistent`).
6. **Tie-out model.** Grain `(org_id, entity_id, supplier, period,
   currency)` — Fleet Fuel's tie-out was per-supplier over
   single-currency files; WO-64 proved a statement can carry multiple
   currencies, and §4.14 forbids summing `gross_local` across
   currencies, so the expectation gains `currency` (a documented
   interpretation, same discipline as WO-50's `line_seq`). Metrics:
   `expected_lines` (required, tolerance 0 — EXACT, always),
   `expected_gross_local` (+ per-row `gross_local_tolerance`, default
   0.02, CHECK-bounded [0.02, 0.05] — the harvested range),
   `expected_net_eur` / `expected_gross_eur` (0.05), and
   `expected_diesel_litres` (0.05 — litres, `product_group ==
   "Diesel"` only; the source gives no explicit litres tolerance, so
   the EUR tolerance is reused and documented as an interpretation).
   NULL metric ⇒ not checked (only figures actually typed from the
   PDF are tied out).
7. **A supplier with no expectation row is not checked** (fail-OPEN by
   absence): the expectation IS the opt-in training target — §5.1's
   own onboarding contract types it per supplier, and spec open
   question 16 confirms it is human-maintained. Once typed, every
   comparison fails CLOSED.
8. **Close wiring.** `run_close` evaluates ALL expectation rows for
   (org, period) BEFORE rebuilding claim lines, collects every
   failure, and raises ONE `ValidationError(code="tie_out_failed")`
   whose message names each (supplier, currency, metric, expected,
   actual) — the harvested "exit AFTER processing every supplier so
   the operator sees all failures at once". `jobs.run_once` already
   rolls back the whole session on a handler exception, so nothing of
   the close survives — the literal translation of "the pickle is not
   written". On success, add `tie_out_checked: <n>` to the existing
   close audit meta.
9. **Aggregate in Decimal, in Python.** `check_period` selects the
   matching rows' `(qty, product_group, gross_local, net_eur,
   vat_eur)` and sums with `Decimal` — never float, never a
   dialect-dependent SQL SUM coercion. Compare `abs(q2(actual) −
   q2(expected)) <= tolerance` for money; litres compared at their
   own 3-dp basis.
10. **Migration** off head `4ae197627e35`, RLS policy in the SAME
    migration (copy the `4ae197627e35` pattern verbatim), composite
    FK `(org_id, entity_id) → issuer_profiles(org_id, id)` RESTRICT,
    unique `(org_id, entity_id, supplier, period, currency)`.
    Up/down/up must be clean; run the scratch-Postgres 16 gate
    (tenancy + a migration are touched).

### Invariants this order must preserve

- **§4.1/4.2/4.3 (tenancy):** the new tenant table ships per-query
  `org_id` filters, the ORM-guard registration, and FORCE RLS in the
  same migration; composite `(org_id, entity_id)` FK; the set-equality
  test (`test_rls_migration_covers_every_tenant_table`) proves it.
- **§4.4:** cross-tenant expectation ids resolve to opaque absence
  (the upsert key is (entity, supplier, period, currency) — a foreign
  org's `entity_id` yields `NotFoundError` 404-shaped, never 403).
- **§4.9:** every comparison is `Decimal` + `q2` ROUND_HALF_UP; no
  float anywhere in either regime.
- **§4.14:** the tie-out grain carries `currency`; no metric ever
  sums `gross_local` across currencies.
- **§4.16:** `set_expectation`/`remove_expectation` audit with
  old→new; the close audit gains the tie-out count.
- **§4.19 (R25's gate semantics):** BOTH regimes are deterministic —
  no AI, no machine-confidence auto-block; the review gate blocks only
  on structural ERRORS and a failed 2-cent document tie-out (the
  spec's own `can_commit`), warnings NEVER block, and a human retypes
  the expectation/coversheet — nothing self-adjusts.
- **ADR-P3 (transport isolation):** both new services import only
  transport models + platform floor (`audit`, `modules`, `money`) —
  never `app.services.validation` (the AP engine) nor any AP model;
  the boundary tests stay green.

### Rollback strategy

Code revert restores WO-65 behaviour exactly (the gate and tie-out are
additive; `coversheet_total` defaults to `None` but the gate itself is
unconditional — reverting the wiring commit removes it). Migration
downgrade is written and tested (drops the table; typed expectations
are lost but re-typeable from the invoice PDFs). Narrow mitigation
without revert: delete an org's expectation rows (the close then
behaves exactly as WO-53 shipped it — fail-open by absence).
