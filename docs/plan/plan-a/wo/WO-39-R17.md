### Objective and business value

Cancelling a payment run is not a money-moving action in itself (an `open` or `approved` run has not
yet paid anyone — `payment_run.cancel_run` just unlinks its invoices back to the scheduled pool and
sets `status=cancelled`), but it IS consequential: cancelling an `approved` run discards a second
person's maker-checker sign-off, and there is no "un-cancel" — the invoices must be re-selected and
re-run through create→approve from scratch. A single misclick (this page renders 1-3 text buttons in
a tight row per run, right next to "Approve"/"Mark paid") currently fires the DELETE with no chance to
back out, which is inconsistent with every other consequential action on this exact page (re-export,
skipped-payee acknowledgement) and with the sibling destructive-action patterns already shipped
elsewhere in the app (R16/R18). Who benefits: the bookkeeper/finance-lead persona running payment
batches (`docs/product/personas.md`) — the same day-one trust/safety gap R16 closed on the AR side,
closed here on the AP side, at zero backend risk since the route's authorization and audit trail are
unchanged.

  with a 409), and calls `audit.record(..., audit.A.AP_RUN_CANCEL, ...)` in the same transaction as
  the mutation — confirmed by reading the route handler and service function before starting. No gap

- Regrouping the run-action button row visually — not requested by the roadmap text, a separate,

### Implementation guidance
1. `ConfirmDialog` is already imported in `PaymentRuns.tsx` (line 4) — no new import needed.
2. Add local state `const [cancelAsk, setCancelAsk] = useState<PaymentRun | null>(null)` alongside the
   existing `reexportAsk`/`skippedAsk` state.
3. Both "Cancel" buttons (`open`-status row, `approved`-status row): change `onClick={() =>
   cancel.mutate(r.id)}` to `onClick={() => setCancelAsk(r)}`.
4. Add a third `ConfirmDialog` (same structural pattern as the existing two at the bottom of the
   component): `open={cancelAsk !== null}`, `title="Cancel this payment run?"`, `tone="danger"`,
   `confirmLabel="Cancel run"`, `cancelLabel` default ("Cancel" — note this is the dialog's own
   dismiss button, distinct from the page action being confirmed; keep the default per the shared
   component to stay visually consistent with the two existing dialogs on this page), `loading={cancel.
   isPending}`. Body text: state the invoice count returns to the scheduled pool, and — conditionally,
   when `cancelAsk?.status === "approved"` — that the existing approval will be discarded and the run
   cannot be un-cancelled. `onConfirm` calls `cancel.mutate(cancelAsk!.id)` then `setCancelAsk(null)`
   (mirror the existing two dialogs' inline-closure style, not a `useEffect`).
5. New e2e spec: mock `/auth/me`, `/auth/organizations`, `/modules`, `/payment-runs/payable` (empty),
   `/payment-runs` GET (one `open` run), `DELETE /payment-runs/{id}`. Assert: (a) clicking "Cancel"
   does NOT call the delete endpoint immediately — the confirm dialog (`getByRole("dialog", { name:
   /Cancel this payment run/ })`) appears first; (b) confirming calls the endpoint exactly once and
   the dialog closes; (c) cancelling the dialog (its own "Cancel" button) leaves the run unmodified
   and issues no request to the delete endpoint. Reuse two fixture runs (one `open`, one `approved`)
   if practical to also assert the approved-run body copy branches, or state clearly in the report if
   only the `open` case was covered and why that is sufficient (the button wiring is identical either
   way — only body copy differs).
