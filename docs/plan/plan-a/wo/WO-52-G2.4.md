# WO-52 — Claim-line construction + note→invoice resolution (board G2.4)

**WORK ORDER 52 — G2.4: claim-line construction + note→invoice resolution (board
G2.4). Effort L (6-12d). Priority P0. Milestone M3. Depends on: WO-49 (G1.1/G2.1/
G2.3 — claim grain + `is_synthetic()`), WO-50 (G1.2 — `fuel_transactions`), WO-51
(G2.2 — the lock table; not a hard dependency for this order's own code, but the
next milestone task on `ARCH_plan.md`'s stated critical path).**

### Objective and business value

WO-49/50/51 shipped the claim grain, the typed transaction line and the lock
table, but nothing yet turns a `FuelTransaction` row into a `VatRefundClaimLine`
— the schema `vat_claim_lines` (WO-49) has existed, empty, since the M3 opener;
verified at HEAD=`a134770` (this order's baseline, 1259 passed/10 skipped): no
`app/services/transport/claim_lines.py` or `app/services/transport/
invoice_match.py` exists, and `VatRefundClaimLine` has zero writers anywhere in
the tree. `ARCH_plan.md`'s own critical path (line 1249) is explicit:
`G1.1 → G1.2 → G2.1 → G2.2 → G2.3 → G2.4 → G2.5 → G2.6 → G2.7` is a strict
chain, and **"G2.5 (frozen claim lines) is the linchpin"** for the whole gate
stack that follows — but G2.5 cannot freeze a line that G2.4 has not yet
constructed. This order is the harvested C1/C3/C4 machinery
(`BA_fleet_fuel.md` §3.C — "Claim construction & the anti-duplicate / anti-
synthetic machinery"): R2 ("claim lines are built ONLY from registered
invoices... never an `ALL:` aggregate") and R16 ("note→invoice overrides
change only the invoice ASSOCIATION, never an amount, validated at both set
time and read time").

Who pays more without this: every downstream G2.x gate (freezing, the
checklist/period-end/minimum/deadline stack, fee freezing, status derivation,
the evidence pack/workbook) reads claim lines — without a real
`invoice_ref`→`invoice_id` resolution and a live-then-frozen line builder,
none of them have anything concrete to gate, freeze or report on. Getting the
ONE resolution order right now (mirroring how R3's `is_synthetic()` had to be
centralized in WO-49) is cheaper than discovering a drifted, ad-hoc
"which invoice does this transaction belong to" re-implementation inside the
checklist gate, the workbook builder and a future UI endpoint, three separate
times, after G2.5/G2.6 are already built on top of whichever one shipped
first.

### Scope

**In scope**
- `app.services.transport.invoice_match` — the ONE note→invoice resolution
  function (`resolve_invoice_ref`), harvested verbatim resolution order (C3):
  two note-matching heuristics (prefix match / stem-contained match — a
  documented interpretation of an underspecified BA phrase, see the module
  docstring), the admin-curated override (only consulted after both
  heuristics fail to resolve uniquely — never displaces a heuristic match),
  the sole-registered-invoice fallback, else `None` (UNMATCHED). `
  registered_invoices()` — what "registered" means in this codebase (an
  `Invoice` belonging to a `Vendor` whose name exactly matches the
  transaction's free-text `supplier`, filtered to the vendor's `country` when
  set).
- `app.models.transport.note_override.VatNoteInvoiceOverride` — the
  admin-curated override table (C4/R16), keyed
  `(org, entity, supplier, refund_country, invoice_ref)`, targeting
  `invoices` via a composite FK. **`ondelete=CASCADE`, not `SET NULL`** — see
  Implementation guidance §3 for the composite-FK defect this order caught
  and fixed before it ever shipped.
- `app.services.transport.invoice_match.set_note_override` — create/update an
  override; refuses a synthetic note key and a target that is not currently
  registered for the exact (supplier, refund_country) pair.
- `app.services.transport.claim_lines.build_claim_lines` — (re)builds the
  LIVE, unfrozen `VatRefundClaimLine` rows for a `draft` claim from its
  in-scope `fuel_transactions` (entity + refund_country + the period's month
  range), grouping by (resolved invoice or `UNMATCHED`, `product_group`) per
  R2. Refuses a non-`draft` claim; only ever replaces `frozen_at IS NULL`
  rows (future-proofing for G2.5).
- Two new minimal, read-only AP-domain seams so `services/transport/*` never
  imports `app.models.invoice`/`app.models.vendor` directly (ADR-P3 rule 2):
  `app.services.invoices` (`list_by_vendor`, `get_by_id` — new module, fills
  the `invoice_service` gap ADR-0023 always named) and
  `app.services.vendors.get_by_name` (a pure read, unlike the existing
  `get_or_create_vendor`).
- Migration `4cb7fca7e508_vat_note_invoice_overrides.py` — one new tenant
  table, RLS in the same migration.
- Two new audit actions: `A.TRANSPORT_NOTE_OVERRIDE_SET`,
  `A.TRANSPORT_CLAIM_LINES_BUILD`.

**Out of scope** (explicitly, future M3 work orders)
- **Freezing claim lines at submission** (G2.5) — `frozen_at` stays NULL for
  every row this order writes; no code here stamps it or freezes the claim's
  `vat_eur`/`vat_local`/`fee_*` columns.
- **The checklist/period-end/minimum/deadline gate stack** (G2.6), **fee
  freezing** (G2.9), **status derivation** (G2.7), **Art. 9 goods-code
  mapping** (G2.8) — `VatRefundClaimLine.goods_code` stays NULL; this order
  never derives it.
- **Wiring `is_synthetic()` into the lock path as "the lock gate"** (G2.3's
  consumer side) — `claim_lines.py` does not call `lock.submit_claim`, and
  `lock.py` is untouched by this order.
- **Per-line `vat_id` capture** — no code here populates
  `VatRefundClaimLine.vat_id`; a line's synthetic-ness is still fully
  detected via `invoice_ref` alone (`is_synthetic(ref, vat_id=None)` already
  covers the `UNMATCHED`/`ALL:`/`INPUT` cases this order can produce).
- **Any `api/routes/transport/*` route**, **any UI**, **the monthly close**
  (G1.3/G1.4).

### Implementation guidance

1. **Read `BA_fleet_fuel.md` §3.C1/C3/C4 (lines 428-455) before writing a
   query.** C3's five-step resolution order is the load-bearing text; the two
   heuristics are named by description only ("note prefix vs registered ref
   prefix", "registered ref stem contained in note") with no literal code —
   underspecified exactly like WO-50's `line_seq` natural-key phrase. This
   order's interpretation (normalize to alphanumeric-uppercase, then prefix-
   match / substring-match with a minimum shared-length floor) is documented
   in `invoice_match.py`'s module docstring, not silently invented.
2. **"Registered invoice" = an `Invoice` belonging to a `Vendor` whose name
   exactly matches the transaction's `supplier`.** This codebase does not
   (yet) model a per-country legal-entity registration for a vendor (that is
   G3.1, future work) — a vendor with no `country` set is NOT excluded by the
   refund-country filter, a documented interpretation, not an invented
   requirement.
3. **The override target FK is `ondelete=CASCADE`, not `SET NULL` — a real
   defect caught and fixed while writing this order's own test.** The first
   draft used `SET NULL` (matching the intuitive reading of "de-registering
   the target stops it resolving"), but both SQLite and Postgres null EVERY
   column in a composite FK on a `SET NULL` action — including `org_id`,
   which is `NOT NULL` on every tenant-scoped table. Deleting the target
   invoice under `SET NULL` therefore raised its OWN `IntegrityError` (a
   `NOT NULL` violation on `org_id`) instead of gracefully nulling the
   target — caught live running `test_g2_4_deregistering_the_target_invoice_
   stops_the_override_resolving` with `PRAGMA foreign_keys=ON` on SQLite,
   and equally true on Postgres (identical composite-FK semantics).
   `ondelete=CASCADE` (delete the whole override row instead) sidesteps the
   conflict entirely and is at least as correct — a dead override has
   nothing useful left to keep. `target_invoice_id` is therefore `NOT NULL`.
4. **`resolve_invoice_ref` and `set_note_override` are both gated on
   `modules.is_enabled("transport")` FIRST**, identical pattern to every
   other transport service (`PermissionError`, `code="module_not_enabled"`,
   never `modules.require_enabled`). `build_claim_lines` gates the same way;
   its internal per-transaction calls into `resolve_invoice_ref` therefore
   re-check the same flag once per transaction — accepted redundancy, not a
   defect, matching this codebase's existing defense-in-depth posture (RLS +
   ORM guard + query filter, all three, always).
5. **`services/transport/*.py` must never import `app.models.invoice` or
   `app.models.vendor` directly** (`test_transport_services_do_not_import_
   other_domain_models`, WO-49). `resolve_invoice_ref` returns a small
   transport-local `MatchedInvoice` dataclass (`invoice_id`, `invoice_number`)
   rather than the AP `Invoice` ORM object, and reads through the two new
   read-only seams (`app.services.invoices`, `app.services.vendors.
   get_by_name`) instead of a raw `select(Invoice)`/`select(Vendor)`.
6. **`build_claim_lines` refuses a non-`draft` claim** (409,
   `code="claim_not_draft"`) and only ever `DELETE`s+re-`INSERT`s
   `VatRefundClaimLine` rows where `frozen_at IS NULL` — belt-and-braces:
   even though no freeze service exists yet (that is G2.5), a future one
   cannot have its frozen rows silently clobbered by this order's rebuild
   logic, proven by `test_g2_4_never_touches_a_frozen_line` (which simulates
   a hypothetical frozen row directly, since no code path can produce one
   yet).
7. **Migration:** `alembic revision --autogenerate`, then hand-edit — RLS for
   the new table in THIS migration (`TENANT_TABLES` module-level tuple,
   identical pattern to the three prior transport migrations). Verify
   `alembic upgrade head && alembic check` reports no drift, and a downgrade/
   upgrade round-trip is clean.
8. **`README.md`/`test_docs_truth.py`:** recount `__tablename__` across
   `app/models/**/*.py` AND top-level `*.py` files under `app/services/`
   (the new `app/services/invoices.py` is a NEW top-level service module,
   unlike the transport-subpackage files, so `service_modules` also moves
   82 → 83 — update both counts together).

tests writes to it yet.

### Rollback strategy

Migration downgrade (`alembic downgrade -1`) drops `vat_note_invoice_
overrides` (and its Postgres RLS policy) — safe, nothing outside this order's
own tests writes to it. A code-only revert without the migration downgrade is
safe (the table simply goes unused); the reverse (reverting the migration
while the code is still deployed) would error the moment
`set_note_override`/`resolve_invoice_ref` is called, so always downgrade the
migration in the same step as reverting the code. No kill switch is needed
for a production incident: the `transport` module stays default-OFF and is
absent from every plan's module set, so this order's entire surface is
unreachable by any tenant regardless of code presence.
