**WORK ORDER 29 — Shared CSV/Excel formula-injection helper; fix the 3 unprotected financial exports (board R1). Effort S 1–2d. Priority P1. Milestone A. Depends on: nothing.**

### Objective and business value

`backend/app/services/payment_run.py::export_csv`, `backend/app/services/reimbursement.py::export_csv`,
and `backend/app/services/explore.py::to_csv` write attacker-influenceable free text (invoice number,
payment-run reference, employee name, expense-report title, analytics dimension values such as vendor
name) directly into a `csv.writer` row with no formula-injection neutralization (CWE-1236). Three sibling
exporters in the same codebase already solve this exact problem correctly, with matching docstrings:
`erp_export.py::_safe` (line 99), `audit_export.py::_safe` (line 32), and `report_writers.py::_safe_cell`
(line 32) — each independently implemented, no shared module. A malicious cell (e.g. a vendor-supplied
invoice number `=cmd|'/c calc'!A1` that a human reviewer edits for correctness but doesn't specifically
screen for a formula-injection payload) reaches the payment-run bank-export CSV or the payroll-adjacent
reimbursement CSV that a finance/HR user typically opens straight in Excel — the textbook CSV-injection
scenario, on the two most money-adjacent export artifacts in the app.

Fixing this closes the last open Milestone A item (`docs/audit/remediation-roadmap.md`): protects the
pilot's own real bank-payment export and payroll-adjacent payout export the moment the AP/reimbursement
modules go live with a real vendor/employee, without which a hostile or careless upstream data source
(an invoice PDF a human transcribes) can plant a payload that executes on a finance user's machine the
moment they open the downloaded file in Excel.

### Scope

**In scope:**
- New `backend/app/core/csv_safety.py` — one shared `sanitize_cell(value) -> str` implementing the
  OWASP-standard mitigation (prefix a cell starting with `=`, `+`, `-`, `@`, tab, or CR with a leading
  `'`), documented as free-text-fields-only (never a formatted numeric/money cell).
- `backend/app/services/payment_run.py::export_csv` — sanitize `run.reference`/`run.id` and
  `inv.invoice_number`. Amount, currency, and method columns are left untouched (numeric/enum, not
  free text).
- `backend/app/services/reimbursement.py::export_csv` — sanitize `batch.reference`/`batch.id`,
  `r.employee_name`, and `r.title`. Amount, currency, and method columns untouched.
- `backend/app/services/explore.py::to_csv` — sanitize each row's dimension values (`row.get(d["key"])`,
  e.g. vendor name, cost center, category). The formatted measure value column is left untouched (it can
  legitimately start with `-` for a negative/credit figure; sanitizing it would corrupt a numeric cell).
- Refactor the three already-correct duplicated helpers (`erp_export._safe`, `audit_export._safe`,
  `report_writers._safe_cell`) to delegate to the new shared `csv_safety.sanitize_cell`, keeping their
  existing local names (tests reference `report_writers._safe_cell` directly) — behavior-preserving
  dedup, a low-risk down payment on board R9 (same root cause: a helper duplicated instead of shared).
- New unit/integration tests proving red-then-green per touched export path.

**Out of scope:**
- `app/api/routes/issued.py::_csv_safe` — a fourth, already-correct, already-safe copy (string-only
  guard) found during recon; not part of R1 (nothing there is unprotected) and not touched, to keep this
  order's blast radius to the three files the audit named plus the shared-helper extraction.
- Full R9 (extracting *every* CSV/Excel-writer duplication codebase-wide) — this order dedups the three
  helpers it directly touches as a natural side effect (per the roadmap: "R9 is not required first but
  doing both together avoids a fourth reviewable change"), but does not re-audit the codebase for other
  unrelated duplication.
- Any change to export business logic, column sets, amount formatting/rounding, or SEPA/pain.001
  generation — this order is additive-safety-only; a well-formed export is byte-for-byte identical.
- R4/R5/R6/R14/R16/R18 (Milestone B items) — untouched, separate work orders.

### Implementation guidance

1. Write `app/core/csv_safety.py` first: `FORMULA_TRIGGERS = ("=", "+", "-", "@", "\t", "\r")` and
   `sanitize_cell(value: object) -> str` — `s = "" if value is None else str(value); return "'" + s if s
   and s[0] in FORMULA_TRIGGERS else s`. Docstring states explicitly: apply only to free-text cells,
   never to a formatted numeric/money/date cell (a legitimate `-12.50` must round-trip untouched).
2. **Reproduce first** — for each of the three unprotected sites, add a test asserting a cell value
   containing `=cmd|'/c calc'!A1` (or similar) lands **raw** in the current code (red). Confirm each
   fails against the pre-fix code before editing the service module.
3. Apply `csv_safety.sanitize_cell` at each of the three sites, touching only the free-text columns named
   in Scope. Do not wrap the amount/currency/method columns.
4. Flip each red test to assert the cell now starts with `'=` (green). Add one negative-amount-but-numeric
   case per touched exporter proving the amount column is NOT prefixed (e.g. an EUR amount rendered as
   `-12.50` from a legitimately negative/credit figure passes through unmodified) — this is the
   don't-double-escape / don't-corrupt-numeric-columns proof the task requires.
5. Refactor `erp_export._safe`, `audit_export._safe`, `report_writers._safe_cell` to import and delegate
   to `csv_safety.sanitize_cell`, preserving their existing names and call signatures so
   `test_erp_export.py`, `test_audit_export.py`, `test_report_writers.py` pass **unmodified**.
6. Run the full targeted test files, then the full suite.
