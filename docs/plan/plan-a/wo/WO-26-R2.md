**WORK ORDER 26 — Row-lock `create_credit_note` to close the over-crediting race (board R2). Effort S 1–2d. Priority P0. Milestone A. Depends on: nothing.**

### Objective and business value

`backend/app/api/routes/issued.py::create_credit_note` (line 620) reads the corrected
invoice via `original = await _load(db, current.org_id, invoice_id)` — no lock. It then
computes `already = issued_service.already_credited(original)` from that unlocked row and,
after acquiring only the *issuer* row lock (line 646, for numbering — it protects nothing
about `credited_total`), writes `original.credited_total = money.q2(min(already +
Decimal(cn.total), Decimal(original.total)))`. This is a classic read-modify-write race: two
concurrent partial credit-note requests against the same invoice can both read the same stale
`already`, and one write is lost. `record_payment` (line 770) already loads the *same* row via
the *same* `_load()` helper with `lock=True` — `_load`'s own comment (line 720-725) states the
lock exists to "serialize concurrent settlement writes on this invoice so the cumulative
amount_paid update + ledger delta are atomic (no double-write / cap bypass)" — but
`create_credit_note` never asked for it. The debate stage (`docs/audit/agent-debate.md` §1)
reproduced this live on a real Postgres 16 cluster: two concurrent €300 + €400 partial credit
notes against a €1000 invoice left `credited_total` at €300, not €700. This is a reproduced
violation of the named non-negotiable invariant at `docs/plan/shared/00_MASTER_CONTEXT.md:89`
("No overpayment / no over-crediting, enforced under a row lock (`SELECT … FOR UPDATE`)").

An understated `credited_total` overstates `effective_total` — the exact cap `record_payment`
trusts (`issued.py:777-782`) to refuse an overpayment — so this single unlocked read silently
widens a real customer's overpay/over-credit exposure the moment two credit-note requests ever
overlap (a double-click, two open tabs, a retried integration call — all realistic even under
a single supervised pilot user). Every customer's AR ledger integrity depends on this number;
fixing it removes the only reproduced financial-correctness P0 blocking Milestone A (any pilot).

### Scope

**In scope:**
- `backend/app/api/routes/issued.py::create_credit_note` — pass `lock=True` on the existing
  `_load()` call (line 620), mirroring `record_payment`'s call (line 770). No new helper, no
  new parameter on `_load`.
- One new Postgres-only concurrency test, mirroring `tests/test_payment_run_pay_concurrency.py`
  and `tests/test_numbering_concurrency.py`'s skip/engine pattern, that fires two genuinely
  concurrent partial credit-note requests **through the real HTTP API** (not the service
  function directly) against the same €1000 invoice and asserts `credited_total` lands at the
  SUM of both credits (€700), not a lost update.

**Out of scope:**
- Any other row-lock gap (R4 expense-approval SoD/concurrency, R6 reimbursement maker≠checker)
  — separate roadmap items, own work orders.
- Any change to `_load()`'s signature, `record_payment`, or the numbering/issuer lock — both
  already correct and already tested; touching them risks the exact regression this order
  exists to prevent.
- Any change to the credit-note business rules (partial/full credit computation, the
  one-cent rounding tolerance, the `already_credited` helper) — the fix is concurrency-safety
  only, zero behavior change to the single-request path (proven by `test_credit_notes.py`
  passing unmodified).
- CI wiring of the new test file into `.github/workflows/ci.yml`'s `postgres` job — that job
  currently runs only `test_rls.py`/`test_numbering_concurrency.py` (a pre-existing gap
  `test_payment_run_pay_concurrency.py` also has); wiring is left to whoever owns that gap,
  not invented here.

### Implementation guidance

1. Edit `issued.py:620` to add `lock=True`. One-line change; no other line in
   `create_credit_note` moves — the issuer lock at line 646 still comes second (invoice row,
   then issuer row — the same lock ORDER `record_payment`+`issuer.lock` callers already use
   elsewhere, so no new deadlock class).
2. Write `tests/test_credit_note_concurrency.py`:
   - Same `PG_URL = os.environ.get("RLS_TEST_DATABASE_URL")` / `pg_only` skip pattern as the
     two existing Postgres-only concurrency tests.
   - Build a dedicated `create_async_engine(PG_URL, ...)` + `async_sessionmaker`, independent
     of `tests/conftest.py`'s SQLite `_db` fixture (SQLite's single shared connection cannot
     reproduce the race — this must run on real Postgres, same as its siblings).
   - Drive the flow through the **real FastAPI app** via `httpx.AsyncClient` +
     `ASGITransport(app=app)`, overriding `app.dependency_overrides[get_session]` to bind to
     the Postgres engine (the same override shape `tests/conftest.py::client` uses for
     SQLite) — register an org (`POST /api/v1/auth/register`), `PUT /api/v1/issuer`, enable
     the `issuing` module, then `POST /api/v1/issued` a single-line €1000.00 invoice
     (`vat_rate=0` so gross == net == 1000.00, avoiding rounding noise).
   - Fire two concurrent `POST /api/v1/issued/{id}/credit-note` calls (one €300.00 line, one
     €400.00 line) via `asyncio.gather`, using an `asyncio.Barrier(2)` (or `asyncio.Event`)
     to maximize overlap, exactly as `test_payment_run_pay_concurrency.py::pay` does.
   - Assert both requests return `201` (two independent partial credits, both individually
     within the un-credited remainder — no business-rule rejection expected) and that
     `GET /api/v1/issued/{id}` afterwards shows `credited_total == "700.00"` — the SUM, not a
     lost update.
   - Clear `app.dependency_overrides` in a `finally` block so this test cannot leak state into
     a later test in the same process.
3. Prove the fix both ways on the scratch Postgres cluster, per the task brief: revert the
   `lock=True` locally, run the new test, confirm it FAILS (reproduces the lost update:
   `credited_total` at €300 or €400, not €700); reapply the fix, run again, confirm it PASSES.

4. Confirm `tests/test_credit_notes.py` passes unmodified (same file, same assertions, same

### Invariants this order must preserve

- **§4/13 — No overpayment / no over-crediting, enforced under a row lock.** This order closes
  the one code path that violated it; proven by the new concurrency test on real Postgres
  (SQLite cannot exercise a real row lock).
- **§4/16 — every mutating operation is audited.** `create_credit_note` already calls
  `audit.record(..., audit.A.ISSUED_CREDIT_NOTE, ...)` inside the same transaction as the
  `credited_total` write; adding the lock does not move that call or change what it records.
- **§4/20 — wire contract frozen.** No response shape, status code, or error payload changes
  for the non-concurrent path (`test_credit_notes.py` unmodified); the concurrent path still
  returns `201` for both legitimate concurrent partial credits (they don't collide on the
  *business* cap, only on the previously-racy bookkeeping write) — this order does not turn a
  previously-`201` case into a `409`; it makes the arithmetic correct.

### Rollback strategy

Pure code revert (`git revert` of the commit) — no migration, no schema, no one-way effect.
The lock is a transaction-scoped `SELECT … FOR UPDATE`; removing it returns the code to its
prior (racy) behavior with no data left in an inconsistent state by the revert itself. No
narrow mitigation needed short of a full revert — the change is a strict safety tightening
with no new failure mode introduced (the lock is already proven safe at `record_payment`).
