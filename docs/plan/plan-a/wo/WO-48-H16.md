# WO-48 — Dogfood fallback: bill our own customers through our own AR module (H1.6)

<!-- ═══════════════ COPY FROM HERE: WO-48 ═══════════════ -->

**WORK ORDER 48 — Dogfood fallback: bill our own customers through our own AR module (H1.6). Effort S (1–2d). Priority P1. Milestone M2. Depends on: nothing.**

### Objective and business value

Verified evidence, read at `HEAD=fbdee00` (repo tip when this order was opened; baseline suite 1157
passed / 8 skipped): `app/services/scheduler.py::DAILY_KINDS` enqueues exactly three per-tenant daily
jobs (`recurring.generate`, `dunning.run`, `ap.due_alerts`) plus `everypay.charge_mit` for EveryPay
subscribers and `billing.report_usage` for Stripe subscribers — **nothing generates a recurring
invoice for a tenant's own InvoiceIQ subscription fee.** `app/services/billing.py` only ever *applies*
a plan/status change reported by a live provider (`apply_subscription_event`/`charge_renewal`); with
`NullProvider` active (`settings.active_billing_provider == "none"`, the default, per ADR-0013
"operationally dead") an org can self-service-switch to a PAID plan via `PUT /billing/plan` (allowed
today whenever `not settings.billing_enabled`, `app/api/routes/billing.py:86`) and nothing ever bills
them for it — no invoice, no reminder, no collection path of any kind. `ARCH_plan.md`'s M2 exit
criteria name this exact gap and its fix: *"Fallback that de-risks the whole milestone: we can invoice
our own customers through our own AR module (dogfooding) if Stripe credentials slip. Revenue is not
blocked on a provider"* (line 479), and the Epic-H breakdown gives H1.6 its own acceptance criterion,
independent of H1.1/H1.4: *"we can issue and collect a real subscription invoice without Stripe"*
(line 1029-1031, "Deps: none").

Who pays more for this gap: H1.1 (live Stripe/EveryPay credentials) and the seller-of-record VAT
process are **owner-blocked** (`docs/DECISIONS-NEEDED.md` §2) with a legal/finance lead time measured
in weeks — WO-47 already shipped the quota-metering substrate those providers will meter against, but
until credentials land, **every pilot customer already switched to a paid plan is receiving the
product for free with no invoice ever produced**, and the operator has no artifact to hand a customer
who is willing to pay by bank transfer today. This order closes that gap without waiting on the
owner-blocked items: it reuses the SAME accounts-receivable module every tenant already uses on their
OWN customers (`issuer.py`'s numbering, `issued_service.build_invoice`'s one true construction path,
the existing PDF/XML/send/dunning surface, all shipped and tested in M1) so InvoiceIQ can invoice its
own subscribers TODAY, collect by bank transfer, and switch over to Stripe/EveryPay later without
having left months of subscription revenue uninvoiced.

### Scope

**In scope**
- `backend/app/core/config.py` — two new settings: `platform_org_id` (which of the platform's own
  organizations — created via the ordinary signup flow like any tenant — issues the invoices; unset =
  the whole feature is an inert no-op) and `platform_subscription_vat_rate` (defaults to `0`, a
  placeholder — see Out of scope); a `dogfood_billing_enabled` property (`platform_org_id` set AND
  `not billing_enabled`, so a tenant is never double-invoiced once a live provider goes live).
- `backend/app/models/issued_invoice.py` — two new nullable columns on `IssuedInvoice`,
  `subscription_org_id` (FK → `organizations.id`, `ondelete=SET NULL`) + `subscription_period` (Date),
  plus `UniqueConstraint("org_id", "subscription_org_id", "subscription_period")` — the exact idiom
  already used for `recurring_id`/`recurring_period`, giving cross-worker idempotency per
  (subscriber org, calendar month) for free.
- `backend/alembic/versions/<new>_dogfood_subscription_billing.py` (**new**) — the two columns + index
  + unique constraint on the EXISTING `issued_invoices` table (no new tenant table, so RLS/model
  set-equality — §4.2 — is untouched).
- `backend/app/services/platform_billing.py` (**new**) — `orgs_due_for_subscription_invoice` (every
  ACTIVE org other than the platform org itself, whose plan has a price, with no invoice yet for the
  period) + `bill_subscriptions` (the orchestrator: gate check, issuer row lock, one
  `issued_service.build_invoice` call per due org, idempotent per period, audited, never raises on a
  business no-op).
- `backend/app/services/job_handlers.py` — new job kind `PLATFORM_BILLING_RUN =
  "platform.bill_subscriptions"` calling `platform_billing.bill_subscriptions`.
- `backend/app/services/scheduler.py` — enqueue `PLATFORM_BILLING_RUN` ONCE per day total, carried by
  `platform_org_id` itself (a real `organizations` row, so no synthetic "carrier" needed, unlike the
  FX refresh), gated on `settings.dogfood_billing_enabled`.
- `backend/app/services/audit.py` — new action `PLATFORM_SUBSCRIPTION_INVOICE =
  "platform.subscription_invoice"`.
- `backend/tests/test_platform_billing.py` (**new**) — service-level + scheduler-wiring + tenancy
  tests (see Testing requirements).
- `docs/architecture/adr/0013-billing-metering.md` — a new "Status of implementation" bullet
  documenting the dogfood path, its gating, and the VAT placeholder.
- `docs/DECISIONS-NEEDED.md` — new §2b: the operational activation steps (create/designate the org,
  complete its issuer profile via the existing `/issuers` screen, set `PLATFORM_ORG_ID`) and an
  explicit flag that the 0% VAT placeholder needs a real rate/scheme once §2's seller-of-record
  decision lands — **this order does not decide that rate**.
- `TODO.md` — mark WO-48 `Completed` under M2, following the WO-47 precedent.

**Out of scope**
- **Stripe/EveryPay credentials, webhook, Billing Meter (H1.1/H1.4)** — owner-blocked, untouched.
  `docs/DECISIONS-NEEDED.md` §2.
- **Payment collection of any kind.** This order GENERATES and enables DELIVERY of an invoice only —
  it never charges a card, never touches `billing_provider.py`, never marks an invoice paid
  automatically. "Collect" in H1.6's acceptance criterion means the pre-existing manual AR path this
  order plugs into: the operator records a bank-transfer receipt via the ALREADY-SHIPPED `PATCH
  /issued/{id}/payment` route, exactly as any tenant already does for their own customers.
- **The exact VAT rate/scheme our own subscription invoices should carry.** This is the seller-of-record
  VAT question already recorded as owner-blocked in `docs/DECISIONS-NEEDED.md` §2 ("we are
  seller-of-record… decision: enable Stripe Tax, and own the filing process"). Inventing a rate here
  would be exactly the kind of business/legal fact §9 of the master context forbids guessing. This
  order applies an explicit, honest **0% placeholder** (asserts nothing, charges nothing extra) via a
  named, sysadmin-overridable setting (`platform_subscription_vat_rate`) and records the open item in
  §2b — the moment finance decides, changing one setting (or, if a scheme like reverse-charge is
  chosen, a follow-up order) is all that's needed; the generation mechanism itself does not change.
- **Which legal entity issues the invoice / real signed contracts with pilot customers.** Not decided
  or fabricated in code. `platform_org_id` names an ordinary `organizations` row the operator creates
  through the SAME signup flow every tenant uses, and its real legal name/VAT/address is entered
  through the SAME `/issuers` screen every tenant already has — zero new data-entry surface, zero
  invented legal facts. No contract/acceptance-act gate is asserted either (the generated invoices
  carry no `partner_id`, exactly like an unlinked recurring invoice today) — this order does not claim
  a signed contract exists.
- **Auto-populating the subscriber's billing-contact email.** `buyer_email` is left unset; the
  operator sets it via the already-shipped `PATCH /issued/{id}` (buyer_email is already a patchable
  field) or supplies an override recipient on `/issued/{id}/send`. Auto-lookup of an org's owner email
  would require an unscoped cross-tenant `User`/`Membership` join outside this order's footprint — a
  small, separate follow-up, not required for H1.6's acceptance criterion.
- **H1.2 (plan-ladder reconciliation) and H1.5 (in-product usage/upgrade surface).** Separate M2 line
  items; H1.5 explicitly depends on H1.4 (owner-blocked) per `ARCH_plan.md`.
- **PDF delivery / dunning automation code.** Not written — reused verbatim. The generated invoice is
  a normal row in the platform org's `issued_invoices`, so the EXISTING `/issued/{id}/send` route and
  the EXISTING daily `dunning.run` job already cover it with zero new code (the platform org is just
  another row the per-org `DAILY_KINDS` loop already visits in `scheduler.enqueue_daily`).

### Implementation guidance

1. **Confirm the gap first** (already done above): `scheduler.DAILY_KINDS` has no subscription-billing
   entry; `billing.py` only ever reacts to a provider event; `PUT /billing/plan` already lets an org
   self-service onto a paid plan with `billing_enabled=False`. Read all three before writing code.
2. **`platform_billing.bill_subscriptions` must be a pure no-op unless
   `settings.dogfood_billing_enabled`** — checked FIRST, before any query, so an unconfigured
   deployment (the default) is byte-identical to before this order (matches the `tenancy.py`
   off-by-default pattern already established in this codebase).
3. **Scope writes to the platform org explicitly inside the service**, via
   `set_current_org(platform_org_id)`/`reset_current_org` in a try/finally — do not rely on the
   caller (job runner) having already scoped it; `billing.apply_subscription_event` is the precedent
   for this nesting-safe pattern.
4. **Reuse `issuer_svc.lock` + `issued_service.build_invoice` exactly as `recurring._generate_one`
   does** — do not reimplement numbering or the seller snapshot. Build an `IssuedInvoiceCreate` with
   `buyer_name=org.name`, one line (`description` naming the plan + billing month, `unit_price=
   plan.price_eur`, `vat_rate=settings.platform_subscription_vat_rate`), `vat_scheme="standard"`,
   `issue_date=today`; leave `payment_terms_days`/`due_date` to the issuer's own default (never invent
   a number). Stamp `inv.subscription_org_id`/`inv.subscription_period` after `build_invoice` returns
   (mirrors `recurring._generate_one` stamping `recurring_id`/`recurring_period`), `db.add`, `flush`
   (assigns the number), then move to the next org — one `issuer_svc.lock` call covers the whole sweep
   for race-free numbering, matching `recurring.generate_due`.
5. **`orgs_due_for_subscription_invoice` filters:** `Organization.id != platform_org_id`,
   `Organization.status == "active"` (a manually canceled/suspended tenant — via `PATCH
   /platform/tenants/{id}` — is never re-invoiced even if its `plan` string is stale), and
   `plans.plan_for(org.plan).price_eur` truthy (excludes `trial`/`enterprise`, exactly like
   `billing.orgs_due_for_charge`'s existing filter). The period bucket is `today.replace(day=1)` — one
   invoice per (subscriber, calendar month); idempotency is the unique constraint, not a stored
   "next charge date" (deliberately simpler than EveryPay's `everypay_next_charge` scheduling field —
   this is a generation fallback, not a payment scheduler).
6. **Guard the missing/misconfigured platform org.** `bill_subscriptions` does `db.get(Organization,
   platform_org_id)`; `None` → return an empty result (never raise), matching
   `billing.apply_subscription_event`'s "no tenant → no-op" precedent.
7. **Migration:** `alembic revision --autogenerate`, then hand-edit — this is an ADD-COLUMN on an
   EXISTING tenant table (`issued_invoices` already has RLS from its original migration), so no new
   RLS policy is needed (§4.2 concerns only a NEW tenant table). Confirm `tests/test_rls.py::
   test_rls_migration_covers_every_tenant_table` still passes unmodified — the tenant-table SET is
   unchanged, only its column list grows.
8. **Delivery is out of this order's code** (see Out of scope) — verify by hand, not by writing new
   code, that `POST /issued/{id}/send` and the daily `dunning.run` job already work against a
   dogfood-generated invoice once a test creates one (a single assertion in the test file is enough:
   after `bill_subscriptions`, log into the platform org and hit `/issued` — the invoice is there,
   ordinary AR from that point on).

### Invariants this order must preserve

- **§4.9/§4.10 (money: Decimal, server recomputes totals)** — `unit_price=plan.price_eur` passes an
  `int` into `IssuedLineIn.unit_price: Decimal` (exact, no float path); `issued_service.build_invoice`
  is the SAME totals-computation path every other invoice uses (`vat.compute`) — this order invents no
  new money arithmetic.
- **§4.1–§4.3 (tenant isolation)** — the generated invoice lives in the platform org's OWN
  `issued_invoices` rows (`org_id=platform_org_id`), subject to the SAME RLS policy as every other
  tenant's AR data; `subscription_org_id` is a plain reference column (like `customer_id`/`partner_id`
  already are), not a second tenant-scoping dimension — proven by a cross-tenant test (a
  non-platform-org login sees none of the platform org's invoices, opaque 404 on direct id fetch).
- **§4.16 (every mutating operation is audited)** — `A.PLATFORM_SUBSCRIPTION_INVOICE` recorded in the
  SAME transaction as the invoice insert, `meta` carries `subscriber_org_id`/`plan`/`period`/`number`
  (no secret/bank data).
- **§4.18 (an issued document is immutable)** — the generated invoice is a normal `issued_service.
  build_invoice` output; correction is by credit note like any other issued invoice, unchanged.
- **Roadmap guardrail "revenue is not blocked on a provider" (M2 exit criteria / H1.6)** — proven by
  the acceptance criteria below: an invoice is issued and can be recorded as paid with zero Stripe/
  EveryPay configuration.

### Database / migration impact

Two new NULLABLE columns on the EXISTING `issued_invoices` table: `subscription_org_id` (GUID, FK →
`organizations.id`, `ondelete=SET NULL`, indexed) and `subscription_period` (Date). New
`UniqueConstraint("org_id", "subscription_org_id", "subscription_period",
name="uq_issued_invoices_subscription_period")` — harmless for every pre-existing row (both columns
NULL there; NULLs are distinct under a unique constraint in both SQLite and Postgres, so no
back-fill collision). No new tenant table, so no RLS policy is added (none is needed — `issued_
invoices` already carries one). Backfill: none required (both columns default NULL, meaning "not a
subscription invoice", the correct value for every existing row). Downgrade drops the two columns +
constraint; what is lost: only the subscriber/period tagging (the invoice document itself, if any were
generated, is untouched by the downgrade — only future dogfood generation would lose its idempotency
tracking until re-upgraded).

- `test_idempotent_per_org_per_month` — calling `bill_subscriptions` twice for the same `today` (or a
  later date in the SAME month) yields exactly ONE invoice per org for that month (the unique
  constraint / due-query intersection, both proven).
- `test_next_month_bills_again` — a second call with `today` advanced a month yields a SECOND, distinct
  invoice (`subscription_period` advances; two invoices total for that org).
- `test_scheduler_enqueues_the_daily_job_once_when_enabled` — `enqueue_daily` produces exactly ONE
  `platform.bill_subscriptions` job (not one per tenant), carried by `platform_org_id`.
- `test_generated_invoice_is_ordinary_ar_from_here` — after `bill_subscriptions`, log in as the
  platform org and `GET /api/v1/issued` shows the invoice; `POST /issued/{id}/send` and `PATCH
  /issued/{id}/payment` work unmodified (proves zero new delivery/collection code is needed).
- `test_cross_tenant_isolation` — a THIRD, unrelated org (neither the platform org nor a subscriber)
  sees zero of the platform org's invoices via its own `/issued` list, and a direct fetch by id is a
  404 (never 403).
- `test_missing_platform_org_is_a_safe_noop` — `platform_org_id` set to a nonexistent id →
  `bill_subscriptions` returns `invoiced=[]`, never raises.

### Rollback strategy

Migration downgrade drops the two columns + unique constraint — safe, loses only the subscriber/period
tagging used for idempotency (see Database/migration impact). A code-only revert without the migration
downgrade is safe in the OTHER direction (dropping the code first, leaving the columns, is harmless —
they simply go unused), but the reverse (reverting the migration while the code is still deployed)
would 500 on the missing columns, so always downgrade the migration in the SAME step as reverting the
code, migration-downgrade-before-code-revert. The narrowest mitigation that doesn't require a full
revert: unset `PLATFORM_ORG_ID` — the feature goes instantly inert with no data loss, no migration
touch needed (this is the primary, cheap kill switch).
