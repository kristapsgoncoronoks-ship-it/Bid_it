# WO-24 — Multi-currency reporting: analytics, benchmark, budget (board C1.7)

**WORK ORDER 24 — Multi-currency reporting (board C1.7). Effort M (3–5d). Priority P1. Milestone M1. Depends on: C1.2, C1.3 (both shipped in WO-8).**

### Objective and business value

Verified evidence, read straight off `HEAD=1e6c561`:

- `app/services/analytics.py::summary` sums `Invoice.total` across every currency the tenant has ever invoiced in, then returns `currency="EUR"` — a hard-coded label, not a computed one (line 91). `spend_over_time`, `top_vendors`, `by_category`, `by_dimension`, `by_status` all do the same raw cross-currency `func.sum(Invoice.total)` / `func.sum(LineItem.amount)` with **no currency filter and no currency field in the response at all** — a EUR+USD tenant's "top vendor" total is a meaningless blend of two currencies with no unit.
- `app/services/benchmark.py::supplier_benchmarks` sums `Invoice.total` per vendor across every currency with no filter (a vendor billing in both EUR and USD gets one blended `total_spend`). `combined_benchmark` sums `LineItem.amount` per category the same way and returns `BenchmarkSummary.currency="EUR"` hard-coded (line 222) regardless of what was actually summed.
- `app/services/budget.py::_gross_eur` (lines 51–55) is subtler: it **does** attempt a real EUR conversion (`Invoice.total_eur`), but when `total_eur` is `NULL` — which is exactly the `fx_source="unknown"` case §4.15 defines as "no rate available, never guess" — it falls back to `coalesce(Invoice.total_eur, Invoice.total) / Invoice.total`, i.e. a ratio of **1**. That silently treats an unconvertible foreign invoice as if it were already EUR: a §4.15 violation with a live symptom (`fx_source="unknown"` invoices already exist per `tests/test_money_invariants.py::test_expense_path_unknown_currency_refuses_never_guesses`'s sibling case on the invoice path).
- The frontend compounds all three: `frontend/src/lib/format.ts::money()` defaults to `currency="EUR"` when none is passed, and every one of `Dashboard.tsx`'s `SpendSnapshot`, `Charts.tsx`'s `SpendChart`/`VendorBar`/`CategoryPie`, and `Benchmark.tsx`'s `IndependentView`/`CombinedView` calls `money(x)` with no currency argument — so a blended non-EUR total is additionally **rendered with a € sign**, and `Benchmark.tsx` line 28 literally prints the caption "Indicative — EUR."

This is the same defect class WO-8 (C1.2/C1.3) already closed in `ap_aging.summarize`, `reimbursement.eur_of` and `payment_run.eur_of`, and that `app/services/issued_reports.py` (the AR reports) never had — `issued_reports._pick_currency` resolves the tenant's most-used currency, filters every query to it, and surfaces `available_currencies` instead of guessing or blending. ARCH_plan (`docs/plan/plan-a/ARCH_plan.md` C1.7) is explicit: *"Follow the AR reports' correct pattern: a currency filter, never a cross-currency sum."* Business value: these three surfaces are exactly what a finance lead reads to decide "am I over budget" and "which vendor costs me the most" — a blended-currency number that is silently wrong, or a real conversion that silently guesses 1:1 for a currency with no rate, produces a decision made on a fabricated figure. The FI-10 invariant (`docs/plan/plan-a/ARCH_plan.md` line 1452) names this exact generalisation as owed.

### Scope

**In scope**
- `analytics.py`: every function that sums money gets the AR pattern — resolve one currency (explicit `currency` param, else the tenant's most-used), filter every query to it, surface `available_currencies`. Row-shaped endpoints (`spend_over_time`, `top_vendors`, `by_category`, `by_status`) are wrapped in a small `{currency, available_currencies, rows}` envelope (a wire-shape change, coordinated with the schema, the route and the SPA per WO-8's precedent). `by_dimension`'s existing `DimensionBreakdown` object gets the two fields added (additive — it is already an object).
- `benchmark.py`: `supplier_benchmarks` gets the same currency filter + envelope; `combined_benchmark`'s `BenchmarkSummary.currency` becomes the real resolved value (not hard-coded) with `available_currencies` added (additive — `CombinedBenchmark` is already an object).
- `budget.py`: fix the `_gross_eur` 1:1-guess fallback — an invoice that cannot convert (`currency != "EUR"` and `total_eur IS NULL`) is **excluded** from the actual, never guessed at parity; `BudgetOverview` gets an additive `excluded_unconverted` count for the requested month so the exclusion is visible, not silent. Budget's own single-canonical-EUR design (documented in its module docstring) stays — this order does not redesign it (that redesign, if wanted, is I1.9, which explicitly depends on this order).
- Matching schema (`app/schemas/analytics.py`, `app/schemas/benchmark.py`, `app/schemas/budget.py`) and route (`app/api/routes/analytics.py`) changes; an optional `currency` query param added to every touched analytics/benchmark endpoint (mirrors `explore.py`'s existing filter).
- Frontend: `frontend/src/lib/types.ts` (new/changed shapes), `frontend/src/pages/Dashboard.tsx`, `frontend/src/components/Charts.tsx`, `frontend/src/pages/Benchmark.tsx`, `frontend/src/pages/Budget.tsx` — pass the real currency into `money()`/`compactMoney()` instead of relying on its EUR default; drop the hard-coded "Indicative — EUR." caption.
- `tests/test_analytics.py`, `tests/test_benchmark.py`, `tests/test_budget.py`, `tests/test_money_invariants.py` (generalise `test_issued_report_never_sums_across_currencies`'s shape to these three services).

**Out of scope**
- Redesigning budget's household-vs-corporate currency model (I1.9 — explicitly deferred, "decide in/out, do not half-build").
- `explore.py`'s own currency handling (C1.6 already unified its dimension registry; its `currency` filter is optional/manual today and is a separate, smaller gap — not named in C1.7's file list, not touched here).
- Any change to `fx.py`'s conversion convention or `CURRENCY_BY_CODE`/`ALL_CURRENCIES` registry (C1.2/C1.5, already shipped) — this order reuses them, never forks them.
- A new shared "pick currency" utility module — mirrors the existing convention of a local `_pick_currency` per reporting module (`issued_reports.py`, `ap_aging.py` each already have their own); introducing a shared abstraction is a refactor for another order, not a C1.7 requirement.

### Implementation guidance

1. **Characterise first.** Run `tests/test_analytics.py`, `tests/test_benchmark.py`, `tests/test_budget.py` green at `HEAD` before touching anything — all three fixture sets are single-currency (EUR, the schema default), so today's numeric assertions are accidentally correct despite the underlying bug. They must **still pass unmodified** after this order (single-currency behaviour is unchanged by construction: with one currency present, "the most-used currency" is that currency and "available_currencies" is `["EUR"]`).

2. **`analytics._pick_currency`** — copy `issued_reports._pick_currency`'s exact shape (group `Invoice.currency` by count over `org_id` only, not date-scoped — matches the AR pattern so the "currencies present" answer doesn't flicker with the report window): resolve `(currency, available)`, uppercase an explicit param, default to the most-used (first row) or `"EUR"` when the tenant has no invoices at all.

3. **Filter, don't post-process.** Add `Invoice.currency == cur` to `_scope` (or a sibling filter) so every existing SQL aggregate becomes single-currency **at the query**, not by discarding rows in Python after the fact — keeps the "aggregation happens in the database" property the module's docstring already promises.

4. **Row-shaped endpoints get an envelope, not a per-row currency field.** `spend_over_time`, `top_vendors`, `by_category`, `by_status` currently return bare `list[X]`. Wrap each in a small schema `{currency: str, available_currencies: list[str], rows: list[X]}` (name the field `rows` — matches `DimensionBreakdown`'s existing convention in the same file). This is a wire-shape change (list → object): update the schema, the route's `response_model`, and the SPA's consumer together, in the same commit, and say so explicitly in the report (WO-8 precedent, `docs/plan/plan-a/wo/WO-08.md` step 6). Do **not** instead add a `currency` field repeated on every row — it is redundant with an object envelope and still leaves `available_currencies` undiscoverable.

5. **`by_dimension` and `combined_benchmark`'s summary are already objects** (`DimensionBreakdown`, `CombinedBenchmark.summary`) — just add the two fields, no shape change.

6. **`supplier_benchmarks`** currently returns a bare `list[SupplierBenchmark]`; wrap it the same way as step 4 (`SupplierBenchmarkList` or similar — name it to match the file's existing naming, e.g. suffix `List`).

7. **`budget._convertible()`** — a boolean SQL predicate: `(Invoice.currency == "EUR") | (Invoice.total_eur.is_not(None))`. Apply it as a `WHERE` clause (not a Python filter) in both `actuals_for_month` and `trend`'s queries. Compute the excluded-invoice count for the requested month with a second `COUNT(DISTINCT Invoice.id)` query using the negated predicate, scoped to the same `[start, end]` window; thread it through `overview()`'s return dict as `excluded_unconverted`. Do **not** apply the same accounting to `trend`'s other five months — the *exclusion filter* must still apply there (so those months' totals are correct), but the order does not require a per-month excluded count; state this trade-off explicitly in the report.

8. **Money basis.** Every quantity stays `Decimal`, rounded with `money.q2`/`q` exactly where it already is — no new float path. §4.9 applies unchanged.

9. **Route params.** Add `currency: str | None = Query(default=None, min_length=3, max_length=3)` to every touched `/analytics/*` endpoint (mirrors `explore.py`'s existing `currency` filter). Budget's route needs no new param — its currency is always EUR by design; only the exclusion count is new.

10. **Frontend.** `frontend/src/lib/format.ts::money()`/`compactMoney()` already accept an explicit `currency` argument — the fix is call-site discipline, not a new capability. Update `Dashboard.tsx`'s `SpendSnapshot`, `Charts.tsx`'s chart components (accept a `currency` prop, or read it off the new envelope's `currency` field passed down from the page), and `Benchmark.tsx` (both views) to pass the resolved `currency` through instead of relying on the "EUR" default. Remove the "Indicative — EUR." hard-coded caption in `Benchmark.tsx`; replace with the resolved currency (or drop the currency mention entirely if the KPI cards already label it).

### Invariants this order must preserve

- **§4.14** (no aggregate sums across currencies without a recorded conversion) — proven by the new mixed-currency tests: a EUR+USD tenant's `analytics.summary()`/`benchmark.combined_benchmark()`/`benchmark.supplier_benchmarks()` totals only the resolved currency, never both.
- **§4.15** (`unknown` yields `NULL`/exclusion, never a guessed number) — proven by `budget`'s new exclusion test: an invoice with `fx_source="unknown"` contributes `0` to `total_actual`, not its raw total.
- **§4.9** (Decimal only) — no new float path introduced; `mypy app` and the existing float-scan test stay green.
- **§4.20** (wire contract) — every change is additive at the field level; the four envelope changes are the only shape changes, and each is coordinated schema+route+SPA+tests in one commit, per WO-8's precedent for exactly this situation.
- FI-10 (`docs/plan/plan-a/ARCH_plan.md` line 1452) — this order **is** the generalisation FI-10 names; `test_issued_report_never_sums_across_currencies`'s shape is replicated for analytics/benchmark/budget.

### Database / migration impact

None. No new column, no new table — `Invoice.currency`, `Invoice.total_eur`, `Invoice.fx_source` already exist (WO-8). No RLS impact (`test_rls.py` unaffected — verify it stays green, don't assume).

### Rollback strategy

Pure application-code + schema-additive change, no migration. A `git revert` of this order's commit(s) is safe and complete — no data was written or backfilled, nothing to restore. If only the frontend envelope changes need reverting (e.g. an unforeseen SPA regression) while keeping the backend fix, that is also safe: the four wrapped endpoints are the only ones an unrevert-ed old frontend would call incorrectly (it would try to read a bare array where an object now sits) — so a *partial* revert must always revert backend-and-frontend together for those four endpoints, never one side alone.

### Documentation to update

`docs/architecture/adr/0010-money-tax-fx.md` — add a paragraph stating FI-10 is now generalised past AR/AP into analytics, benchmark and budget, and describing budget's "convert to EUR, exclude (never guess) what can't convert" variant of the pattern alongside AR/AP's "pick one currency, filter, surface the rest" variant, so a future reader knows both are sanctioned and why they differ (budget wants one canonical total across categories; analytics/benchmark are per-currency reports).
