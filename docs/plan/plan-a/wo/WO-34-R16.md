### Objective and business value

`frontend/src/pages/Issue.tsx`'s `VoidAction` (lines 308-339) and the "Write off" button inside
`DisputeActions` (lines 388-444) call `window.prompt(...)` directly in the `onClick` handler and fire the
mutation as soon as the browser-native prompt is dismissed with OK (even with an empty/whitespace reason) —
there is no branded, styled, explicit "are you sure?" step. This is inconsistent with `PaymentRuns.tsx`,
which uses the shared `ConfirmDialog` component (`frontend/src/components/ui/ConfirmDialog.tsx`) for its
re-export and missing-IBAN-acknowledgement flows — a `Modal`-based dialog with a title, explanatory body,
and explicit Cancel/Confirm buttons (`tone="danger"` renders the destructive-red `Button` variant). A raw
`window.prompt` is small, easy to fat-finger past (Enter submits with an empty reason), not visually
distinguished from a normal browser dialog, and gives no room to explain the consequence (voiding
permanently cancels a live receivable; write-off marks it uncollectible bad debt) the way `ConfirmDialog`'s
body copy does elsewhere in the app.

Who benefits: the bookkeeper persona (`docs/product/personas.md`'s "Marco", switching between many client
entities all day per `commercial-readiness.md` §5) is the exact user most exposed to a misclick on this
screen — `Issue.tsx` is the single largest page component in the app (1,034 lines) with ~12 text-only
action links per row. Giving Void/Write-off the same deliberate, styled confirm step already proven on
Payment Runs closes a real day-one trust/safety gap before self-serve general release, at zero backend risk
(both routes already validate state transitions and audit the action; see below).

### Scope

**In scope:**
- Replace `VoidAction`'s `window.prompt` with a `ConfirmDialog` (`tone="danger"`) that explains the
  consequence, offers an optional reason text input, and only calls `POST /issued/{id}/void` on explicit
  confirm.
- Replace the "Write off" button inside `DisputeActions` with the same `ConfirmDialog` pattern, gating
  `POST /issued/{id}/write-off`.
- A Playwright e2e spec covering the confirm-then-action flow for both, following the LIVE-app +
  `page.route` mocking pattern already used in `frontend/e2e/upload-duplicate.spec.ts` (not the
  `/design` fixture showcase, which per `00_MASTER_CONTEXT.md` is NOT wired to the live app).

**Out of scope:**
- Regrouping the ~12-action list into safe-vs-destructive visual groups — the roadmap's own text frames
  this as an "ideally" secondary suggestion, not the acceptance bar (`Acceptance: both actions require an
  explicit confirm step; existing test_issued_* backend tests unaffected`). It is a larger, separately
  reviewable layout change touching every action in the row (Mark paid/Record/Credit/Dispute/Duplicate/
  Email/Remind/View/PDF/XML) and risks regressing working, tested UI for a P2 item — left as a named
  follow-up in this WO's report, not started here.
- `Credit`, `Dispute`, `Issue`, `Cancel` (draft), and the recurring-schedule `delete` action, which already
  use `window.confirm`/`window.prompt` but are not named in the roadmap's R16 finding — no change.
- Any backend change. `POST /issued/{id}/void` and `POST /issued/{id}/write-off`
  (`backend/app/api/routes/issued.py:827-862` and `:579-599`) already validate lifecycle/state, refuse
  invalid transitions with 409/400, and call `audit.record(..., audit.A.ISSUED_VOID | ISSUED_WRITE_OFF, ...)`
  in the same transaction as the mutation — confirmed by reading the route handlers before starting. If a
  gap had been found here it would be flagged, not silently fixed under this WO's frontend-only scope.
- R18 — a separate, later work order.

### Implementation guidance
1. Import `ConfirmDialog` from `../components/ui` in `Issue.tsx` (already exported via
   `frontend/src/components/ui/index.ts`, same import PaymentRuns/Reimbursements/Vendors use).
2. `VoidAction`: add `confirmOpen`/`reason` state. The "Void" button opens the dialog instead of calling
   `window.prompt`. The dialog: title `Void invoice <number>?`, body explains the effect (permanent,
   removes it as a live receivable) plus an optional reason `<input>`, `confirmLabel="Void invoice"`,
   `tone="danger"`, `loading={doVoid.isPending}`. `onConfirm` calls `doVoid.mutate(reason)`; `onSuccess`
   closes the dialog and resets the reason (in addition to the existing `onDone` invalidation).
3. `DisputeActions`: same pattern for the write-off button — title `Write off invoice <number>?`, body
   explains it marks the invoice as uncollectible bad debt (kept in the audit trail), optional reason
   input, `confirmLabel="Write off as bad debt"`, `tone="danger"`.
4. Leave `Dispute`/`Resolve` (`window.prompt`/direct mutate) untouched — out of scope per above.
5. New e2e spec: mock `/auth/me`, `/auth/organizations`, `/modules` (issuing enabled), `/issuer` (complete),
   `/issued` (one issued invoice, lifecycle `issued`, no payments/credits), `/issued/{id}/void` and
   `/issued/{id}/write-off`. Assert: (a) clicking "Void" does NOT call the void endpoint immediately —
   the confirm dialog (`getByRole("dialog", { name: /Void invoice/ })`) appears first; (b) confirming calls
   the endpoint and the row updates (or `onDone`'s refetch is observed); (c) cancelling the dialog leaves
   the invoice unvoided and issues no network call to `/void`. Mirror the same three assertions for write-off
   against a second fixture invoice (since a voided invoice's row no longer renders `DisputeActions`).
