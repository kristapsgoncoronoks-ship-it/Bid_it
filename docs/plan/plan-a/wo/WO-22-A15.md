## Objective and business value

`app/core/authz.py::Role` declares **8** business roles and a complete
deny-by-default `ROLE_PERMISSIONS` matrix for all of them (proven by
`tests/test_authz.py::test_every_role_is_in_the_matrix`). But the only values
ever written to the stored role column are the 4 legacy ones —
`app/models/user.py::UserRole` has exactly `user_free`, `user`, `admin`, `owner`.
`authz.business_role()` is already forward-compatible (it resolves an
already-expanded stored value directly — `docs/security/authorization-policy-matrix.md`
states this explicitly under "How it works today"), but nothing can ever
*produce* one of those values: `Finance Manager`, `Accountant`, `Approver` and
`Auditor` are fully defined and enforced in the matrix yet structurally
unreachable — no admin, no invite, no SCIM/SSO path can ever assign them. This
was verified by reading `app/core/authz.py` in full (the `Role` enum has 8
members; `ROLE_PERMISSIONS` has a complete row for each) against
`app/models/user.py` (`UserRole` has 4 members) and confirmed by
`docs/security/identity-authz-gap-analysis.md` line 34/54 ("Role assignment 🟡
— Works, but only 4 roles").

Recon also found a **second, latent bug** the enum widening would otherwise
trigger in production: `app/services/access.py::LIMIT_DEFAULTS`/`ROLE_META` are
plain dicts keyed by the 4 legacy `UserRole` values, and
`app/api/routes/invoices.py`/`email.py` call `access.enforce_invoice_quota(db,
org_id, current.role)`/`enforce_upload_quota` with the caller's **raw stored
role** — so the moment any account is assigned one of the 4 new values, its
very next invoice upload or document upload raises an unhandled `KeyError` (a
500, not a graceful denial) inside `access._get_or_seed`. Widening the role
column without this fix would ship a role that is assignable but crashes the
product's two most common actions the first time someone uses it.

Who pays for this: any client big enough to need role separation beyond
"owner/admin/everyone else" — a controller who should approve but not post, a
bookkeeper who should post but not approve, an external auditor who should read
and export but touch nothing, a finance lead who runs the whole function short
of billing/user management. Today none of that is sellable; the accountancy-
practice beachhead segment (`docs/product/personas.md`) explicitly wants
segregation between these functions. Closing this makes the already-built,
already-tested permission matrix an actual product feature instead of a
row in a table nobody can reach.

## Scope

**In scope:**
- Widen the stored role vocabulary (`app/models/user.py::UserRole`) to include
  `finance_manager`, `accountant`, `approver`, `auditor` — matching
  `authz.Role`'s own string values exactly, so `authz.business_role()` resolves
  them with **zero** new mapping code (the forward-compat path already exists
  and is already tested by
  `test_authz.py::test_forward_compatible_with_expanded_role_values`).
- Fix the two dicts in `app/services/access.py` (`LIMIT_DEFAULTS`, `ROLE_META`)
  and `app/core/roles.py::ASSIGNABLE_ROLES`/`ROLE_RANK` so the quota gate and
  the system-limits matrix do not `KeyError` on a newly-reachable role and the
  admin-facing limits UI can configure them.
- Prove, through the real HTTP path (`role_client` + a live route), that each
  of the 4 newly-reachable roles gets **exactly** its matrix permissions when
  assigned — a granted case and a denied case per role, per the acceptance
  criterion in `ARCH_plan.md` ("an Auditor account can read everything + audit
  + export and write nothing; an Approver can approve but not write").
- Mirror the widened vocabulary in the frontend picker
  (`frontend/src/lib/types.ts::UserRoleName`, `frontend/src/lib/roles.ts`) so
  `Team.tsx`'s existing `ASSIGNABLE_ROLES.map(...)` render (already generic —
  no JSX change needed) actually offers the 4 new roles, and existing badges
  don't render `undefined` for a member who already holds one.
- Update `docs/security/authorization-policy-matrix.md` ("How it works today")
  and `docs/security/identity-authz-gap-analysis.md` (the role-assignment row)
  — both explicitly describe the gap this order closes; leaving them stale
  after the fix contradicts them.
- The actual role-**assignment** write path (`PATCH /team/members/{id}`,
  `POST /team/invites`) needs **no code change** — `MemberUpdate.role` and
  `InviteCreate.role` are already typed `UserRole` (Pydantic), so the moment the
  enum gains the 4 new members, both endpoints accept and persist them. This is
  called out explicitly so the self-verification step can prove it rather than
  assume it.

**Out of scope (explicitly, with rationale):**
- **No migration.** Recon of every migration referencing `user_role`
  (`alembic/versions/ec6b16191e19_initial_schema.py`,
  `alembic/versions/deb447b02296_memberships_table.py`) plus the column
  definition itself confirms there is **no CHECK constraint** on the role
  column: `SAEnum(UserRole, native_enum=False, length=20)` with the SQLAlchemy
  default `create_constraint=False` (verified against
  `sqlalchemy/sql/sqltypes.py` in the installed venv) compiles to a plain
  `VARCHAR(20)` — the enum membership is a **Python-side** contract only.
  `app/models/user.py`'s own docstring says this is deliberate: *"Stored as a
  portable VARCHAR (native_enum=False) so the role set can evolve without a
  Postgres ENUM migration."* `alembic/env.py` also never sets
  `compare_type=True`, so `alembic check`/autogenerate would not even notice a
  Python enum change. This order proves the "no migration" claim empirically
  (`alembic upgrade head && alembic check` before and after, zero diff) rather
  than asserting it — see Database/migration impact below. This is a deviation
  from `ARCH_plan.md`'s literal "Add a migration" phrasing; the underlying
  acceptance criterion (roles are genuinely assignable and functional) is met
  without one, and inventing a no-op migration would violate §10's
  no-placeholder-code prohibition.
- **`app/services/oidc.py::_ASSIGNABLE`** (SSO group→role mapping) and
  `app/services/scim.py`'s `default_role` provisioning stay restricted to the
  legacy 3 non-owner values. Expanding federated-identity default-role mapping
  to the 4 new roles is a real, separable feature (a new IdP-group naming
  convention, its own tests) — not required by A1.5's acceptance criterion,
  which is about direct in-app assignment (`role.assign`). Flagged as a
  follow-up below.
- **The expense-report `POST /expenses/{id}/decision` endpoint's flag-based
  "designated approver" gate is intentionally left untouched.** Recon
  (`app/api/routes/expenses.py::_is_approver`) found that *deciding* an expense
  report requires the pre-existing `is_expense_approver` **flag**, not merely
  `EXPENSE_APPROVE` (the router-level dependency `_APPROVE` is necessary but
  not sufficient — the in-handler check is stricter, by design, matching the
  existing documented "two-person control" pattern in
  `authorization-policy-matrix.md`). Widening `UserRole` does not touch this;
  a member assigned `approver` still needs the flag appointed separately (same
  as an `admin` or `owner` needs it today) to decide an expense report. This
  order proves the Approver role's `INVOICE_APPROVE` permission end-to-end
  instead (`POST /invoices/{id}/validate`, which has no such flag), which is
  sufficient to satisfy "an Approver can approve but not write" — re-deciding
  whether expense decisions should also honour the role directly is a product
  question for a separate order, not a reachability defect.
- Re-deciding any permission in `ROLE_PERMISSIONS` — the matrix's *content* is
  presumed correct (already reviewed/tested); this order only makes it
  reachable.
- C1.5, C1.7, C1.9 — real, remaining M1 work, explicitly left for a later run.

## Implementation guidance

1. **`app/models/user.py` first.** Add the 4 enum members with the exact string

   their legacy string values; `authz._LEGACY_ROLE` already maps them and this
   order does not touch that map.
2. **Fix the two dicts that would otherwise `KeyError`** —
   `app/services/access.py::LIMIT_DEFAULTS` and `::ROLE_META`. Give all 4 new
   roles `(0, 0)` (unlimited), `"paid": True`, matching the existing treatment
   of `admin`/`owner` — these are professional/business roles, not a
   free/paid-tier distinction. Write a one-line description per role drawn from
   the existing `authz.ROLE_PERMISSIONS` docstring comments (already written,
   just copy the intent, do not invent new scope).
3. **`app/core/roles.py`** — add the 4 new roles to `ASSIGNABLE_ROLES` (used

   reserved for `admin`/`owner`. This keeps the existing defense-in-depth

4. **Frontend mirror.** `frontend/src/lib/types.ts::UserRoleName` and

5. **Money/rounding:** not touched by this order.
6. **Gate fail-open/closed statement:** `authz.require`/`permissions_for` is
   unchanged and remains deny-by-default (an unrecognised role already falls
   back to `Role.READ_ONLY`, least privilege — this order does not touch that
   fallback, it only makes 4 more values recognised instead of falling into
   it). The quota gate (`access.enforce_*_quota`) fails **safe-but-broken**

   fail **open** (unlimited, `(0, 0)`) for the 4 new roles, matching the
   existing treatment of every non-quota-limited role (`admin`, `owner`). This

7. **Test order:** write `test_access.py`'s regression test FIRST (assign

## Rollback strategy

Pure code change — no migration to downgrade, nothing one-way. If any account
were assigned one of the 4 new roles before a revert, the raw stored string
(`"finance_manager"` etc.) would remain valid VARCHAR data even after
reverting `UserRole` to 4 members (SQLite/Postgres both accept it — there is
no CHECK constraint to violate) but would then fail `UserRole(val)` parsing on
load and `authz.business_role()`'s `except ValueError` branch would fall back
through `_LEGACY_ROLE.get(val, Role.READ_ONLY)` to **`Role.READ_ONLY`** (least
privilege — fails safe, not open). The practical mitigation if a revert is
ever needed post-assignment: reassign those specific members back to a legacy
role via `PATCH /team/members/{id}` before deploying the revert, to avoid
surprising an admin who assigned `finance_manager` with an unexpected
read-only downgrade. Full revert is a plain `git revert` of this order's
commit(s) — no data transformation, no session revocation beyond the normal
role-change re-auth (`team.revoke_member_sessions`, unchanged, already fires
on any role change).
