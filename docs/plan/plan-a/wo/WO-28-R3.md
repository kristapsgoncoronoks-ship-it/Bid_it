**WORK ORDER 28 — Seed data must drive AP invoices through the real workflow so `workflow_state` never diverges from the legacy `status` (board R3). Effort S 1–2d. Priority P0. Milestone A. Depends on: nothing.**

### Objective and business value

`backend/app/seed.py::seed()` (lines ~137-246) sets `Invoice.status` (the legacy aging enum:
`draft`/`pending`/`paid`/`overdue`) directly via `rng.choices(...)` on all ~83 domestic AP
invoices, plus unconditionally on 6 foreign-currency invoices, but never drives any of them
through `/submit` → `/approve` → `/transition` (schedule) → payment-run `/pay`. `Invoice`
carries a SECOND, canonical field — `workflow_state` (`app/models/invoice.py:136-142`,
default `draft`) — which is what every real payables surface reads:
`cash_position.py::_ap_summary` (`Invoice.workflow_state.in_(_PAYABLE_STATES)`,
`_PAYABLE_STATES = (approved, scheduled_for_payment, partially_paid)`),
`payment_run.py::payable_invoices` (`workflow_state == scheduled_for_payment`), and
`ap_aging.py` (the same `_PAYABLE_STATES` filter). Because seed.py never advances
`workflow_state` past its `draft` default, every one of those reads €0 for a freshly seeded
demo org, while `/invoices` — which reads the legacy `status` column — shows the full
>€1,063,592.82 across the same rows. This is a reproduced page-to-page contradiction on the
officially documented, customer-facing demo login (`demo@invoiceiq.app` / `demo1234`), root
-caused independently in `docs/audit/commercial-readiness.md` §3 and
`docs/audit/agent-debate.md` §8.

This blocks the ability to even *demo* the product credibly — Milestone A explicitly requires
it fixed before any pilot conversation, hand-held or not, because a prospect who clicks from
Invoices to Cash Position on the FIRST demo screen sees the two numbers a finance buyer cares
about most (what's owed, what's overdue) silently contradict each other. The fix is
zero-risk to production code: it is entirely confined to the demo-data generator
(`app/seed.py`), calling the SAME `/submit`, `/approve`, `/transition`, and payment-run
`create_run`/`approve_run`/`pay_run` code paths a real customer's browser calls, so
`workflow_state` and `status` end up in sync exactly the way they do for a real customer's
data (per the documented contract at `app/models/invoice.py:38-41` and the real sync point at
`app/services/payment_run.py:369-370` / `app/api/routes/invoice_review.py:670-671`).

### Scope

**In scope:**
- `backend/app/seed.py` — collect every domestic + FX AP `Invoice` created into a list, then,
  after the existing `await db.flush()` (line 257) that makes them queryable, drive each one
  through the REAL review/approval/payment-run endpoint FUNCTIONS (imported directly and
  called as plain async functions, not over HTTP — they are the exact code FastAPI dispatches
  to) so that:
  - every invoice with legacy `status=paid` reaches `workflow_state=paid` via
    submit → approve → transition(`scheduled_for_payment`) → a real payment run
    (create → approve → pay), batched (not one invoice per run, not one giant run);
  - every invoice with legacy `status=pending`/`overdue` reaches `workflow_state=approved`
    (an open, un-scheduled payable) via submit → approve, with a portion of the `pending`
    bucket additionally advanced to `scheduled_for_payment` (still un-paid) to populate the
    payment-run candidate pool (`GET /payable`) realistically;
  - the demo owner (`is_platform_admin=True`) is the sole demo-org user, so the payment-run
    maker≠checker control is satisfied via the SAME explicit, audited `override_sod=True`
    path a real single-admin org would use (WO-9) — never a silent bypass.
- One new regression test file, `backend/tests/test_seed.py`, that runs `app.seed.seed()`
  against a fresh in-memory SQLite DB (module-level `engine`/`SessionLocal` monkeypatched,
  mirroring `tests/conftest.py::_db`'s engine setup) and asserts the workflow_state/status
  parity contract so a future regression is caught in CI, not just noticed in a demo.

**Out of scope:**
- Any change to `cash_position.py`, `payment_run.py`, `ap_aging.py`, or the workflow state
  machine itself — they are correct today; only the seed data is wrong (per the roadmap's own
  root-cause finding).
- Adding more demo users to the AP org for a "real" (non-overridden) maker≠checker demo — out
  of scope for this fix; the audited override is sufficient and is itself real, tested
  production behavior (not a shortcut invented for this seed script).
- R1 (CSV formula-injection) and the rest of Milestone B — separate board items, tracked in
  their own future work orders.

### Implementation guidance

1. In `seed()`, change the domestic-invoice loop (`for month_back in range(12): ...`) to keep a
   reference to each created `Invoice` in a new `ap_invoices: list[Invoice] = []`, and do the
   same for the 6 foreign-currency invoices in the `for vname, ccy, amount, issue in foreign:`
   loop (which unconditionally sets `status=InvoiceStatus.paid`).
2. Add `from app.models.invoice import WorkflowState` to the existing `app.models.invoice`
   import line (already imports `Invoice, InvoiceStatus, LineItem`).
3. After the existing `await db.flush()  # SessionLocal has autoflush off; make invoices
   visible` (so every invoice has its DB-assigned `id`), and after (or interleaved with)
   `linked = await costing.backfill_invoice_links(...)`, call a new
   `ap_ct = await _drive_ap_workflow(db, org.id, owner, ap_invoices, rng)`.
4. `_drive_ap_workflow(db, org_id, owner, invoices, rng)`:
   - Local-import `app.api.routes.invoice_review` and `app.api.routes.payment_runs` (aliased
     `payment_run_routes` to avoid the name collision with `app.services.payment_run`), plus
     `SubmitIn`/`DecisionIn`/`TransitionIn` from `app.schemas.approval` and
     `RunCreate`/`RunApprove`/`RunPay` from `app.schemas.payment_run`. These route functions
     are plain `async def`s — FastAPI's `Depends`/`Annotated` machinery only activates through
     the actual HTTP dispatcher, so calling them directly with `current=owner, db=db` runs the
     exact same body (audit records, webhook `emit`, best-effort `mailer.send`) with no
     network I/O, because the fresh demo org has no webhook endpoints and
     `settings.smtp_enabled` defaults False.
   - For each invoice: `submit()` (version=`inv.version`) → `approve()` (version=the returned
     `.version`). Because there is no `ApprovalPolicy` configured for the demo org,
     `approval_policy.build_chain` yields ONE generic step with `approver_id=None`
     (`is_assigned_approver` → always True), and the demo owner's `is_platform_admin=True`
     bypasses the submitter≠approver guard in `invoice_review._guard_decider` — so a single
     account can legally submit-then-approve its own invoice, exactly as it could in
     production for a solo-admin org.
   - If `inv.status == InvoiceStatus.paid`: `transition()` to `scheduled_for_payment`, then
     collect it for the payment-run pass below.
   - Elif `inv.status == InvoiceStatus.pending` and (`rng.random() < 0.35`): also `transition()`
     to `scheduled_for_payment` (left there — NOT paid, so legacy `status` stays `pending`,
     which is still internally consistent: "scheduled to be paid soon" does not contradict
     "not yet paid").
   - Otherwise (the rest of `pending`, and every `overdue`): stop at `approved` — an open
     payable; `ap_status.status_of` derives `OVERDUE` from the (already-past) `due_date` at
     read time, never from a stored flag, so no `overdue`-status invoice needs special-casing
     here.
   - Batch every `scheduled_for_payment`-and-destined-for-`paid` invoice into payment runs of
     ≤7 invoices via `payment_run_routes.create_run(RunCreate(invoice_ids=..., method=
     "bank_transfer"), current=owner, db=db)`, then
     `approve_run(run.id, RunApprove(version=run.version, override_sod=True), current=owner,
     db=db)`, then `pay_run(run.id, RunPay(version=run.version, reference=f"SEED-RUN-{n}",
     override_sod=True), current=owner, db=db)` — `override_sod=True` is REQUIRED (and
     audited: `payment_run.AP_RUN_SOD_OVERRIDE`) because the owner is both the run's creator
     and its only possible checker/payer in this demo org.
   - Return a small dict of counts (`workflow_state` → count, plus the number of payment runs
     created) for the printed summary line — no behavior depends on the exact numbers, they
     are informational only.
5. Update the final `print(...)` block to report the new counts (e.g. "Drove N AP invoices
   through the review→payment workflow across M payment runs.").
6. Money/rounding: no new money computation is introduced — every amount driven through the
   workflow is the SAME `Decimal` total already stamped on the invoice at creation; the
   payment run's `total_eur` is computed by the existing `payment_run.eur_of()` (already
   proven, `app/services/payment_run.py:146-159`).
7. This is a demo/seed script, not a customer-reachable gate, so there is no "fail open vs
   fail closed" decision to document — a seed-script exception should simply propagate (the
   script already has no try/except around invoice creation) so a broken seed run is loud, not
   silently partial.

### Invariants this order must preserve

- **§4.9/§4.10 (money, Decimal, server recomputes totals)** — untouched; no new money math,
  only routing already-computed invoices through the real state machine and payment-run flow,
  which itself already satisfies these invariants (proven by their own existing test suites).
- **§4.16 (every mutating operation audited)** — automatically satisfied: `submit`/`approve`/
  `transition`/`create_run`/`approve_run`/`pay_run` all call `audit.record(...)` internally;
  no seed-specific audit bypass is introduced.
- **§4.8 (segregation of duties)** — explicitly exercised via the SAME audited
  `override_sod=True` production escape hatch (WO-9), never silently bypassed; this is the
  correct way for a single-admin demo org to pay its own runs, and the audit trail records it
  as an override (`payment_run.sod_override` / `AP_RUN_SOD_OVERRIDE`), not as ordinary SoD
  compliance.
- **§4.11 (payment status is derived, never stored)** — unaffected; `ap_status.status_of`
  keeps deriving PAID/OVERDUE/OPEN from `total`/`amount_paid`/`due_date` at read time exactly
  as before. This work order only ensures `workflow_state` — the separate, also-never-forked
  APPROVAL lifecycle field — is no longer stuck at its default.

### Database / migration impact
None. No model, column, or migration change — `workflow_state` already exists
(`app/models/invoice.py:136-142`); this order only changes what the seed SCRIPT writes into it.

### Testing requirements

  `app.seed.engine`/`app.seed.SessionLocal` to a fresh in-memory SQLite engine (mirroring
  `tests/conftest.py::_db`'s `create_async_engine("sqlite+aiosqlite:///:memory:",
  connect_args={"check_same_thread": False}, poolclass=StaticPool)` +
  `async_sessionmaker(engine, expire_on_commit=False)`), run `await seed.seed()`, then on a
  fresh session against the same engine:
  - assert `SELECT workflow_state, count(*) FROM invoices WHERE org_id=<demo org> GROUP BY
    workflow_state` contains **zero** rows at `WorkflowState.draft` (today's bug — currently
    100% of them);
  - assert **every** invoice with legacy `status == InvoiceStatus.paid` has
    `workflow_state == WorkflowState.paid` (the exact R3 divergence);
  - assert **every** invoice with legacy `status in (InvoiceStatus.pending,
    InvoiceStatus.overdue)` has `workflow_state` in `{approved, scheduled_for_payment,
    partially_paid}` (an open payable, never `draft`/`rejected`/`cancelled`);
  - assert `cash_position.summary(db, org_id)["payables"]["outstanding"] > 0` and
    `["count"] > 0` (today: `0.00`/`0` — the exact contradiction the audit reproduced against
    `/invoices` showing >€1M);
  - assert `payment_run.payable_invoices(db, org_id)` is non-empty (the run-candidate pool the
    Payment Runs screen lists is not empty either);
  - assert at least one `PaymentRun` row exists with `status == RUN_PAID` for the org (proves
    the payment-run pass actually ran, not just the transition).
- `python -m pytest tests/test_seed.py tests/test_cash_position.py tests/test_payment_runs.py
  tests/test_ap_aging.py -q` green (existing suites unmodified in behavior/assertions).
