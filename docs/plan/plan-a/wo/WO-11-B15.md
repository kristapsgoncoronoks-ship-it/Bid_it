# WORK ORDER 11 — B1.5

**WORK ORDER 11 — Finish `users.org_id` → memberships (board B1.5). Effort M 3–5d. Priority P1. Milestone M1 (carried M0 exit criterion #9). Depends on: WO-4 (identity dependency + live-membership gate), WO-10 (exit-gate analysis).**

### Objective and business value

The identity/membership split (Slices 6a–6d) is IN FLIGHT, not resolved — verified in
`docs/M0-exit-gate.md` criterion 9. Memberships are dual-written and roster-authoritative,
and `app/api/deps.py::get_current_identity` enforces a live membership per request; but the
system still reads `users.org_id` **as a membership assertion** in four services —
`app/services/scim.py:148,157` (`get_user`/`list_users` filter `User.org_id`),
`app/services/scim.py:113` (cross-workspace 409 keyed off `existing.org_id`),
`app/services/privacy.py:84` (`_scan` locates the erasure subject by `User.org_id`),
`app/services/reimbursement.py:232` (SEPA payee bank details filtered by `User.org_id`),
`app/services/expense_approval.py:78` (`_emails_for` filters `User.org_id`) — and, one layer
down, **both defence layers treat `users.org_id` as the tenancy of the users table**: the ORM
guard (`app/core/tenant.py::_apply_tenant_scope`, `User` in `TENANT_MODELS`) and the Postgres
RLS policy on `users` (`alembic/versions/b2c3d4e5f6a7_row_level_security.py`) key visibility
off `org_id`, i.e. off the *active-org pointer* that org-switching repoints.

Who loses money: a member of org B whose ACTIVE org is currently A is invisible to org B's
SCIM listing (the IdP re-provisions or fails offboarding), to org B's reimbursement payee
resolution (their IBAN is "missing" → they are skipped from the payout file → an unpaid
employee), to org B's expense-approver e-mail resolution, and to org B's GDPR-erasure scan
(a DSAR reports "0 user accounts" for a real member — a compliance mis-statement). This is
exactly the divergence B1.5 exists to close (ARCH_plan risk T-4: "half-done migrations rot").

### Scope

**In scope:**
- Tenant visibility of the `users` table becomes **membership-driven** at both defence
  layers: the ORM guard scopes `User` by `EXISTS membership in current org` (not
  `User.org_id == org`), and a new migration replaces the `users` RLS policy with a
  membership-`EXISTS` predicate (`WITH CHECK` additionally allows the same-transaction
  create-user-then-membership window via the `org_id` pointer).
- The four named modules stop filtering `User.org_id`:
  `scim.get_user`/`scim.list_users`/`scim.create_user` (membership join; the
  exists-in-another-workspace conflict becomes a caught unique-email `IntegrityError` →
  409, since a scoped session can no longer — and must no longer — read a foreign user row),
  `privacy._scan`, `reimbursement.batch_sepa`, `expense_approval._emails_for`
  (membership joins).
- `users.org_id` is kept and **documented as the denormalized ACTIVE-ORG pointer**
  (repointed by org-switching; verified against a live membership on every request by
  `get_current_identity`; read by nothing as a membership assertion). Docstrings in
  `models/user.py`, `models/membership.py`, `services/memberships.py`, `api/deps.py`,
  `api/routes/auth.py` updated to state the resolved contract.
- Tests proving the new semantics (member-active-elsewhere visible; non-member invisible,
  404 / zero rows) + a Postgres RLS test for the new `users` policy.
- Docs: `docs/security/multi-org-membership-plan.md` (contract-step outcome),
  `docs/architecture/data-model.md` §identity row, `docs/M0-exit-gate.md` criterion 9
  flipped to MET with evidence (final commit).

**Out of scope (anti-scope-creep):**
- Dropping the `users.org_id` / `users.role` columns (plan 6e "contract" as a schema
  change). The exit-gate acceptance explicitly allows the documented-pointer outcome; the
  column drop is deferred until the pointer has soaked (a future B-epic order).
- `users.role` / `users.is_expense_approver` projection semantics (synced on switch and on
  member-update; unchanged here — same rationale).
- Tenant offboarding (B1.8), platform console (J1.6) — dependents, not parts.
- Any change to org-switching behaviour: `tests/test_org_switch.py` and
  `tests/test_membership_enforcement.py` must pass **UNMODIFIED**.

### Implementation guidance

1. Characterise first: run the targeted suites green at baseline (`test_org_switch`,
   `test_membership_enforcement`, `test_scim`, `test_privacy_erasure`,
   `test_reimbursement*`, `test_expense_approval*`, `test_tenancy_parity`,
   `test_cross_tenant_isolation`, `test_isolation`, `test_memberships`,
   `test_membership_writes`, `test_org_roster`).
2. Service layer (SQLite-provable): membership joins in the four modules. Join predicate is
   always `Membership.user_id == User.id AND Membership.org_id == :org` — membership
   **existence**, not status: a suspended member is still org data (SCIM must list them as
   `active: false`; erasure must reach them). SCIM `create_user` order stays
   user-flush → membership-ensure → commit; wrap the flush in `try/except IntegrityError`
   → rollback → `ScimError(409)` (fail CLOSED: a scoped session must not read the foreign
   row to phrase the conflict).
3. ORM guard: special-case `User` in `_apply_tenant_scope` with the membership-EXISTS
   criterion. Other models keep `org_id == current`. This *widens* visibility only to
   actual members (previously hidden when active elsewhere) and *keeps* non-members at
   zero rows.
4. RLS migration (fail CLOSED at the DB): membership-EXISTS `USING`; `WITH CHECK` keeps the
   `org_id`-match disjunct **only** for the insert window (SCIM creates the user row one
   flush before its membership row inside one scoped transaction) — documented in the
   migration docstring. No `TENANT_TABLES` in this migration (`users` stays in the
   set-equality union via b2c3d4e5f6a7; the model stays in `TENANT_MODELS`).
5. Docs last, evidence-based; flip exit-gate criterion 9 in the final commit.

### Database / migration impact

One PG-only migration: `DROP POLICY`/`CREATE POLICY tenant_isolation ON users` (predicates
above). No column/table change, no backfill, no data migration. Downgrade restores the
b2c3d6a7-era `org_id`-equality policy exactly (written and exercised on scratch PG via
`upgrade head` → `downgrade -1` → `upgrade head`). Nothing is lost on downgrade — the
policy is derived, not data.

### Rollback strategy

Code revert is clean (no schema change). Migration downgrade restores the previous `users`
policy verbatim and is exercised on scratch PG. One-way effects: none (no data touched).
Narrow mitigation without full revert: reverting only the service-layer joins restores the
old per-module behaviour while the guard/RLS change (a pure widening-to-members) stays.
