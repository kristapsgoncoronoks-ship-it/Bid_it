# WO-53 — The monthly close as a durable job + locked-line protection (board G1.3, G1.4)

<!-- ═══════════════ COPY FROM HERE: WO-53 ═══════════════ -->

**WORK ORDER 53 — G1.3/G1.4: the monthly close as a durable, idempotent,
restartable job; locked lines protected from a re-close. Effort M (3-5d).
Priority P0. Milestone M3. Depends on: WO-50 (G1.2 — `fuel_transactions`),
WO-51 (G2.2 — the lock table, for G1.4's RESTRICT-FK proof), WO-52 (G2.4 —
`build_claim_lines`, what the close actually invokes).**

### Objective and business value

WO-49-52 shipped the claim grain, the typed transaction line, the lock
table, and the claim-line builder, but nothing yet finalizes a period on a
schedule — verified at HEAD=`fd101b3` (this order's baseline, 1290 passed/10
skipped): no `app/services/transport/close.py` exists, and `app.services.
job_handlers` has no `transport.close` kind. `ARCH_plan.md`'s own critical
path (`G1.1 -> G1.2 -> G2.1 -> G2.2 -> G2.3 -> G2.4 -> G2.5 -> ...`) treats
G1.3/G1.4 as siblings of the G2.x chain, both now unblocked (G1.2/G2.2/G2.4
are done). R31 ("the monthly close is an independent, lock-guarded,
restartable orchestrator... halts on the first failure") and R60
("automated capture and the monthly close run OUT-OF-BAND on a worker tier,
never inline in a web request") are the harvested rules; R30/ADR-P3 add
"locked lines are protected from a re-close."

**A translation, not a port — stated plainly up front.** Fleet Fuel's own
monthly close was `consolidate -> build_master -> history -> run_control ->
backup`, a whole ETL pipeline re-deriving its analytics store from raw
supplier files. That pipeline is explicitly out of scope to copy
(master-context §10; `ARCH_plan.md` names those functions as Fleet-Fuel-
specific) and there is nothing to consolidate FROM in this codebase —
`fuel_transactions` ingestion (WO-50) is already insert-or-no-op on a
structural natural key, not Fleet Fuel's DELETE-by-period-then-reinsert, so
there is no "rebuild the analytics store" step to redo. What DOES translate
is R31's actual property list — durable, idempotent-by-(org,period),
restartable, one-audit-trail, halts-on-first-failure — and this order
delivers exactly that, built on the PRE-EXISTING `app.services.jobs`
framework (already used by `dunning.run`/`recurring.generate`/`retention.
purge`), applied to the one thing in this codebase a period boundary
legitimately needs to finalize: a draft claim's live claim lines (G2.4).

Who pays more without this: every future gate (G2.5's freeze, G2.6's
checklist/deadline stack) assumes a period's claim lines are up to date with
whatever transactions have posted to it. Without a durable, restartable
close, "make sure this period's claims reflect this period's transactions"
either happens ad hoc inside a web request (violating R60 directly, and
risking a long-running request timing out mid-write) or not at all until
someone remembers to call `build_claim_lines` by hand. Landing this now,
on the existing job framework rather than inventing a parallel one, is
strictly cheaper than discovering the "no durable close" gap after a claim
ships with stale lines.

### Scope

**In scope**
- `app.services.transport.close.run_close(db, org_id, period)` — for every
  `draft` claim in the org whose scope (`claim_lines.period_months`)
  includes the `"YYYY-MM"` `period`, calls `build_claim_lines` (G2.4);
  audits once per RUN (not once per claim — that's `build_claim_lines`'s own
  job); returns a summary dict. Gated on the `transport` module entitlement
  first, identical pattern to every other transport service.
- `app.services.transport.close.enqueue_close(db, org_id, period)` — a thin
  wrapper over `app.services.jobs.enqueue`, keying the job on
  `idempotency_key=f"transport.close:{period}"`; returns the job's `id`
  (a plain string, never the `Job` ORM row — see Implementation guidance
  §2 for why).
- `app.services.transport.close.validate_close_period` — `"YYYY-MM"` shape
  check, refused before any query (mirrors `claim.validate_ref_period`).
- Registration in `app.services.job_handlers`: `transport.close` handler
  that unpacks `payload["period"]` and calls `close.run_close`.
- `claim_lines.py::period_months` made public (was `_period_months`) so
  `close.py` shares the exact same period-to-months mapping — the same
  drift-prevention reason `is_synthetic()`/`derive_product_group()` are
  centralized.
- New audit action `A.TRANSPORT_CLOSE_RUN`.

**Out of scope** (explicitly, future M3 work orders)
- **Any automatic scheduling of `enqueue_close`** — unlike `retention.purge`/
  `billing.report_usage` (which the existing `scheduler.py` auto-enqueues
  daily), this order does NOT wire a cron-like trigger. There is no route/UI
  yet for an admin to configure a close cadence, and inventing one (daily?
  monthly-on-the-1st? per-entity?) would be a product decision this order
  does not make. `enqueue_close` is the callable seam; wiring it to a
  schedule is future work once a route/decision exists.
- **The checklist/period-end/minimum/deadline gate stack** (G2.6), **freezing
  claim lines at submission** (G2.5), **fee freezing/status derivation**
  (G2.9/G2.7), **the goods-code mapping table** (G2.8).
- **Any `api/routes/transport/*` route**, **any UI**.
- **A NEW mechanism for "locked lines are protected"** — G1.4 turned out to
  already be structurally true from G2.2/G2.4 alone (see Implementation
  guidance §3); this order adds the PROOF (two new tests), not new code.

### Implementation guidance

1. **Read `BA_fleet_fuel.md`'s R31/R60 rows (lines 1398, 1442) before writing
   a query.** They name PROPERTIES (durable, idempotent, restartable, one
   audit trail, halts-on-first-failure, out-of-band) — not Fleet Fuel's
   specific pipeline stages, which this order does not port (see the
   Objective section's "translation, not a port").
2. **`enqueue_close` returns the job's `id` (a `str`), never the `Job` ORM
   row.** `app.models.job` is NOT under `app.models.transport`/`app.models.
   base`, so returning (or type-annotating with) the raw `Job` object from
   a `services/transport/*.py` function would need importing
   `app.models.job` there — a violation of `test_transport_services_do_not_
   import_other_domain_models` (the boundary test scans EVERY import
   statement structurally, including ones nested under `if TYPE_CHECKING:`,
   so there is no annotation-only escape hatch). Mirrors `invoice_match.
   MatchedInvoice`'s same reasoning from WO-52.
3. **G1.4 requires NO new mechanism — verify, don't build.** `build_claim_
   lines` (G2.4) already refuses a non-`draft` claim and only ever replaces
   `frozen_at IS NULL` rows; `run_close`'s own query (`status == "draft"`)
   means a submitted claim's lines are invisible to the close in the first
   place. `VatClaimedInvoice`'s `RESTRICT` FK into `fuel_transactions`
   (WO-51) is the second, independent layer — but no prior order's test
   suite ever exercised it against an actual delete attempt (WO-51's own
   tests only proved the UNIQUE-constraint lock behavior, not the
   RESTRICT-FK behavior). This order's `test_g1_4_a_locked_transaction_
   cannot_be_deleted_the_database_refuses_it` is the FIRST test to prove
   that FK fires — worth calling out explicitly since it closes a real,
   previously-unproven gap, even though no code changed to make it pass.
4. **`run_once`'s existing rollback-then-fail IS "halts on the first
   failure, nothing partially applied" — do not add a second transaction
   boundary.** `run_close` never catches its own exceptions and never calls
   `db.commit()` (only `build_claim_lines`'s internal `flush()`s accumulate
   in the SAME open transaction); `app.services.jobs.run_once` already rolls
   back the whole session on any handler exception before marking the job
   failed. Proven by `test_g1_3_halts_on_first_failure_nothing_partially_
   applied`, which forces the SECOND of two claims in one run to raise and
   asserts BOTH claims' lines are absent afterward — not just the one that
   raised.
5. **SQLite FK enforcement in tests needs a per-test `PRAGMA foreign_keys=
   ON`.** `tests/conftest.py`'s ad-hoc test engine does not attach the
   app's production connect-listener (registered on the app's own module-
   level `engine` object in `app/core/database.py`); the RESTRICT-FK test
   sets the pragma once via `db_session.execute(text("PRAGMA foreign_keys=
   ON"))` (the fixture's StaticPool means one physical connection for the
   whole test, so it persists) — same technique WO-52 used for its
   CASCADE-firing override test.
6. **`expire_on_commit=False` + `rollback()`/`expire_all()` needs captured
   ids, not live attribute access, afterward.** Any assertion reading an
   ORM object's column AFTER a rollback in an async test must read a plain
   variable captured BEFORE the rollback — accessing an expired attribute
   triggers an implicit async reload outside the SQLAlchemy greenlet
   context and raises `MissingGreenlet`, not the value you wanted. Both new
   test files hit this and fix it the same way (capture `.id` early).

### Invariants this order must preserve

- **§4.16 (every mutating operation is audited)** — `run_close` audits once
  per RUN regardless of how many claims it touches (never per-claim, which
  `build_claim_lines` already does); `test_g1_3_audit_event_fires_once_per_
  close_run` proves exactly one event per call.
- **§10 "no new tenant-scoped table without an RLS policy in the same
  migration"** — moot; this order adds no table.
- **R31/R60 verbatim** — proven by `test_g1_3_close.py`'s idempotent-enqueue,
  restartable-via-`jobs.retry`-eligible (a `queued`/`dead` job, never silently
  dropped), halts-on-first-failure, and never-inline (`jobs.run_once` is the
  only path that executes it) tests.
- **ADR-P3 rule 1/2 (transport owns only its own tables; reads the core
  through services, never joins)** — `close.py` reads/writes only
  `VatRefundClaim` (its own domain model) and calls `build_claim_lines`
  (its own domain service); `test_transport_services_do_not_import_other_
  domain_models` stays green over the new file.
- **G1.4 (locked lines protected from a re-close)** — proven by the two new
  tests in `test_g1_4_close_protects_locked_lines.py` (structural: a
  submitted claim's lines are invisible to the close's own query; database-
  level: RESTRICT refuses deleting a locked transaction).

### Database / migration impact

None. No new model, table, or column. `app.models.job`'s existing `jobs`
table carries the new `kind="transport.close"` rows exactly like every
other job kind — no schema change.

### Testing requirements

`backend/tests/transport/test_g1_3_close.py` (11 tests): period-shape
validation (both sides); `run_close` rebuilds lines for in-scope draft
claims and ignores out-of-scope periods and non-draft claims; re-running is
idempotent (no duplicate lines); module-off inertness; exactly one audit
event per run; `enqueue_close` is idempotent by (org, period) and refuses a
malformed period; the close runs end-to-end through `jobs.run_once` (never
inline); a forced mid-loop failure rolls back EVERY claim's rebuild from
that run, not just the one that raised.

`backend/tests/transport/test_g1_4_close_protects_locked_lines.py` (2 tests):
`run_close` never touches a submitted claim's lines (the exact same line
row survives a re-close untouched, proven by row-id equality); a raw delete
of a locked `FuelTransaction` raises `IntegrityError` and the row survives
(the RESTRICT FK proof, real FK enforcement via `PRAGMA foreign_keys=ON`).

### Rollback strategy

Code-only revert: delete `close.py`, the `job_handlers.py` registration, and
the `A.TRANSPORT_CLOSE_RUN` audit action. No migration to downgrade — this
order added no table/column. No kill switch needed for a production
incident: the `transport` module stays default-OFF and is absent from every
plan's module set (per WO-49), so `run_close`/`enqueue_close` are
unreachable by any tenant regardless of code presence; additionally, no
scheduler wires `enqueue_close` automatically (deliberately, see Scope), so
even with the module on, nothing calls this code path unless a future route
or an operator explicitly does.
