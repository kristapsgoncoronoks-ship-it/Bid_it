### Test-quality findings (read the bodies, not the names)

**What's genuinely excellent — say so plainly:**
- `test_rls.py::test_rls_users_visibility_is_membership_driven` — asserts membership-driven visibility across THREE orgs (pointer-org A with no membership → 0 rows; membership-org B → visible; stranger-org C → 0 rows) AND that a scoped INSERT into a foreign org with no membership is refused by the database itself — a raw-SQL test that bypasses the ORM entirely, proving the Postgres backstop and not the app.
- `test_tenancy_parity.py` (1483 lines, 56 tests) is not "1000 shallow tests" padding — it is one disciplined design: `PROBES`/`EXEMPT` partition `TENANT_MODELS` **exactly** (`test_exemption_list_has_no_stale_entries` fails on either an unclassified new tenant table OR a stale exemption), overlapping-data seeding (same names/amounts in both tenants, so a broken filter can't pass "by luck" on distinct fixtures), and — critically — `test_parity_check_catches_a_deliberately_unscoped_query` proves the checker itself can fail (monkeypatches the vendors service to drop its org filter AND neutralizes `TENANT_MODELS`, then asserts the probe raises `AssertionError` with "TENANT LEAK"). Very few test suites prove their own checker is not vacuous; this one does, and I ran it — 56/56 pass in 98.93s.
- `test_authz_coverage.py` is bidirectional and self-proving: forward (every route has a declared permission or a reasoned `PUBLIC_ROUTES` entry, floor-checked against `MIN_EXPECTED_ROUTES=200` so a broken enumerator can't vacuously pass), reverse (no stale allow-list entries), and `test_coverage_checker_detects_an_unclassified_route` runs the checker against a **scratch FastAPI app** (never the real one) to prove it actually flags an unclassified route.
- `test_payment_run_export_guard.py` and `test_payment_runs_sod.py` — read in full; assert audit-event metadata contents (MsgId, `export_count`, named skipped payees, `total_eur`), parse the real pain.001 XML with `ElementTree` to check `CdtTrfTxInf` counts, and `test_existing_double_payment_guards_still_hold` even reads `inspect.getsource(pr_routes._load)` to assert `with_for_update` literally appears in the locking path — a genuinely paranoid, evidence-grade test.
- `test_vendor_change_requests.py::test_iban_change_on_existing_vendor_does_not_mutate_the_row` re-queries the DB row directly (not just the API response) to prove the stored IBAN is untouched pending approval — the kind of test that would catch a "the API says pending but the DB already mutated" bug the API-only assertion would miss.
- `test_boundaries.py` enforces the models→core→services→api layering via AST inspection (no code executed) — architecture-as-a-test, not just a doc claim.

**Where the QUALITY story breaks down — real findings, not nitpicks:**

1. **The ClamAV fail-closed malware-scan path (`app/services/filesec.py::scan_malware`, lines 194–213) has ZERO test coverage anywhere in the suite.** `grep -rn "clamav\|clamd" tests/*.py` → no matches at all. `test_filesec.py` thoroughly covers EICAR-signature detection, executable/script/zip-macro rejection, and oversize — all of which run with `clamav_enabled=False` (the default). But the actual security-critical branches — a configured scanner returning `FOUND`, a configured scanner returning a non-OK status, and (most important, since it's the documented differentiator: "fail CLOSED when a scanner is configured but unreachable") a configured-but-unreachable scanner — are never exercised, not even with a monkeypatched fake `clamd` module. If that `except Exception` handler regressed to fail-open, or the `status == "FOUND"` string comparison broke against a real clamd response shape, nothing in CI would catch it. **Debate outcome: submitted P1 → downgraded to P2** — the underlying control is currently implemented correctly (verified live by injecting a fake `clamd` module), ClamAV is optional/off-by-default/not even a declared runtime dependency, so this is a coverage/regression-prevention gap in an unreachable-by-default branch, not a live defect. See `docs/audit/agent-debate.md`.

2. **Expense-approval decisions (`POST /api/v1/expenses/{id}/decision`) have no optimistic-concurrency guard and no row lock — unlike every other money-adjacent mutation in the codebase, and there is no test proving this asymmetry is safe (because the protection itself doesn't exist to test).** Evidence:
   - `app/schemas/expense.py::ExpenseDecision` carries no `version` field at all (contrast `ExpenseDecision`'s neighbors: invoice `submit`/`approve`/`transition` and payment-run `approve`/`pay` all require and check `version`, proven by `test_invoice_review_e2e.py` (`stale.status_code == 409` twice) and `test_payment_runs_sod.py`/`test_payment_run_pay_concurrency.py`).
   - `app/api/routes/expenses.py::_load` (line 135) does a plain `select(ExpenseReport)...` with no `.with_for_update()`. Repo-wide `grep -n "with_for_update" app/api/routes/*.py app/services/*.py` shows the lock is applied in `payment_runs.py`, `receipts.py` (×2), `reconciliation.py` (×4), `issuer.py` (×2), `issued.py`, `reimbursements.py` — **every other row that two users could race to mutate — except the expense-decision path.**
   - Consequence: two approvers (or the same approver double-clicking) deciding the same pending step concurrently would both read `status in IN_APPROVAL` / `pending_step(steps)` as valid, both call `expense_approval.decide_step`, both `audit.record`, and both `webhooks.emit` — a plausible double-approval / duplicate-webhook / inconsistent-chain-state race that the payment-run team explicitly hardened against (WO-9) but expense approval did not receive the same treatment.
   - I did not have time to reproduce this race live (would need a dedicated Postgres concurrency test analogous to `test_payment_run_pay_concurrency.py`, which does not exist for this path) — flagging as a plausible, evidenced gap, not a confirmed live bug. **Debate outcome: CONFIRMED at P1** — the debate stage found this is worse than described: a live, UI-reachable `mark_reimbursed` action bypasses the one path (`reimbursements.py`) that IS locked, and racing `decide()` calls double-fire un-deduplicated outbound webhooks. See `docs/audit/agent-debate.md`.

3. **`test_fx.py::test_refresh_owner_only_and_graceful` does not test "owner only."** The function body only calls `POST /api/v1/fx/refresh` as the (default owner) `auth_client` and accepts `ok in (True, False)` — it never asserts a non-owner is rejected. The route IS gated by `SETTINGS_MANAGE` (`app/api/routes/fx.py:122`), and that permission is well-covered generically (`test_authz.py`'s full 8-role matrix unit tests, `test_config_guards_authz.py`'s representative-endpoint 403 sweep), but `/fx/refresh` is not in `test_config_guards_authz.py::_CONFIG_ENDPOINTS`'s representative list either — so this specific route's negative case is asserted nowhere, only implied by the test's own docstring/name. Low severity (the general mechanism is solid) but a concrete instance of a test name overclaiming what it verifies — worth checking for elsewhere, and I did not have time to grep the whole suite for this pattern exhaustively.

4. **No application-level backup/restore tooling exists at all**, unlike the pattern this review board's charter implies is expected of a financial system (the doc even asks "does backup/restore tooling even exist here?"). `grep -rln "backup\|restore" backend/app/*.py` returns nothing except incidental hits in `integrity.py`/schema files (unrelated). `find` for `*backup*` in the repo finds only vendored `botocore` data. `docs/DECISIONS-NEEDED.md` explicitly defers this to "infrastructure, not app code" — which may be a reasonable call for a Postgres-managed-service deployment, but it means **there is no tested, application-owned disaster-recovery path** for a system that moves SEPA payment files and holds vendor IBANs. This is a documented deferral, not a silent gap, but it is a real absence worth the board's attention.

5. **Sheer single-assert-mutation test count is high (68 files/functions matched a "≤1 assert + a POST/PATCH/PUT + status_code check" grep) but almost all of these are legitimate negative/rejection tests** (`test_overpayment_refused`, `test_wrong_region_login_refused`, etc.) where a single status-code+detail-message assertion is the correct, sufficient check — I read a representative dozen of these in full and did not find a case where a genuinely ambiguous financial mutation was under-asserted; the sibling positive-path tests (e.g. `test_partial_then_full_payment` immediately preceding `test_full_payment_in_one_shot` in `test_ap_payments.py`) carry the numeric/ledger verification, and the terse test is a deliberate complementary case, not a lazy one. I flag this only so the next reviewer doesn't need to re-derive it: **the count is not itself evidence of weakness; I checked, and it isn't.**

### Honest quality verdict
This is **not** "1000 shallow tests passing for reassurance." The suite's hardest-guarantee files (`test_rls.py`, `test_tenancy_parity.py`, `test_authz_coverage.py`, `test_numbering_concurrency.py`, `test_payment_run_pay_concurrency.py`, `test_migrations.py`) are sharp, self-proving (each has an explicit "prove the checker can fail" test), and I reproduced every one of their headline claims myself on a real Postgres instance rather than trusting either the baseline agent's numbers or the tests' own reputations. Money-movement paths (payment runs, SEPA export, vendor bank-detail dual-control) are exceptionally well hardened and well tested, including audit-trail content assertions, not just status codes. The gap is real but narrow and specific: **expense-approval decisions were not brought up to the same concurrency-safety bar as payment runs/reimbursements/reconciliation/issued-invoice-numbering, and nothing tests that they weren't** — this is exactly the kind of asymmetric-hardening gap a fresh adversarial pass should catch (debate-confirmed at P1). The ClamAV fail-closed path being entirely untested is a second concrete, fixable gap in an otherwise disciplined security-test posture (debate-adjusted to P2 — currently unreachable by default). Neither finding contradicts the 1091-passed/4-skipped baseline number — both are coverage gaps, not test-correctness failures.
