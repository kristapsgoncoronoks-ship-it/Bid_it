## P0-1 — The archive never expires. Nothing enforces `expires_at`. — **FIXED same day**

Built as specified below: `archive.purge_expired` + `collect_bytes`, the
`ARCHIVE_PURGE` handler, a `DAILY_KINDS` entry, and `tests/test_archive_expiry.py`
(10 tests). One nuance the fix surfaced: seeding the org predicate OFF the DELETE
alone leaves the cross-tenant test green, because the org-scoped SELECT is a
redundant second layer — only removing both goes red. Recorded in TODO.md so the
green seed is not mistaken for a vacuous test.

**Where:** `app/services/archive.py`, `app/services/job_handlers.py`,
`app/services/scheduler.py`.

**What is true today.** `archive_records()` stamps `expires_at`, the column is
indexed (`ix_archived_invoices_expires`), the API publishes it, and the client
screen prints it. There is no job, no handler and no scheduler entry that ever
deletes an expired row. `expiring_soon()` has no caller outside its own tests.

Verified: `grep -rn "archive" app/services/job_handlers.py app/services/scheduler.py`
returns one code comment and nothing else.

**Why it matters — three separate harms, not one.**

1. **The product states something untrue.** `/invoices/archive` tells the client
   their records are "kept for 3 years from the day it was archived, then
   removed". Nothing removes them. This is the same class of defect as the Trash
   screen printing an unpaginated total over a truncated table, except the
   sentence is about destroying client data rather than counting it.
2. **Storage limitation (GDPR Art. 5(1)(e)).** Invoices carry personal data.
   Retaining them indefinitely past a stated period is the failure a retention
   commitment exists to prevent, and this period is going into a DPA.
3. **The document bytes are never collected either.** `_archive_batch`'s
   docstring says in as many words that the PDF bytes "live exactly as long as
   the archive row that points at them, and are collected when THAT expires
   rather than here." Since nothing expires, nothing collects: every client PDF
   ever deleted is retained forever, and the store grows without bound.

**Fix.**

```python
# app/services/archive.py
async def purge_expired(db, org_id, *, now=None) -> dict:
    """Destroy archive rows past `expires_at`, and the bytes nothing else needs."""
```

- Refuse (no-op) under `retention.is_on_hold` — the same rule, and for the same
  reason, as `invoices.purge_expired_bin`. A preservation duty overrides a
  retention window on every path, including the ones added later.
- Batch at `PURGE_BATCH`, and **re-assert `org_id` and `expires_at <= now` on the
  DELETE itself** rather than inheriting them from the SELECT: the tenant guard
  does not touch a non-SELECT statement, so on the only irreversible path the
  WHERE clause is the entire tenant boundary.
- **Delete a document's bytes only when no other archive row references that
  sha.** The document store is content-addressed and shared — the same PDF
  uploaded twice is one object. Deleting on the first expiry would silently break
  a second client record that is still inside its window.
- Audit `archive.purge` with the destroyed records, not just a count. After this
  runs, the audit event is the only remaining trace.
- Register `ARCHIVE_PURGE` in `job_handlers` and add it to `scheduler.DAILY_KINDS`
  — every tenant, like `BIN_PURGE`, not only tenants with a retention policy.

**Regression tests to add:** a row past `expires_at` is destroyed; a row inside
its window is not; a legal hold refuses the whole run; a sha still referenced by
another archive row survives; the DELETE carries the org predicate (seed its
removal and watch a cross-tenant test go red).

## P0-2 — The archive can outlive the tenant's own retention policy, and the retention purge does not know the archive exists

**Where:** `app/services/retention.py` (`CATEGORIES["invoices"]`,
`_delete_object_bytes`, `purge`) against `app/services/invoices.py`
(`purge_expired_bin`) and `app/services/archive.py`.

Two directions of one inconsistency. Both are real.

**(a) Retention purge destroys invoices outside the chain.**
`CATEGORIES["invoices"]` hard-deletes `Invoice` and `LineItem` directly. No
recycle bin, no consent warning, no archive copy. A tenant that configures a
365-day invoice policy has invoices destroyed by a path that never learned the
deletion chain exists.

**(b) Binned invoices are invisible to retention, so the archive outlives the
policy.** `retention.purge` selects through the ordinary session, which means the
central soft-delete guard hides every binned row from it. So an invoice deleted
by a client and sitting in the bin is skipped by the tenant's retention purge,
then collected 30 days later by the bin purge — into an archive that keeps it for
**three years**. A tenant whose configured retention window is 90 days ends up
with a three-year copy of exactly the records they told the system to destroy.
That is the precise outcome a retention policy exists to prevent, produced by two
correct-looking components meeting.

**(c) Purging the `invoices` category orphans its bytes.**
`_delete_object_bytes` branches on `expenses` and `email_intake` only. The
`invoices` category deletes rows and leaves the uploaded PDFs in the store with
nothing pointing at them — invisible, undeletable through any UI, and retained
indefinitely.

**Fix.** Pick ONE rule and enforce it in ONE place; the danger here is two purge
paths with different guarantees, not either path individually. Recommended:

- Make retention's invoice category route through the same chain (soft-delete →
  bin → archive) so there is a single destruction pipeline, OR
- keep it as the deliberate hard-delete path and then it must: run under
  `tenant.include_deleted()` so binned rows are covered rather than skipped;
  delete the tenant's `archived_invoices` rows for those invoices too; and delete
  the upload bytes as the other two categories do.
- Either way, `archive.retention_years()` must be capped by the tenant's own
  configured invoice retention when one is set. An archive window is a *maximum*
  the platform offers, never a floor it imposes on a client who asked for less.

**Regression test:** a tenant with a 30-day invoice retention policy, an invoice
deleted into the bin, both purges run — assert no `archived_invoices` row
survives past the tenant's window.

## P2-1 — `access.record_usage` loses increments under concurrency — **FIXED same day**

Fixed as specified: one `ON CONFLICT DO UPDATE SET count = count + n` upsert
(native Postgres, SQLite ≥ 3.24), tests in
`tests/test_usage_counter_concurrency.py` — the observable create-then-increment
path on the default suite, the genuinely concurrent N-writers proof Postgres-
gated alongside the numbering test. The commit stays in the function for now:
the upload route has no commit after this call, so moving commit ownership is a
separate behavioural change, not something to smuggle into a race fix.

**Where:** `app/services/access.py::record_usage`.

```python
counter.count = (counter.count or 0) + n
await db.commit()
```

A read-modify-write in Python. Two uploads landing at once both read `N` and both
write `N + 1`; one upload is never counted. The `IntegrityError` guard covers
concurrent *creation* of the row, not concurrent *increment* of it.

**Why it matters:** this counter is the upload quota, and the quota is the paid
boundary between plan tiers. Undercounting hands out free uploads, silently and
repeatably, on exactly the tenants busy enough to be paying. When metered billing
goes live it becomes under-billing. (Secondary: the function commits inside a
service, contrary to engineering-rules §3 — the caller should own the
transaction.)

**Fix:** make the increment atomic in the database, not in Python.

```python
stmt = insert(UsageCounter).values(org_id=org_id, period=_period(), metric=metric, count=n)
stmt = stmt.on_conflict_do_update(
    index_elements=[UsageCounter.org_id, UsageCounter.period, UsageCounter.metric],
    set_={"count": UsageCounter.__table__.c.count + n},
)
```

SQLite ≥ 3.24 supports the same `ON CONFLICT DO UPDATE`, so one statement covers
both backends. Leave the commit to the caller. Test it with two concurrent
sessions and assert the counter reads 2, not 1 — this is one of the few places
where a genuinely concurrent test is worth its cost.

## P2-2 — The audit trail records who and when, but not from where

**Where:** `app/models/audit.py`, `app/services/audit.py::record`.

`audit_events` columns: `org_id`, `seq`, `actor_id`, `actor_email`, `action`,
`target_type`, `target_id`, `meta`, `at_ms`, `prev_hash`, `hash`. There is no IP,
no user agent, and no session id.

The owner's requirement for the deletion trail was recorded as: *what was
deleted, when it was deleted, by whom, and from what location / IP address*. The
first three are captured. The fourth is not, and cannot be reconstructed after
the fact: `_ip()` and `_ua()` exist in `routes/auth.py` and the IP is stored on
`sessions`, but nothing ties an audit event to a session, so one actor with two
active sessions is unresolvable.

**Fix:** add nullable `ip` and `session_id` columns to `audit_events` and
populate them from request context, set by the same middleware that already does
`audit.set_actor`/`reset_actor`, via a ContextVar. Two details that matter:

- Put them in **columns**, not in `meta`. `meta` is documented as small JSON with
  no secrets, and — more importantly — the columns are what the tamper-evident
  hash chain covers. An IP recorded outside the chain can be edited without
  breaking it, which defeats the reason for recording it.
- An IP is personal data. Adding it means stating its basis and retention in the
  DPA; it should not silently inherit "forever" (see P0-1).

## P2-3 — A test-quality class: negative assertions with no positive anchor

**Confirmed instance (already fixed).** `e2e/invoice-archive.spec.ts`, "the
notice window is the server's, not the page's": the assertion was
`toHaveCount(0)` with nothing asserted present first, so it resolved against a
page that had not finished its first fetch. Proven by seeding the exact violation
it claims to catch — hardcoding the notice window back to 60 in `Archive.tsx` —
and watching the test stay **green**. With a positive anchor added first, the
same seed turns it **red**. Fixed in `8235722`.

**Confirmed non-instance.** `e2e/nav.spec.ts`, "base user role hides admin/owner
-gated items": same shape — a loop of eight `toHaveCount(0)` before any positive
assertion. Seeded the removal of the entire nav role gate in `Layout.tsx`; the
test **failed** as it should. So the shape is a risk, not automatically a defect,
and reporting all matches as bugs would have been wrong.

**Scale:** 52 tests across 16 spec files open with a negative assertion. Each is a
test that *might* be proving nothing; only seeding tells you which.

**Fix:** make the shape unwritable rather than auditing 52 tests by hand. A small
CI check (or ESLint rule) that fails a spec whose first `expect` is
`toHaveCount(0)` / `not.toBeVisible()` / `not.toBeAttached()`. The remedy is
always the same single line — assert something PRESENT before asserting something
absent — so the rule is cheap to satisfy and cheap to justify.

## P3 — `bulk_delete_drafts` issues one query per id

**Where:** `app/services/invoices.py::bulk_delete_drafts`. A `SELECT` per invoice
id inside the loop. Bounded at 200 by `bulk.normalise_ids` (`MAX_BATCH`), so it
is 200 round trips at worst, not unbounded — a performance note, not a
correctness bug. Worth folding into one `WHERE id IN (...)` load if bulk delete
becomes common.

## Checked and found SOUND

Recorded so the scan's coverage is legible, and so these are not re-checked.

- **Bulk request sizes are capped server-side**, not only in the UI:
  `bulk.normalise_ids` enforces `MAX_BATCH = 200`, so the Postgres 65535
  bind-parameter ceiling is not reachable from `POST /invoices/bulk-delete`
  despite `BulkDeleteIn.invoice_ids` carrying no `max_length`.
- **`BIN_PURGE` is scheduled for every tenant**, in `DAILY_KINDS` rather than
  behind a retention policy — so the 30-day promise is kept for tenants who never
  configure retention. The chain up to the archive genuinely runs.
- **The bin purge's tenant boundary is re-asserted on the DELETE**, and it batches
  to stay under the bind ceiling.
- **No bare `round()` on currency** anywhere in `app/services`. The two hits are a
  match score and a day count.
- **Custom-priced plans cannot be self-selected.** `PUT /billing/plan` refuses
  `price_eur is None` unconditionally, so the new `practice` tier (200 seats,
  custom price) added on 2026-08-15 cannot be self-upgraded into for free.
- **`access.invoices_this_month` counts binned invoices** (`include_deleted()`),
  closing the delete-and-recreate quota loop.
