# Read-path performance baseline — 2026-08-27 (WO-R, audit item R15)

This closes `RELEASE-READINESS.md` §3.5, which said, verbatim: *"Performance is
untested beyond current fixture scale. `expected_rebate` loads a tenant's whole
transaction history into memory to learn medians — fine now, unmeasured at
scale."*

It is now measured. **The headline: the whole-history walk is sub-linear across
50× of data, so the specific fear §3.5 recorded is not realised.** The endpoint
that grows fastest is a different one — the analytics `explore` group-by — and
it is superlinear, not quadratic. Details below, with the numbers that say so.

## How these were produced

`backend/scripts/perf_harness.py`, which drives the **real ASGI app** through
the **real router stack** (auth, tenant guard, RLS, services) against a dataset
it seeds itself. Nothing is mocked or stubbed; every figure here is something
the product actually did.

```
make perf       PERF_URL=postgresql+asyncpg://user:pw@host:port/db SCALE=400
make perf-shape PERF_URL=postgresql+asyncpg://user:pw@host:port/db SCALE=2000
```

Per scenario the harness discards 2 warm-up calls (lazy imports, pool fill,
first-time statement planning — real costs, but paid once per process rather
than once per user) and then times 12. The reported p95 is nearest-rank, so it
is always a call that actually happened rather than an interpolation between
two calls that did.

### The machine these numbers came from

| | |
|---|---|
| CPU | Intel Xeon @ 2.80 GHz, 4 vCPU |
| Memory | 15 GB |
| Postgres | 16.13, local socket, default `postgresql.conf` |
| Python | 3.11.15 |
| Date | 2026-08-27 |

**A millisecond figure here is only comparable against this class of machine.**
That is the whole reason the CI gate is a growth RATIO and not a millisecond
budget: a slower runner makes both halves of a ratio bigger and leaves the
ratio alone.

## Baseline: p95 by dataset size

`scale` is invoices AND fuel-transaction lines seeded per run; the fuel lines
all belong to ONE supplier, so `expected_rebate`'s median walk has a real
history to walk rather than a fixture.

| scenario | 400 | 5,000 | 20,000 | 400 → 20,000 (50× data) |
|---|---:|---:|---:|---:|
| `dashboard` | 38.1 ms | 49.6 ms | 88.0 ms | **2.3×** |
| `invoice_list` (page 1 of 50) | 17.9 ms | 22.4 ms | 63.1 ms | **3.5×** |
| `ap_aging` | 13.4 ms | 17.7 ms | 27.4 ms | **2.0×** |
| `cash_position` | 22.6 ms | 27.6 ms | 38.0 ms | **1.7×** |
| `explore_by_vendor` | 17.5 ms | 69.1 ms | 436.3 ms | **24.9×** |
| `transport_reliability` | 34.5 ms | 234.2 ms | 599.3 ms | **17.4×** |

Every scenario is sub-linear in the data: 50× the rows costs at most 25× the
time, and mostly far less.

## What the numbers actually say

**1. §3.5's concern does not reproduce.** `transport_reliability` is the
endpoint that walks a supplier's entire history. Across 50× of data it slowed
by 17×. A whole-history walk that were quadratic would have slowed by 2,500×.
It is linear-with-a-good-constant, and the reason is visible in the code: the
history is fetched once, in one query, and reduced in a single pass — not
re-queried per line.

**2. The endpoint to watch is `explore`, not `expected_rebate`.** The analytics
group-by grows fastest (24.9× for 50× data, and 6.3× on the 5k → 20k step
alone). It is a whole-table aggregate with a sort, so some superlinearity is
expected — but it is the first read that would need an index or a rollup if a
workspace's invoice count grew another order of magnitude. It is not a problem
at any size this product has today, and it is the one with the tightest
headroom against its budget.

**3. Per-step ratios are noisier than the overall curve**, because Postgres
picks different plans at different table sizes. `transport_reliability`
measured 2.6× on the 5k → 20k step and 4.9–5.9× on the 2k → 8k step; the
overall 17×-across-50× is the trustworthy figure, and the per-step ceilings in
the harness are set with that spread in mind rather than hugging one reading.

## The gate

`backend/tests/test_perf_shape.py`, two layers:

- **Structural, always on** (runs in the default SQLite suite, milliseconds): no
  scenario may exist without both a millisecond budget and a growth ceiling; no
  ceiling may be loose enough to admit a quadratic endpoint (≥ 16× at 4× data);
  the harness's refusal to measure on SQLite is executed, not assumed; the
  percentile is proven to be a real measurement.
- **Measured, in CI**: the `postgres` job runs it against the same migrated
  database as the RLS gates, at 1,200 → 4,800 rows, in about 17 seconds. It
  seeds both scales and fails any endpoint that grew past its ceiling. Locally,
  set `PERF_TEST_DATABASE_URL`. The gate runs the harness as a subprocess, so the
  parent test run's SQLite configuration is never disturbed — running the main
  suite against Postgres produces dialect artifacts that have cost this project
  a bad certification before.

  A perf check earns a place in CI only because the verdict is a ratio: a shared
  runner is slower at both scales, which cancels. An absolute budget there would
  be a flake generator.

**The gate was proven to bite before it was trusted.** A deliberate `O(n²)`
pass was seeded into `reliability.report()` and the measured layer failed with:

```
transport_reliability 11.35× (ceiling 8.0×, 247.3ms → 2807.1ms)
```

— naming the endpoint, the ratio, the ceiling and both readings. The seed was
then removed by the exact inverse edit and the diff verified empty.

## Deliberate deviation from the plan

`docs/plan/DEVELOPMENT-PLAN-2026-08.md` sized WO-R as *"k6 or locust"*. Neither
was used, and the reasoning is recorded in the harness docstring: k6 is a Go
binary absent from this toolchain that cannot drive an ASGI app in-process (so
every run would need a second live environment to keep true), and locust drags
`gevent`, `flask` and `werkzeug` into a backend that has added no dependency
without cause. `httpx` + `asyncio` already ship in `requirements.txt` and
already drive every API test here, so the harness measures exactly the stack the
tests measure and runs anywhere they run.

## Not covered by this baseline, and honestly so

- **Concurrency.** Every figure is a single sequential caller. This measures
  per-request cost, not what happens under N simultaneous users; connection-pool
  saturation and lock contention are unmeasured. (Arc 3's WO-Y carries the
  `pay_batch` concurrency question separately.)
- **Write paths.** Ingest, OCR and batch upload are not scenarios here. WO-X
  adds batch upload with progress and is the natural place to measure them.
- **Production hardware.** The VPS is not this machine. Re-run `make perf` there
  to get an absolute baseline for it; the ratios in the gate carry over
  unchanged.
- **Cold caches.** Warm-up is discarded on purpose, so these are steady-state
  figures. A first request after a deploy is slower and is not described here.
