# PERF-016 — the tail was the garbage collector (2026-09-06)

**Trigger.** CI #545 (`main`, 9ac4b8d — the queue tail's deploy) failed the R15
growth gate:

```
transport_reliability         20.2     247.3     12.24       8.0  GREW TOO FAST
```

CI #544 had read **7.47×** (26.3 → 196.4 ms) on the **same commit** forty
minutes earlier; three local runs read 4.25×, 6.19×, 6.21×; the 2026-08-27
baseline read 6.93×. `app/services/transport/reliability.py` had not changed
since 2026-08-27, and Postgres was cleared first: `EXPLAIN ANALYZE` of the
window query is a bitmap scan on `ix_fuel_transactions_org_period`, 94 shared
buffers, identical with and without the tenant setting.

## What was measured

Machine: this session's container (Postgres 16.13, same class as the
2026-08-27 baseline). Scale 1,200 seeds ~600 fuel rows in the report's 12-month
window; scale 4,800 seeds 2,387.

**1. The service call alone, collector instrumented** (24 calls each):

| condition | 600 rows p50 / p95 | 2,387 rows p50 / p95 | p95 ratio | p50 ratio | gen-2 passes (cost each) |
|---|---|---|---|---|---|
| GC on, imported app | 15.8 / 17.1 | 47.4 / 202.7 | **11.83×** | 3.00× | 1 of 24 / 6 of 24 (131–146 ms) |
| GC on, after `gc.freeze()` | 15.8 / 18.4 | 46.7 / 52.8 | **2.87×** | 2.96× | 1 of 24 / 9 of 24 (0.6–1.6 ms) |
| GC off (floor) | 14.3 / 15.1 | 42.2 / 50.5 | 3.35× | 2.94× | — |

The imported application tracks **335,660 objects**. A generation-2 pass walks
all of them and costs ~140 ms; it fires when enough allocations have survived
the young generations, i.e. in proportion to how many ORM rows a request
hydrates — about every third call at 2,387 rows, about one in twenty-four at
600. The p95 of twelve samples is the second-slowest, so at the large scale it
almost always contains a pass and at the small scale it almost never does:
the ratio is a coin toss between ~3× and ~12× on identical code. The CI
failure is reproduced here without HTTP.

**2. Through the real ASGI stack** (`GET /api/v1/transport/reliability`, 24
requests, per-request collector accounting):

| scale | unfrozen p50 / p95 / max | frozen p50 / p95 / max |
|---|---|---|
| 1,200 | 35.6 / 38.3 / 174.2 | 35.3 / 41.6 / 45.9 |
| 4,800 | 65.1 / 210.9 / 220.7 | 65.2 / 68.3 / 69.8 |

Every sample above 100 ms carried exactly one gen-2 pass of 137–152 ms. The
endpoint itself grows **1.85×** for 4× the data, at p50 and at p95 alike.

**3. The gate as CI runs it** (`--shape --scale 1200`, three runs each):

| harness | transport_reliability p95 ratio | p50 ratio |
|---|---|---|
| before (CI #544, #545; local ×3) | 7.47, 12.24; 4.25, 6.19, 6.21 | — |
| frozen at startup, seed garbage collected (local ×3 + logged run) | **2.66, 1.50, 2.45, 3.07** | 1.75, 1.71, 1.75, 1.68 |

## What changed

- `app/core/gc_tuning.py::freeze_startup_heap` — `gc.collect()` then
  `gc.freeze()`: the static object graph (modules, mappers, routers, schemas)
  moves to the permanent generation the collector never walks again.
  CPython ≥ 3.7, no dependency, no behaviour change; the documented use of the
  API for a large long-lived heap.
- `app/main.py::lifespan` calls it **last**, after the schema step and the ECB
  seeding — so nothing dead is parked and nothing hot is left out. Each
  uvicorn worker runs the lifespan, so each worker freezes its own heap.
- `scripts/perf_harness.py` calls the same function once per process before
  measuring (httpx's ASGITransport runs no lifespan), and reclaims the
  workspace seed's ~130k dead ORM objects before the stopwatch starts — the
  first full pass inside the window would otherwise pay ~30 ms for garbage the
  harness made. The growth table now prints the **p50 ratio** beside the gated
  p95 ratio: when the two disagree by a lot the tail is not the algorithm's.
- `tests/test_perf016_startup_heap_freeze.py` pins all three (functional freeze,
  lifespan order, harness order in both modes) and that the gate stays on p95.

The `transport_reliability` ceiling stays at 8.0 — still below the 16× a
quadratic walk would read, and now held by a measurement of the endpoint
(2.9×) rather than of the collector.

## What remains, stated rather than assumed closed (PERF-017)

Freezing removes the startup heap from every later pass, but the process keeps
building long-lived objects after boot — compiled-statement caches, lazily
built validators, the tenant registry. A logged shape run shows ~160–190k
tracked objects alive after warm-up, and a gen-2 pass over them costs
**40–56 ms**, firing about every third request at 2,387 rows. That is the
residual tail visible in the "frozen" shape runs (large p95 ≈ 100 ms against a
p50 of ≈ 65) and it is production's too: any read that hydrates a few thousand
ORM rows pays it, per worker, and a full pass is stop-the-world for every
request in flight on that worker — which is a second, untested suspect for
CONC-001's 11–12× on the aggregate reads (the pool was the first). Two
remedies, neither taken here because both change more than a startup line:

1. **Hydrate less.** `reliability.report` (and the other whole-window reads)
   select full ORM rows to read a dozen columns; a column `select` returns
   `Row` tuples that are a fifth of the objects and carry no instance ↔ state
   cycle for the collector to trace. Equivalence must be proven per read, as
   PERF-002/003 did.
2. **Collect less often.** Raise the third GC threshold so full passes happen
   an order of magnitude less often; costs memory between passes and needs a
   measurement of that cost first.

CI's concurrency step now runs with the frozen heap; **datapoint 2 is the
first with PERF-016 in place**, and it says whether CONC-001 moves.

**It moved (CI #547, 772f4c6, 2026-09-06 11:52 UTC).** On the GitHub runner
the R15 gate read `transport_reliability` **2.59×** (28.6 → 74.0 ms; p50
ratio 1.94) — every scenario's p95 ratio within 0.1 of its p50 ratio, which
is what "the tail is the endpoint's" looks like. The concurrency step, same
run, 8 in flight (`CONCURRENCY-2026-09-06.md`, datapoint 2): `ap_aging`
12.0× → **6.99×**, `cash_position` 11.7× → **7.18×**, `transport_reliability`
11.2× → **7.40×** — no longer CONTENDED — while `dashboard` went 11.4× →
**10.36×** and stays the one contended read. Three of CONC-001's four rows
were the collector; the dashboard's remaining tail is the pool suspicion,
now narrowed to one endpoint. CI #548 (main, the deploy run) repeated both
readings: R15 `transport_reliability` **2.50×** (45.0 → 112.4 ms; p50 ratio
2.09), concurrency `dashboard` 11.5× and the other three 6.8–7.6×.

## Reproducing

```
cd backend
DATABASE_URL=postgresql+asyncpg://user:pw@host:port/db \
  python scripts/perf_harness.py --shape --scale 1200
```

To see the old tail, comment out `_freeze_like_production()` in `run()` and
watch `transport_reliability`'s p95 ratio leave its p50 ratio behind.
