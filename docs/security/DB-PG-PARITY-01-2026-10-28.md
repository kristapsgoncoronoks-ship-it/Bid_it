## Correction and refusal boundary

`app/core/migration_schema.py` first verifies the reflected PostgreSQL action
for each named constraint and the unchanged portable ORM constraint/element
options. It then clones the entire metadata and represents only those four
existing column-specific actions on the clone. Alembic compares the complete
schema against that copy. No comparison operation is filtered or discarded;
columns, targets, indexes, types and unrelated constraints retain normal drift
detection. Wrong targeted actions or an unexpected portable model policy refuse
explicitly instead of being normalized away.

The Alembic environment selects this metadata only for PostgreSQL
check/autogenerate through Alembic's `RevisionContext`, including programmatic
commands with `cmd_opts=None`. Ordinary upgrade/downgrade, offline SQL generation
and SQLite keep their existing path. Application metadata remains unchanged.
There is no schema repair, data rewrite or destructive migration.
