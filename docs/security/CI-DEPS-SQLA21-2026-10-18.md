## Problem and implemented change

Dependency PR #63 fails on its older base. Isolating **SQLAlchemy 2.1.4** on the
repaired development branch reproduced **five failures / 15 passes / one skip**
in the initial focused run and **118 mypy errors across 18 files** (421 sources).
Two `Result.tuples()` calls raise deprecations under the existing warning gate;
single-entity `Select[tuple[Model]]` annotations propagate incorrect tuple types
through transport consumers. More precise nullable/dynamic result typing exposes
additional declarations. The dependency's broader Core-EXISTS tenant scoping also
contradicts the old test's negative expectation.

The candidate pins SQLAlchemy **2.1.4**, consumes rows directly, uses the new
single-entity `Select[Model]` convention and types the actual dynamic model/result
sets. `NotNullable` marks projections only where the existing SQL excludes NULL
(`IS NOT NULL`, or the payment-run `IN` filter). It returns the expression unchanged:
no query predicate, SQL cast, money calculation, data migration or retention rule
was added or removed. No new `Any`, type-ignore or warning exemption was added.

The tenant control now requires the nested invoice predicate. A new SQLite test
queries Alpha's vendors conditional on Beta's invoice existing. On 2.0.52 it
incorrectly returns Alpha's vendor; on 2.1.4 the same statement returns no rows
for Alpha and Beta's vendor for Beta, repeatedly alternating tenants. This is a
synthetic mechanism probe, not evidence of a vulnerable public route. SQLite has
no RLS, so the row test proves the ORM predicate works independently. Existing
membership, alias, registry, cache-key/value and PostgreSQL controls remain.
The [ADR qualification addendum](../architecture/adr/0004-tenant-isolation.md)
records the changed reach and its limits.

## Additional finding: PERF-HARNESS-STARTUP

The unchanged 1,200→4,800-row growth check initially failed supplier reliability
at **9.76×**, above **8×**. Four controlled comparisons, with the broad suite paused
and no image build running, reproduced failures on both SQLAlchemy versions:

| Harness | SQLAlchemy | Reliability p95 growth, two runs |
| --- | --- | --- |
| Before correction | 2.0.52 | 10.06× / 9.95× |
| Before correction | 2.1.4 | 11.87× / 12.98× |
| Corrected startup | 2.0.52 | 2.37× / 2.36× |
| Corrected startup | 2.1.4 | 2.43× / 1.30× |

The embedding runtime had frozen **375 objects before application import**.
The harness interpreted any nonzero `gc.get_freeze_count()` as completed app
startup, leaving the imported application heap unfrozen and the collector at
**(700, 10, 10)** despite the configured gen-2 value **100**. The actual service
lifespan always calls `freeze_startup_heap()` after startup.

The harness now tracks its own successful initialization, freezing/applying the
existing settings once after app import and before seeding. A failed initialization
remains retryable. Two functional tests failed before this repair, seeding an
already-frozen runtime and a failed initialization. They replace the old source
assertion that demanded the incorrect global-count condition; the structural
ordering and real heap-freeze tests remain. All six endpoint growth limits pass
in all four corrected comparisons. Initial failed measurements are retained.
No threshold, dataset, repetitions, warmup, percentile or GC configuration value
was changed; startup behavior of the application itself is unchanged.

## Review, alternatives and rollback

Proposal: use the supported result/type APIs and accept the additional tenant
predicate; make the benchmark run the same startup configuration as the service.
Retaining 2.0 would defer the dependency update and preserve the demonstrated
nested-query gap. Muting warnings, weakening the reach/type controls, raising the
growth limit or changing GC values would hide the defects and were rejected.
The small compatibility edits reuse the current architecture and add no framework.

Adversarial objection: extra nested predicates may change legitimate queries, and
freezing at the wrong point could park seed data or hide a real performance defect.
The alternating-tenant probe, existing tenant/transport/exports tests, PostgreSQL
checks and paired old/new growth runs address those risks; the harness ordering
test keeps initialization before seeding and once per process. This evidence does
not cover every future SQL shape or certify hardware capacity.

**Lead decision: pending.** Review the corrected safety-control expectations,
typing assumptions and startup equivalence. Revert the pin and compatibility/
control changes together, then restart; no data migration is involved. Reverting
to 2.0 restores its documented nested-query limitation, so explicit service scoping
and RLS remain essential. The full build/service image gate, historical PII work,
provider/restore decisions and release acceptance remain open. Nothing here is
merged, deployed or release-cleared.
