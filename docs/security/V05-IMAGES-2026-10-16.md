## Changes and validation

Frontend origin now uses the audited maintained NGINX stable image pinned at
`sha256:970364228b1e4f932abc22d321932816782cca8a20b85a77552a7cfe9acfb3b5`.
Node 22 and Python 3.14 bases are pinned by digest. Node's build-only npm is 12.2.0;
application package versions stay unchanged except the independent V04 lock repair.
Backend builds use HTTPS Debian repositories, install OCR/tini without a standalone
curl executable, and remove runtime pip/setuptools plus ensurepip's bundled wheels.
Python owns the fixed-loopback health probe. Builds support an optional public CA
bundle via a BuildKit secret; TLS verification stays enabled and no CA/proxy secret
is baked into the output. No application runtime credential is supplied at build.

NGINX runs as UID/GID 101, with a writable /tmp PID and owned cache; copied default
config has explicit readable permissions. API/worker remain UID 10001. Production
API/worker/origin drop all capabilities and use no-new-privileges. The origin's
network namespace explicitly makes its existing low listen ports unprivileged;
no database/MinIO initialization capability policy was changed. Do not blanket
mark the entire compose stack read-only: storage and DB lifecycle need real paths.

Actual Docker checks passed for API/origin startup, SPA fallback, authenticated
API refusal/proxy, verified TLS hostname/certificate, HTTPS health, hashed-asset
CSP/security headers and the 20 MiB proxy limit. A synthetic invoice issued through
the real API yielded an actual 7,913-byte PDF through the TLS origin; disposition,
MIME, nosniff and the backend's restrictive document CSP were preserved. Invoice
PDF byte hash is in the local probe log, not a promise of deterministic generation.
Processes were observed non-root, zero effective capabilities and NoNewPrivs=1.
Packaged OCR model is not writable by the app user; no Docker socket is in the app.
Library imports, Tesseract and PDF child-process smoke passed in Python 3.14.
These are isolated synthetic smoke checks, not production acceptance or a supported
minimum-hardware benchmark. Current-head full CI/PG/OCR validation remains required.

## Residual findings — release blocked

The final NGINX application image has **0 high/critical findings** in Trivy 0.76.0.
The final Python/OCR image has **76 rows (75 high, 1 critical), 33 unique advisory
IDs, no fixed version listed by the scanner**. Removing curl reduced the prior
78 rows; libcurl remains an OCR dependency. The JSON groups every ID with installed
packages, vendor status, primary reference and observed boundary. No ignore file,
blanket exclusion, severity reduction or auto-approved VEX was introduced.

Important conditions need review, not invented exploit claims: util-linux/mount
findings involve helper/privilege paths not used by inspected app functions;
Tesseract findings describe crafted traineddata while deployed models are packaged
read-only; X libraries describe a malicious X server while none is configured.
The critical libxml2 record's title mentions mingw; that alone cannot certify the
Debian amd64 package unaffected. XML/TIFF/native code still needs exact function/
platform/vendor assessment. PDF resource budgets do not prevent arbitrary native
code execution and do not waive image findings. Upstream rebuilds/distro changes
need compatibility evidence; disabling OCR is a product change, not an audit fix.

The build-stage scan additionally reports 17 high rows: four in bundled npm tools
and 13 in the shipped native TypeScript compiler's Go dependencies. npm 12.2.0 is
current but still carries those scanner findings; TypeScript 7's available release
is 7.0.2. None ships in the final NGINX image. Build input/execution risk remains,
so do not describe a clean npm lock audit as clearing the compiler/build image.

CI now loads final built images, generates CycloneDX SBOMs and blocks the existing
Docker gate on high/critical findings or scanner errors, uploading evidence even
on failure. The local gate failed as expected on the backend findings and recorded
both images. This strengthens enforcement; it does not make checks green by hiding
unfixed packages. A reviewed supported fix or individual proven non-applicability
is needed before release; no risk acceptance was invented here.

## Rollout and rollback requirements

Production config must be readable by the NGINX user. Certificate directories need
traversal and the private key must be readable by group 101 (e.g. root:101, 0440);
keep the key read-only and never world-readable. Test this in an isolated container
before replacing a root-run origin. Existing root-only mounted TLS keys otherwise
prevent startup. Synthetic TLS smoke used this group/permission contract.

Rebuild/restart API and workers after package changes. Publish immutable application
image digests only after review; local image IDs are not published registry tags.
Keep the preceding tested application/config artifacts and backup/restore plan.
Rollback must preserve readable mounts/permissions and a patched base; do not claim
the old affected NGINX or vulnerable JWT/PDF pins are security-cleared fallbacks.
