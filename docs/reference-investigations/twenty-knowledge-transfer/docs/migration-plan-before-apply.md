# Migration Safety: Plan Before Apply

Status: **Required engineering policy**

Twenty's metadata tooling makes destructive create/update/destroy impact visible before mutation. InvoiceIQ should transfer the principle, not Twenty's metadata engine.

The existing migration `c4d6e8f0a2b4_db_integrity_batch3.py` is the positive local example: it inspects existing values, refuses ambiguous bad state, names the table/value/count and only normalizes the one value whose meaning is exact.

## A migration requires an explicit impact section when it can

- drop a table/column/index/constraint;
- change FK `ON DELETE` behavior;
- narrow a CHECK/enumeration;
- make a column non-null;
- change uniqueness;
- reinterpret financial state;
- rewrite money/tax/payment rows;
- move/merge tenant identifiers;
- alter retention/audit records.

## Required work-order/migration content

### IMPACT
List exact tables/columns/constraints and whether the operation creates, updates, restricts or destroys data/schema.

### PREFLIGHT
A query or function that proves existing data can safely cross the new boundary.

### REFUSAL
Ambiguous data causes a named exception with enough identifiers/counts for repair. Never “fix” unknown semantics by widening the target constraint.

### NORMALIZATION
Allowed only when semantic equivalence is exact, documented and regression-tested.

### POSTCONDITION
State the DB invariant that must be true after upgrade.

### ROLLBACK / REPAIR
Explain whether downgrade is safe and how to repair a refused migration.

## CI / deployment rules

1. Every migration runs on real PostgreSQL before merge.
2. Test the refusal path for destructive/narrowing migrations.
3. `alembic check` remains green.
4. Only one production migration/deploy writer runs at once.
5. Never edit a migration that has shipped.
6. AI-generated migrations receive the same review; “generated by AI” is not a lower-risk category.
7. A destructive change may not be hidden in a general feature work order.

## Future tool, only if justified

If migration frequency or review failures become a measurable problem, add a small repository checker that requires structured IMPACT/PREFLIGHT metadata for new destructive revisions. Do **not** introduce a parallel schema-management engine merely to create a preview screen.
